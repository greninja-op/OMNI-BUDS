## 3. Dependency direction

The map below is `areaLayer` in `DependencyDirectionTest.kt:33-48` read as-is, and `coreAreasDependOnlyOnMoreFoundationalAreas` (`:213-229`) enforces it: an import may point only at a **strictly lower** layer, or at the importing file's own area.

```text        layer
  4  protocol
  3  session          persistence
  2  device · capability · audio · config · diagnostics      (five islands)
  1  transport        platform        ◄── `platform` added by ADR-P2-001
  0  common           state           ◄── `state` moved from 1 to 0 during Phase 2
```

Two facts about this map must be read plainly rather than smoothed over.

- **`state` was at layer 1 in Phase 1 and is at layer 0 now** (`DependencyDirectionTest.kt:34-37` versus the map in Phase 1 `design.md` §3). The in-file comment gives the reason it was given ("an enum of states is vocabulary, not a policy layer"), and the mechanical reason is visible in the code: `platform` at layer 1 imports `state.VerificationLevel` (`core/src/main/kotlin/com/omnibuds/core/platform/PlatformFeatureSupport.kt:3`), which would be a sideways edge under the old numbers. **No ADR records the demotion.** ADR-P2-001 places `platform` "alongside `state` and `transport`" and says the area "depends only on `common`", and neither clause matches the map as it now stands. `docs/phases/phase-2/decisions.md:13` is the record; `DependencyDirectionTest.kt:37` is the code.
- `platform` depends on exactly two areas: `common` (`OperationOutcome`, `OmniBudsError`, `OmniBudsErrorCategory`, `TransportKind`) and `state` (`VerificationLevel`). It does **not** depend on `transport`, and `transport` does not depend on it: `LeAudioTransport.kt:21-31` names `PlatformFeature.LE_AUDIO`, `ApiAvailability` and `BluetoothPlatformCapabilities.candidateTransports` in prose and says in the same sentence that this package may name but not import them (`:24-26`). ## 5. The adapter abstraction

Three shapes, one reading path.

`BluetoothAdapterHandle` (`adapter/BluetoothAdapterHandle.kt:19-34`) is the narrowest seam in the module and speaks deliberately in the platform's own raw integers: `adapterPresent`, `readRawState(): Int?`, `openStateChanges(emit: (Int) -> Unit): PlatformRegistration`. Three members because three questions are authorised; its KDoc (`:14-18`) names the fourth members that were not added (enabling the adapter, listing bonded devices, opening a transport) and why each would be an unauthorised capability wearing an innocuous name. `SystemBluetoothAdapterHandle` is the only implementation (`:30-116`), and its `register(...)` (`:73-79`) branches on the device API level because the export flag is described in the research as a `targetSdk ≥ 34` rule whose **constants** exist from API 33 (`bluetooth-api-research.md` §5 Q6 item R-1): passing `RECEIVER_NOT_EXPORTED` from 33 up states the intent early, and below 33 there is nothing to pass. `ACTION_STATE_CHANGED` is a protected system broadcast, so the flag-free overload would be legal too; both branches are lint-suppressed and the two suppressed checks are named in the KDoc (`:65-71`).

`AdapterStateSource` (`platform/AdapterStateSource.kt:19-37`) is core's question, not Android's: `suspend fun readState(): OperationOutcome<BluetoothAdapterState>` and `suspend fun openStateChanges(): OperationOutcome<AdapterStateChangeChannel>`. A missing or unreadable adapter is a `Failure` or an `UNKNOWN` state, never a thrown framework exception (`AndroidAdapterStateSource.kt:40-94` wraps every platform call in `runCatching().fold` and produces `PLATFORM_EXCEPTION` carrying the exception's class simple name and nothing else). `AdapterStateSource.unavailable()` (`:33-36`, backed by the private object at `:47-65`) is **not** a claim that the phone has no Bluetooth: it answers `Failure(ADAPTER_UNAVAILABLE)` with the detail "no adapter state source was available", which is the audit's R-6 correction — the earlier shape reported the `UNAVAILABLE` *state* for what is a wiring fact.

`AdapterStateChangeChannel` (`:40-45`) pairs the live `Flow<BluetoothAdapterState>` with the `PlatformRegistration` that owns it, and the Android side closes the channel when the registration is disposed (`AndroidAdapterStateSource.kt:108-135`) so a teardown can never leave a collector suspended on a receiver that has already gone away. The channel is `Channel.CONFLATED` (`:72`) — adapter state is a latest-wins value and the observer already drops consecutive duplicates, so buffering would let a slow collector act on states the phone left behind and would suspend the broadcast thread once a buffer filled (`:65-68`). Registration happens at `openStateChanges()` rather than at first collection (`:57-64`), because the observer must be able to dispose a registration that was never collected — and that case is tested (`AndroidAdapterStateSourceTest.kt:90`).

## 6. State observation and the single-slot machine

`AdapterStateObserver` (`platform/AdapterStateObserver.kt:36-184`) is where prompt section 5.4's list becomes behaviour, and it is in `:core` precisely so each item is testable without a radio (ADR-P2-007).

```text
observe() called  → nothing happens; channelFlow is cold (:63)
        │  collected
        ▼
slot.tryLock() ──false──► one Failure(RESOURCE_UNAVAILABLE) emitted, stream ends (:64-75)
        │ true; teardownProblem cleared (:83)
        ▼
source.readState()                                                     (:85)
  ├─ Success(s)   → emit Success(INITIAL_READ, s); lastState = s;
  │                 startingValueAnnounced = true                      (:86-98)
  ├─ Failure(e)   → emit Failure(e); lastState and startingValueAnnounced
  │                 stay unset; CONTINUE to the event stream           (:100-105)
  └─ Cancelled    → emit Cancelled (not a Failure); stream ends        (:107-114)
        ▼
source.openStateChanges()                                              (:117)
  ├─ Success(ch)  → registration = ch.registration                     (:119)
  │                collect ch.states:                                  (:120)
  │                   state == lastState           → suppressed        (:121)
  │                   otherwise                    → PLATFORM_EVENT if a starting
  │                                                  value was announced,
  │                                                  INITIAL_EVENT if it was not  (:122-126)
  ├─ Failure(e)   → emit Failure(e)                                    (:141)
  └─ Cancelled    → emit Cancelled; the slot still releases below      (:143-146)
        ▼
finally: dispose(registration), capturing any throw as teardownProblem (:149-161)
         release the slot, if still held                               (:162)
```

Five decisions give the machine its shape, and all five are load-bearing rather than stylistic.

- **A failed initial read is not fatal.** `lastState` stays `null`, `startingValueAnnounced` stays `false`, and the event stream still runs (`:100-105`): "we could not look right now" plus "the platform may still announce something" is more truthful than a stopped stream, and the state stays `UNKNOWN` rather than becoming `DISABLED` (`BluetoothAdapterState.kt:12-14`, ADR-P0-016). Tested at `AdapterStateObserverTest.kt:160-182`.
- **Duplicates are suppressed; A-B-A is not.** `state == lastState → return@collect` (`:121`) drops a repeat announcement — the platform can announce the same state twice, and passing both on would make a UI animate or a state engine re-run discovery for no reason — while a genuine off-on-off sequence is three different claims and all three survive (`AdapterStateObserverTest.kt:65-90`). The suppression is deliberately invisible in the value type: `ObservationKind` has four members and no "deduped" one, because "an enum entry nothing can produce is vocabulary standing in for a capability" (`AdapterStateObservation.kt:12-14`).
- **`INITIAL_EVENT` means "this is where we started", and only that.** `startingValueAnnounced` (`:79-82`) is set by a successful initial read, so after one, every delivered change is `PLATFORM_EVENT`; `INITIAL_EVENT` is reachable only when the read did not answer, where the first differing event genuinely is the start of the consumer's knowledge. That is the closure of audit finding R-8, and it is asserted in both directions: `theFirstChangeAfterASuccessfulReadIsAPlatformEventNotAnInitialOne` (`AdapterStateObserverTest.kt:92-111`) and the `INITIAL_EVENT` assertion after a failed read (`:181`).
- **One observation at a time, by mutex.** `private val slot = Mutex()` (`:40`) with a non-suspending `tryLock()` (`:64`): a second concurrent collector is refused with `RESOURCE_UNAVAILABLE` instead of producing a second platform registration, which is where a leaked receiver hides. `isObserving` (`:43-44`) reads `slot.isLocked` so the guard is observable rather than assumed. The slot is **per instance**, so uniqueness is really an invariant of the composition root, and `OmniBudsBluetooth.kt:34-38` says so plainly: the factory deliberately does not cache, because a hidden global would produce a registration nobody owns, and two constructed platforms would mean two registrations for one fact — the leak ADR-P2-007 exists to prevent. The honest limit: nothing in the build enforces one instance per process.
- **Cancellation stays cancellation, and a thrown teardown is captured rather than emitted.** A `Cancelled` from either platform call is forwarded as `OperationOutcome.Cancelled` (`:107-114`, `:143-146`) instead of being relabelled a platform fault — the closure of audit finding R-7, against ADR-P1-004 and Phase 0 `specs.md` §5 rule 3 — and both halves are driven from the double (`FakeAdapterStateSource.kt:25, 28, 71`) and asserted (`AdapterStateObserverTest.kt:211-224`, `:226-238`). A *throwing* teardown is a different case and lands in `teardownProblem` (`:53-54`, `:149-161`) as `RESOURCE_UNAVAILABLE` carrying the cause's class simple name, because by the time the `finally` runs the channel may already be closed and a send there would raise a second, unrelated failure on top of the real one.

The second entry point is deliberately inert: `readOnce()` (`:166-179`) maps a single `source.readState()` into a `PLATFORM_READ` observation and takes neither the slot nor a registration, which is the correct shape for a one-shot inspection and is tested as such (`AdapterStateObserverTest.kt:240-254`, which also checks that `openCalls` stays 0).

## 7. Permission architecture

Three questions, three owners, and the separation is the design.

**What does this operation need?** `PermissionRequirementResolver` (`platform/PermissionRequirementResolver.kt:35-37`) with one implementation, `FrozenPermissionRequirementResolver` (`:57-289`). It takes `PermissionContext(targetSdk, deviceSdk, assertsNeverForLocation)` (`PermissionContext.kt:17-32`) and returns `OperationOutcome<PermissionPlan>`. **It branches on `targetSdk`, never on the phone's level** — ADR-P2-009, which corrects Phase 0 `SEC-PERM-002` and follows `bluetooth-api-research.md` §1, §3 and §5 Q6 item R-2, where the recurring documentation sentence is "for apps targeting `Build.VERSION_CODES.S` or higher…". `deviceSdk` is still carried because enforcement, not requirement, can depend on it, and it reaches the answer through `caveat` rather than through the requirement list (`:232-249`) so a caveat can never be read as a permission to request. An unknown `targetSdk` returns `Failure(INVALID_STATE)` (`:63-70`) instead of the safer-looking band: a permission asked for on a guess is one the user cannot be given a reason for. `PermissionPlan` (`:15-32`) separates `runtimePermissions` from `installTimePermissions` (`:23-28`) — an install-time grant is never a prompt — and defines `needsNoPermission` as "not indeterminate and nothing required" (`:31`).

**What does the platform hold right now?** `AndroidPermissionStateProvider.standingOf` (`permission/AndroidPermissionStateProvider.kt:42-62`): `null` from the reader is `UNKNOWN` (no answer is not a refusal), `true` is `GRANTED`, and `false` splits three ways — a non-runtime permission that reads false is `DENIED` because the manifest does not declare it (`ADR-P2-011` keeps it empty, and that is a developer decision, not a user's refusal), a runtime permission the session did record a request for is `DENIED`, and one it never asked about is `NOT_REQUESTED`. The platform cannot make that last distinction (`PermissionRequestLedger.kt:8-13`), so the app keeps the record itself, in memory, deliberately **not** persisted: a stored "we already asked" would survive an OS permission reset and turn a temporary denial into a permanent one (`:15-17`). `stateFor(operation, permission, context)` (`:75-96`) composes the two questions and is the only path that can produce `NOT_REQUIRED`, which keeps "not required" a plan's answer rather than a platform's; a failed or cancelled plan yields `UNKNOWN`, never `NOT_REQUIRED` (`:91-95`).

**What may the app conclude?** Seven `PermissionState` values (`PermissionState.kt:13-34`) with three derived predicates. `DENIED_PERMANENTLY` and `REQUIRES_USER_ACTION` are in the model and unreachable from app code (ADR-P2-012): research §5 Q4 found no app-visible signal that establishes permanent denial, and `shouldShowRequestPermissionRationale` — the API a naive implementation would reach for — is called nowhere in this tree. The behaviour is asserted, not hoped for: `AndroidPermissionStateProviderTest.kt:71-87` names both states as forbidden outputs, and `AndroidPlatformCapabilityProviderTest.kt:134-145` asserts no permission report ever carries `DENIED_PERMANENTLY`.

`BluetoothPermission` (`platform/BluetoothPermission.kt:17-36`) carries only stable facts about a permission — manifest name, introduction level, runtime-or-install, legacy-or-not — and its KDoc (`:8-11`) states why the *matrix* is not here: a correction to the matrix must not require editing an enum, and no call site may invent a requirement by reading a field. `ApiRange` (`:42-70`) expresses a band as an inclusive range so a hole cannot be created by a missing `else`, and its `MIN_MATRIX_SDK`/`MAX_MATRIX_SDK` constants (`:61-62`) are deliberately not called `minSdk`/`targetSdk`: they bound the matrix, and the app's own values live in `gradle/libs.versions.toml:12-14`. The audit's R-9 (two owners of one number) is answered by naming rather than by injection, and `ApiRange.LEGACY_BLUETOOTH_MODEL` / `MODERN_BLUETOOTH_MODEL` (`:65-68`) are declared but read by no code — `FrozenPermissionRequirementResolver` builds its ranges from its own `MIN_MATRIX_SDK`/`LEGACY_MAX`/`MODERN_TARGET` constants (`:265-268`).

`BluetoothOperation` (`platform/BluetoothOperation.kt:18-93`) is twelve operations, five authorised in Phase 2, four in Phase 3, two in Phase 6, one in Phase 10, each tagged `authorizedInPhase` and carrying one description string so a reason is never improvised at a call site. Enforcing that tag at runtime would need an ambient "current phase" value — the hidden global ADR-P2-014 refuses — so the field stays data and `isAuthorizedIn(phase)` (`:92`) is called only from `PhaseTwoScopeTest` (`core/src/test/.../platform/PhaseTwoScopeTest.kt:36,43,50-52`). The pre-computed Phase 3/6/10 rows are answers to a permission question, not authorisation to perform anything, and prompt section 5.3's "do not blindly declare or request every permission" is honoured by the resolver never being given a requesting path at all: nothing in this tree can call `requestPermissions`, and rule 7 now bans the name in the platform module (§14).

## 8. Platform capability model

ADR-P2-008 fixes the rule and ADR-P2-017 fixes the evidence; the types are their expression. Prompt section 5.5 names four facts and forbids collapsing them, and `PlatformFeatureSupport` (`platform/PlatformFeatureSupport.kt:24-63`) keeps three of them as separate fields — `apiAvailability` (the OS), `hardwareEvidence` (the phone, a `VerificationLevel`), `permissionState` (the user) — with `isUsable` requiring all three (`:33-36`) and `blockingReason` naming which one refused (`:44-53`). The fourth, connected-device support, is absent by decision (`:21-22`): it belongs to the per-device capability model, and a phone advertising `FEATURE_BLUETOOTH_LE` says nothing about a particular pair of earbuds.

`availabilityOf` (`capability/AndroidPlatformCapabilityProvider.kt:147-162`) populates the OS axis only: a `PackageManager` feature flag or an API-level floor decides `apiAvailability`, and `hardwareEvidence` is `VerificationLevel.INFERRED` for **every** feature (`:115`) because no radio was opened, so `isUsable` is false everywhere and `blockingReason` is non-null everywhere — asserted at `AndroidPlatformCapabilityProviderTest.kt:118-131`. A probe that **throws** yields `UNKNOWN`, not "absent" (`probe()` at `:170`, `fromAdvertised()` at `:164-168`, tested at `:75-88`). Two rows report `UNKNOWN` because answering them would need a call Phase 2 is not authorised to make: A2DP and HEADSET connection state would need `getProfileConnectionState`, which is `PROFILE_CONNECTION_STATE_INSPECTION` (Phase 3) and needs a permission this manifest does not declare (`:136-141`, asserted at `:103-115`). LE Audio reports only the class's existence at the running level (`:157`), because the SDK declares no public feature constant for it (`:141-145`), so `candidateTransports` (`:183-197`) can gain `CLASSIC_BLUETOOTH`, `RFCOMM`, `BLE` and `GATT` from the phone's own flags but never `LE_AUDIO` by inference (`AndroidPlatformCapabilityProviderTest.kt:90-100`).

The `permissionState` of a feature row is **not** a general statement about that feature: it is the standing of the permission that `PERMISSIONS_BY_FEATURE` (`:222-231`) pairs with the operation that `OPERATIONS_BY_FEATURE` (`:211-220`) pairs with the feature, judged against this app's `targetSdk` — and the file says exactly that, including that the two rows paired with `PLATFORM_CAPABILITY_INSPECTION` answer `NOT_REQUIRED` "because assembling this report genuinely asks the user for nothing", which is not a claim that classic or BLE use in general is permission-free (`:57-63`). That is the distinction `AndroidPermissionStateProvider.stateFor` carries into code, and it is why `AndroidPlatformCapabilityProviderTest.kt:148-167` can assert both a `NOT_REQUIRED` row and a `GRANTED` row in the same report.

`BluetoothPlatformCapabilities` (`platform/BluetoothPlatformCapabilities.kt:14-65`) is the report: nullable `apiLevel`, an `adapterPresent` axis, a **sparse** feature map where an absent entry means "not determined" and `supportFor` returns `PlatformFeatureSupport.unknown()` rather than a refusal (`:41-42`), a `permissionStatus` map of what the platform actually answered, and `candidateTransports`. `unobserved()` (`:57-63`) is the state before anything was asked, and `isObserved` (`:49-50`) says honestly whether the report rests on readings at all. `apiLevel` is validated positive if present (`:34-37`). Nothing in the type can express a codec, a device or a battery — the layer map forbids the import, and the phase forbids the claim.

## 9. Transport boundaries

Prompt section 5.6 asks for interfaces and section 6 forbids everything that would make one real, so the deliverable is a vocabulary. `BluetoothTransport` (`transport/BluetoothTransport.kt:31-69`) extends Phase 1's `TransportContract` and adds exactly one member, `suspend fun probeAvailability(): OperationOutcome<TransportAvailability>`, restating `kind` so the Bluetooth rule lives with the Bluetooth boundary. Five sub-interfaces exist (`BleTransport`, `GattTransport`, `ClassicTransport`, `RfcommTransport`, `LeAudioTransport`), each adding nothing but a pinned `kind` via a default getter — `override val kind: TransportKind get() = TransportKind.GATT` (`GattTransport.kt:34-39`) and the same shape in the other four. ADR-P2-013 explains why a default getter is legal where a behaviour would not be: it is a constant, not an implementation, and it converts the invariant "each boundary answers for exactly one transport" from prose into something `TransportKindPinningTest` can fail a build over (`core/src/test/.../TransportKindPinningTest.kt:23-49`, including the check that no boundary pins `UNKNOWN` or `VENDOR_SPECIFIC`). `TransportKind` gained `BLE` for the same reason (`common/TransportKind.kt:11-17`): the BLE link layer and the GATT attribute protocol that may sit on it are different things (master section 8). The stale half of that history is visible in two documents: `BleTransport.kt:20-23` still asserts in prose that `TransportKind` "deliberately has no `BLE` constant" while `:36-41` pins one, and `docs/phases/phase-2/transport-boundaries.md:64-71` records the same pre-ADR-P2-013 position. Both are documents; the code and ADR-P2-013 are the current record.

`TransportBoundary` (`:41-131`) and `TransportNegotiation` (`:28-97`) are the two value types that turn the section's rules into constructor failures: a row cannot report `available = true` below `LAB_TESTED` (`TransportBoundary.kt:75-82`), `kind` must equal `availability.kind` (`:70-74`), a blank note is rejected while an absent note is a real state (`:87-90`), and a selection must name a candidate **and** name it as the available one (`TransportNegotiation.kt:47-62` — the second half is stricter than the brief, and it is what stops "selected: GATT" being stored beside "GATT: refused"). `preferring(order)` (`:90-96`) applies the caller's order and holds none of its own; `isUndetermined` (`:72-73`) is true for both an empty and a wholly-refused list, which is the state every Phase 2 record is actually in.

Two absences are the design, not gaps in it. `open()`/`close()`/`exchange()` are inherited and implemented nowhere — `noProductionClassImplementsTheProtocolOrRepositoryContracts` (rule 3) covers `TransportContract`, and `TransportKindPinningTest.kt:57-87` reads pinned kinds through an abstract test-only reader whose every member throws, because an object that answered would be a transport implementation in a phase that forbids one. And `probeAvailability()` has **no caller**: `TransportBoundariesTest.kt:331-356` asserts the symbol is declared once, in `BluetoothTransport.kt`, that no line contains `.probeAvailability`, and that no GATT/RFCOMM/socket mechanism name appears in a code line of the package. `docs/phases/phase-2/transport-boundaries.md` carries the per-transport deferred list and the reason each absence exists; A2DP, AVRCP and HFP are given no `TransportKind` at all, because they are profiles Android speaks, not control channels OmniBuds opens.

## 10. Data flow: platform → observation → consumer

```text
 ANDROID FRAMEWORK (nothing external is contacted)
   BluetoothAdapter.state ─┬─ ACTION_STATE_CHANGED broadcast ─┐
   PackageManager ─────────┤                                  │
   checkSelfPermission ────┤                                  │
   applicationInfo ────────┴──────────┐                       │

        ▼                             ▼                       ▼

                                                                                       ▼   + registration)
                                                              AdapterStateSource (core seam)

                          AdapterStateObserver.readOnce()     AdapterStateObserver.observe()
```

Unknown is preserved at every hop, which is the point of the chain rather than a property of it. A null adapter object becomes `adapterPresent = false`, which the mapping resolves to `UNAVAILABLE` **before** the raw value is considered (`AdapterStateMapping.kt:22`); a broadcast with no extra becomes `RAW_STATE_UNREADABLE = -1` (`SystemBluetoothAdapterHandle.kt:87`, `AdapterStateMapping.kt:38`) and therefore `UNKNOWN`, not `STATE_OFF`; an unrecognised integer becomes `UNKNOWN` (`:28`), never the friendlier-looking `DISABLED`. A failed read stays a `Failure` beside an unset `lastState` rather than becoming a state. A platform exception contributes only its class simple name to `detail` (`AndroidAdapterStateSource.kt:50`, `:89`; `AndroidPlatformCapabilityProvider.kt:88`), so nothing device-shaped can ride out of it. A clock that gave no reading leaves `observedAtEpochMillis` null (`AdapterStateObservation.kt:23-33`) rather than sorting an unknown event to the epoch.

**There is no consumer.** `BluetoothPlatform` has exactly one implementation (`AndroidBluetoothPlatform.kt:41`) and no caller; `omniBudsBluetoothPlatform` (`OmniBudsBluetooth.kt:44`) is called from no file in the tree; `InMemoryPermissionRequestLedger.record` (`PermissionRequestLedger.kt:28`) is called only from a test, because there is no prompt to record. `PermissionPlan.bandLabel` (`PermissionRequirementResolver.kt:18`) is set at `:219` and read nowhere, `BluetoothOperation.isAuthorizedIn` (`BluetoothOperation.kt:92`) is read only from a test, and `BluetoothPlatformCapabilities.supportedFeatures` (`:31`) and `usableFeatures` (`:45`) have no reader at all. This is the honest shape of a foundation phase: the seam is complete, wired and tested, and the first thing that will pull on it is Phase 3's connected-device detection, which prompt section 6 forbids here.

## 11. Lifecycle and cleanup

No Android `LifecycleOwner`, no `Service`, no `BroadcastReceiver` declared in a manifest, no foreground service, no worker. The lifecycle unit is a **coroutine scope owned by the caller of `observe()`**, and cleanup is expressed as four rules, three of them enforced:

1. **Collection registers; losing the collector unregisters.** `channelFlow`'s `finally` disposes the registration on cancellation, normal completion and a downstream throw alike (`AdapterStateObserver.kt:148-162`), and disposing the channel's registration also closes the channel (`AndroidAdapterStateSource.kt:124-134`) so no collector hangs.
2. **Every `PlatformRegistration` is disposable more than once.** `SystemBluetoothAdapterHandle.ReceiverRegistration` guards `unregisterReceiver` with an `AtomicBoolean` compare-and-set (`:100-111`) — unregistering a receiver the platform does not know throws, so the guard is the difference between a clean teardown and a crash on the way out — and a `SecurityException` from a genuinely needed unregister is rethrown rather than swallowed, surfacing as `teardownProblem`.
3. **A one-shot read holds nothing.** `readOnce()` takes no slot and opens no registration (`AdapterStateObserver.kt:166-179`), asserted by `aSingleReadDoesNotOccupyTheObserverSlot` (`AdapterStateObserverTest.kt:240-254`, which checks `openCalls == 0`).
4. **There is no polling and no retry.** `SystemBluetoothAdapterHandle.kt:24-28` states the case for the broadcast over a repeating read (prompt section 5.8 forbids hidden background work), and neither module contains a `delay`, a repeating read or a retry counter — the only loop over platform questions is the single pass at `AndroidPlatformCapabilityProvider.kt:110-123`, once per `capabilities()` call. §12's table marks which of these a scan proves and which rests on reading.

What is *not* here: process death and permission revocation are the same event on Android (`bluetooth-api-research.md` §5 Q5: revocation "kills all processes running in the calling UID"), so cleanup on that path is the platform's, not this code's; and because the ledger is in memory (`PermissionRequestLedger.kt:15-17`), "already asked" does not survive a kill — which is the intended direction, since a resurrected "we already asked" would be a fabricated permanent denial.

## 12. Concurrency: enforced versus declared

Prompt section 5.8 lists eight rules. They are not all the same kind of thing, and pretending otherwise would be the sort of claim this project does not make.

| Rule | Where it lands | Status |
|---|---|---|
| No blocking Bluetooth work on the main thread | every platform entry point wraps its work in `withContext(dispatcher)` defaulting to `Dispatchers.IO` (`AndroidBluetoothPlatform.kt:41,51,66`; `AndroidAdapterStateSource.kt:41,71`) | **implemented** for the four reads; **not enforced by any check** — no rule inspects dispatchers, and `core` is forbidden from exposing one (Phase 1 `specs.md` §5.2 rule 2), so the enforcement is the default parameter plus review |
| Structured concurrency, no `GlobalScope`, no unmanaged scopes | no `launch`, no `CoroutineScope`, no `GlobalScope`, no `Dispatchers.Main` appears in either module's main source | **enforced only by absence** — nothing declares a scope; the caller's scope owns the collector |
| Explicit cancellation | `Cancelled` is an outcome case (`OperationOutcome.kt:28`) and is propagated, not relabelled: `AdapterStateObserver.kt:107-114` and `:143-146` forward it and still release the slot (`:162`) | **implemented and tested** (`AdapterStateObserverTest.kt:211-224`, `:226-238`) — audit finding R-7 closed |
| Bounded operations, no unbounded retry | no retry call site exists; `OmniBudsError.attempts` is carried and defaulted to 1 (`OmniBudsError.kt:20-24`) but never incremented anywhere in Phase 2 | **implemented as absence** |
| No leaked receivers or callbacks | §11 rules 1-3 | **implemented and tested** |
| No duplicate concurrent adapter observers | `Mutex` slot, refusal path (`AdapterStateObserver.kt:64-75`) | **enforced per instance**, and asserted (`AdapterStateObserverTest.kt:113-131`, `AndroidBluetoothPlatformTest.kt:80`); one-instance-per-process is declared in `OmniBudsBluetooth.kt:34-38` and enforced by nothing |
| No hidden background polling | no `delay`, no repeating read, no timer; one single pass over the feature enum (`AndroidPlatformCapabilityProvider.kt:110-123`) | **implemented as absence** |
| Flow discipline | `observe()` is a cold `channelFlow` (`:63`); the platform stream is a conflated `receiveAsFlow` (`AndroidAdapterStateSource.kt:72-114`) | **declared in prose, not in parameters**: Phase 0 `specs.md` §5.5 rule 5 forbids a cold flow for device state and requires every flow to declare buffering and overflow. The buffer policy *is* declared and implemented (conflated, latest-wins: `AndroidAdapterStateSource.kt:57-68, 72`), but the audit (§7) recorded the cold shape as needing an ADR and **ADR-P2-001 … 017 contain none**. The claim "amended by decision" is not available |

Shared mutable state is the narrowest honest statement available: `AdapterStateObserver` holds a `Mutex` (`:40`), two per-collection locals (`:77-82`), and the `teardownProblem` property (`:53-54`), which makes it the second mutable holder in `:core` main source after `diagnostics/SnapshotBuilder`, and the only one that is concurrently reachable. `teardownProblem` is reset at the start of each collection (`:83`) and read after it ends, so it is last-run state, not a per-collection value; two collectors cannot overlap because of the slot, but a reader racing a second `observe()` could see the newer run's value. `InMemoryPermissionRequestLedger` uses `ConcurrentHashMap.newKeySet` (`PermissionRequestLedger.kt:25`) and is the module's only thread-safe accumulator. Every Phase 2 data model — `AdapterStateObservation`, `PermissionPlan`, `PermissionRequirement`, `PermissionContext`, `PlatformFeatureSupport`, `BluetoothPlatformCapabilities`, `ApiRange`, `TransportBoundary`, `TransportNegotiation` — is an immutable value, and `BluetoothPlatformCapabilities.withFeature` (`:52-53`) returns a copy rather than mutating the report the provider is assembling.

## 13. Error handling

ADR-P2-004 widened the vocabulary to 23 categories by union, never substitution (`common/OmniBudsErrorCategory.kt:20-47`; the seven Phase 2 additions are `:41-47`), and the two refusals recorded there are as much the decision as the seven: cancellation stays an outcome case rather than a category (ADR-P1-004), and "adapter state could not be read" stays a `BluetoothAdapterState.UNKNOWN` **state** rather than becoming a second, weaker representation of the same fact that could disagree with it. `ADAPTER_STATE_UNKNOWN` existed in the working copy the audit examined (`architecture-audit.md:322-330`) and is absent now, which is the correction ADR-P2-004 describes.

ADR-P2-005 is the enforcement half, and it is real: `common/OmniBudsErrorCategoryTest.kt:20-37` pins the 23-member name set, `:40-73` pins every `retryClass` through a `Map<OmniBudsErrorCategory, RetryClass>` guarded by `assertFullCoverage` (`:124-128`, which compares the map's keys to `entries` **and** rejects a duplicate), and `:85-118` does the same for `invalidatesSession`. Phase 1's known issue 6 — a new category joining neither branch of a two-list assertion and passing unnoticed — is closed by the shape rather than by a list, and `:76-82` keeps the safety rule the audit caught being widened: exactly one category, `READ_FAILED`, may be repeated without first re-reading state.

Where Phase 2 produces errors, and how the platform's refusals are translated (ARCH-AND-003): a platform throw becomes `PLATFORM_EXCEPTION` (`AndroidAdapterStateSource.kt:46-54, 85-92`; `AndroidPlatformCapabilityProvider.kt:84-91`) — in `:core` no code constructs that category at all; a refused or throwing registration becomes `RESOURCE_UNAVAILABLE` (`AdapterStateObserver.kt:66-72, 154-161`); an unwired seam becomes `ADAPTER_UNAVAILABLE` (`AdapterStateSource.kt:47-65`); an undeterminable permission band becomes `INVALID_STATE` (`PermissionRequirementResolver.kt:64-70`); and a read that could not classify the adapter stays a failure whose *state* remains `UNKNOWN`. `specs.md` §8 carries the produced-and-by-whom table, which shows how few of the 23 categories Phase 2 can actually emit. `TransportBoundary.refused(...)` (`:119-129`) will accept any category as a reason, and `TransportAvailability`'s invariant (`:43-59`) forces available-and-reason to be mutually exclusive; nothing in Phase 2 maps a platform status code into either record, because no platform status code is available to map (§9).

## 14. Security

**Zero manifest permissions, in both Android modules.** `platform/android/src/main/AndroidManifest.xml:11` is `<manifest xmlns:android=… />` — no `<uses-permission>`, no `<uses-feature>`, no `<application>`, no component — and ADR-P2-011's reasoning is the phase's: research §5 Q7 established that every Phase 2 operation is permission-free for a 31+ target, so a declaration would be a capability claim with no call behind it, and a *library* manifest merges into every consumer APK silently. `tools/companion-shell/src/main/AndroidManifest.xml` declares no permission either. The claim is machine-checked, not asserted: `platformManifestDeclaresNothingUnjustified` parses `<uses-permission android:name=…>` against an **empty** allowed set and rejects any `<receiver`, `<service`, `<activity` or `<provider>` (`DependencyDirectionTest.kt:438-457`).

**No prompt can be issued, and that is now a check rather than an observation.** There is no `requestPermissions` call, no `ActivityResultLauncher`, no rationale API anywhere (`PermissionStandingReader.kt:14-17` reads standing only), and rule 7 added `requestPermissions` and `requestPermission` to the platform module's forbidden tokens (`DependencyDirectionTest.kt:298-301`) with the comment that this turns prompt section 5.3's "do not repeatedly trigger permission prompts" from a reading of the module into a build failure.

**No device identifier can appear, because no device is contacted.** The chain reads the phone's own facts (§4's ten-call list) and there is no API in `BluetoothPlatform`, `AdapterStateSource`, `BluetoothAdapterHandle` or the capability provider that returns a device, an address, a name, a scan result or a payload. Diagnostics discipline follows: `OmniBudsError.detail` is documented as never carrying a Bluetooth address, device name or manufacturer data (`OmniBudsError.kt:11-13`), and every Phase 2 `detail` string on disk is either a fixed sentence about a seam or `${problem::class.simpleName}` (`AndroidAdapterStateSource.kt:50, 89`; `AndroidPlatformCapabilityProvider.kt:88`; `AdapterStateObserver.kt:159`). No logger is implemented and no sink exists — `diagnostics/OmniBudsLogger` is untouched by Phase 2, so the redaction duty `ADR-P1-019` assigns to the Phase 36 sink still has no owner and nothing in this phase can emit. `TransportBoundary.notes` must never carry a vendor or model name (`:59-66`), and the audit's R-5 concern about `ADAPTER_UNAVAILABLE` becoming a legal "unavailable reason" for a channel nobody probed stands unresolved in the type: `TransportAvailability` accepts it (`:77-78`), and only the absence of any caller (§9) keeps it unused.

**Phase boundary as a security property.** `platformModuleContainsNoUnauthorisedCapabilities` (`:292-316`) rejects `connectGatt`, `BluetoothGatt`, `writeCharacteristic`, `startDiscovery`, `BluetoothLeScanner`, `startScan`, `createRfcommSocket`, `listenUsingRfcomm`, `TileService`, `AppWidgetProvider`, `NotificationListenerService`, `androidx.appcompat`, `androidx.compose`, `setContentView`, `ComponentActivity`, `requestPermissions` and `requestPermission`; rule 8 (`:321-340`) rejects the five media-audio types in **either** module; rule 10 (`:383-407`) confines receiver types to `bluetooth/adapter/` and forbids `sendBroadcast`, `sendOrderedBroadcast`, `PendingIntent` and `LocalBroadcastManager` everywhere in the platform module; rule 11 (`:412-435`) confines sources to `bluetooth/` and `di/`. A later phase that wants one of these must amend the ADR, not relax a check mid-implementation (ADR-P2-006, ADR-P2-016).

## 15. Extensibility

New platform mechanism enters through five seams, all of which already carry a second implementation shape: `AdapterStateSource` (core's question), `PermissionRequirementResolver` (a matrix that is not this frozen one), `TimeProvider`, and inside the platform module `BluetoothAdapterHandle`, `PermissionStandingReader`, `PermissionRequestLedger`, `ApiLevelProvider`, `TargetSdkProvider`, `PlatformFeatureProbe`. Each of the last six is a `fun interface` or a two/three-member interface, which is what lets `AndroidBluetoothPlatformTest.kt:126-148` compose the whole platform against lambdas and a `ScriptedHandle`, and `AndroidPermissionStateProviderTest.kt:41-44` exercise the real ledger. A desktop platform (Phase 47) supplies its own `AdapterStateSource` and equivalent of `BluetoothAdapterHandle`; `com.omnibuds.core.platform` imports no Android type and is scanned to keep it that way, so the shared half needs no edit.

Extension points Phase 2 deliberately left un-extended, each with a named owner: transport `open`/`close`/`exchange`/`probeAvailability` bodies (Phase 6), adapter state's *transition* legality (no transition table exists — §16), `BluetoothPlatformCapabilities`' fourth axis (per-device capability model, Phase 8), `PermissionState.REQUIRES_USER_ACTION` and `DENIED_PERMANENTLY` (a genuine future platform signal), `TransportKind`'s `VENDOR_SPECIFIC` (Phase 20/23), `PlatformFeature` members (the phase that probes one), and the notification/event member `TransportContract` still lacks (Phase 6, `transport-boundaries.md` §4 cross-cutting item 1). `TransportNegotiation.preferring` takes a caller's order and holds none, so a selection policy can be added above it without touching it. The one thing that must not extend this way is the manifest: adding a permission is ADR-gated by rule 11's empty allowed set, and `PermissionRequirement` cannot be constructed without a reason (`PermissionRequirement.kt:18-22`).

## 16. Android platform limitations

These are Android's facts about itself, all traceable to `bluetooth-api-research.md` or to a file on disk. None is a workaround; each is a place where the design refuses to know more than the platform permits.

- **Permanent permission denial is not app-detectable.** Research §5 Q4: the only identification path the docs give is `adb shell dumpsys package` (`USER_FIXED`), and the underlying flag is `@hide`/`@SystemApi` while `getPermissionFlags` needs `GRANT`/`REVOKE`/`GET_RUNTIME_PERMISSIONS` — none obtainable by a third-party app. `shouldShowRequestPermissionRationale` returning `false` is documented only for "show rationale now", so it is returned identically for never-asked, permanently-denied, policy-fixed and auto-reset. Consequence in code: `DENIED_PERMANENTLY` unreachable (§7), `AndroidPermissionStateProvider.kt:26-33` states it, and the ledger exists only to distinguish *asked-and-refused* from *never-asked*, which is the one half the platform cannot tell.
- **A silent `false`, an empty set or `STATE_DISCONNECTED` cannot be told apart from "off" or "absent".** Research §4 items 8-9 and §5 Q6 items R-3/R-5: `getBondedDevices()` returns an empty set when the adapter is not `STATE_ON`; `getProfileConnectionState()` returns `STATE_DISCONNECTED` when it is off; `startDiscovery()` returns `false`. So "profile disconnected" and "adapter off" are the same reading, and neither call is made here at all — `availabilityOf` answers `UNKNOWN` for both profile rows (`AndroidPlatformCapabilityProvider.kt:159-161`), and prompt section 6 is why discovery is not called. The general rule the phase adopts: where a call can return a falsy or empty result for two different reasons, report what was observed and leave the state unknown (ADR-P2-012).
- **Mid-operation permission revocation may never be observable.** Research §5 Q5: no permission-scoped cancellation callback exists on `BluetoothGatt`, `BluetoothGattCallback`, `BluetoothLeScanner`, `BluetoothAdapter`, `BluetoothDevice` or `BluetoothLeAudio` — code built on such a name would not compile — and revocation is implemented as process death (`Context.revokeSelfPermissionsOnKill`, API 33). Design consequence: standing is re-read at every entry (`AndroidPermissionStateProvider.kt:42-62` caches nothing), and nothing here claims a revocation is handled gracefully. The `PermissionState` model keeps `REQUIRES_USER_ACTION` for the shape, unproduced.
- **Adapter state can be observed but never caused.** Research §5 Q6 item R-4: `enable()`/`disable()` are deprecated at API 33 and "will always fail and return false" for a `TIRAMISU`+ target; the sanctioned route is `ACTION_REQUEST_ENABLE`, which itself needs `BLUETOOTH_CONNECT`. Hence no enable/disable member exists on `BluetoothAdapterHandle` (`:14-18` names it as a refused fourth member) and OmniBuds can only ever *react* to the user turning Bluetooth on.
- **Requirements key off `targetSdkVersion`; enforcement can key off the device level; and the two are different numbers.** Research §1, §3 and §5 Q6 item R-2. The sharper edge for this repository: `targetSdkVersion` is an **application** property and `:platform:android` is a library that declares none (`bluetooth-api-research.md:50`), so the value must be read at runtime — `context.applicationInfo.targetSdkVersion` (`AndroidPlatformCapabilityProvider.kt:36`) — and the catalog's `androidTargetSdk = "35"` (`gradle/libs.versions.toml:14`) is used by only one module today, the harness (`tools/companion-shell/build.gradle.kts:21,30`). Whatever app hosts this library owns the band, and the resolver's `Failure(INVALID_STATE)` is the honest answer when it cannot be read.
- **API-level floors are documentation, not permission.** `AndroidPlatformCapabilityProvider.kt:202-209` reads them from the SDK's own table (`platforms/android-35/data/api-versions.xml`): `BluetoothSocket` 5, `BluetoothGatt` 18, `BluetoothManager` and `Context.BLUETOOTH_SERVICE` 18, `BluetoothLeAudio` 31. Meeting a floor proves the class exists. Research §4 item 11 and §6 U-7 go further on LE Audio: `BluetoothProfile.LE_AUDIO` is API 33 while the class page says 31 and much of it is `@SystemApi`, so the research's own guidance is to gate *profile-based* work at 33 — a distinction Phase 2 never has to apply because it calls no profile API, and one Phase 10 must.
- **Two unverified cross-band questions, unresolved by design.** Research §6 U-1 (whether a 31+ target omitting the legacy permission still succeeds on device API 26-30) and U-4 (what `requestPermissions` does for a permission the running platform does not define). Both become load-bearing the moment a legacy-band permission is declared, and prompt section 6's scope means Phase 2 never gets there. U-6 also removed a tempting shortcut: whether `ACTION_STATE_CHANGED` is still sticky is unverified, so initial state comes from the adapter's own state read (`AdapterStateObserver.kt:85`), never from `registerReceiver`'s return value.
- **`BluetoothPermission.introducedAtSdk` disagrees with the research.** The enum says 18 for `BLUETOOTH` and `BLUETOOTH_ADMIN` (`BluetoothPermission.kt:30-31`); `bluetooth-api-research.md` §2 records both as existing since API 1, citing `Manifest.permission`, and the audit's R-13 had flagged the number as unverified. The field is read by no code path in Phase 2 — no resolver, provider or test consults it, and `isLegacyForTargeting31Plus` is likewise unread — so nothing in this phase's behaviour depends on it, but the value as written is not supported by the cited research and is owed a correction by the phase that first reads it.
- **No adapter state transition is validated.** `BluetoothAdapterState` has six values and no transition table: unlike `state/ConnectionState.kt`, which has `ConnectionStateTransitions.canTransition` behind `DeviceState.attemptConnection`, the observer accepts whatever the platform announces next (`AdapterStateObserver.kt:120-138` filters duplicates only). A nonsensical sequence — `ENABLED` straight to `ENABLING`, or `UNKNOWN` after `ENABLED` — reaches consumers as delivered. The design reason is that the platform's own state machine is not a contract Phase 2 verified, and inventing legality edges would be inventing behaviour; the consequence is that transition legality, if it is ever needed, belongs to the session layer that owns `ConnectionState`, and Phase 2 makes no claim about it.
- **OEM variance is unmeasured.** Research §7.3 item 5: the documentation speaks for AOSP. A specific phone is a separate evidence item, and `docs/security/device-access-policy.md:44-63` records the one attached device as off-limits until the user supplies instructions, so no Phase 2 statement about real Android behaviour is verified — every Android fact in this file is at documentation tier.

## 17. What enforces what, and with what test surface

Test layout mirrors the areas: `core/src/test/kotlin/com/omnibuds/core/platform/` (`AdapterStateObserverTest` 16, `PermissionRequirementResolverTest` 10, `PhaseTwoScopeTest` 5, plus `FakeAdapterStateSource`), `core/src/test/.../transport/` (five classes, 37 tests), `core/src/test/.../common/OmniBudsErrorCategoryTest` (7 tests, four of them new or rewritten in Phase 2), and `platform/android/src/test/` (five classes / 45 tests) — the Android module's first test source set, which the audit named as missing (R-12). `common/OmniBudsErrorCategoryTest.kt:40-128` is the exhaustive retry-and-invalidation table pair; `architecture/DependencyDirectionTest.kt` is the 12-rule set §3 tabulates. `docs/phases/phase-2/test-plan.md` (another workstream's file) owns test ids and tier labels; nothing here invents one.

Two honesty notes about the test surface itself. `TransportBoundariesTest.kt:25-29` and `AdapterStateObserverTest.kt:21-28` state their own limits — fixtures are invented, a category appears because a test needed a refusal rather than because anything was observed, and "no case here makes any claim about a real device" — and no test result in this phase may be cited as evidence about a radio (`transport-boundaries.md` §6, PROTO-VERIFY-001). And the Android module's JVM tests touch no framework *method*: `AndroidBluetoothPlatformTest.kt:3` imports `android.bluetooth.BluetoothAdapter` solely for the inlined `STATE_ON` constant, and the framework-calling classes — `SystemBluetoothAdapterHandle`, `SystemPermissionStandingReader`, `SystemPlatformFeatureProbe`, `SystemTargetSdkProvider`, `SystemApiLevelProvider` — have **no** test at all, which `platform/android/build.gradle.kts:45-48` states as the deliberate shape ("only the seam-bearing classes are tested this way"). Those five classes' behaviour is compiled and lint-checked, nothing more, and `validation.md` must keep it that way in its own words.

Three places where Phase 2's prose currently overstates its code, recorded rather than smoothed: `PermissionState.kt:42-45`'s KDoc says `NOT_REQUIRED` *and a genuine grant* allow silent proceeding while the predicate returns true only for `NOT_REQUIRED`; `AndroidAdapterStateSource.kt:30-33` says the exception "is preserved in the error's cause" while `OmniBudsError` has no `cause` field (`OmniBudsError.kt:15-21`) and only the class simple name reaches `detail`; and `ApiAvailability.kt:25-31`'s KDoc describes the phone-hardware axis above a function that answers the OS axis (`:32-36`). Phase 1 `specs.md` §11 rule 6 is the rule they owe.
