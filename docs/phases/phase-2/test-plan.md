# Phase 2 — Test Plan

**Phase:** 2 — Android Bluetooth Foundation · **Scope id:** `P2` · **Owner agent:** Agent F (testing and QA) / orchestrator as integration owner
**Instantiates:** `docs/phases/phase-0/testing-governance.md` — tiers T1–T8 (§2.1), the mandatory eight-field record (TST-REC-001), the id grammar (TST-REC-002), the `REQ` ↔ `TEST` ↔ tier ↔ level matrix (TST-REC-006), the mocking ceiling (TST-MOCK-001, TST-MOCK-006), the no-relaxation rule (TST-GOV-001) and the governance-check rule (TST-ACC-006) — using `docs/templates/test-plan-template.md`.
**ID discipline.** Phase 2 prompt §8/§9 seeds ids in a `TEST-P2-...` prose form; `ADR-P0-013` and TST-REC-002 fix the canonical grammar as `TEST-<SCOPE>-<NNN>`, so every record below carries `TEST-P2-<NNN>`, allocated monotonically from 001, never reused, never renumbered. Said once here and not repeated per record. Ids `TEST-P2-023` … `TEST-P2-040` are allocated to **gaps** (§9) so that each unmet obligation of prompt §9 has a permanent id; a gap id is a record of something NOT RUN, never a passing test (TST-REC-005).
**Record shape.** One record per executing test cluster. Every method name below was copied from a `@Test` on disk and cross-checked against the executed JUnit `testcase name` attribute, so the cluster counts sum to the measured totals. No name in this file is paraphrased or inferred.
**Requirement linkage.** `docs/phases/phase-2/requirements.md` does not exist at the time of writing (that directory holds `architecture-audit.md`, `bluetooth-api-research.md`, `decisions.md`, `execution-prompt.md`, `transport-boundaries.md`), so no `REQ-P2-<NNN>` id is invented here. Each record links to the **phase 2 execution-prompt section** it executes plus the ADR that governs it, and **the orchestrator must reconcile `REQ-P2-<NNN>` ids into §8 once `requirements.md` is issued** (TST-REC-003 makes that linkage mandatory, not optional; until it exists this plan is incomplete by its own rule, and says so).
**Mocked versus physical — the line this plan will not blur.** Every test below is a JVM unit test against scripted fakes. **No Bluetooth hardware, no headset, no phone, no emulator, no instrumentation test and no CI was used to produce any result in this file.** The only physical-device runs anywhere in this repository belong to the separate deployment-harness workstream and are discussed in §7, where it is stated why they can say nothing about Bluetooth.

### 1.3 Evidence ceiling — what a green suite here is worth

Per `testing-governance.md` §2.1, a T1 pass justifies at most **`IMPLEMENTED`**. Every cluster below is T1, so **the ceiling for all of Phase 2's test evidence is `IMPLEMENTED`**, and:

- nothing here justifies `LAB_TESTED`, `HARDWARE_VERIFIED` or `PERSISTENCE_VERIFIED` (TST-MOCK-001);
- nothing here is evidence that any phone, adapter, OEM build or headset does or does not support anything (TST-GOV-004, TST-HW-004);
- `PlatformFeatureSupport.hardwareEvidence` is `INFERRED` for every feature and `isUsable` is false everywhere, which is the code agreeing with this ceiling rather than a test raising it (`AndroidPlatformCapabilityProviderTest.nothingIsClaimedUsableBecauseNoRadioWasOpened`);
- no capability moves above `UNKNOWN`, no codec enters `ACTIVE`/`NEGOTIATED`, and persistence is untouched (TST-TIER-003, TST-PER-001).

**Ceiling conflict, surfaced rather than resolved silently.** Two Phase 2 documents read T1 as earning `LAB_TESTED`: `docs/templates/test-plan-template.md` §3 (unit row) and `docs/phases/phase-2/transport-boundaries.md`, whose header row says unit tests of the value types are "`LAB_TESTED` evidence about the types". Governance §2.1 caps T1 at `IMPLEMENTED` and TST-GOV-001 forbids a phase relaxing it, so **this plan uses `IMPLEMENTED` throughout and asks the orchestrator to normalise both documents** — `transport-boundaries.md`'s claim is the more damaging of the two because it is inside the phase record. TST-FAIL-001 row 3 is the failure this would be.

**`UNKNOWN` is never collapsed.** No test in this plan asserts, and no production path reached by a test produces, a `false` / `0` / `UNSUPPORTED` rendering of an absent fact. The methods that hold that line, by name: `aMissingReadingIsUnknownNotOff`, `anUnrecognisedNumberIsUnknownNotDisabled`, `anUnreadableValueIsUnknownRatherThanDisabled`, `aProbeThatThrowsIsUnknownRatherThanAbsent`, `anUnansweredQuestionIsUnknownRatherThanDenied`, `anUnrequestedRuntimePermissionIsNotReportedAsADenial`, `anUnknownTargetSdkIsNotSilentlyTreatedAsRequiringNothing`, `anUnknownTargetSdkIsNotSilentlyReadAsNoRequirement`, `aFailedFirstReadIsReportedAndTheChangeStreamStillRuns`, `aTimestampIsRecordedOnlyWhenThePlatformSuppliesOne`, `profileConnectionStateIsNeverClaimed`, `anEmptyCandidateListAndAnAllRefusedListAreBothUndetermined`, `aRefusedCandidateIsLegalAtEveryEvidenceTier`, `theResolverRefusesRatherThanInventingForAnUndeterminedContext`, `anUnknownTargetSdkProducesNoPlanRatherThanAGuessedBand`. The invariant they encode is master §53 and ADR-P0-016; the audit finding R-6 (`docs/phases/phase-2/architecture-audit.md:327`) is the counter-example that survives in main source and is carried as `RISK-041`, not as a passing test.

## 2. How to read the records

Each record states: purpose · tier · setup (which fake stands in for what) · input (the real method names) · expected result · failure condition · hardware requirement · automation · evidence level · result · linkage. Hardware requirement is `NONE` in every record because **every executed test needs no radio**, and that column is a statement about the test, not about the obligation. Result is `pass` because every name listed was found in the XML for its class with `failures="0" errors="0" skipped="0"`; a test that exists but did not execute would be recorded NOT RUN, and there is no such case in §3. Linkage is by prompt section plus ADR until `requirements.md` exists (§0). TST-REC-004's rule — a test referencing no `REQ` is orphan filler — is satisfied by that mapping being total: all 98 Phase 2-relevant methods appear in exactly one record.

## 9. Manual device validation — instructions for a Phase 3 human session

**Nothing in this section is a claim. It is a script for someone who has a phone in their hand.** Perform it only under `docs/security/device-access-policy.md` — the phone is a personal device, every action is user-directed, and no setting, permission grant or uninstall may be changed to make a check pass. Record each step in `docs/phases/phase-3/validation.md` with the device identity fields the platform actually reports, writing `UNKNOWN` where a field is unavailable (TST-HW-003). Until this list has been run, gap ids `TEST-P2-023` … `TEST-P2-031` stay open and no statement in §3 rises above `IMPLEMENTED`.

1. **Note the identity first.** Model, Android version, `SDK_INT`, OEM build (`getprop` for `ro.build.version.incremental` and the MIUI/HyperOS release), and the **application's own `targetSdkVersion`** as installed — the last because the resolver reads it at runtime and a library build declares none (RISK-033).
2. **Adapter present and `getState()`.** Install an app module that hosts `:platform:android` and call `readAdapterState()`; write down the raw integer the platform returned and the `BluetoothAdapterState` the mapping produced. Confirm that a phone with Bluetooth off yields `DISABLED` and that nothing in the app ever produced `UNKNOWN` from a successful read (closes `TEST-P2-023`, part of `TEST-P2-030`).
3. **`ACTION_STATE_CHANGED` delivery.** Start `observeAdapterState()`, toggle Bluetooth from the system Settings UI (not from the app — `enable()`/`disable()` are dead for third-party apps, research Q6 R-4), and record: does an event arrive, how many, in what order, with which `EXTRA_STATE`, and does the stream's first element still read `INITIAL_READ`? Then answer, by observation rather than by argument: is the broadcast sticky (research U-6), and does `RECEIVER_NOT_EXPORTED` on a system broadcast behave identically on this OEM build to the flagless overload (RISK-028, RISK-029)?
4. **Duplicate and transition behaviour.** Toggle off→on→off→on and confirm the observer's suppression and A-B-A preservation hold against real broadcast timing, and that `openCalls`-equivalent registrations never exceed one; then attempt a second concurrent observation from a real UI and record the refusal (`TEST-P2-012`'s claim, on hardware).
