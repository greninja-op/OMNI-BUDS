## Boundary, build and area registration

### REQ-P2-001 — The Android mechanism stays behind `:platform:android`, and the policy half is a registered core area
**Description.** Bluetooth *policy* (adapter-state vocabulary, the permission matrix and its resolver, the observation machine, the platform-capability types) SHALL live in the `:core` area `com.omnibuds.core.platform`, registered at layer 1, and the transport boundaries SHALL live in the existing `transport` area at the same layer; Bluetooth *mechanism* (framework calls, receiver registration, `checkSelfPermission`, `hasSystemFeature`, `SDK_INT`) SHALL live only in `com.omnibuds.android.bluetooth.*` or `com.omnibuds.android.di` inside `:platform:android`; `:core` SHALL NOT import `android.`, `androidx.` or `com.omnibuds.android.`, and SHALL NOT name an Android framework type in any code line; no new Gradle module SHALL be created for Phase 2's subject matter.
**Rationale.** Prompt §5.1 ("clean boundary … Android framework types must not leak"), §5.9 (composition root), and ADR-P2-001, which registers the area and refuses a `:bluetooth` module; the split table is `docs/phases/phase-2/architecture-audit.md` §2.2. A permission matrix that lives in the Android module cannot be tested off-device, which is the whole reason Phase 2's 45 Android tests are wiring tests.
**Dependencies.** REQ-P1-002, REQ-P1-003, REQ-P1-011; REQ-P0-001; ADR-P2-001, ADR-P2-006.
**Acceptance criteria.** AC-1 `platform` is registered at layer 1 in the layer map. AC-2 no `:core` main import begins `android.`/`androidx.`/`com.omnibuds.android.`, and no `:core` code line names any of the sixteen named framework types. AC-3 every `:platform:android` source sits under one of the two authorised package roots. AC-4 the module dependency points one way only. AC-5 dependency direction inside `:core` still forbids sideways and upward edges with `platform` in the map. AC-6 `settings.gradle.kts` lists three modules and none of them is a Phase 6 `:bluetooth` shell.
**Verification.** AC-1/AC-5 by `architecture/DependencyDirectionTest.everyCoreAreaIsRegisteredInTheLayerMap` (`DependencyDirectionTest.kt:232`) and `.coreAreasDependOnlyOnMoreFoundationalAreas` (`:213`), with the map itself at `:33-48` (`"platform" to 1` at `:39`) — note that this map also moved `state` from Phase 1's layer 1 to layer 0 (`:34-37`, justified by its own comment) so that `platform` may import `state.VerificationLevel` (`PlatformFeatureSupport.kt:3`), a re-layering that ADR-P2-001 describes only as placing `platform` "alongside `state` and `transport`" and that no Phase 2 ADR records; AC-2 by `.coreMainSourcesDoNotImportAndroidFrameworks` (`:121`) and `.coreReferencesNoAndroidFrameworkTypes` (`:146`, token list at `:151-156`); AC-3 by `.platformSourcesLiveOnlyUnderTheAuthorisedPackages` (`:412`, allowed roots `:422-425`, fail-loud clause `:413-419`); AC-4 by `.theAndroidModuleDependsOnCoreAndNotTheReverse` (`:463`). ## Adapter availability and state observation

### REQ-P2-002 — Adapter availability is inspected as a fact with an unknown rung, never as a boolean or a crash
**Description.** The system SHALL distinguish "no usable adapter", "adapter exists and is off", "adapter is transitioning", "adapter is on" and "not established" as six `BluetoothAdapterState` values, SHALL expose adapter presence as `ApiAvailability` (which has an `UNKNOWN`), SHALL treat a missing adapter as a reported fact rather than an application failure, and SHALL resolve any unrecognised or missing platform reading to `UNKNOWN` rather than to `DISABLED`.
**Rationale.** Prompt §5.2's nine-way distinction and "Do not treat a missing adapter as an application crash"; master §53; ADR-P0-016. The named boolean in the prompt's illustrative `isBluetoothAvailable(): Boolean` (`execution-prompt.md:278`) was deliberately **not** copied: a two-valued answer cannot express "we were not permitted to look" apart from "there is no radio", which prompt §5.3 forbids conflating. `BluetoothPlatform` (`core/platform/BluetoothPlatform.kt:20-38`) therefore answers through `readAdapterState()`, `capabilities()` (whose `adapterPresent` is `ApiAvailability`, `BluetoothPlatformCapabilities.kt:19`) and the state's own predicates.
**Dependencies.** REQ-P2-001, REQ-P2-013; ADR-P2-001, ADR-P2-012.
**Acceptance criteria.** AC-1 the enum holds exactly `UNKNOWN, UNAVAILABLE, DISABLED, ENABLING, ENABLED, DISABLING` with `isUsable()` true only for `ENABLED`, `isProvablyDisabled()` true only for `DISABLED`, `isIndeterminate()` true for `UNKNOWN` and `UNAVAILABLE`. AC-2 `getState()` values map 1:1 to the four real states, an absent adapter maps to `UNAVAILABLE` before the raw reading is considered, and a null or unrecognised raw value maps to `UNKNOWN`. AC-3 the broadcast-missing-extra marker sits outside the platform's own state range so it cannot be read as a state. AC-4 a source with nothing behind it fails with `ADAPTER_UNAVAILABLE` and never reports `ENABLED`.
**Verification.** AC-1 by `platform/AdapterStateObserverTest.onlyUsableAdapterStatesAreReportedUsable` (`AdapterStateObserverTest.kt:278`) and AC-4 by `.anUnavailableSourceReportsUnavailableAndNotEnabled` (`:257`), against `BluetoothAdapterState.kt:16-44` and `AdapterStateSource.kt:47-65`; AC-2 by `mapping/AdapterStateMappingTest.enabledAdapterStateMapsToEnabled`, `.disabledAdapterStateMapsToDisabled`, `.transitioningStatesMapToTheirOwnNames`, `.anAbsentAdapterIsUnavailableWhateverItsLastReadingWas`, `.aMissingReadingIsUnknownNotOff`, `.anUnrecognisedNumberIsUnknownNotDisabled` (`AdapterStateMappingTest.kt:19,27,35,47,59,67`) over `mapping/AdapterStateMapping.kt:21-29`, plus `adapter/AndroidAdapterStateSourceTest.anAbsentAdapterIsReportedAsUnavailable` (`AndroidAdapterStateSourceTest.kt:40`) and `.anUnreadableValueIsUnknownRatherThanDisabled` (`:47`); AC-3 by `.theUnreadableMarkerIsOutsideThePlatformsStateRange` (`AdapterStateMappingTest.kt:78`) against `RAW_STATE_UNREADABLE` (`AdapterStateMapping.kt:38`) and its use in the receiver (`SystemBluetoothAdapterHandle.kt:89`). **Inspection residue:** the real framework calls behind presence and state — `context.getSystemService(BluetoothManager::class.java)?.adapter` (`SystemBluetoothAdapterHandle.kt:35`) and `adapter?.state` (`:46`) — are named in **no** test (`SystemBluetoothAdapterHandle` appears in no file under `platform/android/src/test`), so the claim "a phone with no radio yields a null adapter and therefore `UNAVAILABLE`" is a reading of that file plus `docs/phases/phase-2/bluetooth-api-research.md` §4 item 1, not a test result.
**Priority.** MUST · **Status.** partly-tested

### REQ-P2-003 — Adapter-state observation reports what the adapter is now, then what changes, and suppresses duplicates without losing transitions
**Description.** A fresh observation SHALL emit one initial value obtained by reading the adapter before any platform event is acted on; SHALL drop a platform announcement equal to the last reported state; SHALL preserve a genuine A-B-A sequence; SHALL label each element with the reason it was emitted (`ObservationKind`, whose four members distinguish a starting value from a transition); SHALL forward a cancelled platform answer as cancellation rather than relabelling it a fault; and a failed initial read SHALL be reported as a structured failure while the change stream continues, leaving the state unknown.
**Rationale.** Prompt §5.4 ("Initial state retrieval", "State changes", "Duplicate broadcast prevention"); ADR-P2-007, which states why consecutive-duplicates and A-B-A are different claims; ADR-P2-018, which fixed audit findings R-7 (a cancelled read had been re-emitted as `PLATFORM_EXCEPTION`) and R-8 (the first genuine transition after a successful read had been tagged as the start of the observation) in the machine rather than carrying them as notes, and deleted the unconstructible `DEDUPED` member; ADR-P0-016 for the failed-read rule. Stopping the stream on a failed read would report "we could not look now" as "nothing will change", a second fabricated negative.
**Dependencies.** REQ-P2-002, REQ-P2-004, REQ-P2-012; ADR-P2-007, ADR-P2-018.
**Acceptance criteria.** AC-1 first element is `INITIAL_READ` carrying the read value. AC-2 a repeated `ENABLED, ENABLED` yields one emission. AC-3 `ENABLED` initial then `DISABLED, ENABLED, DISABLED` yields four elements tagged `INITIAL_READ, PLATFORM_EVENT, PLATFORM_EVENT, PLATFORM_EVENT`. AC-4 after a *successful* read, a repeat then a change yields `INITIAL_READ, PLATFORM_EVENT` — `INITIAL_EVENT` never follows a successful read. AC-5 a read that fails emits the structured failure and the subsequent platform change still arrives, tagged `INITIAL_EVENT`, with no `UNKNOWN`→`DISABLED` substitution. AC-6 a one-shot `readOnce()` is tagged `PLATFORM_READ`, does not take the observer slot and registers nothing. AC-7 a cancelled read ends the stream with `OperationOutcome.Cancelled` and registers nothing; a cancelled registration ends it with `Cancelled` and releases the slot. AC-8 timestamps come only from the injected `TimeProvider`: null when it answers nothing, never `0`. AC-9 no enum member claims to represent a suppressed duplicate.
**Verification.** AC-1 `platform/AdapterStateObserverTest.anObservationStartsWithWhatTheAdapterIsRightNow` (`AdapterStateObserverTest.kt:40`); AC-2 `.aStateThePlatformAnnouncesTwiceIsNotPassedOnTwice` (`:53`); AC-3 `.anOffOnOffSequenceIsPreservedRatherThanCollapsedToTheLastValue` (`:66`, kind list asserted at `:82-88`); AC-4 `.theFirstChangeAfterASuccessfulReadIsAPlatformEventNotAnInitialOne` (`:93`); AC-5 `.aFailedFirstReadIsReportedAndTheChangeStreamStillRuns` (`:161`); AC-6 `.aSingleReadDoesNotOccupyTheObserverSlot` (`:241`, `openCalls == 0` at `:250`) against `AdapterStateObserver.kt:172-179`; AC-7 `.aCancelledReadIsReportedAsCancellationNotAsABrokenAdapter` (`:212`, `openCalls == 0` and the released slot asserted at `:222-224`) and `.aCancelledRegistrationIsReportedAsCancellationAndReleasesTheSlot` (`:227`) against the two forwarded branches at `AdapterStateObserver.kt:107-113` and `:146`; AC-8 `.aTimestampIsRecordedOnlyWhenThePlatformSuppliesOne` (`:267`) against `TimeProvider.kt:11-18`; AC-9 by `AdapterStateObservation.kt:11-14,16-21`, whose KDoc states that suppression drops a repeat before any value is labelled, so no member names one. The wiring is re-proved at platform level by `AndroidBluetoothPlatformTest.anObservationReportsTheCurrentStateBeforeItReportsChanges` (`AndroidBluetoothPlatformTest.kt:65`) and `.aSingleReadCarriesThePlatformAnswerAndTheInjectedTime` (`:50`). The two residues this record carried before `8fc2bda` — cancellation being relabelled `PLATFORM_EXCEPTION` and an unconstructible `DEDUPED` — are closed, and `docs/phases/phase-2/architecture-audit.md` findings R-7 and R-8 are answered by ADR-P2-018 rather than by a note.
**Priority.** MUST · **Status.** tested

### REQ-P2-004 — At most one adapter-state observation runs at a time, and the platform registration is torn down on every exit path
**Description.** A second concurrent observation SHALL be refused with `RESOURCE_UNAVAILABLE` instead of registering twice; the registration handle obtained from the source SHALL be disposed in a `finally`; a disposal that throws SHALL be captured on the observer as `teardownProblem` rather than emitted into a channel that cancellation may already have closed; the slot SHALL be released only after teardown; and a stream opened but never collected SHALL still be disposable.
**Rationale.** Prompt §5.8 ("No leaked receivers or callbacks", "No duplicate concurrent adapter observers") and §5.4 ("Resource cleanup"); ADR-P2-007, which chose the single-slot machine and the recorded-teardown-failure rule; audit findings R-5 and R-7. A second registration for one fact is precisely the leak the check exists to catch.
**Dependencies.** REQ-P2-003, REQ-P2-014; ADR-P2-007.
**Acceptance criteria.** AC-1 concurrent second attempt yields `Failure(RESOURCE_UNAVAILABLE)` and exactly one platform open call. AC-2 normal completion disposes once, leaves zero active registrations, clears `isObserving` and reports a null `teardownProblem`. AC-3 cancellation disposes once and releases the slot. AC-4 a throwing disposal is recorded as `RESOURCE_UNAVAILABLE` on `teardownProblem` without swallowing the observations. AC-5 a refused registration hands back nothing to dispose and leaves zero active registrations. AC-6 disposing twice reaches the platform once, and disposal closes the stream so no collector hangs.
**Verification.** AC-1 `AdapterStateObserverTest.aSecondConcurrentObserverIsRefusedInsteadOfRegisteringTwice` (`AdapterStateObserverTest.kt:114`, `openCalls == 1` at `:109`) and `AndroidBluetoothPlatformTest.aSecondConcurrentObservationIsRefusedThroughThePlatformWiring` (`AndroidBluetoothPlatformTest.kt:80`); AC-2 `.theRegistrationIsTornDownWhenTheStreamEndsNormally` (`:134`); AC-3 `.cancellationTearsTheRegistrationDownToo` (`:147`); AC-4 `.aTeardownThatThrowsIsRecordedInsteadOfDisappearing` (`:185`) against `AdapterStateObserver.kt:148-162`; AC-5 `.aRefusedRegistrationOpensNothingAndReportsWhy` (`:198`); AC-6 `adapter/AndroidAdapterStateSourceTest.disposingTwiceReachesThePlatformOnce` (`AndroidAdapterStateSourceTest.kt:104`) and `.disposalEndsTheStreamSoNoCollectorHangs` (`:116`) against `ClosingRegistration` (`AndroidAdapterStateSource.kt:124-134`), plus `.aRegistrationOpenedWithoutCollectingIsStillDisposalReady` (`:90`) against the eager-registration decision documented at `AndroidAdapterStateSource.kt:57-69`. **Inspection residue:** AC-1's slot is per-observer-instance (`AdapterStateObserver.kt:40`), so "exactly one observer object exists in the process" is enforced only by the composition-root convention in `di/OmniBudsBluetooth.kt:34-38` and by REQ-P2-016's manual wiring; no check counts live `AdapterStateObserver` instances, and `AdapterStateSource.unavailable()`'s existence (`AdapterStateSource.kt:33-36`) means a mis-wired caller can still obtain a second source.

## Permission model

### REQ-P2-005 — Permission requirements are resolved centrally, version-aware, with a mandatory reason for every row
**Description.** A single centralised resolver SHALL answer "what does this operation need" from a frozen table keyed on the app's **`targetSdkVersion`**, with the device API level producing caveats rather than requirements; it SHALL model both the legacy band (26–30, install-time `BLUETOOTH`/`BLUETOOTH_ADMIN`, location-coupled scan results) and the modern band (31+, runtime `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT`); it SHALL refuse to produce a plan when the target SDK is unknown, returning `Failure(INVALID_STATE)` instead of choosing a band; and no `PermissionRequirement` SHALL be constructible without a non-blank reason.
**Rationale.** Prompt §5.3 ("Determine which permissions are required for each authorized operation and Android version", "Create a centralized permission requirement resolver"); ADR-P2-002 (minSdk 26 means two models must both be answered); ADR-P2-009, which corrects Phase 0 `SEC-PERM-002`'s device-version framing on the strength of `bluetooth-api-research.md` §3 and Q1-Q3; `PermissionRequirement.kt:11-26`'s guard is the project's answer to SEC-PERM-004.
**Dependencies.** REQ-P2-001, REQ-P2-006, REQ-P2-018; ADR-P2-002, ADR-P2-009.
**Acceptance criteria.** AC-1 the five Phase-2-authorised operations need nothing on a 31+ target and produce no runtime prompt. AC-2 on the legacy band, adapter-state inspection requires install-time `BLUETOOTH` only, and adapter-availability inspection requires nothing on either band. AC-3 an unknown target SDK yields `Failure(INVALID_STATE)`, not a band. AC-4 the Phase-3 scan rows carry `BLUETOOTH_SCAN` plus fine location unless `assertsNeverForLocation`, and the legacy scan band carries exactly the four permissions with per-item reasons and bands that do not spill across 30/31. AC-5 connect-class operations follow the compatibility guide below 31 and the reason string names that asymmetry. AC-6 LE Audio below the modern band answers as an API-availability limit with a caveat, not a permission answer. AC-7 profile-state and scan caveats depend on the device level, and a plan for an authorised inspection carries no caveat. AC-8 no Phase-2 operation ever requires a location permission, on either band.
**Verification.** AC-1 `platform/PermissionRequirementResolverTest.phaseTwoOperationsRequireNoPermissionForAModernTarget` (`PermissionRequirementResolverTest.kt:33`) and `PhaseTwoScopeTest.everyAuthorisedOperationHasAPlanAndNoneOfThemPromptsTheUser` (`PhaseTwoScopeTest.kt:56`); AC-2 `.theLegacyBandStillRequiresTheInstallTimePermissionForAdapterReads` (`:48`); AC-3 `.anUnknownTargetSdkProducesNoPlanRatherThanAGuessedBand` (`:61`) and `PhaseTwoScopeTest.theResolverRefusesRatherThanInventingForAnUndeterminedContext` (`:89`); AC-4 `.scanningNeedsLocationUntilNeverForLocationIsAsserted` (`:72`), `.theLegacyScanBandCarriesAllFourPermissionsAndSaysWhyPerItem` (`:86`); AC-5 `.connectClassOperationsFollowTheGuideWhereTheMethodDocsAreSilent` (`:106`); AC-6 `.leAudioOnALegacyTargetIsAnApiLimitNotAPermissionQuestion` (`:125`); AC-7 `.profileStateCarriesTheDeviceLevelEnforcementCaveat` (`:135`); AC-8 `.noPhaseTwoOperationEverAsksForLocation` (`:150`); plus `.everyRequirementNamesTheOperationItBelongsTo` (`:169`). ### REQ-P2-006 — Permission status is inspected without prompting, and "not asked" is distinguishable from "refused" and from "could not tell"
**Description.** The Android layer SHALL report a permission's standing from `Context.checkSelfPermission` plus the session's own request record, mapping a grant to `GRANTED`, a runtime refusal that the app did record asking for to `DENIED`, an unrecorded runtime refusal to `NOT_REQUESTED`, an undeclared install-time permission to `DENIED`, and a platform that did not answer to `UNKNOWN`; it SHALL never issue a prompt, and the operation-relative question SHALL answer `NOT_REQUIRED` only when the plan genuinely requires nothing, and `UNKNOWN` when the plan could not be determined.
**Rationale.** Prompt §5.3 ("permission-state inspection", "Do not repeatedly trigger permission prompts", "Do not silently bypass denied permissions") and §6 (no user-facing flows in Phase 2); research Q7 establishes that inspecting standing needs no permission, which is what makes `PERMISSION_STATUS_INSPECTION` authorised at all. `UNKNOWN`-versus-`DENIED` separation is ADR-P2-012's and ADR-P0-016's rule applied to permissions.
**Dependencies.** REQ-P2-005, REQ-P2-007; ADR-P2-011, ADR-P2-012.
**Acceptance criteria.** AC-1 the seven prompt §5.3 states exist as `PermissionState` and are not collapsed. AC-2 the four standing mappings above hold, and `standings()` covers every `BluetoothPermission`. AC-3 a standing query issues no prompt (no request API exists anywhere in the module).
