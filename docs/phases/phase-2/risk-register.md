# Phase 2 — Risk Register

Numbering continues the single project-wide register: Phase 0 wrote `RISK-001` … `RISK-015`, Phase 1 wrote `RISK-016` … `RISK-025`, so Phase 2 starts at `RISK-026` and does not restart the sequence (`phase-0/risk-register.md`, `phase-1/risk-register.md:3`). Scale as in both earlier phases: probability and impact are `low | medium | high`, exposure = probability × impact; Phase 0 also used the word `severe` for a high × high entry, and the two entries here that sit in that band are RISK-029 and RISK-035. Every entry is `open` unless its own text says otherwise, and the field shape is Phase 1's: probability/impact/exposure, description, mitigation, detection, fallback, owner.

**Eleven ids in this range were already cited by `docs/phases/phase-2/test-plan.md` before this register existed** — `RISK-026` … `RISK-034`, `RISK-039` and `RISK-041` — each with a stated meaning, and those anchors are honoured here rather than re-allocated, because a register that gave an already-cited id a different meaning would contradict the phase's own test record. The ids the test plan does not use (`035`–`038`, `040`, `042`–`043`) are allocated below, and nothing outside `docs/phases/phase-2/` cites an id above `RISK-025`, which was verified across every `.md`, `.kt`, `.kts` and `.toml` file in the repository before this file was written.

**The phase's central exposure is stated once, in RISK-035, and no other entry in this file closes it or implies it is closed.** No Bluetooth code in this repository has ever run on hardware, and no headset has been touched. `validation.md:13` records the build-gate row as `Physical Bluetooth run: NONE — no Phase 2 code executed on hardware`; known issue 1 (`validation.md:158`) gives the structural reason; `test-plan.md:8` states that no hardware, phone, emulator or instrumentation produced any result in that file; `docs/security/device-access-policy.md:61` says the same about Phase 2's validation. Every mitigation below is a *design* mitigation — a shape, a table, an assertion about our own code. None of them is evidence that a phone behaves as the transcription claims. Read in that light, an entry like RISK-029 or RISK-032 is a *specialisation* of RISK-035, not a peer of it.

### RISK-026 — The architecture checks read source text, not bytecode
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** The id `test-plan.md:175-176` cites against `coreMainSourcesDoNotImportAndroidFrameworks`, `coreReferencesNoAndroidFrameworkTypes`, `theAndroidModuleDependsOnCoreAndNotTheReverse` and `platformSourcesLiveOnlyUnderTheAuthorisedPackages`. Phase 1 raised this as RISK-017 (`phase-1/risk-register.md:17-23`), and Phase 2 did not narrow it — it extended the same mechanism with six further text-scan rules over the same two source roots (`DependencyDirectionTest.kt:111-116` for the platform walk, `:121`, `:412`, `:463`). A scan sees imports, identifiers on code lines with comments stripped, and file layout; it cannot see reflective access, a JVM API reached through an alias, or a transitive dependency pulled in by a library. The second half is now live rather than theoretical: ADR-P2-003 restored `kotlinx-coroutines-core` as an `api` production dependency of `:core` (`core/build.gradle.kts:29`; catalog `gradle/libs.versions.toml:10` for the version and `:20` for the library), so RISK-017's mitigation — "`:core` has zero production dependencies, which shrinks the transitive surface to nothing" — no longer holds. `architecture-audit.md:260` predicted exactly that this re-scoring would be needed.
**Mitigation.** Rules are expressed as imports *and* named identifier patterns; every scan fails loudly when a source root, a build script or the boundary manifest is missing rather than passing vacuously (`DependencyDirectionTest.kt:113`, `:440`, `:465`; ADR-P2-016 makes `platformSourcesLiveOnlyUnderTheAuthorisedPackages` fail on a source-free module); the new dependency carries its reason in the build file and in an ADR rather than arriving silently; `specs.md:127` records that the magic-literal scan finds no other numeric literal in Phase 2 main source, so the scanned surface stays enumerable by a human.
**Detection.** A Phase 46 KMP conversion that fails on a dependency no scan named; a production dependency appearing in `:core` without an ADR; any future bytecode- or AST-level architecture tool.
**Fallback.** Adopt a bytecode-level architecture check as an ADR-gated dependency, accepting the resolution cost RISK-016 describes; meanwhile re-verify `:core`'s dependency list by reading `core/build.gradle.kts`, not by trusting the scan.
**Owner.** Architecture Agent.

### RISK-027 — The guards are editable token lists and inheritable path prefixes
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** The id `test-plan.md:76, 88, 178, 222` cite, at `platformModuleContainsNoUnauthorisedCapabilities` and at the broadcast-confinement rule. Phase 2's scope enforcement is literal vocabulary: `DependencyDirectionTest.kt:292` holds a `listOf(...)` of forbidden tokens (`:293-298`), and `platformBroadcastUseIsConfinedToListeningForAdapterState` (`:383`) permits receiver vocabulary on any path *containing* the substring `bluetooth/adapter/` (`:390`). Both facts are recorded honestly in the test plan — "a **token list**, and widening it is a one-line edit that a later phase could make without noticing it is making it" (`:76`) and "a file placed at `bluetooth/adapter/x/` inherits the permission by string containment, and RISK-027 applies to this rule too" (`:88`). ADR-P2-016 is the mechanism that created the second half: Phase 2 had to give up the blanket `Intent` token, so it replaced it with a package-shaped allowance. That is the correct move by the ADR's own stated rule — narrow a guard with a recorded reason and re-guard narrower elsewhere — but the narrowing now sits one list literal and one path string away from being widened, and it means an intent-based capability placed inside `bluetooth/adapter/` is invisible to the guard that exists to stop intent capabilities.
**Mitigation.** ADR-P2-006 states that extending the token list happens "by amending this ADR, rather than relaxing a check mid-implementation", which makes a widening a documented act instead of a diff; the checks were deliberately falsified once before acceptance, with a scratch file that imported `android.content.Intent` from an unauthorised package, failing both new rules, then deleted (`validation.md:93`); the source walk fails rather than returning empty (`DependencyDirectionTest.kt:111-116`), so neither rule can go vacuous by losing its target.
**Detection.** A diff to `DependencyDirectionTest.kt` touching a token list or the `bluetooth/adapter/` string without a matching ADR in `decisions.md`. Note that the obvious negative-space probe — a file placed at `bluetooth/adapter/x/` — is not written today, so detection is review, not a check.
**Fallback.** Convert the path-substring allowance into an explicit package allowlist derived from the layer map registered by ADR-P2-001, so inheritance is by registration rather than by `in`.
**Owner.** Architecture Agent.

### RISK-028 — The receiver registration is a reasoned suppression whose rule is keyed differently from the documentation
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** The id `test-plan.md:275` cites. `SystemBluetoothAdapterHandle.kt:72` carries `@SuppressLint("InlinedApi", "UnspecifiedRegisterReceiverFlag")`, and `:platform:android:lintDebug`'s clean report depends on exactly those two suppressions — `test-plan.md:30` states plainly that lint "reports no issues *because* the two warnings are suppressed at the call site". Two later edits turn the suppression into a mask: the `apiLevel() >= RECEIVER_FLAG_API_LEVEL` guard (`:74`, constant `33` at `:114`) can be changed so the flag is passed where the overload does not exist, or a non-system action can be added to the `IntentFilter` (`:51`), which is the moment the flag stops being optional. `bluetooth-api-research.md:336-340` (Q6 item R-1) found the phase's framing is off by a band: the `Context.RECEIVER_*` constants exist and may be passed from API 33, but the *requirement* is keyed to `targetSdkVersion ≥ 34`. The mismatch is stated where the branch lives instead: `register()`'s KDoc now separates the two facts — constants passable from API 33, requirement keyed to targetSdk 34, protected-system-broadcast exemption — and the `ALIAS_API_LEVEL` / `RECEIVER_EXPORT_TARGET_SDK` constants that used to name the policy in `:core` while no code consulted them were deleted at close-out, because an unread named value reads like an enforced rule that does not exist. None of this is testable off-device: `registerReceiver` with and without the flag is reached only on Android (`TEST-P2-023`, `test-plan.md:248`).
**Mitigation.** Both suppressions carry their reasoning in the KDoc immediately above the annotated function (`:64-71`) rather than in a throwaway comment, and `validation.md:60-67` records the two warnings as examined and answered, including the rejected `androidx.core` alternative; the filter holds one protected system action and nothing else; `enable()`/`disable()` are never called (research Q6 R-4), so the registration cannot turn into a control.
**Detection.** `./gradlew --offline :platform:android:lintDebug` regaining a finding after the guard or the filter changes — which is the case the suppression would otherwise hide. Device-session step 3 (`test-plan.md:275`) asks, by observation, whether `RECEIVER_NOT_EXPORTED` on a system broadcast behaves identically to the flagless overload on this OEM build.
**Fallback.** Take `androidx.core`'s `ContextCompat.registerReceiver` under an ADR (rejected in ADR-P2-016 as the module's first AndroidX dependency for no behavioural gain), or pass no flag on any branch and record the system-broadcast exemption explicitly at the call site.
**Owner.** Bluetooth Agent / Security Agent.

### RISK-029 — OEM variance now has real code to bite on
**Probability.** high · **Impact.** high · **Exposure.** high
**Description.** The id `test-plan.md:162, 214, 250, 275` cite. Phase 0's RISK-001 (OEM Bluetooth differences, `phase-0/risk-register.md:9-15`) was, until this phase, a hazard with nothing Android-shaped to land on. Phase 2 supplies the first exposure: an adapter mapping over the platform's state integers whose sentinel `mapping.RAW_STATE_UNREADABLE` is chosen to fall outside that range (`specs.md:124`), tested against "an OEM integer outside the four (unknown whether one exists)" (`test-plan.md:162`) — a case the plan itself says is unknown; and `SystemPlatformFeatureProbe.hasFeature` is a bare `packageManager.hasSystemFeature(featureName)` (`PlatformFeatureProbe.kt:27`) whose real answer on a HyperOS build is gap `TEST-P2-025`. The one phone physically reachable from this workstation is a Xiaomi `2311DRK48I`, Android 14, API 34, HyperOS `V816.0.8.0.UNLINXM` (`docs/development/adb-deployment/validation.md:12-16`), and no Phase 2 code ran on it (`validation.md:39`, `adb devices -l` → no device attached at close).
**Mitigation.** An unrecognised integer resolves to `UNKNOWN`, never to `DISABLED` (`anUnrecognisedNumberIsUnknownNotDisabled`); a probe that throws yields `UNKNOWN` and does not take the phone's other answers down with it, so the API level the phone did report survives (`aProbeThatThrowsIsUnknownRatherThanAbsent`, `AndroidPlatformCapabilityProviderTest`); the feature names queried are the platform's own strings (`android.hardware.bluetooth`, `android.hardware.bluetooth_le`) rather than paraphrased ones (`test-plan.md:144`); per TST-GOV-005 and TST-HW-004 a divergent OEM answer is recorded as a per-phone fact and never as "Xiaomi does not support" (`test-plan.md:279`).
**Detection.** Device-session steps 2, 3 and 7 (`test-plan.md:274-279`); the cross-phone matrix scheduled at Phase 32. Detection here is genuinely mechanical — a raw integer the mapping does not name, or a `hasSystemFeature` answer that contradicts the phone's own documentation.
**Fallback.** Report the feature unavailable *on this phone*, with the observed integer recorded alongside it, and leave the state `UNKNOWN` rather than guessing which of the four the OEM meant.
**Owner.** Bluetooth Agent / Testing Agent.

### RISK-030 — DENIED_PERMANENTLY and REQUIRES_USER_ACTION are expressible and unreachable
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** The id `test-plan.md:140` cites, with the caveat already attached: they are "unreachable by construction in the Android layer, which is a statement about our code, not about Android". ADR-P2-012 keeps both enum members and forbids the platform layer from ever producing them; `noInputProducesAnUnsupportedClaim` walks every `BluetoothPermission` × granted {true, false, null} × requested {true, false} and asserts neither state appears anywhere in it (`test-plan.md:140`). The reason is research Q4: no app-visible signal establishes permanent denial on current Android. The user-facing consequence lands later. `checkSelfPermission` returns the same answer for never-asked and for asked-and-refused, so the distinction is carried entirely by an in-memory, deliberately unpersisted process record (`PermissionRequestLedger.kt:9-17` states why it is not persisted; the production ledger is `:24-32`). A Phase 49 UI that asks, is refused, and is then restarted finds an empty ledger, reports `NOT_REQUESTED`, and prompts again — against prompt §5.3's "do not repeatedly trigger permission prompts". Separately, research Q6 R-4 shows `enable()` always fails for a target-33+ app, which is exactly the `REQUIRES_USER_ACTION` shape the app can perceive only as an unexplained refusal.
**Mitigation.** The unreachability is proved exhaustively rather than by inspection; a refusal this process actually saw maps to `DENIED`, an unavailable answer to `UNKNOWN`, and never to `UNSUPPORTED`; the ledger is a `fun interface` seam so the phase that needs persistence can substitute it under an ADR instead of editing a constant; ADR-P2-012's stated purpose is to remove the temptation to render "we were not allowed to look" as "your phone has no Bluetooth".
**Detection.** The first permission-explaining UI: a permanent-denial sentence the platform never established, or a prompt repeating across a process restart. `TEST-P2-031` is the related gap — revocation mid-operation may be observable only as process death (research Q5).
**Fallback.** Give the ledger a persisted session lifetime with an explicit reset rule tied to an actual request, and surface the refusal as "we asked, you said no" using the reason strings the resolver already carries.
**Owner.** Security Agent (Phase 3 prompt flow) / UI owner (Phase 49).

### RISK-031 — Single-slot uniqueness is per object and rests on one composition root
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** The id `test-plan.md:173` cites, against `aSecondConcurrentObserverIsRefusedInsteadOfRegisteringTwice` and `aSecondConcurrentObservationIsRefusedThroughThePlatformWiring`. `AdapterStateObserver`'s slot is `private val slot = Mutex()` (`AdapterStateObserver.kt:40`), so what those tests prove is that one object refuses a second concurrent collector — not that the process holds one observation. Audit finding R-5 (`architecture-audit.md:326`) named this precisely ("the single-observer slot is per-instance state on a class nothing forces to be a singleton; two injected observers = two platform registrations"), and the answer chosen was an invariant on the composition root rather than a check. That root is `di/OmniBudsBluetooth.kt`, whose KDoc asserts "One instance per process" (`:34-38`) in prose and deliberately does not cache; no code counts live instances, and `TEST-P2-029` records that no test constructs the root at all (`test-plan.md:254`). From the first UI plus one notification onward, two consumers contend for one slot and the second receives `RESOURCE_UNAVAILABLE` (`AdapterStateObserver.kt:64-75`) — the refusal ADR-P2-007 chose over reference counting on the grounds that the two-consumer case is a Phase 26 concern.
**Mitigation.** The contention answer is typed, structured and loud (`RESOURCE_UNAVAILABLE` with a detail string) instead of a silent second registration; `isObserving` (`AdapterStateObserver.kt:43-44`) exposes the slot for diagnostics; the refusal is proved through the real platform wiring, not only through the core class (`AndroidBluetoothPlatformTest`, five methods, `test-plan.md:146`); teardown releases the slot in a `finally` even when the registration is never collected (`:148-163`, known issue 10 at `validation.md:167`).
**Detection.** Any construction site of `omniBudsBluetoothPlatform` other than the application's root; the first feature needing two live observations (`TEST-P2-029` stays open until then); a device session that attempts a second concurrent observation from a real UI (`test-plan.md:276`).
**Fallback.** Move the guard onto `AdapterStateSource`, which is the real per-process object, or introduce reference counting — both are ADR-P2-007's own rejected alternatives and must return under an ADR with the leak test rewritten, not widened.
**Owner.** Bluetooth Agent / Core Agent.

### RISK-032 — The permission matrix is a frozen table whose band edges were inferred
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** The id `test-plan.md:168, 260` cite. `FrozenPermissionRequirementResolver.planFor` branches on `targetSdk` and never on `deviceSdk` (`PermissionRequirementResolver.kt:59-224`, `specs.md:295`; ADR-P2-009), which makes four boundaries load-bearing and all four `INFERRED`: the 30/31 split, the `neverForLocation` interaction (`:245, :285`), the device-level enforcement caveats, and the asymmetry ADR-P2-009 records as Note A — where the compatibility guide states a requirement the per-method reference omits, the guide wins. `TEST-P2-035` shows the edges are not merely unproven but unexercised: `planFor` is run at `targetSdk` 30 and 35 only, never at 26, 31 or 34, and `BluetoothPermission.introducedAtSdk` is asserted by **no test at all** while `:core` carries `18` for `BLUETOOTH`/`BLUETOOTH_ADMIN` (`BluetoothPermission.kt:30-31`) against the documented `API 1` (`bluetooth-api-research.md:64-65`). That mismatch is a realised instance, not a hypothetical. The matrix also has a declared ceiling: `ApiRange.MIN_MATRIX_SDK = 26` and `MAX_MATRIX_SDK = 35` (`BluetoothPermission.kt:61-62`) because compileSdk 35 is what was examined (`validation.md:165`), so Android 16 / API 36 lies outside the matrix entirely — which is at least a loud failure, since an `ApiRange` starting above the ceiling throws at construction (`:44-46`) rather than answering quietly.
**Mitigation.** `theLegacyBandIsJudgedFromTheTargetSdkNotThePhone` pins the asymmetry that actually matters by asserting `(30, 35)` GRANTED against `(35, 30)` NOT_REQUIRED; `anUnknownTargetSdkIsNotSilentlyTreatedAsRequiringNothing` returns `Failure(INVALID_STATE)` instead of the safer-looking band, on ADR-P2-009's reasoning that a permission asked for on a guess cannot be explained to the user; every row carries its own reason string traceable to a `[C-]` citation (`bluetooth-api-research.md` §4, §8); the research leaves what it could not settle labelled U-1 … U-9 (§6) instead of absorbing it into the table; ADR-P2-009 corrects Phase 0's `SEC-PERM-002` in the open rather than editing history.
**Detection.** `TEST-P2-035` is the T1 test that does not exist yet and needs no device; `TEST-P2-024` and `TEST-P2-025` are the device-side ones; the day `compileSdk` moves to 36, which must re-verify the matrix per SEC-PERM-003 before `MAX_MATRIX_SDK` changes and would otherwise be an out-of-range request.
**Fallback.** Answer `UNKNOWN` for any band not re-verified, and let a row move from `INFERRED` only with a citation or an observation attached — never by relaxing the matrix to fit a demo.
**Owner.** Bluetooth Agent / Security Agent.

### RISK-033 — The band decision reads an input no artifact in this repository supplies
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** The id `test-plan.md:252, 273` cite. ADR-P2-009 makes `targetSdkVersion` the value that selects which permission model applies, and `SystemTargetSdkProvider` reads it from `context.applicationInfo.targetSdkVersion` (`AndroidPlatformCapabilityProvider.kt:36`) — but `:platform:android` is a library module, which declares no `targetSdk`, so at runtime the answer belongs to the *hosting application*, and no such application exists. The only installable module is `:tools:companion-shell`, and `TEST-P2-027` forbids using it to answer this question precisely "because it is not the product" (`test-plan.md:252`); its own `targetSdk = shellTargetSdk` (`tools/companion-shell/build.gradle.kts:30`) is a harness value with no bearing on the model. So today the resolver's real input is `null`, `anUnknownTargetSdkProducesNoPlanRatherThanAGuessedBand` (`PhaseTwoScopeTest.kt:89`) is the branch that would actually be taken on a device, and the `(30, …)` / `(35, …)` values inside the tests are values the tests supply, not values a phone supplied.
**Mitigation.** The read is wrapped in `runCatching` and yields `null` rather than a plausible default (`AndroidPlatformCapabilityProvider.kt:36`); an unknown `targetSdk` produces `UNKNOWN`/`Failure(INVALID_STATE)` and never "requires nothing" (ADR-P2-009, `test-plan.md:140`, `anUnknownTargetSdkIsNotSilentlyReadAsNoRequirement`); `AndroidAdapterStateSource`'s report refuses to complete when the presence question cannot be answered, so a missing input degrades to a structured failure rather than a guess; device-session step 1 (`test-plan.md:273`) requires recording the *installed application's* own `targetSdkVersion` before any other measurement is trusted.
**Detection.** `TEST-P2-027`, owned by "the phase that ships an app module" — Phase 3 if the user authorises a device-hosting module (`validation.md:175`), otherwise Phase 49. The symptom of the risk arriving is a band chosen from a harness value and read as a product fact.
**Fallback.** Have the application module pass the band in explicitly so the library never infers it, and record which artifact owns the value — audit finding R-9 (`architecture-audit.md:330`) is the warning against a second copy of the same fact living in `libs.versions.toml`.
**Owner.** Bluetooth Agent / Orchestrator.

### RISK-034 — The manifest check can only ever refuse more declarations, never require one
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** The id `test-plan.md:96, 222` cite. `platformManifestDeclaresNothingUnjustified` (`DependencyDirectionTest.kt:438`) parses `platform/android/src/main/AndroidManifest.xml`, rejects any `<uses-permission>` name outside the empty Phase 2 set (`:443`) and any `<receiver`, `<service`, `<activity` or `<provider` tag (`:444-445`). That is a one-directional guard: it proves nothing forbidden is present and says nothing about anything that must be. ADR-P2-011 keeps the manifest empty, and the file on disk is a single `<manifest … />` element (`AndroidManifest.xml:11`) with a comment explaining the omission. Research Q7 (`bluetooth-api-research.md:383-414`) justifies zero declarations line by line for every authorised Phase 2 operation, so the choice is correct for this phase — the exposure is the next one. When a later phase calls an API that needs `BLUETOOTH_CONNECT` and forgets to declare it, Android does not raise a "missing permission" build error: it answers falsy or empty, or the `runCatching` in `SystemPermissionStandingReader` returns `null` (`PermissionStandingReader.kt:29-31`), and the app sees `UNKNOWN` or an empty set. Research Q5 and Q6 R-5 are the general form — `startDiscovery()` → `false`, `getBondedDevices()` → empty set, `STATE_DISCONNECTED` for two different truths — so a missing declaration looks like a platform answer.
**Mitigation.** The check fails when the manifest file is absent (`DependencyDirectionTest.kt:440`), so it cannot go vacuous by losing its target; `PhaseTwoScopeTest.everyAuthorisedOperationHasAPlanAndNoneOfThemPromptsTheUser` (`:56`) is what makes zero declarations safe *for the authorised set*, and `nothingThatTouchesADeviceIsAuthorizedInPhaseTwo` (`:42`) keeps that set from growing silently; ADR-P2-012 forbids resolving a falsy answer to "off"; each later phase re-verifies before acting (SEC-PERM-003), and ADR-P2-011 states the reason plainly — a library's manifest merges into every consumer APK, so over-declaration propagates silently, which is the same class of error as a fabricated capability.
**Detection.** This check will not detect it. Detection is a device session observing what `checkSelfPermission` answers for an undeclared dangerous permission (step 6, `test-plan.md:278`, closing `TEST-P2-024`), or `TEST-P2-030` — whether a real unauthorised call throws, returns `false`, or returns an empty-shaped answer (research U-8).
**Fallback.** When permissions arrive, pair the negative guard with a positive requirement check — every operation whose matrix row is non-empty must have its permission declared in the manifest of the module that ships — recorded as an ADR so the guard gains its other direction deliberately.
**Owner.** Security Agent / Bluetooth Agent.

### RISK-035 — Nothing in this phase has ever executed on Android, and no headset has been touched
**Probability.** high · **Impact.** high · **Exposure.** high
**Description.** This is the phase's central exposure, and the register's other entries are consequences of it rather than independent findings. Every Android fact Phase 2 encodes was transcribed from documentation and never run: `adapter?.state` behind `BluetoothManager.getAdapter()` (`SystemBluetoothAdapterHandle.kt:35, 47`), `ACTION_STATE_CHANGED` (`:51, :83`), `packageManager.hasSystemFeature` (`PlatformFeatureProbe.kt:27`), `context.checkSelfPermission` (`PermissionStandingReader.kt:30`), `context.applicationInfo.targetSdkVersion` (`AndroidPlatformCapabilityProvider.kt:36`), `Build.VERSION.SDK_INT` (`ApiLevelProvider.kt:22`). The four `System*` classes named at `validation.md:159` — plus `SystemApiLevelProvider` (`ApiLevelProvider.kt:21`) and `SystemTimeProvider` (`SystemTimeProvider.kt:14`), which `test-plan.md:236` also lists as never executed — have zero automated tests, and correctly so: on a JVM the stub `android.jar` throws "not mocked", so a mock there would prove only that the mock works. `test-plan.md:37` states the environment as machine-checked fact — no framework method body executed in any test, and `:platform:android` declares no `isReturnDefaultValues`, no Robolectric, no `androidx.test`, and no `src/androidTest` source set exists in any module. The executed totals are 356 `:core` and 45 `:platform:android` JVM tests, 0 failures / 0 errors / 0 skipped (`validation.md:30-32`), and every one of them interrogates a seam this phase wrote. The reason the gap could not be closed by better effort is structural and stated twice: the platform module is a library with no host, and the only installable module is deliberately unable to import it (`validation.md:158`, `validation.md:54`, ADR-P2-010).
**Mitigation.** The ceiling is declared before any claim is made — all Phase 2 evidence is T1, so `IMPLEMENTED` at most, and nothing here justifies `LAB_TESTED`, `HARDWARE_VERIFIED` or `PERSISTENCE_VERIFIED` (TST-MOCK-001, `test-plan.md:41-46`); each unmet obligation carries a permanent gap id, `TEST-P2-023` … `TEST-P2-040`, so it cannot be quietly forgotten (`test-plan.md:242-265`); `test-plan.md:269-284` is an ordered device-session script naming the exact facts to record, gated by `docs/security/device-access-policy.md`; `validation.md:118` leaves the physical-verification row of the definition of done explicitly unchecked rather than rewording it.
**Detection.** The Phase 3 device session, and `adb devices -l` — which returned no device at close (`validation.md:39`). Until that session runs, detection of this risk is a promise about a future execution, and the honest statement is that no check in this repository can currently detect a wrong transcription of Android's behaviour.
**Fallback.** `UNKNOWN`. The design was built so that a device answer contradicting the transcription is absorbable rather than destructive: `hardwareEvidence` is already `INFERRED` and `isUsable` already false for every platform feature (ADR-P2-008, ADR-P2-017), so the correction lands in a matrix row or a mapping table, not in a capability claim that was shown to a user. If the contradiction cannot be absorbed, the affected feature is reported unavailable with the observed platform answer attached.
**Owner.** Bluetooth Agent / Testing Agent, with the device authorisation owned by the user (`validation.md:17`, `validation.md:194`).

### RISK-036 — The event channel conflates adapter states by design
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** `AndroidAdapterStateSource.kt:72` opens `Channel<BluetoothAdapterState>(Channel.CONFLATED)`, and `:65-68` gives the reason: latest-wins, with buffering rejected because it would let a slow collector act on states the phone left behind and would suspend the broadcast thread when full. `validation.md:162` known issue 5 records the cost — correct for a latest-wins reading, wrong for a phase that must see every transition, and "that phase must decide it as an ADR rather than flip a constant". Two interactions make the loss concrete rather than theoretical: the observer already drops consecutive duplicates (`AdapterStateObserver.kt:120-121`), so a fast ON → TURNING_OFF → OFF that the conflated channel coalesces to a single delivered value cannot be recovered; and research U-6 leaves whether `ACTION_STATE_CHANGED` is delivered stickily unverified, so even "how many events arrive" is an open question deferred to device-session step 3 (`test-plan.md:275`).
**Mitigation.** The choice is documented at the channel, in the phase record, and in the ADR rather than left implicit; ADR-P2-007 keeps the A-B-A preservation rule explicit and tested (`anOffOnOffSequenceIsPreservedRatherThanCollapsedToTheLastValue`), so "suppressed duplicate" and "lost transition" remain different, nameable things; `openStateChanges()` hands back the `PlatformRegistration` so a consumer can prove a registration exists even when it never collects (`AdapterStateSource.kt:28-32`).
**Detection.** A phase that needs to count transitions — reconnect timing, background behaviour (Phase 28), or anything that must distinguish OFF from TURNING_OFF→OFF — will find it the first time a test expects three elements and receives one. That is a design conversation, not a bug to file.
**Fallback.** A buffered or `UNLIMITED` channel, or a per-transition sequence number, decided in an ADR with the buffering cost the source's KDoc names; never by editing `Channel.CONFLATED` in place (`validation.md:162`).
**Owner.** Bluetooth Agent.

### RISK-037 — `hardwareEvidence` stays INFERRED forever unless something tests it
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** ADR-P2-008 and ADR-P2-017 cap `hardwareEvidence` at `INFERRED` for every `PlatformFeature` without exception, because no radio was opened and no lab procedure ran. `nothingIsClaimedUsableBecauseNoRadioWasOpened` asserts `hardwareEvidence == INFERRED`, `isUsable == false` and a non-null `blockingReason` for every feature, and `test-plan.md:144` calls it "this phase's honesty made executable". The risk is not that Phase 2 overclaims; it is the pressure applied to the next phase. A demo-oriented phase needs a green capability table, and the cheapest available route is one constant in `AndroidPlatformCapabilityProvider` instead of the procedure `TST-GOV-004` requires — and because `isUsable` is false everywhere today, the diff that flips it will look like a small fix rather than a capability claim. `validation.md:180` defers raising the level to "whichever phase runs the test", and research U-1 … U-9 record the questions that only a device can answer.
**Mitigation.** The cap is enforced by an assertion over the whole enum, so an unearned raise fails the build rather than passing review; the three facts stay three fields (`apiAvailability`, `hardwareEvidence`, `permissionState`) with `isUsable` requiring all of them and `blockingReason` naming which one refused, so raising one cannot silently raise the others (ADR-P2-008); a feature flag populates API availability *only* and a throwing probe yields `UNKNOWN` rather than absence (ADR-P2-017); `candidateTransports` can never gain `LE_AUDIO` by inference, and the host-side list is explicitly not headset evidence (`validation.md:166`, `test-plan.md:144`).
**Detection.** A diff touching `hardwareEvidence` in a phase whose `validation.md` records no procedure with a device identity attached; the Phase 31 cross-device and Phase 32 cross-phone matrices, which are the sanctioned route; code review for any `isUsable` that became true without a named test.
**Fallback.** Keep `INFERRED` and say so: ADR-P2-008 makes "not usable because we were not permitted to look" expressible and distinct from "unsupported by this phone", which is the fallback the whole ladder assumes.
**Owner.** Testing Agent / Protocol Research Agent.

### RISK-040 — The Kotlin Gradle plugin is loaded in more than one subproject and Gradle says it may break the build
**Probability.** medium · **Impact.** low · **Exposure.** medium
**Description.** `validation.md:163`, known issue 6: `:core` applies `kotlin.jvm` (`core/build.gradle.kts:4`) while `:platform:android` and `:tools:companion-shell` both apply `kotlin.android` (`platform/android/build.gradle.kts:5`, `tools/companion-shell/build.gradle.kts:5`), with no root declaration, and Gradle warns that this "may break the build". It is pre-existing since Phase 1 and was deliberately not fixed, because the remedy — a root `build.gradle.kts` declaring each plugin `apply false` — is a build-topology change outside Phase 2's authorised scope, and `validation.md:181` assigns it to a Phase 3 build task. It reproduces in every Gradle run of this repository. The risk therefore is not the warning itself but habituation: an advisory that is always present stops being evidence, and the first run in which it *means* something will be read as the usual noise. It is also the only known warning-level defect standing between this phase's zero-warning discipline and a clean build.
**Mitigation.** One catalog version supplies the plugin in all three modules (`gradle/libs.versions.toml:9`, kotlin 2.0.21), so the plugin classes are identical; `allWarningsAsErrors = true` holds a zero-warning compile for every source set including tests (`validation.md:33`), so genuine compiler warnings cannot hide behind the Gradle one; the warning is recorded as a numbered known issue with an owning phase instead of being suppressed or repeated as accepted behaviour.
**Detection.** A Gradle or AGP upgrade converting the advisory into an error; `./gradlew --offline build` output on any task graph that loads both plugin families.
**Fallback.** Add the root `build.gradle.kts` declaring each plugin `apply false` — a one-file change deferred deliberately, and it must be made as a build task with a full `--rerun-tasks` verification run attached, not as a drive-by edit.
**Owner.** Orchestrator / Build owner.

### RISK-041 — The absent-adapter path has only ever been a scripted answer
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** The id `test-plan.md:179` cite, against `anAbsentAdapterIsReportedAsUnavailable`, `anUnavailableSourceReportsUnavailableAndNotEnabled` and `anAbsentAdapterIsUnavailableWhateverItsLastReadingWas`, whose hardware column reads "a phone with no adapter" and whose gap is `TEST-P2-023`. All three pass; all three reach their conclusion through a `BluetoothAdapterHandle` that a test instructs to answer, so what is proved is the source's decision, not the platform's absence. The residual shape comes from audit finding R-6 (`architecture-audit.md:327`): `AdapterStateSource.unavailable()` (`AdapterStateSource.kt:33-36`, backed by the private object at `:47-65`) was corrected to answer `Failure(ADAPTER_UNAVAILABLE)` with the detail "no adapter state source was available" instead of reporting the `UNAVAILABLE` *state* for a wiring fact (`design.md:143`, `specs.md:494`) — but a wiring failure and a hardware absence still share one category, so only a detail string separates "nothing was plumbed" from "this radio does not exist". `BluetoothManager.getAdapter()` returning null on radio-less hardware is asserted in the handle's own KDoc (`SystemBluetoothAdapterHandle.kt:19-20`) and has never been observed.
**Mitigation.** `anAbsentAdapterIsUnavailableWhateverItsLastReadingWas` forbids the last-reading shortcut, so a cached `ENABLED` cannot outlive an absent adapter; `aMissingReadingIsUnknownNotOff` and `anUnreadableValueIsUnknownRatherThanDisabled` keep a null away from a defaulted `ENABLED`/`DISABLED`; `specs.md:494` records that the `unavailable()` default is constructed by tests only, which is the honest scope of the claim; `PhaseTwoScopeTest.nothingThatTouchesADeviceIsAuthorizedInPhaseTwo` (`:42`) means no Phase 2 path can *act* on a wrong answer about absence; ADR-P2-012 forbids resolving a falsy platform answer to a hardware conclusion.
**Detection.** `TEST-P2-030` — whether a real failing adapter call throws `SecurityException`, returns `false`, or returns an empty/`STATE_DISCONNECTED`-shaped answer (research U-8, Q6 R-5), and therefore whether `PLATFORM_EXCEPTION` is even the category a real phone produces; a device with Bluetooth permanently off, or an emulator with no adapter; any consumer that begins branching on `ADAPTER_UNAVAILABLE` without reading `detail`.
**Fallback.** Report `ADAPTER_UNAVAILABLE` with the observed reason and never a defaulted state; if a Phase 3 consumer must distinguish "not wired" from "no radio", give the wiring case its own category under an ADR rather than overloading the detail string, since ADR-P2-004 already refused `ADAPTER_STATE_UNKNOWN` precisely to stop one fact having two representations.
**Owner.** Bluetooth Agent / Testing Agent.

### RISK-043 — The diagnostics sink that redaction is defined against does not exist
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** `OmniBudsLogger.kt:30-32` states the contract: "Redaction is the sink's job at the point of emission, not on export (`SEC-LOG-002`). [DiagnosticEvent.message] arrives as pre-redaction text; a sink that writes it out verbatim is where an identifier leak actually happens." No sink exists — the only implementation of `OmniBudsLogger` in the repository is `RecordingLogger` in `OmniBudsLoggerTest.kt:63` — and `architecture-audit.md:296` (known-issue interaction 5) judged leaving it silent as *not* safe, because SEC-LOG-002's redaction duty has no owner until Phase 36 while Phase 2 is the first phase with a real reason to emit logs. Phase 2 already produces detail strings: `AdapterStateObserver.kt:159` writes `"adapter-state registration teardown reported ${cause::class.simpleName}"`, and the audit's own reading of the in-flight strings is the honest one — "that is luck about a code path, not a rule". The next phase that wants visibility will add the obvious `Log.i(tag, message)` line, and nothing in the build prevents it: `MessageDigest`/`Log` are not in any forbidden token list, and the architecture rules scope to imports of Android UI and Bluetooth-traffic types only.
**Mitigation.** The rule is stated in the type's own KDoc at the point an implementer reads it, together with the packet-level gating (`SEC-LOG-004`, `SEC-LOG-005`) and no-silent-exfiltration rules (`SEC-LOG-008`, `SEC-PRIV-001`); ADR-P2-015 keeps framework type names out of `:core` string literals, which removes one route by which a diagnostic could become a platform-coupled identifier; `isEnabled` exists as a cost gate so a message is not built for a disabled level. There is no *mechanical* mitigation, and this entry does not pretend otherwise: the audit's own preferred option — ship no sink at all — is the current state and is what the phase chose.
**Detection.** The first commit adding a logging sink or any `android.util.Log` call in a product module; a device-identifier-bearing string appearing in a logcat capture or an exported diagnostics file; Phase 36 when the redaction rule set acquires an owner.
**Fallback.** Emit only `category` + `operationId` + severity, never `message` and never `OmniBudsError.detail`, exactly as `architecture-audit.md:296` ranks it; if a fuller sink is wanted, the redactor arrives in the same ADR, not in the one after it.
**Owner.** Security Agent / Diagnostics owner (Phase 36).

Phase 2 **raises** (gives a previously theoretical risk its first real exposure):

- **RISK-001** — Android OEM Bluetooth differences (`phase-0/risk-register.md:9-15`). - **RISK-017** — architecture rules enforced by source scanning (`phase-1/risk-register.md:17-23`). Not resolved; extended to six new rules, and its "zero production dependencies" mitigation was discharged by ADR-P2-003, which `architecture-audit.md:260` said would need re-scoring. - **RISK-018** — contracts ossify before hardware evidence exists (`phase-1/risk-register.md:25-32`). Sharpened: Phase 2 froze a permission matrix and an adapter-state mapping onto shapes never exercised, and `TEST-P2-035` shows the band edges are unexercised even by tests that need no device. - **RISK-023** — documentation drifts behind code inside a single phase (`phase-1/risk-register.md:65-71`). Recurred, with four realised instances this time, and is now an id of its own: RISK-039.
