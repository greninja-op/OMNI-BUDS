# Phase 3 — Risk Register

**Numbering continues the single project-wide register and does not restart it.** Phase 0 wrote `RISK-001` … `RISK-015`, Phase 1 `RISK-016` … `RISK-025`, Phase 2 `RISK-026` … `RISK-043`, so **Phase 3 begins at `RISK-044`** and runs to `RISK-064` — twenty-one entries. Scale as in all three earlier registers: probability and impact are `low | medium | high`, exposure = probability × impact, and the word `severe` marks the high × high band Phase 0 introduced (three entries here sit in it: RISK-044, RISK-045, RISK-048). Field shape is Phase 2's: id + title, then probability/impact/exposure, description, mitigation, detection, fallback, owner, and status where the entry's own text qualifies it.

**Pre-cited ids were checked before allocation, and every citation is honoured — and the check had to be run a second time, which is the honest version of this paragraph.** When this register was first drafted it could report that a `grep` over `docs/phases/phase-3/*.md` returned exactly five `RISK-0…` citations, all in `architecture-audit.md:97-101`, and that all five named Phase 2's existing entries rather than claiming new numbers: `RISK-035` (nothing has executed on Android), `RISK-031` (single-slot uniqueness), `RISK-038` (the unwritten `bluetooth-governance.md`), `RISK-039` (records asserting what the tree no longer does) and `RISK-041` (the absent-adapter path is a scripted answer). None was re-allocated here, because giving an already-cited id a second meaning is the failure `docs/phases/phase-2/risk-register.md:5` exists to avoid; each is **re-scored in the final section under its own number**, which is what the audit's line 99 asked for without inventing a duplicate. That "exactly five" sentence was true only while the phase's other records were unwritten, and it has been replaced rather than left standing: the finished set now cites **34 distinct earlier-phase ids** across `requirements.md`, `design.md`, `specs.md`, `task-list.md`, `test-plan.md`, `decisions.md`, `architecture-audit.md` and `connection-observation-research.md`, and all 34 were re-verified against the Phase 0/1/2 registers — **none is unallocated, and none is re-used as a Phase 3 number.** The reconciliation ran in the other direction too: `RISK-044` … `RISK-064` are each cited at least once outside this file, no id above `RISK-064` appears anywhere in `docs/`, and the one time a record cited a number this register had not minted (`RISK-065`, in a draft of `validation.md`) it was corrected here rather than the register being stretched to fit it.

**The phase's central exposure is stated once, in RISK-044, and no other entry closes it.** Then RISK-045 states the sharper half: that exposure is no longer gated by anything. Every mitigation below is a design mitigation — a type, an ordering, a table, a token list, an assertion about our own code. None of them is evidence that a handset behaves as the transcription claims, and ADR-P3-014 has moved the session that would produce such evidence to the end of the project.

### RISK-044 — The framework half of this phase has never executed, and every device claim in it is a transcription
**Probability.** high · **Impact.** high · **Exposure.** severe
**Status.** open, and now open-ended by user directive (ADR-P3-014).
**Description.** Phase 3 was the phase that was going to close this: `docs/phases/phase-3/architecture-audit.md:97` records RISK-035 as "OPEN, and **Phase 3 is the phase that closes it**", because the user had chosen instrumented verification (ADR-P3-007). The scaffolding was built, the suite was written and compiled, and the run was then deferred indefinitely. The result is a phase whose Android half is, in evidence terms, exactly what Phase 2's was and now has **1,372 lines of framework-facing code** sitting behind it (`bluetooth/connection/`, three files, measured at close-out): `SystemConnectedDeviceHandle.kt` — `getSystemService` (`:61`), `manager.adapter` (`:62`), `getProfileProxy` (`:217`), `closeProfileProxy` (`:252`, `:281`), the `ServiceListener` bridge (`:329-354`), `AnnouncementReceiver.onReceive` reading `EXTRA_DEVICE`/`EXTRA_STATE`/`EXTRA_BOND_STATE` (`:361-391`), the exported registration (`:409-416`), the eight-action filter (`:520-554`), and the per-field `deviceReportOf` reads of `address`/`name`/`bondState` (`:487-498`) — is constructed by **no executed test**. So is `SystemBluetoothAdapterHandle` after Phase 3 edited it (RISK-063). Twelve instrumented cases exist for all of it — four smoke and eight connection — and none has run (`docs/phases/phase-3/test-plan.md` §3.19); `adb devices -l` printed an empty list in the research session (`connection-observation-research.md:79-86`), and ADR-P3-014 makes that the standing condition rather than a temporary one. Every framework fact Phase 3 encodes came from the compileSdk 35 stubs and the `android-15.0.0_r11` reference source — good evidence, and evidence of *documents*: research §0.1 caps `[SDK]` at existence and `[AOSP-35]` at "one implementation of one release; OEMs fork it".
**Mitigation.** The engine lives in `:core` behind `ConnectedDeviceSource`/`ConnectedDeviceHandle` so the 122 executed Phase 3 methods (77 in `:core`, 45 in the boundary module per variant) test decisions, not framework calls (`ConnectedDeviceSource.kt:72-89` states that as the interface's purpose); the ceiling is declared before any claim — all executed evidence is T1, therefore `IMPLEMENTED` at most, and `TEST-P3-019` earns **no level at all** (TST-MOCK-001, TST-REC-005); every unmet obligation carries a permanent gap id, `TEST-P3-021` … `TEST-P3-040`, so it cannot be quietly forgotten; `docs/security/device-access-policy.md:88-102` writes the run boundary before the run, and §9 of this phase's test plan is an ordered script naming the exact facts to record; the `androidTest` source set is compiled in the build gate, which is the difference between a plan and a paragraph and nothing more.
**Detection.** The deferred device session, and `adb devices -l`. Stated plainly, because the honest form of this line is uncomfortable: **no check in this repository can currently detect a wrong transcription of Android's behaviour**, and Phase 3 is the third consecutive phase for which that sentence is true.
**Fallback.** `UNKNOWN`, and the design was built so a contradicting handset answer is absorbable: the profile axis reports `NOT_ANSWERABLE`/`UNKNOWN` rather than absence (`ObservedProfile.kt:130-142`), a refusal carries no device list (`ObservationStage.kt:45-54`), and an untranscribable integer becomes `UNKNOWN` rather than a state (`AndroidConnectedDeviceSource.kt:290-305`). If the contradiction is not absorbable, the affected observation is reported unavailable with the platform's actual answer attached, and the phase that needs it re-decides under an ADR.
**Owner.** Bluetooth Agent / Testing Agent, with the device authorisation owned by the user.

### RISK-045 — Deferral has no owner, no expiry and no trigger, so an unverified claim can become permanently unverified without anyone deciding to abandon it
**Probability.** high · **Impact.** high · **Exposure.** severe
**Status.** open. This entry is a process risk, and it is deliberately separate from RISK-044: that one is a state of the evidence, this one is that nothing any longer forces the state to change.
**Description.** ADR-P3-014 removed device verification from every phase's completion criteria "for the whole of that stretch", which was the user's decision and is the right one for the project's shape: the application gets built first. But the mechanism that made RISK-044 survivable in Phases 1–2 was that the *next* phase was supposed to close it — `architecture-audit.md:97` named Phase 3, and Phase 3 built the route and did not walk it. With the session parked at the end of a 50-plus-phase project, three things are now unscheduled: nobody owns the deferred list, nothing re-checks that it is still valid, and no phase boundary refuses to proceed while it is open. The ADR's own "Consequences" name the sharp edge exactly — "**deferral is only honest if the unverified stays visibly unverified**… A deferred device run is the exact case where 'we did not look' must not quietly become 'it works'" — and that honesty is a maintenance obligation on this register and on `test-plan.md` §8/§9, not a property of the decision. Two concrete decay paths are already visible: the instrumented suite's five coordinates were resolved online once (ADR-P3-007), so a clean machine now needs a resolve before `--offline` works again, and a suite that has not compiled in a future tree will fail at the worst possible moment — at the end of the project, with 40 phases of drift to unpick, rather than at a phase boundary where it is one commit's problem.
**Mitigation.** The deferral is an ADR with a status line, not a mood: ADR-P3-014 is indexed in `docs/decisions/README.md`, so a change to a completion criterion is recorded where a change to a completion criterion belongs. Every deferred claim carries an id in `test-plan.md` §8 and §9, which converts the end-of-project session from archaeology into a list. This register re-scores RISK-035 and RISK-041 rather than replacing them, so the pre-ADR-P3-014 framing is still on the record. The scaffolding is kept "unrun and inert" by user choice and cannot enter a release artifact, which is the fact that makes the deferral cheap enough to be stable. And nothing in this phase blocks on it: the user's rule is that device testing never becomes a blocker, and this entry does not propose making it one.
**Detection.** A phase record or UI string asserting something about a handset that has no `TEST-P3-0NN`-or-later deferred id behind it; `compileDebugAndroidTestKotlin` failing in a tree where nobody was compiling it; the deferred list being shorter than it was without an ADR saying which item was dropped and why; the first `HARDWARE_VERIFIED` claim made without an attached device identity (TST-HW-003, TST-FAIL-001 row 4).
**Fallback.** Keep the claims where they are — `UNKNOWN`, deferred, named — and let the session that runs them be scheduled by the user, not by this register. If the session is ultimately abandoned, that is a decision requiring an ADR that retracts the claims, not a silence that keeps them.
**Owner.** Orchestrator.

### RISK-046 — On a fresh install every device round refuses, and nothing in this repository can ever change that
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** Phase 3 declares `android.permission.BLUETOOTH_CONNECT` (`AndroidManifest.xml:39`) and never asks for it — correctly, because prompt §13 forbids a background component prompting, `DependencyDirectionTest.kt:336` fails the build over `requestPermissions`/`requestPermission`, and both instrumented files state the rule in their headers. ADR-P3-009 then makes standing load-bearing, and `refusalFor` clears only a grant (`AndroidConnectedDeviceSource.kt:257-267`, `isClearedFor` at `:269-279`): `NOT_REQUESTED`, `UNKNOWN` and `DENIED` all refuse. On a target-31+ install where the user has not yet granted the permission, `checkSelfPermission` says not-granted, the process-local ledger says nothing was asked (`PermissionRequestLedger.kt:9-17`, deliberately unpersisted), so the standing is `NOT_REQUESTED` and **all three entry points refuse**. The first thing the whole device layer does on a real phone is therefore report `PERMISSION_DENIED` three ways, and the only paths out are a UI this phase is forbidden to build (Phase 49) or a user opening Android's Settings app unprompted. Phase 2's RISK-030 predicted the shape of this ("the user-facing consequence lands later") and Phase 3 is where it lands.
**Mitigation.** The refusal is a typed, category-carrying fact rather than an empty list — which is the entire point of ADR-P3-009, and the alternative this phase refused is worse: "the app would say 'no devices connected' to a user whose permission was refused". The `detail` string states what was *not* done ("no device enumeration and no receiver registration was attempted; a refusal is not a report of no connected devices", `:263-265`), so the reason a Phase 49 UI needs already exists in the error rather than in a comment. `AndroidPermissionStateProviderTest.noInputProducesAnUnsupportedClaim` still guarantees the platform layer never manufactures `DENIED_PERMANENTLY` or `REQUIRES_USER_ACTION`, so a refusal cannot be rendered as "you can never use this" — a claim Phase 2 proved nothing here can establish.
**Detection.** The first UI: a screen that shows "no devices" where the round was refused, or a prompt loop repeating across a process restart because the ledger is empty again. `TEST-P3-021`'s first two instrumented cases are the closest thing to a machine check and they script the refusal rather than resolving it.
**Fallback.** Surface `PERMISSION_DENIED` with the resolver's own reason string and nothing else; never re-derive a UI-facing state from an empty list. The prompt flow belongs to the phase that owns a screen, and this register should say whose it is rather than let it be discovered: **Phase 49**.
**Owner.** Security Agent / UI owner (Phase 49).

### RISK-047 — A permission revoked mid-observation is invisible to the engine, and the projection keeps claiming connections
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** Prompt §13 lists "Permission revoked" as a case to handle and prompt §19 lists it as a test to write; **no test exists** (`TEST-P3-024`), and the honest reason is that the case may not be observable as anything but a process death — Phase 2's research Q5 found the platform's model is `revokeSelfPermissionsOnKill` killing every process in the UID, ADR-P2-012 recorded that no in-process signal establishes permanent denial, and no file in `core/src/main` or `platform/android/src/main` mentions revocation at all. What Phase 3 *does* add is a new way to be wrong about it: standing is settled **once per entry point** (`profileSupport`/`snapshot`/`openConnectionEvents` each call `refusalFor` at their own start), an announcement stream is never re-authorised, and `aRoundThatDidNotAnswerLeavesTheLastProjectionIntact` proves that a refusal deliberately leaves the previous projection standing. Compose those two facts: if standing disappears while an observation is live, the announcements stop, no round fails, and `connectedDevices` keeps reporting the user's earbuds as connected for the lifetime of a projection that is no longer entitled to say so — with no `refresh()` caller to notice (`TEST-P3-025`) and no timer permitted to poll (prompt §8).
**Mitigation.** The projection's connectedness is a *report*, not an assertion: `isReportedConnected` requires `availability.isObservable() && link.isConnected()` (`DeviceObservation.kt:80-82`), so a later phase that marks records unobservable invalidates them without inventing a disconnect, and `anAdapterGoingQuietMarksDevicesUnobservableAndNeverPoweredOff` proves that machinery exists for the adapter path. Refusals are structured with `PERMISSION_DENIED` and a `RETRY_AFTER_REREAD`-class category rather than swallowed, so a re-read after a standing change *is* the designed remedy — ADR-P3-009's "a broadcast stream that produces nothing while standing is granted is a different finding and is reported as one". `ObservationStage` stays separate from failure causes (ADR-P3-005), which is what stops a revoked observation being rendered as a normal shutdown.
**Detection.** Only the deferred manual step 8 of Phase 2's script, restated as `TEST-P3-024`: revoke a permission from Settings with an observation running and record **what the app actually experiences** — callback, silence, or process death — and classify it honestly, which if the process dies means writing "the process died", never "handled gracefully". A second signal: any consumer that reads `connectedDevices` without ever reading the outcome that produced it.
**Fallback.** If revocation is observable as silence rather than as death, the engine needs a standing re-check per round with an owner for it, which is `refresh()` gaining a caller. If it is observable only as process death, that is the answer and it should be written down once with the phone's name attached, and `PERMISSION_DENIED` stays the only revocation-shaped category this project produces — ADR-P3-006 refused `PERMISSION_REVOKED` precisely because a category with no producer is a fiction.
**Owner.** Bluetooth Agent / Security Agent, with the observation owned by the deferred device session.

### RISK-048 — Permission denial is structurally invisible to the platform's own answers, so the whole defence is an ordering rule with one implementation
**Probability.** high · **Impact.** high · **Exposure.** severe
**Description.** This is the research's bluntest finding and the phase's central hazard, in the research's own words (§12 item 3): "On every enumeration path, permission-denied, adapter-off, service-null and non-active-user all return the same empty/`STATE_DISCONNECTED` value… This is Phase 2 R-5 generalised." The platform's own shipped Javadoc says the enumeration "will be empty on error"; `getProfileConnectionState` answers `STATE_DISCONNECTED`; the only `SecurityException` in the entire surface is the legacy `targetSdk < 31` branch of `getProfileProxy`, so the catch-everyone-reaches-for does not fire (ADR-P3-009). Phase 3 adds the receiver-side version, which the boundary manifest comment states in the phase's own words (`AndroidManifest.xml:12-19`): the stack sends these announcements **with `BLUETOOTH_CONNECT` as the receiver permission**, so "an ungranted app is not told it was refused, it simply hears nothing". Silence and emptiness are therefore the platform's *only* vocabulary for two very different truths, and the sole defence is a rule about call order inside one class.
**Mitigation.** Ordering is the mechanism, and the type makes ordering the only option: `ConnectedDeviceSource.snapshot()` returns `ObservationRound`, "which has no representation for a list from a round that was not allowed to produce one" (`ConnectedDeviceSource.kt:79-89`). `refusalFor` precedes every framework question in all three entry points, and a standing read that *throws* is treated as a refusal rather than as an exception (`AndroidConnectedDeviceSource.kt:253-256` — "with the standing unknown, the ordering rule cannot be honoured, and the safe side of that ambiguity is not looking"). A declined profile is never enumerated (`:170`), so an empty union can only mean an answered census. The rule is checked where it is testable: `TEST-P3-015` asserts on the fake's **empty request logs**, and the record's own KDoc says why — "the only way to hold a line drawn in order of operations is to observe the calls that did not happen". `anEmptyListIsReportedOnlyAfterEveryProfileInTheUnionAnswered` pins the census condition.
**Detection.** `TEST-P3-021`'s first two instrumented cases run the ordering against the real object graph and would falsify it on a handset; `TEST-P3-030`/U-8 still ask whether a real unauthorised call throws, returns `false`, or returns empty-shaped silence. Inside `:core`, detection is review: nothing at the engine layer distinguishes an honest empty union from a source that enumerated while ungranted (RISK-049).
**Fallback.** `UNKNOWN`, always, and refuse the round rather than report zero — ADR-P3-009's own sentence: "refusing to look is honest where reporting zero is not". Where a handset shows the emptiness/permission collapse to be worse than the transcription, the fallback is to narrow the phase's claims to the announcement stream and report the enumeration axis as unavailable, which the model can already express per profile.
**Owner.** Security Agent / Bluetooth Agent.

### RISK-049 — The engine trusts its source, and no test can catch a source that lies or merely re-orders itself
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** ADR-P3-009's ordering rule is enforced *inside* `AndroidConnectedDeviceSource`, one level below the boundary the engine reasons about. `ConnectedDeviceObserver` decides whether an empty list is a census by reading the source's own `ProfileSupportReport` (`ConnectedDeviceObserver.kt:508-511`), and a source that answered `allProfilesAnswerable()` and then handed back an empty list after refusing would satisfy every assertion in `TEST-P3-011`. The engine cannot detect it, the fakes cannot model it (a fake that lies would be a test of the fake's willingness to lie), and the only check is `TEST-P3-015`, which lives in the same class as the rule. That is not a defect — the seam is the point — but it means the phase's central safety property has exactly one implementation and one self-inspection, and a second `ConnectedDeviceSource` (a desktop port, a test host, a vendor bridge) inherits no obligation from the compiler.
**Mitigation.** The interface contract states the obligation where an implementer will read it (`ConnectedDeviceSource.kt:79-114`: "A source may only return [an empty Success] after its standing check passed, and it must not substitute an empty list for a refusal it could not distinguish"), which is the same technique ADR-P2-015 used for the string-literal rule; the vocabulary makes the dishonest shape hard to write, since `ObservationRound.Success` is the only carrier for a list; the maintained union is asserted against the enum by `theUnionAskedOfThePlatformIsTheMaintainedListAndNotSomethingInventedHere`, so a source cannot quietly enumerate a smaller set than it claims to have asked about; and `ProfileSupportReport.unansweredWithin` takes the *caller's* list rather than reporting its own keys (`ObservedProfile.kt:161-169`), so a source cannot shrink the census by omission from the report.
**Detection.** A second `ConnectedDeviceSource` implementation appearing without `TEST-P3-015`'s call-log assertions being copied onto it; `TEST-P3-021`/`TEST-P3-022` on a handset, which are the only cases that would show the *real* platform being worse than the fake; the first test that would pass if the standing check were moved after the enumeration.
**Fallback.** Promote the rule from convention to contract: a `ProfileSupportReport` carrying the standing decision, or a source interface split into "settle" and "read", decided under an ADR — the audit's rule that a guard's shape is a decision, not an accident. Meanwhile accept the boundary as it is and say so: the engine's guarantee is conditional on its source, and RISK-048's mitigation is where the unconditional part lives.
**Owner.** Core Agent / Bluetooth Agent.

### RISK-050 — The maintained profile union silently omits every profile not in it
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** ADR-P3-008's consequence, in its own words: "every profile not in it is a class of connection Phase 3 will not see". There is no call that returns all connected devices, no `getSupportedProfiles` in the public API at all (`SystemConnectedDeviceHandle.kt:26-32`), and no callback a third-party app may reach, so the seven entries of `ObservedProfile` **are** the observability boundary — and a boundary drawn by a list produces no signal when it is the wrong shape. The documented exclusions are reasonable and cited (`ObservedProfile.kt:22-33`: deprecated HEALTH, which the reference implementation refuses outright; constants with no public proxy type; the GATT server role; the hidden profiles) but they are *this* phase's judgement, and two asymmetries already sit inside the list: **HID_DEVICE is enumerable and never announceable** because no public connection-state action exists for it in the compile SDK (`SystemConnectedDeviceHandle.kt:449-453`), so a keyboard's link can appear in a snapshot and never in a delta; and U-7 records that the reference implementation aggregates profile state for only fourteen profiles and omits CSIP and HAP_CLIENT from its filter, which would make those two entries permanently `STATE_DISCONNECTED` on an AOSP-shaped build — "one implementation and OEMs fork it".
**Mitigation.** Each entry carries a `reason` whose stated job is to stop a later phase pruning it — "it looks unused precisely because its job is to be present when a device finally appears" (`ObservedProfile.kt:17-20`) — and `theEnumerationUnionCarriesItsReasonAndItsIntroductionLevel` fails the build if any reason goes blank, any level goes missing, or `enumerationUnion` drifts from the enum. The silence itself is surfaced rather than absorbed: `unansweredProfiles` names the profiles that did not answer (`ConnectedDeviceObserver.kt:443-450`), a decline is not an empty list (ADR-P3-008), and `AndroidConnectedDeviceSourceTest.aProfileTheRunningOsDoesNotExposeIsDeclinedWithoutAskingTheHandset` proves the API gate runs before the mechanism. `docs/phases/phase-3/connection-observation-research.md` §3.2 is the citable inventory of what was left out and why.
**Detection.** A device class the product later cares about reporting as absent — the honest detection is a user's bug report, so the practical one is the deferred session, where the device session is asked to check this list against a handset (ADR-P3-008's own consequence); U-3 and U-7 are the named measurements. A `technicalName` appearing in a report with no `reason` behind it is detectable today by `TEST-P3-014`.
**Fallback.** Report the class as unobservable rather than as absent — which the availability axis does — and let the phase that needs the omitted profile add it under an ADR with the API level and the proxy type verified, never by widening the list to make a demo pass. `enumeratedProfiles` is a constructor parameter on both the observer and the source (`ConnectedDeviceObserver.kt:166`, `AndroidConnectedDeviceSource.kt:79`), so a narrower list is expressible honestly; a *wider* one is a source change.
**Owner.** Bluetooth Agent.

### RISK-051 — The first union round is routinely unavailable, which is correct and user-visible
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** `getProfileProxy` is asynchronous, returns a bare `boolean` with no error code, and its callback may never come; the handle explicitly does not wait for it (`SystemConnectedDeviceHandle.kt:44-47`, "blocking a snapshot on one would turn an UNVERIFIED promise into this project's own hang"). The ordering that follows from refusing to wait is mechanical: a bind still in flight is `AWAITING_CALLBACK` (`:176-183`), which maps to `ProfileObservationSupport.UNKNOWN` (`AndroidConnectedDeviceSource.kt:237-238`), which means the profile is skipped in the union (`:170`), which means a round that names nobody on a cold start produces exactly the combination ADR-P3-015 rule 7 refuses — an empty `Success` where nothing answered — and the engine reclassifies it as `Failure(RESOURCE_UNAVAILABLE)` (`ConnectedDeviceObserver.kt:347-358`, `:371-376`). That is the *right* answer and it is also, on a real handset, the *likely first* answer. Nothing then re-reads: the only recovery paths are an adapter edge (`reconcileAdapterSwitch`, `:407-411`) or `refresh()`, which has no caller (RISK-058), and polling is forbidden (prompt §8). The GATT entry is the exception that proves the shape — it answers from the manager object with no binding at all (`:81-83`) — and whether it answers is U-3, an open source disagreement the research could not settle "at all costs" because the reference code logs "Unknown profile" and returns `false`.
**Mitigation.** The refusal is the honest design and it is deliberate, chosen over "an empty device list, and never a silent skip" (ADR-P3-008); the category is `RESOURCE_UNAVAILABLE` rather than `UNSUPPORTED_OPERATION` precisely because its retry class says `RETRY_AFTER_REREAD`, so a caller is told to look again rather than to give up (ADR-P3-015 rule 7, the one recorded orchestrator override, with the agent's own preferred category named in the ADR). `unansweredProfiles` makes the message specific instead of existential, `lifecycleIsReportedAsAStageAndNeverAsAFailureShape` guarantees a refused round leaves the lifecycle intact so a consumer cannot read it as a broken observer, and `aUnionWhereNothingAnsweredCannotReportAnEmptyRoom` plus `aSilentProfileCannotWithdrawALinkItNeverRestated` pin the whole rule set.
**Detection.** The deferred session's first cold start, where `aDecliningPlatformNeverLooksLikeAnEmptyRoom` (`TEST-P3-021`) is exactly the authored check — and, until it runs, the fact that **no JVM test scripts an awaiting-then-answerable transition across two rounds**, so the recovery path from the ordinary cold-start case is unproven. That is `TEST-P3-034`/RISK-058 territory and is the sharpest remaining T1 gap: it needs no device.
**Fallback.** `RESOURCE_UNAVAILABLE` with `RETRY_AFTER_REREAD`, and a re-read owned by something — the phase that owns a UI, or the phase that owns observation lifecycle. If a handset shows the first-round refusal to be permanent rather than transient, the design choice is ACL-only observation with the profile axis reported unobservable, which is ADR-P3-008's own stated fallback and is expressible today.
**Owner.** Bluetooth Agent / UI owner (Phase 49).

### RISK-052 — The paired census is read live, so the risk moved from "no producer" to "never let it become a store", and no check defends the new boundary
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Status.** rewritten at close-out, not closed. This entry was authored while prompt §10's collection B had a type and no producer — `getBondedDevices()` was called nowhere, and `BONDED_DEVICE_LIST_INSPECTION` was an authorised operation with no code path. ADR-P3-017 superseded that framing while the phase was still open: the bond list is now read once per round through `ConnectedDeviceSource.bondedDevices()`, under its own standing, and arrives in `ConnectedDeviceSnapshot.pairedDevices`.
**Description.** What is left is a different exposure. The census is a live view of the phone's own pairing records, and the rule that keeps it from being a saved-device store is a fold rule: `foldingPaired` **replaces** the collection on every answered round, so a device the phone unbonded leaves when the next read says so, and nothing accumulates. That rule is tested (`eachPairedRoundRestatesTheCollectionInsteadOfAccumulatingIt`), and it holds inside this process — but nothing checks the next consumer. The moment a Phase 4 session or a Phase 49 screen persists `pairedDevices` "so the list is there when the phone is off", prompt §10.C and §16's prohibition is breached by a file that never writes to disk, and every test in Phase 3 still passes. Two secondary exposures ride along: whether an OEM's bond read behaves as the reference implementation does (the adapter-state dependency in particular) is unverified, exactly as for every other framework call here — this is RISK-044's subject applied to a new member; and a paired record now carries a `displayName` beside the projection's, so the label exposure RISK-043 describes is doubled in surface while the address guarantee stays unchanged.
**Mitigation.** The no-store rule is structural rather than a convention in two places: `BondedDeviceObservation` has no link field, so the census cannot masquerade as collection A even by accident, and the bond axis reaches projection records only through `DeviceObservation.creditingBond`, which takes a record and a bond state and touches nothing else. The type carries a KDoc prohibition on retention, the census-replacement test pins the in-process behaviour, and `isPairedCensus` distinguishes "a phone with no pairings" from "we were not allowed to look" so a refusal cannot restate zero.
**Detection.** The first `pairedDevices` consumer that writes anywhere but memory; a UI string that renders the census as "your devices" without saying it is the phone's pairing list; a Phase 3+ record claiming bonded-device history is available offline. ### RISK-053 — A binaural pair is two devices to this model, and the product's whole subject is one product
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** Two of the seven union entries exist precisely because a real pair reports two links — `LE_AUDIO` "in the binaural case [gives] two independently transitioning entries for one physical product - the shape the reconciler exists for", and `CSIP_SET_COORDINATOR` "is what makes an LE Audio pair's two device entries attributable to one set; without it they are indistinguishable from two unrelated devices" (`ObservedProfile.kt:79-90`). The model has no set, group or product concept: `DeviceObservation` is one key, one name, one link, one profile set (`DeviceObservation.kt:44-75`), the join is key-equality and nothing else, and `twoDevicesCarryingTheSameNameRemainTwoDevices` is a *correct* test that will also be read as a *sufficient* one. **Mitigation.** The join rule's conservatism is what keeps this from becoming the worse failure: two entries for one product is a cosmetic defect, while one entry for two products is a data defect, and the type makes the second unreachable — `joinableWith` requires both keys to identify and be equal (`DeviceObservationKey.kt:114-115`), `mergedWith` throws on an unjoinable pair, and the key's own KDoc states the intended asymmetry: "the designed failure mode of a wrong answer is 'the same product appears twice', never 'two products became one'". **Detection.** Any UI that renders `records.size` as "devices", which is the first one anyone writes; the deferred session's multipoint step (U-5 asks whether the second earbud produces any adapter-level event at all); and Phase 10's LE Audio work, where U-8 must be measured before grouping is claimed.
**Fallback.** Report the count as *entries observed* and never as devices, which is what the type actually supports; introduce grouping in the phase that can justify it (Phase 10 or Phase 49), under an ADR, and if the platform's group id is unavailable, say the projection is ungrouped rather than inventing a name-based heuristic — that heuristic is exactly what prompt §12 forbids.
**Owner.** Core Agent / UI owner (Phase 49), with LE Audio owned by Phase 10.

### RISK-057 — Concurrency in this phase is proven only on one thread
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** Phase 3's engine is more concurrent than Phase 2's and was tested with the same single-threaded tools. `ConnectedDeviceObserver` holds two mutexes (`:169-170`), an unbounded arrival channel (`:220`), two launched pumps and a closer (`:245-272`), and a `finally` that tears down under `NonCancellable` (`:305-317`); `AndroidConnectedDeviceSource` hands back an unbounded `Channel` fed from a callback that "arrives on the main thread" while the reads run on the caller's dispatcher (`:138-141`, `SystemConnectedDeviceHandle.kt:300-303`); the handle keeps a `CopyOnWriteArrayList` of channels, a `synchronized` binding map, four `@Volatile` fields and an `AtomicBoolean` (`:72`, `:188-189`, `:298-313`, `:164`). **No executed test creates a second thread.** All 56 suspending Phase 3 methods run under `runTest`'s single-threaded scheduler, and `AndroidConnectedDeviceSourceTest.kt:550-554` deliberately pins `Dispatchers.Unconfined` on the stated grounds that its assertions are about order — a sound reason, and one that buys determinism by giving up the only thing the concurrency machinery exists to survive. The specific properties left unproven are the interesting ones: whether a snapshot fold racing an announcement can lose either; whether `tryLock`/`unlock` in the `finally` can free a slot another observer has already taken; whether `disposeAll`'s loop runs while a callback is still arriving.
**Mitigation.** The design reduces the surface rather than relying on luck: one slot per object, refused loudly and typed (`RESOURCE_UNAVAILABLE`, `:207-218`); every projection mutation inside `projectionLock.withLock` with the decision taken *inside* the lock precisely because "the question 'could this round see anything?' is answered by the same profile bookkeeping that the fold is about to change" (`:345-347`); the two pumps joined before the arrival channel closes, because closing from either pump "would cut the other stream off mid-announcement, which is a lost transition with a tidy shutdown on top" (`:265-267`); channel-per-resource ownership in the handle so a second open cannot overwrite a first receiver (`:64-72`). The two-ordering tests in `TEST-P3-009` are the substantive coverage of the race and they hold, on one thread.
**Detection.** `TEST-P3-034` needs no device for its first half: a `Dispatchers.IO`-based test with two collectors and an arrival storm is writable today. On hardware, the detection is a lost or duplicated transition in the deferred session's U-9 timing run (which asks for 20 connect/disconnect cycles and reorder statistics), or an `IllegalStateException` from an unregister racing a dispose.
**Fallback.** Keep the single-slot refusal as the concurrency contract — one observation at a time is the design, and ADR-P2-007 chose it over reference counting deliberately — and move the multi-thread proof into the deferred session rather than claiming it here. If the fold turns out to be racy on two threads, the fix is a confined projection actor or a state-flow with compare-and-set, under an ADR, not a lock added at the call site that failed.
**Owner.** Core Agent / Testing Agent.

**Fallback.** If announcements do not arrive, that is a platform correction with its own ADR and Phase 2's adapter path is corrected the same way it was here, not quietly. If they arrive only under some third registration shape, the shape becomes the documented rule and the reasoning moves into that ADR. The observation engine degrades honestly either way: a silent stream plus an answered snapshot is expressible as a partial observation, and ADR-P3-009's rule means it can never be reported as "nobody is connected".
**Owner.** Bluetooth Agent / Security Agent, with the arbiter owned by the deferred session.

### RISK-064 — Two mechanisms disagreeing about a bond are resolved by rank, in silence, by a data class
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** `DeviceObservation.mergedWith` combines two reports of one device, and where they disagree it takes the more positive answer by rank: `strongerBond` prefers `BONDED > BONDING > NONE > UNKNOWN` (`DeviceObservation.kt:164-177`), `strongerLink` and `strongerAvailability` do the same on their axes, and the type's own KDoc states the principle behind the ordering — "a positive report beats an unread one" — and then, in the same paragraph, states the limit it does not implement: "nothing here picks a winner between two positive reports of different kinds - a `BONDED` record keeps that answer against a `NONE` one, **because two mechanisms disagreeing is a finding for a human, not something a data class may splice into a hybrid**". `BONDED` beating `NONE` *is* picking a winner between two positive reports, and it is done by a comparator. Nothing records that the disagreement happened: refusals are surfaced for impossible *link* transitions (`RefusalKind.IMPOSSIBLE_TRANSITION`, `ConnectedDeviceObserver.kt:604-613`, `:639-647`), and there is no counterpart for a bond, so a handset whose profile enumeration and whose bond announcement contradict each other produces a clean-looking `BONDED` record and no trace of the conflict. No test drives the case — `aMergeTheKeyCannotAttributeIsRefusedRatherThanGuessed` asserts the profile union and the refusal half, and `requirements.md:94` records that "no test walks every rank of `mergedWith`". Gap `TEST-P3-042`.
**Mitigation.** The disagreement cannot leak into a device *count*, because the join is the address and nothing else (`joinableWith`, `DeviceObservationKey.kt:114-115`), so the worst case is one device wearing one label rather than two devices welded or one split. The rank is a total order over a four-member enum, decided once, in the one merge the model offers — `mergedWith` is the only public combination and it refuses on unjoinable keys, so there is no second place where a different rule could apply. The asymmetry is chosen in the safe direction for this product: `UNKNOWN` ranks last on every axis, so a silence never overrules a report, which is ADR-P0-016's rule rather than a preference. And the ordering is *visible* in the type: the rank functions sit inside the companion that documents them, next to the sentence that says what they should not be used for.
**Detection.** A phase that reads the bond as a fact worth acting on — a "this device is paired, so offer to reconnect" affordance is the first likely one — would surface a wrong answer as a wrong suggestion. Machine-side detection does not exist yet and is cheap: one test that merges `BONDED` with `NONE` and asserts what a consumer is entitled to conclude. `TEST-P3-042` is that missing test.
**Fallback.** Two options, and both are ADR-gated rather than a drive-by edit: carry a bond disagreement into `refusedTransitions` as a third `RefusalKind` alongside the two link kinds, which reuses machinery the projection already bounds at eight; or forbid the merge from deciding at all, keep the two reports side by side, and let the phase with a user in front of it present the contradiction. Whichever is chosen must not be "leave it ranked and quiet", because that is the state that reads as agreement.
**Owner.** Core Agent, with the presentation half owed by Phase 49.
