# Phase 3 — Test Plan

**Phase:** 3 — Connected Device Detection · **Scope id:** `P3` · **Owner agent:** testing-and-risk workstream / orchestrator as integration owner
**Instantiates:** `docs/phases/phase-0/testing-governance.md` — tiers T1–T8 (§2.1), the mandatory eight-field record (TST-REC-001), the id grammar (TST-REC-002), the `REQ` ↔ `TEST` ↔ tier ↔ level matrix (TST-REC-006), the mocking ceiling (TST-MOCK-001, TST-MOCK-006), the no-relaxation rule (TST-GOV-001), the regression discipline (TST-REG-005, TST-REG-006) — using `docs/templates/test-plan-template.md`. Phase 3 adds no rule and relaxes none; where this file is stricter than governance, §1.3 says so and why.
**ID discipline.** Phase 3 prompt §19 seeds test obligations as prose bullets ("Test: Connected device observation. Bonded versus connected distinction. …") with no ids, exactly as Phases 1 and 2 did; TST-REC-002 fixes the canonical grammar as `TEST-<SCOPE>-<NNN>`, so the seeds are mapped onto `TEST-P3-<NNN>` **once, here**, and never in the `P3-TEST-001` or `OB-P3-…` form the prompt's neighbouring sections use. Ids are allocated monotonically from `001`, never reused, never renumbered, and a retired id keeps its number with the reason recorded. Ids `TEST-P3-021` … `TEST-P3-044` are allocated to **gaps** — obligations with no executing test, plus one suite that exists and has never been run — so that every unmet bullet of prompt §19 has a permanent address. A gap id is a record of something NOT RUN and is never a passing test (TST-REC-005). `041` … `044` were allocated after §4 and §6.1 were written, from re-reading `requirements.md`'s own `Verification` clauses against the source rather than from a wish to lengthen the list, and they are flagged as late additions in §8 because a gap discovered during record-writing is the kind most easily lost. **`045` … `048` are executing clusters, allocated in a second late wave for the same reason in the other direction:** the paired census and the Phase 3 scope test landed in the working tree (`ac135c2`, `caf286e`, `d3b03df`) after §3 was closed, and a suite that runs and has no record is a passing test nobody can trace to an obligation. Two gap ids changed state in that wave rather than being deleted: `TEST-P3-036` is **closed** by `PhaseThreeScopeTest` (§8 keeps the row with its closure) and `TEST-P3-026` is **narrowed** — collection B now has a producer, so what remains of the gap is the handset half of it (§8).
**Record shape.** One record per executing cluster. Every method name below was copied from an `@Test` on disk and cross-checked against the `testcase name` attribute in the executed JUnit XML, so the cluster counts sum to the measured totals in §1.1. No name in this file is paraphrased, inferred from a requirement, or quoted from a plan written before the file existed.
**Requirement linkage.** `docs/phases/phase-3/requirements.md` was issued by a sibling workstream while this plan was being written, and it carries `REQ-P3-001` … `REQ-P3-027`; §6.1 reconciles them bidirectionally with the ids allocated here, which discharges TST-REC-003/004 rather than deferring them as Phase 2's plan had to. That file cites methods with `file:line` rather than this plan's ids, and its line 41 correctly states why: "an id proves nothing a method name does not". Neither convention is abandoned here — every cluster in §3 names methods, and §6.1 names requirements — because TST-REC-006 asks for the matrix and TST-REC-001 asks for the records, and only having both satisfies both rules.
**Mocked versus physical.** **All 523 executed JVM test cases named in this plan — Phase 3's own 122 and the 401 they re-run beside them — are JVM tests against scripted seams.** The instrumented suite in `platform/android/src/androidTest/` **compiles and has never been executed**; there is no `adb` target attached (`docs/phases/phase-3/connection-observation-research.md:79-86`), and ADR-P3-014 (`docs/phases/phase-3/decisions.md:117-122`) moved every device claim in this phase to a deferred end-of-project session. §9 is that deferral, written as an instruction, and it reports no result. **No test in this file touched a radio, an adapter, a phone, an emulator, a headset or a Bluetooth announcement, and no test in this file read a real bond list** — the paired census (§3.21, §3.24) is scripted through the same seam as everything else, so `BondedDeviceObservationTest`'s green run proves the fold, not that anybody's phone has anything in its pairing records.

### 1.3 Evidence ceiling — what a green suite here is worth

Per `testing-governance.md` §2.1, a T1 pass justifies at most **`IMPLEMENTED`**. Every executed cluster in §3 is T1, so **the ceiling for the whole of Phase 3's test evidence is `IMPLEMENTED`**, and:

- nothing here justifies `LAB_TESTED`, `HARDWARE_VERIFIED` or `PERSISTENCE_VERIFIED` (TST-MOCK-001). This phase observes devices and writes nothing to any of them, so persistence is not merely untested but out of scope (prompt §10, §16);
- nothing here is evidence that any phone, adapter, OEM build or headset does or does not expose anything (TST-GOV-004, TST-HW-004). The words "the platform reports" in a test below always mean "the fake was instructed to report";
- the instrumented suite earns **no level at all** — not `INFERRED`, not `IMPLEMENTED` — because it has not run. Compiling it proves the calls exist in the compile SDK; it proves nothing about behaviour, and §3.19 records it as NOT RUN rather than as a tier (TST-FAIL-001 row 5 is the failure this avoids);
- no capability moves above `UNKNOWN` anywhere in this phase, and no `PlatformFeature` gains a usable claim: Phase 3 did not touch `AndroidPlatformCapabilityProvider`'s evidence tiers, which remain capped at `INFERRED` by ADR-P2-008/ADR-P2-017 and are still asserted as such by `nothingIsClaimedUsableBecauseNoRadioWasOpened`.

## 2. How to read the records

Each record states: purpose · tier · setup (which fake stands in for what, **and what that cannot prove**) · input (the real `@Test` names) · expected result · failure condition · hardware requirement · automation · evidence level · result · linkage. Hardware requirement is `NONE` in every executing record because no executed test needs a radio, and that column is a statement about the test, never about the obligation — the obligation's hardware requirement lives in §8's gap register. `Result` is `pass` because every name listed was found in the XML for its class with `failures="0" errors="0" skipped="0"`; a test that exists but did not execute is recorded NOT RUN, and the only such bodies in this phase are the twelve named in §3.19, which sit in a source set no executed test task runs. **Linkage** is by prompt section, by ADR and by `REQ-P3-<NNN>`: `docs/phases/phase-3/requirements.md` was issued by a sibling workstream while this plan was being written and carries `REQ-P3-001` … `REQ-P3-027`, so the bidirectional mapping TST-REC-003 makes mandatory is in §6.1 rather than deferred as Phase 2's plan had to defer it (`docs/phases/phase-2/test-plan.md:7`). That file names methods with `file:line` instead of ids and says why (`requirements.md:41`): "an id proves nothing a method name does not". Both forms are kept here — §3 records methods, §6.1 records requirements — because TST-REC-001 asks for the records and TST-REC-006 asks for the matrix, and only having both satisfies both rules.

Cluster counts sum: 13 + 9 + 4 + 8 + 7 + 2 + 8 + 1 = 52 in `:core`'s three Phase 3 classes as first drafted, **+ 17 + 8 = 77 across the five that exist now** (`BondedDeviceObservationTest` and `PhaseThreeScopeTest` are §3.21 and §3.22), and 7 + 13 + 5 + 4 = 29 in `:platform:android`'s one as first drafted, **+ 10 + 6 = 45 across the two that exist now** (the bond cluster is §3.24, `ProfileAnswerabilityTest` is §3.23) — 77 + 45 = **122** new methods, which with the 356 + 45 Phase 2 methods re-executed unchanged (§3.20, §3.6) gives §1.1's totals of **433** and **90 per variant** with no method counted twice and no Phase 2 method deleted.

## 9. Deferred physical validation — a numbered instruction to a future session, **not a result**

**Nothing in this section is a claim.** It is prompt §19's ten-step manual validation, recorded verbatim in intent as a script for a session that has not happened, plus the twelve authored-not-run cases that would run beside it. ADR-P3-014 deferred it; the user's standing instruction is that device testing is taken up at the end of the project, and "deferred" is a schedule, not an outcome — RISK-044 and RISK-045 exist so this does not quietly become "assumed fine".

Perform it only under `docs/security/device-access-policy.md` (§"Phase 3: instrumented verification, authorised and bounded", `:88-102`): the phone is a personal device; only `com.omnibuds.android`'s own `androidTest` APK may be installed; **no permission may be granted by shell command without the user's explicit say-so at the time**; no `dumpsys bluetooth_manager`; no log or result file may carry a device name or address, because instrumented output leaves the phone through logcat and through the XML in this repository's build directories. Record each step in the end-of-project validation report with the device identity fields the platform actually reports, writing `UNKNOWN` where a field is unavailable (TST-HW-003).

1. Attach the user's handset, confirm `adb devices -l` shows it, and note model, Android version, `SDK_INT`, OEM build and the **installed application's own `targetSdkVersion`** before trusting any other measurement.
2. Pair the earbuds through Android's normal Bluetooth settings. OmniBuds must not pair, connect, enable or request anything (prompt §1, §16).
3. Connect the earbuds normally, from the system UI.
4. Open or refresh OmniBuds' observation — and note that today `refresh()` has no caller (`TEST-P3-025`), so this step requires the phase that owns a UI, or an instrumented run that calls `ConnectedDeviceObserver.observe()` directly.
5. Verify the connected device is detected **if the platform exposes it**, and record which profile named it. An empty result is a finding about the union, not a pass.
6. Disconnect the earbuds.
7. Verify the active observation updated — `connectedDevices` empties and `records` keeps the device as `DISCONNECTED`.
8. Reconnect.
9. Verify no duplicate device records appeared, and specifically whether an LE Audio pair arrives as two entries (`TEST-P3-031`).
10. Disable Bluetooth and verify no stale connected-device state is presented as active; the expected shape is the one `anAdapterGoingQuietMarksDevicesUnobservableAndNeverPoweredOff` proves in code — records marked `UNAVAILABLE` with `link == UNKNOWN` and a `BLUETOOTH_DISABLED` refusal, **never** a claim that the headset was powered off.

Then run the twelve authored cases (§3.19), and settle the three questions they were written for that nothing else can: **U-4** — do the ACL, bond and per-profile announcements actually arrive at a `RECEIVER_EXPORTED` context receiver on this build, and does Phase 2's newly-exported adapter-state receiver now receive what it may not have been receiving (ADR-P3-013, `TEST-P3-022`)? **U-3/U-7** — which of the seven union profiles bind, and what does `getProfileProxy` return for GATT? **U-2** — is the address of a bonded earbud stable across reboots and reconnects (start the ≥ 7-day snapshot the research asks for)? Record the phone model, Android version and the profile actually observed, and write **nothing** about compatibility in the universal tense: prompt §19's own closing rule and TST-HW-004 forbid generalising from one handset.
