Four boundary decisions carry the design, and each is a place where the obvious alternative was refused.

- **Framework → handle.** `ConnectedDeviceHandle` (`connection/ConnectedDeviceHandle.kt:30-93`) declares **five** members because five questions are authorised — is there an adapter, can this profile answer, what does it answer, will it announce changes, and what has this phone paired — and its KDoc (`:24-28`) names the sixth that was refused (pair, connect, enable, ask a device for something) as "a capability this phase forbids behind a name that sounds like a read"; the fifth was added by ADR-P3-017 with the argument that it is a read in exactly the same sense as the other four, asking nothing of any device and changing nothing. The seam speaks in *raw* named cases — `RawLinkState.UNREADABLE` (`:102-108`), `RawBondState.UNREADABLE` (`:111-116`) — rather than in `:core`'s states, so the difference between "the stack said a number" and "the stack said nothing" survives far enough to be tested; a mapping that collapsed it at the boundary would make ADR-P3-005's subject undecidable. `BondedListing`'s four cases (`:195-207`) are the same argument one level up, because there the unreadable thing is not a value but a situation: the platform answers four worlds with one empty collection. One class holds the device-facing framework references — `SystemConnectedDeviceHandle` (`:58-567`), "the one class in this codebase permitted to touch Android's device-facing Bluetooth API" (`:24`), with `SystemBluetoothAdapterHandle` remaining Phase 2's holder of the adapter-facing ones — and its own doc (`:20-57`) records which of its claims are confirmed by the SDK and which are carried as unknowns (U-3).
- **Handle → source.** The translation from raw to domain is `linkStateOf`/`bondStateOf` (`AndroidConnectedDeviceSource.kt:386-401`), five branches and four, total, with `UNREADABLE → UNKNOWN` and no default that could silently swallow a new platform value — which is why an unreadable bond on a paired record reads `UNKNOWN` and never `NONE` (`AndroidConnectedDeviceSourceTest.kt:724`). This is where `ObservedProfile` meets the framework constant table (`SystemConnectedDeviceHandle.kt:644-652`), because a core enum may not carry framework numbers — rule 2 (`DependencyDirectionTest.kt:189-201`) would fail the build over a single framework type name in `:core`, and the reverse lookup lives in the same file for the same reason (`:655-656`).
- **Source → observer.** The seam's return types are the design (`§5` below): nothing a source can return is a plain list of devices, so the phase's central honesty rule is carried by the type rather than by a comment. The paired member is the same argument pointed at a second question — `bondedDevices()` returns `ObservationRound<BondedDeviceObservation>` (`ConnectedDeviceSource.kt:147`) and not a wider `snapshot()`, because a list whose emptiness means "nobody is connected" must not also be the list that answers "who is paired".
- **Observer → projection.** The engine is in `:core` so that every hard case is testable without a radio (ADR-P3-003), exactly as `AdapterStateObserver` was in Phase 2; the Android module contains **no** reconciliation logic. `di/OmniBudsBluetooth.kt:83-85` states the consequence in the other direction: a composition root that re-implemented the fold would be a second copy of the rules the `:core` tests cover.

**The consumer box is empty, and that is the honest shape of the phase.** `omniBudsConnectedDeviceObserver` (`di/OmniBudsBluetooth.kt:102`) is called from no source file in the tree; `ConnectedDeviceObserver.snapshot` and `refresh()` have readers only inside `ConnectedDeviceObserverTest` (`:417, 430, 593, 607`) and the never-executed instrumented suite; `connectedDevices` (`ConnectedDeviceObserver.kt:149-150`), `isUnionComplete` (`:154-155`) and `isPairedCensus` (`:161-162`) are consulted by nothing in production. Phase 4 owns the first thing that pulls on this surface, and prompt §21 places it after this boundary. The census widens the surface a consumer will find, and it is worth naming what an empty `pairedDevices` does and does not mean before somebody reads it as a settings screen: it is a census only when `isPairedCensus` says so, and even then it says "the phone named nobody in its bond list", never "nobody has ever been paired" (§9).

## 3. Three axes, and what collapses them

ADR-P3-001 splits what prompt §6 listed as one vocabulary into three independent types, and the split is what the rest of the design depends on.

| Axis | Type and members | What it answers | What it must never be read as |
|---|---|---|---|
| Link | `DeviceConnectionState` {`UNKNOWN`, `CONNECTING`, `CONNECTED`, `DISCONNECTING`, `DISCONNECTED`} — `DeviceConnectionState.kt:22-28` | what the stack says about a link it did not create | a session position; `state/ConnectionState` is Phase 4's and its own KDoc calls `IDENTIFYING`/`CAPABILITY_DISCOVERY` OmniBuds' work |
| Bond | `DeviceBondState` {`UNKNOWN`, `BONDED`, `BONDING`, `NONE`} — `DeviceBondState.kt:16-28` | whether a pairing exists | whether anything is connected — the platform's own `BOND_BONDED` doc says so (research §2a) |
| Availability | `DeviceAvailability` {`UNKNOWN`, `AVAILABLE`, `UNAVAILABLE`} — `DeviceAvailability.kt:16-30` | whether the platform would tell us about this device at all | a link condition; prompt §6's `UNAVAILABLE` describes our view, not the radio |

Each axis has its own predicates, and the interesting ones are the asymmetries: `isConnected()` is true of one member and `isProvablyDisconnected()` of one other, so `UNKNOWN` is neither (`DeviceConnectionState.kt:31, 40`); `isUnsettled()` covers `UNKNOWN` **and** the two intermediates (`:43-46`). `DeviceBondState.isBonded()` refuses `UNKNOWN` (`DeviceBondState.kt:31`) while `isKnown()` accepts `NONE` (`:34`) — which is what an "unpaired" affordance needs and a "no report" one must not get. `DeviceAvailability.isUnread()` (`DeviceAvailability.kt:41`) deliberately excludes `UNAVAILABLE`, because a positive report of refusal was itself a report.

What collapses the axes is not a merge of enums — none is possible, they are three types — but a **derived field**. `DeviceObservation` carries all three (`DeviceObservation.kt:52-58`), and `DeviceObservationVocabularyTest.bondedAndDisconnectedAreBothTrueAtOnce` (`core/src/test/.../DeviceObservationVocabularyTest.kt:90-99`) plus `.theThreeAxesAreIndependentTypesWithNoCoercion` (`:118-124`) are the build-level statement that one cannot stand in for three. The one place the engine *does* derive a link from something else is the aggregate in `withLinkEvent` (`ConnectedDeviceObserver.kt:822`), where a non-empty profile set forces `CONNECTED`; §6 explains why that is the only honest derivation available and what it costs.

The census is the axes held apart rather than collapsed, and it is worth stating why a second type was cheaper than a flag. `BondedDeviceObservation` (`DeviceObservation.kt:226-283`) carries four fields — key, reported name, the device's own bond reading, a reading time — and no link, no profile set and no availability axis, because the bond list is a set of stored link keys and a link field on its records could only be filled by the inference prompt §6 forbids in both directions. Its own KDoc (`:198-225`) says so, and `BondedDeviceObservationTest.thePairedRecordHasNoFieldThatCouldClaimALink` (`BondedDeviceObservationTest.kt:365`) enforces it by reading the declared field set, so the prohibition is a build failure rather than a convention. Where the two collections do meet, one axis crosses: `DeviceObservation.creditingBond` (`:159-160`) copies a bond state onto a record the link mechanisms already named and touches nothing else, and there is no sibling function with a link parameter to misuse. The disagreement case is kept rather than smoothed — a bond list that still names a device whose own `bondState` says `BOND_NONE` reports what the device says (ADR-P3-017, `BondedDeviceObservationTest.kt:269`), on `mergedWith`'s rule that two mechanisms disagreeing is a finding and not something to splice.

## 4. The profile union is a maintained decision

There is no public call that returns all connected devices (research §3, §3.4: `BluetoothAdapter.getConnectedDevices` and `getSupportedProfiles` are absent from `android.jar`), so the enumeration list *is* the definition of what Phase 3 can see. `ObservedProfile` (`platform/ObservedProfile.kt:35-115`) carries seven entries, each with a `technicalName`, the API level at which it became askable, and a `reason`; `enumerationUnion` (`:113`) is the list a snapshot folds over, and it is held by both the source (`AndroidConnectedDeviceSource.kt:85`) and the engine (`ConnectedDeviceObserver.kt:232`) so "the platform did not list this device" can only be read as a disconnect when every entry actually answered. **The union governs collection A alone.** The paired read is not profile-scoped and does not consult it — `bondedDevices()` asks the adapter (`SystemConnectedDeviceHandle.kt:152-159`) — which is why a device held only by a profile excluded from this list can still arrive as a pairing, and why the two answers have to be joined by a consumer on the key rather than assumed to be the same population (§9).

Two axes were refused for this one, both in ADR-P3-002 and restated in the file's own KDoc (`ObservedProfile.kt:7-14`): `TransportKind` names channels OmniBuds could open and has no member for any of these, and `PlatformFeature` answers a *host* question. A device fact read out of a capability report is how "this phone has the API" becomes "these earbuds support the feature", and that is the phase's central fabrication risk. The separation is now stated from both sides: `PlatformFeature.kt:10-14` gained the matching paragraph — `A2DP` appears in both vocabularies and means "this handset can tell me about A2DP at all" here and "this device's A2DP link was reported to us" there — and `docs/phases/phase-2/transport-boundaries.md` gained the amendment note ADR-P3-002's consequences required at its `:227-237`, both landing at `335c31d` while this file was being written. One sentence of that older document did not follow: `transport-boundaries.md:126` still reads "Phase 3 — `DEVICE_DISCOVERY_SCAN` for advertisements", which ADR-P3-018's correction to `authorizedInPhase = 5` left behind; §18 of `specs.md` records it as a cross-document divergence rather than editing another workstream's file.

**What the exclusions cost.** ADR-P3-015 rule 1 names four excluded families with reasons, and the file states them too (`ObservedProfile.kt:22-33`): the deprecated health profile (the platform refuses its binding outright, research §3.3); profiles with a public constant but no public proxy type, so nothing typed could be asked of the returned object; the attribute-protocol *server* role, because Phase 3 runs no server and observing one another app opened is a different question with different keys; and every profile absent from the compile SDK. The cost is a class of connection this phase reports nothing about, and it is stated rather than left to be rediscovered: a device held only by an excluded service is invisible, and — because absence-from-the-union becomes a disconnect only for profiles that answered (§9) — invisibility is not reported as `DISCONNECTED`.

One asymmetry inside the union is worth naming before §15: `HID_DEVICE` is enumerable but **never announceable** — the action table (`SystemConnectedDeviceHandle.kt:520-554`) has no human-interface entry, because the compile SDK exposes no public connection-state action for it, which the comment at `:451-453` records as a stated gap rather than an oversight. Such a device can appear in a snapshot and cannot appear in an announcement, so it is only ever seen at round boundaries.

## 5. Standing before looking, and why ordering is the only mechanism

ADR-P3-009 rests on a platform finding the research quotes directly (research §6, §6.1): a denied `BLUETOOTH_CONNECT` yields an **empty set** from `getBondedDevices`, an **empty list** from the GATT and profile enumerations, **`STATE_DISCONNECTED`** from `getProfileConnectionState`, and **silent non-delivery** from every broadcast; the only `SecurityException` in the whole surface is the legacy `targetSdk < 31` branch of `getProfileProxy`. The platform therefore answers "you may not look" and "nobody is connected" with the same value, and prompt §14 forbids the second reading of the first.

Nothing written *after* a read can separate them, so the separation is temporal. **All four entry points** begin with the same call and refuse before doing anything else: `profileSupport()` at `AndroidConnectedDeviceSource.kt:90`, `snapshot()` at `:103`, `bondedDevices()` at `:159`, `openConnectionEvents()` at `:215` — each with the operation it is about to perform, so the bond-list read settles `BONDED_DEVICE_LIST_INSPECTION` and not its neighbour's grant. `refusalFor` (`:353-363`) clears only on a grant, and `isClearedFor` (`:365-375`) asks `stateFor(operation, BLUETOOTH_CONNECT, context)` first, then the legacy `BLUETOOTH` row only when the modern answer is `NOT_REQUIRED` — which none of the three device operations this source consults can produce, because the frozen resolver requires `BLUETOOTH_CONNECT` for `CONNECTED_DEVICE_INSPECTION`, `BONDED_DEVICE_LIST_INSPECTION` and `PROFILE_CONNECTION_STATE_INSPECTION` (`PermissionRequirementResolver.kt:104-106`) at target ≥ 31 (`:108-116`) and legacy `BLUETOOTH` below it (`:117-126`). `UNKNOWN`, `NOT_REQUESTED` and `DENIED` therefore all refuse (stated in the KDoc at `:338-352`, delivered at `:365-375`), and a permission provider that *throws* is treated as a refusal rather than as a platform exception, because with standing unknown the ordering cannot be honoured (`:354`).

The mechanism is structural, not behavioural, and this is the part a later reader should not miss: `ConnectedDeviceSource.snapshot()` returns `ObservationRound<DeviceObservation>` (`ConnectedDeviceSource.kt:119`) and `bondedDevices()` returns `ObservationRound<BondedDeviceObservation>` (`:147`), and `ObservationRound` (`platform/ObservationStage.kt:45-54`) has **no representation** for "a list, from a round that was not allowed to produce one". A `Failure` carries an error and no list; a `Cancelled` carries nothing. `ADR-P3-005` is the decision that split lifecycle (`ObservationStage`, three members) from failure (the outcome), and the refusal of a `PARTIAL` outcome is the same decision's other half — whether Android makes a partial enumeration observable is a research question the phase did not settle (U-3 and U-7, research §11), and a member invented before the platform answers is Phase 2's `DEDUPED` mistake repeated. ADR-P3-017 leans on exactly that structure for the second question: because `BondedDeviceObservation` has no link field, a paired list cannot arrive as a connected list even by accident, and the seam's type is what enforces the phase's central distinction.

Standing is necessary but not sufficient for the bond list, and this is the one place the ordering rule is not the whole answer. `getBondedDevices()` answers empty to a caller whose standing *was* granted whenever the adapter is not `STATE_ON`, so a cleared round can still be a round that saw nothing; the handle therefore reports the adapter facts alongside the set as `BondedListing`'s four cases (`SystemConnectedDeviceHandle.kt:152-159`) and the source turns three of them into refusals before the set can be counted (`AndroidConnectedDeviceSource.kt:163-197`) — the ladder §9 explains, rebuilt on the pairing side.

The rule is testable without a radio, which is the point: `AndroidConnectedDeviceSourceTest` asserts the order by observing what the handle was *not* asked (`:62, 89, 105` — refusal before enumerating, before reading binding state, before registering; `:553` the same for the bond read, with `bondReads == 0` asserted at `:561`), `theBondListIsClearedByItsOwnPlanAndNeverByTheConnectedDevicesOne` (`:569`) refuses a source that would borrow its neighbour's grant, and `aRefusedPermissionArrivesAsAFailureCarryingNoDeviceList` (`ConnectedDeviceObserverTest.kt:336`) closes it at the engine. Prompt §13's "do not bypass runtime permissions" is honoured by the absence of any request path at all (§13 below).

## 6. Snapshot, event and the race between them

Prompt §9 names the hazard: an announcement can arrive while the initial union is in flight, and an engine that registers late — or that lets the snapshot replace the projection wholesale — reports a device that had already dropped as connected. Phase 3 orders it one way. `observe()` (`ConnectedDeviceObserver.kt:272-384`) takes the slot (`:273`), sets the stage (`:294`), **opens the announcement stream and starts its pump first** (`:296-313`), opens the adapter stream and its pump next (`:315-330`), installs the closer that ends the arrival loop only when both pumps have joined (`:334-338`), and only then asks the profile-support question (`:340-352`) and reads the first round (`:354`). Announcements delivered during the read land in `arrivals`, an unbounded channel (`:286`), and are applied by the loop at `:364-370` — *after* the fold, so the later report wins over the staler read. Both directions are asserted: `aTransitionAnnouncedWhileTheSnapshotWasInFlightSurvivesIt` (`ConnectedDeviceObserverTest.kt:75-101`) and `aDeviceThatAppearedWhileTheSnapshotWasInFlightIsNotLost` (`:104-124`). The second is only a test of the engine's buffer rather than of coroutine luck because the scripted source yields before answering on **each** read (`FakeConnectedDeviceSource.kt:71-73, 85-88`).

A round is now two reads, and the ordering between them is the source's business rather than the engine's. `readRound()` (`ConnectedDeviceObserver.kt:404-405`) calls `source.snapshot()` and then `source.bondedDevices()` and hands both to `reconcileRound()` (`:422-437`), which folds the device round first (`foldingDevices`, `:440-450`) and the paired round second (`foldingPaired`, `:472-487`) **inside one `projectionLock.withLock`** — the reason §9's second collection could not simply be another flow. Two folds, one publication: no consumer can observe a projection whose link half came from a cleared round while its pairings half came from a refused one, which is the same authority rule ADR-P3-005 states for a single collection, applied across two. The returned round is still the *device* answer (`:436`), because that is the question prompt §14 asks; a paired refusal is recorded beside it rather than relabelled as a failure of the link observation.

Inside a fold, `withSnapshotReported` (`:715-752`) applies three rules, each of which is a way of getting the device count wrong: reports of one key from several profiles become one record naming every profile that listed it (`:725`, via `mergedWith`); a record the union did not list loses only the profiles that actually answered (`:767-773`); and records the platform never keyed **cannot be carried across rounds at all** — each round's unkeyed reports replace the previous ones (`:721-727, 740`) rather than accumulating a shadow population nobody can attribute (ADR-P3-015 rule 6). Existing records are emitted before new ones (`:731-740`) so a consumer can diff the list. The paired fold has the same three, run over the second collection: `pairedCensusOf` (`:497-508`) joins one address to one record, keeps unkeyed pairings separate and after the keyed ones, and `foldingPaired`'s `Success` arm *replaces* `pairedDevices` outright (`:481`) — which is where prompt §10.C's no-history rule lives for collection B, since an engine that unioned every bond list it had ever read would be a saved-device store wearing a projection's name.

**Duplicate suppression** is value-based, not kind-based, and it is the reason there is no `ObservationKind` analogue in this phase. `saysSameAs` (`:919-925`) compares key, name, link, bond, availability and profile set — and pointedly *not* `arrival` or the timestamp — so a repeat announcement republishes nothing "not even a newer timestamp" (`:853-855`); `reconcileAnnouncement` returns null when nothing moved and the stream emits no element (`:555`). A snapshot round, by contrast, is always published (`:355`), because a completed union is itself news about every device. Idempotence goes the other way for a genuine repeat: three identical `DISCONNECTED` announcements apply once (`ConnectedDeviceObserverTest.kt:234-252`), which is prompt §11's requirement, and the transition table makes a same-state repeat legal rather than illegal (`DeviceConnectionState.kt:105-106`) because broadcast delivery promises neither uniqueness nor order. The paired fold adds the third case this phase had never had to distinguish — a round that answered *and moved nothing*: `creditingBondAxis` (`:520-527`) returns each record unchanged when its own bond read was already the more positive report, so a confirming census republishes no news, asserted by `BondedDeviceObservationTest.theBondListCreditsTheBondAxisAndLeavesEveryOtherFieldAlone` (`BondedDeviceObservationTest.kt:215`).

Refused moves are facts, not drops. A transition the table forbids keeps the previous state and appends a `RefusedDeviceTransition` carrying the table's own `refusalReason` string (`:789-798` for snapshots, `:824-832` for announcements); a report with no key appends an `UNATTRIBUTABLE_REPORT` refusal and applies nothing (`:810-812`, `:898-916`). The window is bounded at eight (`REFUSAL_WINDOW`, `:935`), because an unbounded window is a device history wearing a diagnostic's costume — prompt §10 forbids the history (§17). The paired refusal is *not* in that window: `pairedRoundRefusal` (`ConnectedDeviceObserver.kt:134`, set at `:475`) is a single slot holding the reason the census is not currently a census, because it is a claim about this app's standing to read, not an event about a device, and a bounded ring of the latter is no place to keep the former.

## 7. Join by key; a name is not identity

`DeviceObservationKey` (`platform/DeviceObservationKey.kt`) holds ADR-P3-010's three rules, and the third was amended by ADR-P3-015 rule 11, which this file states as built rather than as intended.

- **Absence is a value.** `NotReported` (`:83-88`) is a member, not a null, so a caller cannot write `?: someOtherKey`. Its `canIdentifyAcrossObservations` is false (`:84-86`), and that is the load-bearing line: two `NotReported` records are equal as values and are *not* one device.
- **Equality plus attributability is the join, and it is the whole join.** `joinableWith` (`:114-115`) requires both sides to identify and both sides to be equal; nothing reads a name, a class or a proximity. Every engine lookup goes through it (`ConnectedDeviceObserver.kt:524, 738, 813, 864, 893` — the first being the paired census's credit step) rather than through a map keyed by equality alone. `mergedWith` enforces the same rule from the model side by refusing on an unjoinable pair (`DeviceObservation.kt:104-106`), and the paired record has its own copy of that refusal for the same reason (`:254-257`, asserted at `BondedDeviceObservationTest.kt:389`), which is what actually enforces "a display name participates in no join" — ADR-P3-010's original wording said *no equality*, was read literally by the implementation, and the amendment narrows the claim to the join. Two records of one device may therefore differ in `displayName` after an alias refresh without becoming two devices; the data-class comparison stays a comparison of *reports* (`DeviceObservation.kt:39-42`).
- **Redaction is a property of the type.** `AddressBacked` keeps the value private and unreadable (`:50`), offers one construction route (`AddressBacked.from`, `:69-73`, reached through `ofReportedAddress`, `:101-102`), and prints kind and length only (`:58-59`). A caller cannot hand an address to a log formatter, a UI string or a persisted field without editing this file. The normalisation it performs — trim, upper-case — is a normalisation of the *comparison*, done once so two mechanisms reporting the same device in different conventions still join (`:93-100`; asserted at `DeviceObservationKeyTest.kt:70-78`). Both collections use it, so the guarantee extends to a paired record's key without a second mechanism: `BondedDeviceObservation` is keyed by the same `ofReportedAddress` call (`AndroidConnectedDeviceSource.kt:290-296`).

**What is not redacted, stated plainly.** `displayName` is carried as reported and a `DeviceObservation` is a data class, so a record's own `toString()` includes the name. The address guarantee is a type property; the name is a platform string, and the only thing between it and an emitted log line is the absence of any sink in this phase (§13) plus the instrumented suite's address-shaped pattern check (`ConnectedDeviceObservationInstrumentedTest.kt:240-252, 294-300`), which catches an address and not a name. Blank and whitespace-only reported text is demoted to null at the factory (`DeviceObservation.reported`, `:129-147`, `normalisedText` `:296`) — rule 12 of ADR-P3-015, following `DeviceIdentity`'s precedent that a domain type may not silently rewrite evidence, which leaves the primary constructor able to hold a blank name and makes `hasReportedName` (`:85-86`) the guard that says so. **The paired census now carries the same exposure, and it is worth stating as a cost rather than a surprise** (ADR-P3-017 names it): `BondedDeviceObservation.displayName` is the platform's `getName()` on a device from the bond list (`AndroidConnectedDeviceSource.kt:290-296`, `SystemConnectedDeviceHandle.kt:557-561`), it is subject to the same blank demotion (`BondedDeviceObservationTest.kt:410`), and a census of *pairings* is a more personal list than a census of live links — it names everything the user has ever put on this phone that the platform will still describe. Nothing in this phase can emit it; the emission duty is Phase 36's (ADR-P1-019), and the check that would catch it is still the address-shaped one, which does not fire on a name.

The key is not identity. `device/DeviceIdentity` gains no address field, and the file that would need it says why (`DeviceObservationKey.kt:24-27`): for a bonded classic device the address is effectively stable while for a never-bonded low-energy one it may rotate, and that is U-2 — device-level knowledge, not documented fact. The design therefore accepts one failure mode and refuses the other: a wrong answer to U-2 means "the same product appears twice", never "two products became one".

## 8. Disconnection, adapter disablement, and what may not be inferred

Prompt §11 asks for six behaviours on disconnect and three on adapter-off. The disconnect half is a projection edit: a record stays in `records` with its link restated (`:770`, `:846`), `connectedDevices` (`:149-150`) stops reporting it because `isReportedConnected` requires both availability and a connected link (`DeviceObservation.kt:81-82`), and the transition itself is preserved long enough to be published — inside the snapshot's bounded refusal window rather than as a second flow (ADR-P3-015 rule 8). Nothing is deleted and nothing is saved: there is no user-saved profile here to auto-delete, and no store to write. The paired collection is deliberately *not* touched by a disconnect at all — a link going down says nothing about a pairing, and `BondedDeviceObservation` has no link field to notice (`DeviceObservation.kt:198-225`).

The adapter half is where the honesty lives. `reconcileAdapterSwitch` (`ConnectedDeviceObserver.kt:579-626`) has three answers, and the middle one is the phase's claim about the world:

| Adapter state | Engine reaction | What it refuses to say |
|---|---|---|
| `isUsable()` (`ENABLED`) | re-read **both collections** and fold them (`:582`, via `readRound` at `:404-405`) | nothing — this is the re-snapshot the research's snapshot-on-start architecture asks for |
| `isProvablyDisabled()` (`DISABLED`), or `UNAVAILABLE` | mark **every** record `link = UNKNOWN`, `availability = UNAVAILABLE`, `observedProfiles = emptySet()` (`:590-598`) and record a `pairedRoundRefusal` with the same category (`:599-612`), then emit `ObservationRound.Failure` carrying `BLUETOOTH_DISABLED` or `ADAPTER_UNAVAILABLE` (`:614-622`) | that a remote device was powered off. The detail string says so: "this is not evidence about the power state of any remote device" (`:618-620`). Links return to `UNKNOWN`, not `DISCONNECTED` — and the paired list keeps its entries, because a radio going quiet is not a phone unpairing everything it ever met |
| the indeterminate adapter states — `ENABLING`, `DISABLING`, `UNKNOWN` | return null; publish nothing (`:625`) | an inference about a transition we cannot see |

Records are **marked rather than deleted** (`:591-598`), which is what lets a later round restore them: a completed union restates `availability = AVAILABLE` on carried records (`:772, 784`) — ADR-P3-015 rule 5, on the reasoning that a stale `UNAVAILABLE` is a claim, not a caution. Both directions are tested: `anAdapterGoingQuietMarksDevicesUnobservableAndNeverPoweredOff` (`ConnectedDeviceObserverTest.kt:254-283`) and `theAdapterComingBackReReadsTheUnionInsteadOfAssumingAnything` (`:285-306`). The paired half of the middle row is the one behaviour on this edge that had no precedent to follow, and it is tested on its own terms: `anAdapterGoingOffKeepsThePairedEntriesAndClearsOnlyTheClaim` (`BondedDeviceObservationTest.kt:290`) asserts the entries survive, `isPairedCensus` falls and `pairedRoundRefusal` names the adapter, which is the projection's way of holding "the phone's own list survives, our view of it does not". A round that did not answer leaves the projection exactly as it found it (`reconcileRound`'s `foldingDevices`, `:443-444`, tested at `:582-597`), because a refusal has no authority over what the platform last said.

## 9. Availability semantics for a profile that declined

ADR-P3-008's rule — "a proxy that never binds yields `UNAVAILABLE` for that profile, never an empty device list and never a silent skip" — is implemented as three cooperating answers.

1. **Answerability before enumeration.** The handle reports four cases per profile (`ProfileAnswerability`, `ConnectedDeviceHandle.kt:129-141`): `NOT_REQUESTED`, `AWAITING_CALLBACK`, `ANSWERABLE`, `REFUSED`. When several channels give different answers the handle takes the strongest by an explicit rank, not by declaration order (`evidenceRank`, `:160-165`: `NOT_REQUESTED` 0, `REFUSED` 1, `AWAITING_CALLBACK` 2, `ANSWERABLE` 3; combined at `SystemConnectedDeviceHandle.kt:90-91`), so a channel that has a bound service out-ranks another channel's decline, and **a bind still in flight out-ranks a refusal** — which is the ordering the function's own KDoc (`:143-159`) and the call-site comment (`SystemConnectedDeviceHandle.kt:86-89`) describe, and the ordering `ac135c2` corrected the rank function to match under ADR-P3-019. This paragraph previously recorded the prose and the numbers as contradicting each other; that divergence is closed, and the reason it mattered is in the ADR: `REFUSED` maps to `NOT_ANSWERABLE` and a pending bind maps to `UNKNOWN`, so a refusal out-ranking a pending bind let one channel's `getProfileProxy` returning `false` outvote another channel that had not called back, turning a round that was merely early into a round the platform declined. `ProfileAnswerabilityTest` now pins the ladder in both directions (6 methods, `:20`–`:80`), which is the guard that did not exist when the mistake was made. `enumerate` is never reached for a profile that has not answered (`AndroidConnectedDeviceSource.kt:250`).
2. **Support before silence.** `ProfileObservationSupport` (`ObservedProfile.kt:130-142`) is the domain answer, produced by two gates in order: does the running OS expose the profile at all (`availabilityAt`, `:101`, consumed at `AndroidConnectedDeviceSource.kt:323-336`), and did the mechanism answer? `NOT_ANSWERABLE` for an OS-level absence, a refused bind or a service that went away; `UNKNOWN` for a bind still in flight — which is what lets a later round answer without rewriting this one. `ProfileSupportReport.supportFor` falls back to `UNKNOWN` for a profile nobody asked about (`ObservedProfile.kt:158-159`), so an implementation cannot default its way to an answer.
3. **Union completeness as a readable fact.** `ConnectedDeviceSnapshot.unansweredProfiles`, `profileSupportConsulted` and `restsOnCompletedRound` (`ConnectedDeviceObserver.kt:100-112`) exist to make one question answerable: *may this empty list be read as a census?* `isUnionComplete` (`:154-155`) says only when the support question was consulted, the records came from a round that completed, and nothing is outstanding. Without the second boolean a projection that had only ever been refused would report itself a completed census of nobody (ADR-P3-015 rule 9). Absence from a union then means `DISCONNECTED` **only for the profiles that answered** (`:767-773`; `aSilentProfileCannotWithdrawALinkItNeverRestated`, `ConnectedDeviceObserverTest.kt:404-438` runs the same input against a declining and a complete union to show the difference is entirely in who spoke).

**The second collection, and why its answerability ladder is a copy rather than a reuse.** The same three answers, rebuilt for the bond list, because the same four platform worlds arrive at its read and none of them is a profile. (1) *Standing before looking* is `bondedDevices()` resolving `BONDED_DEVICE_LIST_INSPECTION` for itself (§5). (2) *Answerability before the value*: the handle reports the adapter facts alongside the set as `BondedListing`'s four cases (`ConnectedDeviceHandle.kt:195-207`, read at `SystemConnectedDeviceHandle.kt:152-159`) — `Reported(devices)`, `AdapterAbsent`, `AdapterNotOn`, `ReadFailed` — because `getBondedDevices()` answers all four with an empty collection or a null, its own Javadoc saying "If Bluetooth state is not STATE_ON, this API will return an empty set" and "@return unmodifiable set of BluetoothDevice, or null on error". Only `Reported` may carry an empty list, and it is reachable only with an adapter present, reading itself as `STATE_ON` and answering with a set. (3) *Completeness as a readable fact*: `restsOnCompletedPairedRound` and `pairedRoundRefusal` (`ConnectedDeviceObserver.kt:124, 134`) feed `isPairedCensus` (`:161-162`), which is the paired mirror of `isUnionComplete` and is deliberately **not** derivable from it — a projection can hold a completed link census and a refused bond list in the same instant, and the empty `pairedDevices` that goes with the second is not a finding about anybody's pairings. `AndroidConnectedDeviceSource` turns the three non-`Reported` cases into the categories the model already had — `ADAPTER_UNAVAILABLE` (`:171-178`), `BLUETOOTH_DISABLED` (`:180-187`, quoted rather than inferred from the platform's own documented behaviour) and `RESOURCE_UNAVAILABLE` for the "null on error" answer (`:189-196`) — and only `Reported` becomes records (`:164-169`, mapped at `:290-296`). Tests: `anEmptyPairedListArrivesOnlyFromAReadTheAdapterAnswered` (`AndroidConnectedDeviceSourceTest.kt:650`), `.anAbsentAdapterRefusesTheBondListInsteadOfReportingNoPairings` (`:663`), `.anAdapterThatIsNotOnRefusesTheBondListBecauseThatIsWhatThePlatformDoes` (`:678`), `abondListThatAnsweredTheErrorValueRefusesRatherThanCountingZeroPairings` (`:693`), and at the engine `aRefusedBondListIsNeverRestatedAsAPhoneWithNoPairings` (`BondedDeviceObservationTest.kt:67`) with `.aGoodPairedRoundThenARefusalKeepsTheEntriesAndWithdrawsTheCensus` (`:92`) for the half that says a *later* refusal withdraws the claim and not the entries. A `Cancelled` paired round changes nothing at all, including a refusal already on record (`foldingPaired`'s `Cancelled` arm, `ConnectedDeviceObserver.kt:476`; `BondedDeviceObservationTest.kt:118`), because a called-off read is not a finding.

And the sharpest case: a `Success` carrying no devices from a union in which *nothing* answered is refused outright (`couldSeeNothing`, `:693-696`; `emptyUnionRefusal`, `:538-543`) and reported as `RESOURCE_UNAVAILABLE` — reclassified from `UNSUPPORTED_OPERATION` on ADR-P3-015 rule 7's review, because the operation *is* supported, a later enumeration of the same union will succeed, and a `NEVER_RETRY` category would instruct a caller to abandon a stack that was merely not ready. **The paired side declines to copy that rule, and the asymmetry is deliberate:** an empty `Reported` set is a real answer about a phone with no pairings, so there is no "saw nothing" state to refuse — the answerability work happens entirely in `BondedListing`, and `foldingPaired` accepts an empty census (`:477-486`). A source that reported `Reported(emptyList())` while the adapter was off would lie past every check in the suite, which is the same lying-source ceiling `requirements.md` records against REQ-P3-005 and which only the instrumented eighth method can falsify.

## 10. Lifecycle, proxy binding and cleanup

No `LifecycleOwner`, no `Service`, no manifest component, no foreground service, no worker — and that is now machine-checked rather than observed: rule 11's manifest check rejects any `<receiver`, `<service`, `<activity` or `<provider>` (`DependencyDirectionTest.kt:508-532`). The lifecycle unit remains the caller's coroutine scope, and Phase 3 added the resource class Phase 2 never had: a **bound profile service**, which `getProfileProxy` hands over asynchronously and `closeProfileProxy` must reclaim (research §7.1).

Five rules, each with a file:line and most with a test.

1. **Collection registers; losing the collector unregisters and unbinds.** `observe()` is a cold `channelFlow` (`:272`), its `finally` cancels both pumps and the closer (`:372-374`) and disposes every registration inside `NonCancellable` (`:378-381`) — because that is the path cancellation actually takes, and a half-torn-down teardown would leave a bound service and a registered receiver with no owner left who could release them.
2. **A channel owns its bindings, and one channel cannot overwrite another.** `SystemConnectedDeviceHandle` keeps a `CopyOnWriteArrayList` of open channels (`:74`) so each owns its own receiver and its own proxies; ownership per handle would leak a receiver nobody could unregister when a second open raced a first. `openAnnouncements` adds the channel *before* starting it and `abort()`s it if the start throws (`:170-183`, `:305-320`), so a caller that receives an exception receives no orphaned resource with it.
3. **Teardown is idempotent and complete.** `dispose()` compares-and-sets an `AtomicBoolean` before unregistering (`:274`) because Android throws at an unregister it does not recognise and the observer's `finally` may run on a path that already disposed; both halves are attempted even when one throws, and the first problem is rethrown only after the rest has been tried (`:275-295`). The source wraps the handle's registration in `ClosingRegistration`, which closes the announcement channel *before* re-raising so no collector hangs on a half-released receiver (`AndroidConnectedDeviceSource.kt:430-442`), and `disposeAll` reports first-cause-class plus the counts that did and did not release (`ConnectedDeviceObserver.kt:667-690`) — "one of two leaked" and "both leaked" are different sizes of bug. The bond read adds nothing to this list and that is part of its cost case: it registers no receiver and binds no proxy (`SystemConnectedDeviceHandle.kt:141-145`).
4. **A registration never collected is still disposable.** `openConnectionEvents()` hands back the channel with its registration eagerly (`AndroidConnectedDeviceSource.kt:213-232`) and closes the channel if the open itself throws (`:227-230`), which `AndroidConnectedDeviceSourceTest.kt:437-467` exercises.
5. **No polling, no retry, no re-arm.** A bind still in flight is reported `AWAITING_CALLBACK` and nothing waits for it, because the platform promises no completion for a `true` return (`SystemConnectedDeviceHandle.kt:44-47`); a refused profile is not re-requested (`:243-262`), and a service that goes away is marked refused rather than silently re-bound (`:376-385`), because a silent re-request *is* the retry loop this phase forbids. The bond-list read is one read per round with no cache and no re-arm of its own (`:152-159`, and `BondedDeviceObservationTest.kt:321` for the count). There is no `delay`, no `Timer` and no `Handler` in either module.

`teardownProblem` (`:258-259`) is held on the observer rather than emitted for the same reason Phase 2 holds it: by the time a caller can look, the stream may already be closed by the cancellation that made teardown matter. It is last-run state, reset at the start of each collection (`:291`), and — as in Phase 2 — nothing in the build enforces one observer instance per process; `di/OmniBudsBluetooth.kt:87-95` states that the rule now extends to the profile bindings and that `adapterStates` is a parameter precisely so a second `ACTION_STATE_CHANGED` receiver is not constructed behind the first platform's back.

## 13. Security and privacy

**Identifiers.** The only device identifier Phase 3 handles is the reported address, and it is held privately inside `DeviceObservationKey.AddressBacked` with a `toString()` that emits kind and length (`DeviceObservationKey.kt:50-59`). There is no getter, so redaction cannot be forgotten at a call site; `DeviceObservationKeyTest.aKeyNeverPrintsTheAddressItWraps` (`:25-39`) asserts against an address *pattern* rather than a fixture, and `theRedactedTextStatesTheKindAndTheLengthAndNothingElse` (`:131-140`) pins the exact text. Both collections use the same key type, so the guarantee covers a paired record's key as read (`DeviceObservation.kt:228`) and the second read obtains it the same way, through `ofReportedAddress` (`AndroidConnectedDeviceSource.kt:292`). Every `detail` string in Phase 3 is a fixed sentence, a count (`ConnectedDeviceObserver.kt:618`), an operation's `technicalName` (`AndroidConnectedDeviceSource.kt:359`) or a `${problem::class.simpleName}` (`:380`) — no identifier-shaped hole exists in any of them, including the four bond refusals at `:171-196`, which quote the platform's behaviour rather than anything the platform named. A framework exception's message is *not* carried, and the file says why: a platform exception text can contain a device address (`AndroidConnectedDeviceSource.kt:74-77`).

**No request, and no grant.** No code line in either module calls `requestPermissions`, holds an `ActivityResultLauncher`, or consults `shouldShowRequestPermissionRationale` — the last appears only in the comment that explains why it is not consulted (`permission/AndroidPermissionStateProvider.kt:26-31`), and `PermissionStandingReader` reads standing alone. Rule 7 bans `requestPermissions` and `requestPermission` by name in the platform module's production, **instrumented and JVM-unit** sources through one list (`DependencyDirectionTest.kt:344`, consumed at `:357` via `platformCapabilitySources()` at `:141-142`), and `ADR-P3-014`'s deferral means even the never-executed instrumented suite is written to record a refusal rather than route around it (`ConnectedDeviceObservationInstrumentedTest.kt:82-107`).

**The manifest.** Exactly one `<uses-permission>`, `android.permission.BLUETOOTH_CONNECT` (`AndroidManifest.xml:39`), amending ADR-P2-011 per ADR-P3-012; the file's own comment block (`:2-37`) records what is *not* declared and why — `BLUETOOTH_SCAN` would move the app into the Nearby devices prompt group for a feature that does not exist, the location permissions are unused because no connection-observation member mentions location (research §5.3), and the legacy install-time pair belongs to a band this module does not target. The machine check now has an allowed set of **one name** (`DependencyDirectionTest.kt:525`) rather than being relaxed, and still refuses every component. The census needed no change here and the reason is worth keeping: `getBondedDevices()` is a `BLUETOOTH_CONNECT` call on the same modern band, so the resolver's pre-computed row (`PermissionRequirementResolver.kt:104-106`) and the one declared permission already covered it — `PhaseThreeScopeTest` (`:129-149`) asserts that all three device reads plan exactly that permission and nothing else.

**The instrumented boundary.** `docs/security/device-access-policy.md` §"Phase 3: instrumented verification, authorised and bounded" (lines 88-102) was written *before* the first run: only our own `androidTest` APK may be installed, assertions are on counts, states, categories and shapes, no permission is granted by shell, and the one deliberate exposure — `RECEIVER_EXPORTED` on Bluetooth actions — is named with its reason rather than waved away. `BluetoothInstrumentedSmokeTest.theInstrumentationRunsAgainstOurOwnPackage` (`androidTest/.../BluetoothInstrumentedSmokeTest.kt:57-63`) turns "our package only" into a test rather than a promise, and `assertNoAddressLeak` (`:154-160`) plus the second suite's whole-record check (`ConnectedDeviceObservationInstrumentedTest.kt:239-251`) make the identifier rule falsifiable. `describeRound` (`:288-292`) is the only form in which a round may leave the phone: a case name, a count and a stage.

**Broadcast exposure.** Both receivers register exported from API 33 (ADR-P3-013), and the reasoning is stated at each call site rather than assumed: `protected` governs who may send, `RECEIVER_NOT_EXPORTED` governs who may hear, and the Bluetooth stack relays from its own UID, so a not-exported filter is documented to lose exactly the traffic the phase depends on (`SystemConnectedDeviceHandle.kt:393-416`, `SystemBluetoothAdapterHandle.kt:56-91`). The security cost is stated, not minimised: no third-party app can forge a protected action, so export admits no spoofing. ADR-P2-016's original flag reasoning stays as authored history with this ADR as its correction.

**Retention.** Nothing persists. The projection is process-lifetime state in a `MutableStateFlow` (`ConnectedDeviceObserver.kt:172`), unkeyed records are replaced each round rather than accumulated (§6), the refusal window is capped at eight, and ADR-P3-010's consequence — that persisting this key is a later phase's data-retention decision with its own justification — is unexercised here.

**No sink.** `diagnostics/OmniBudsLogger` is untouched by Phase 3 and ADR-P1-019's redaction duty still has no owner, so nothing in this phase can emit; the discipline that matters is therefore the type-level one above.

## 14. Extensibility toward Phases 4, 5 and 6, without claiming them

Phase 4 (sessions) gets three things: a `StateFlow` projection it may subscribe to, three axes it may translate into `state/ConnectionState` — the mapping ADR-P3-001 explicitly assigns to it — and the `arrival` field (`DeviceObservation.kt:71`) plus `RefusedDeviceTransition` (`ConnectedDeviceObserver.kt:49-56`), which are the raw material for a transition history it may own. Nothing in Phase 3 creates a `DeviceState`, a session or a revision counter, and prompt §21 stops at that line.

Phase 5 (fingerprinting) gets a joinable key and the knowledge that it is *not* identity: `DeviceIdentity` still has four nullable strings and no address field, and `DeviceFingerprint` is untouched. Phase 3 reads exactly three descriptors — `address`, `name`, `bondState` (`SystemConnectedDeviceHandle.kt:492-497`) — and calls no others: `getType()`, `getBluetoothClass()`, `getUuids()` and `getAlias()` appear nowhere in the module, which is not an oversight but the shape prompt §16 and research §5.1/§5.2 impose, since a class value is documented as a hint whose own matcher "errs on the side of false positives" and a name cache that scanning fills is cold for an app that does not scan. The handle's KDoc names the refused *fifth member* in the other direction — "pair, connect, enable, ask the device for something", each "a capability this phase forbids behind a name that sounds like a read" (`ConnectedDeviceHandle.kt:23-27`). A later phase that wants a descriptor has to add the read and the provenance label together. Phase 6 (transports) gets the `ProfileSupportReport` as a candidate-input it did not pay for: `ObservedProfile` and `TransportKind` have no mapping function, no `toTransportKind()` and no shared ordinal (ADR-P3-002), so "A2DP is connected" cannot silently become "a classic control channel exists".

The extension points Phase 3 deliberately left un-extended, each with an owner: the enumeration union as a caller-suppliable narrower list (`ConnectedDeviceObserver.kt:166`) with no mechanism to *widen* it without editing `ObservedProfile`; the profile → constant table, whose fourth member would need a new entry in both `platformConstant` and `fromPlatformConstant` (`SystemConnectedDeviceHandle.kt:580-592`); `ProfileObservationSupport`'s absent `PARTIAL` (ADR-P3-005); the `ObservationArrival` pair, which a history-owning phase may extend but which nothing here persists; and the DI seam for `adapterStates` (`di/OmniBudsBluetooth.kt:104`), which exists so the one-instance rule does not have to be reinvented. What must not extend this way is the manifest: a second permission name fails rule 11 (`DependencyDirectionTest.kt:508-532`), and a receiver outside `bluetooth/adapter/` or `bluetooth/connection/` fails rule 10 (`:449-477`).

## 15. Android platform limitations

All traceable to `connection-observation-research.md` (which carries the `[DOC]`/`[SDK]`/`[AOSP-35]` citations) or to a comment in the module that names its SDK source. None is a workaround; each is a place where the design refuses to know more than the platform permits.

- **There is no list-connected-devices call.** `BluetoothAdapter.getConnectedDevices` and `getSupportedProfiles` are absent from `android.jar` (research §3.1), and `BluetoothManager.getConnectedDevices(int)` documents and enforces `GATT or GATT_SERVER`, throwing `IllegalArgumentException` for anything else (§2e, §3). The architecture is therefore a reconciling union over a hard-coded profile list (§4), and `BluetoothAdapter.registerBluetoothConnectionCallback` — the per-device callback with a disconnect reason that would have made this unnecessary — is `@SystemApi`/`@hide` behind `BLUETOOTH_PRIVILEGED` (§4.2). Phase 3 cannot ask the handset *which* profiles exist (§3.4); it carries its own list.
- **The connection callback a normal app can reach is an aggregate edge trigger.** `BluetoothAdapter.ACTION_CONNECTION_STATE_CHANGED` fires on the 0↔1 transitions of a global counter (`updateCountersAndCheckForConnectionStateChange`, research §2b citing `[AOSP-35]` `AdapterProperties.java` l.856-908), so the second earbud of a pair produces nothing. The action is excluded from the filter by name (`SystemConnectedDeviceHandle.kt:444-446`), and the honest consequence is U-5.
- **Denial is empty, not loud.** §5 of this file is the design response; the residual is that a granted-but-still-empty result from `service == null`, a secondary user or a headless profile cannot be distinguished from a real empty room by any app-visible signal (research §6.1, §6.4). That is U-11, and it is why `unansweredProfiles` is a field rather than a comment.
- **Alias and name are cache reads with a cold-cache default.** `getName()` returns a value "from the cache" that scanning fills, `getAlias()` silently falls back to it, and both answer null "if there was a problem" (research §5.1); an observer that maps a null name to "unknown device" fabricates a device state. Phase 3 keeps the name out of every join (§7), demotes blank text at the factory, and never subscribes to `ACTION_NAME_CHANGED`/`ACTION_ALIAS_CHANGED`/`ACTION_CLASS_CHANGED` because they carry no link fact and every descriptor is re-read at the next snapshot (`SystemConnectedDeviceHandle.kt:448-451`).
- **One A2DP device per Javadoc, two entries per LE Audio pair.** `BluetoothA2dp` documents one connected device at a time while `BluetoothLeAudio` and `BluetoothHearingAid` document that "in the binaural case, there will be two different LE devices … each device will have their own connection state changes" (research §7.4). Grouping is only available through `getGroupId`/CSIS at API 33 and is U-8; there is **no** public grouping API for classic earbuds, so left/right correlation for an A2DP-only set would be our inference and Phase 3 does not make it. The engine instead does the thing that is safe under both shapes: it attributes by key and never merges two keys because they look like a pair. `getMaxConnectedAudioDevices()` is not called, so multipoint capacity (§7.4) is a number this phase declines to reason about.
- **Masking and address stability are open questions, not settled facts.** The public doc for `getAddress()` is one sentence with no privacy qualifier while the reference implementation distinguishes identity from pseudo addresses and keeps the resolver privileged (research §5.4). `getAddressType()` is API 35 and cannot inform a minSdk 26 key strategy. The design caps the blast radius rather than the claim: wrong-key behaviour degrades to a duplicate, never to a merge (§7).
- **A proxy bind is asynchronous, owns a resource, and has no error surface.** `getProfileProxy` returns a bare `boolean`, `false` for a null context or listener, for `HEALTH`, for an unsupported `HEARING_AID` and for any profile with no constructor entry — and the shipped Javadoc names `GATT` and `GATT_SERVER` as valid where the reference implementation has no constructor for either, which is U-3 (§3.3, §7.1). `closeProfileProxy` documents *fewer* profiles than `getProfileProxy` (§7.1), which is why teardown closes exactly what this instance bound (`SystemConnectedDeviceHandle.kt:249-256`). `ERROR_PROFILE_SERVICE_NOT_BOUND` exists in `BluetoothStatusCodes` but is returned by no observation call, so Phase 3 reports un-answerability as its own state rather than borrowing a code it never receives (§7.2).
- **A `SecurityException` catch would be theatre.** The dominant refusal mode is empty/silent (§6.2), so the phase's answer is ordering, not catching — and the handle suppresses lint's `MissingPermission` rather than duplicating a permission decision with a second owner (`SystemConnectedDeviceHandle.kt:100-109`).
- **Requirements key off `targetSdk`, enforcement can key off the device level, and the library declares neither.** `:platform:android` is a library, so standing is judged against `context.applicationInfo.targetSdkVersion` at runtime (`AndroidConnectedDeviceSource.kt:270-273` via `SystemTargetSdkProvider`), and an unknown target refuses the round rather than choosing a band (`AndroidConnectedDeviceSourceTest.kt:109-119`; the resolver's own `Failure(INVALID_STATE)` at `PermissionRequirementResolver.kt:63-70`).
- **Export posture was settled from documentation and awaits confirmation.** ADR-P3-013 corrected ADR-P2-016's flag choice from the platform's own receiver guidance; U-4 narrows to "confirm that adapter-state and ACL announcements actually arrive under the documented rule on this handset", and a failure to arrive becomes a platform correction with its own record rather than a code shuffle.
- **API-level floors are documentation, not permission.** `ObservedProfile.introducedApiLevel` (`ObservedProfile.kt:38-43`) is read from the SDK's own table per ADR-P2-017's discipline, and the LE Audio entry is the level of the **constant** rather than of the class — the enum holds one number and the constant is what is passed (ADR-P3-015 rule 1). Research §9 marks the distinction: the class exists at 31, the profile constant at 33.
- **`BluetoothClass` proves nothing about earbuds, so no such field exists.** The shipped class doc calls it a hint that "does not reliably describe which profiles or services are actually supported" and its own matcher "errs on the side of false positives" (research §5.2); `DeviceObservation` has no class, type or UUID field, and the KDoc names the temptation (`DeviceObservation.kt:30-37`).
- **OEM variance is unmeasured.** Every `[AOSP-35]` finding above is one implementation of one release (§7.4, §0.3), and `docs/security/device-access-policy.md:84-86` records that no Phase 2 class ever executed on a device. Nothing in this file is verified on hardware.

## 16. What enforces what, and with what test surface
