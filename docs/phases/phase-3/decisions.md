### ADR-P3-001 — Platform link state, bond state and availability are three axes, not one enum
**Status.** accepted
**Context.** Prompt §6 requires a model that distinguishes `BONDED, CONNECTED, DISCONNECTED, CONNECTING, DISCONNECTING, UNKNOWN, UNAVAILABLE`, and calls the paired-versus-connected split mandatory. The repository already has `com.omnibuds.core.state.ConnectionState` (`state/ConnectionState.kt:15-27`) with `UNKNOWN, DISCOVERED, PAIRED, CONNECTED, IDENTIFYING, CAPABILITY_DISCOVERY, READY, CONTROL_SESSION, DISCONNECTED, TEMPORARILY_UNAVAILABLE, ERROR`, an enforced transition table (`ConnectionStateTransitions`, `:40+`) and an `isOperational` predicate — and its KDoc says `IDENTIFYING` and `CAPABILITY_DISCOVERY` are "OmniBuds' own work". That is a *session* position. Android reports a *link* fact, knows `CONNECTING`/`DISCONNECTING`, and has never heard of `READY`.
**Decision.** Three independent axes, all in the `platform` area. `DeviceConnectionState` {`UNKNOWN`, `CONNECTING`, `CONNECTED`, `DISCONNECTING`, `DISCONNECTED`} carries only the link. `DeviceBondState` {`UNKNOWN`, `NONE`, `BONDING`, `BONDED`} carries only pairing, so a bonded-and-disconnected device — the normal case — is expressible without inventing a compound member. `DeviceAvailability` {`UNKNOWN`, `AVAILABLE`, `UNAVAILABLE`} carries whether the platform would tell us about this device at all, which §6's `UNAVAILABLE` actually means: it describes our ability to observe, not the link's condition. None of the three has a default value, and `UNKNOWN` is never rendered as `DISCONNECTED` or `NONE` (ADR-P0-016). The name `ConnectionState` is deliberately not reused for the link axis: two types with one name in two areas is the "same fact modelled two ways" error Phase 1 prompt §24 and ADR-P1-004 exist to stop, and the distinction has to live in the name rather than in a package path.
**Alternatives considered.** Extend `state.ConnectionState` with `CONNECTING`/`DISCONNECTING` — rejected: it edits a Phase 1 type whose transition table, `isOperational` semantics and tests are settled, and it would put a platform fact in the same field as a product-work state, so no consumer could tell which one changed. One flattened enum with `BONDED_NOT_CONNECTED` and `UNAVAILABLE` members — rejected: every transition would have to guess which of three facts moved, and the prompt's mandatory distinction becomes an inference. Map platform states straight onto `ConnectionState` values — rejected: it fabricates session progress, which is exactly how "connected" comes to be reported as "supported".
**Consequences.** Translating these three axes into a session `ConnectionState` is Phase 4's work, and Phase 3 creates no `DeviceState` and no session (prompt §21). A machine check keeps the axes apart: no `DeviceConnectionState` value may be coerced into `ConnectionState` inside `:core`, and the observation types must not import `session` (the layer map already forbids the edge — `platform` is 1, `session` is 3 — so the rule is enforced arithmetically, not by goodwill). `isProvablyDisabled()`'s Phase 2 precedent — a predicate that distinguishes "positively off" from "not observed" — is the pattern the new axes' predicates follow.

### ADR-P3-002 — Android profile observations do not enter `TransportKind`
**Status.** accepted
**Context.** Prompt §7 puts `observedProfiles` on the observation model, and §12 requires handling multiple profiles per device without duplicating the device. The obvious-looking reuse is `common.TransportKind` (`common/TransportKind.kt`: `BLE, GATT, RFCOMM, CLASSIC_BLUETOOTH, LE_AUDIO, VENDOR_SPECIFIC, UNKNOWN`), which ADR-P2-013 just spent an ADR separating BLE from GATT over. A profile axis is different again: A2DP, HEADSET/HFP, HID, HEALTH, PBAP and friends are *system services that hold connections*, not channels OmniBuds could open, and `TransportKind` is pinned to transport boundaries by `TransportKindPinningTest`.
**Decision.** A new `platform` enum for the profile axis, whose members name what Android reports and carry the API level each was introduced at, read from the SDK's own API table rather than from memory — the discipline `AndroidPlatformCapabilityProvider`'s companion comments established (ADR-P2-017). It has no relationship to `TransportKind` in code: no mapping function, no `toTransportKind()`, no shared ordinal. Where a later phase needs to reason from "A2DP is connected" to "classic audio exists on the host", it will state that as a policy decision in that phase, with its own evidence.
**Alternatives considered.** Reuse `TransportKind` — rejected: it would claim that observing an audio profile implies something about a control channel, which is the conflation ADR-P2-013 and master §8 were written to prevent, and `A2DP` is not even a member, so the mapping would silently drop information. Reuse `PlatformFeature` (`platform/PlatformFeature.kt`), which already has `A2DP_CONNECTION_STATE` and `HEADSET_CONNECTION_STATE` members — rejected: that enum answers *host* capability ("could this phone expose it at all"), and prompt §5.5/ADR-P2-008 keep host facts and device facts apart; putting a per-device profile observation there would make the capability report mean two different things depending on who filled it in.
**Consequences.** Two profile-shaped enums now exist and must never merge; the difference is stated in both files' KDoc, because a reader who finds `A2DP` in one place will assume it is the same `A2DP`. `PlatformFeatureSupport`'s per-feature evidence tiers stay untouched — Phase 3 reports what it observed, not what it verified about the host. `transport-boundaries.md` gains a short note recording that the profile axis is not a transport.

### ADR-P3-003 — Observation vocabulary lives in `platform` at layer 1; no 13th area
**Status.** accepted
**Context.** Phase 3 introduces a source seam, an observation model, an observation key, a stage/health type and a reconciliation engine. The layer map (`DependencyDirectionTest.kt:33-48`) registers 12 areas, and prompt §5 forbids creating structure that would be empty or meaningless. Two placements were live: a new `observation` area, or the existing `platform` area, which Phase 2 established as "host-side platform facts read through an injected seam".
**Decision.** Everything Phase 3 adds to `:core` goes into `platform`, layer 1. This mirrors the one precedent that demonstrably works: `AdapterStateSource` + `AdapterStateChangeChannel` + `AdapterStateObservation` + `AdapterStateObserver` are all in `platform`, and a device observation is the same *kind* of thing — a platform fact, obtained through a seam, deduplicated, timestamped, expressed with `OperationOutcome`. Layer 1 keeps the observation types below `device` (2), `session` (3) and `persistence` (3), which is exactly where an input to those layers belongs, and lets them import `common` (0) and `state` (0) without an upward edge.
**Alternatives considered.** A new `observation` area at layer 1 — rejected: 12 files is not a boundary, it is a folder with a registration cost, and `everyCoreAreaIsRegisteredInTheLayerMap` plus ADR-P2-001's refusal of a `:bluetooth` module set the precedent that areas are earned by *different dependency shapes*, not by different nouns. Put `DeviceObservation` in `device` (2) next to `DeviceIdentity` — rejected: `device` holds who a device *is* (identity, fingerprint, session, firmware), and Phase 3 must not write into `DeviceFingerprint` (prompt §16 bans fingerprinting); placing a platform-derived observation there would invite exactly that, and would let layer-2 identity types depend on layer-1 observation types in a direction nothing forbids. Put it in `session` (3) — rejected: sessions are Phase 4 and the prompt's stop condition names it.
**Consequences.** The `platform` area roughly doubles, which `architecture-audit.md` §7 flags as the honest cost: the area now holds two distinct subject matters (host facts, device-adjacent facts) and its KDoc has to say so or a newcomer will read `platform` as "the adapter stuff". A future phase that wants a real boundary must propose it with a different dependency shape, not with a bigger folder. No new Gradle module is created, so ADR-P1-001 and ADR-P2-001 stand unchanged.

### ADR-P3-004 — `ConnectedDeviceSnapshot` — a projection is not a `Repository`
**Status.** accepted
**Context.** Prompt §14 sketches `interface ConnectedDeviceRepository { val connectedDevices: Flow<…>; val observationState: StateFlow<…>; suspend fun refresh() }`. In this codebase `Repository` already has a settled meaning: `persistence/DeviceRepository.kt:30` and `persistence/CapabilityRepository.kt:32` are storage contracts, and master §32/Phase 1 prompt §25 introduced the word to keep callers away from storage. Prompt §10 separately forbids Phase 3 from persisting anything, and §16 forbids a saved-device database.
**Decision.** The §14 abstraction is named `ConnectedDeviceSnapshot` (the current projection) plus the observer that produces it, and it lives in `platform` at layer 1. It stores nothing: no disk, no process-death-surviving cache, no history. The prompt's `refresh()` becomes a suspend function that re-reads and re-publishes, and its result is typed, because a refresh that "succeeds" while returning nothing must not read as a successful observation of zero devices.
**Alternatives considered.** Keep the prompt's name — rejected: it would put a second, non-persistent `Repository` in the same dependency graph as the persistence contracts, and the one thing a name like that must do is be unambiguous about whether data is stored. Adopt `ConnectedDeviceStore` or `…Cache` — rejected: both imply retention, which §10 forbids, and a reader would have to check. Rename the persistence types instead to free the word — rejected: that edits Phase 1's settled vocabulary to accommodate a newcomer, which is the wrong direction for a correction.
**Consequences.** The prompt §14 conceptual sketch is recorded as adapted rather than reproduced, the way ADR-P2-013 recorded the `BleTransport` disagreement. Any later phase that *does* persist devices must introduce that under `persistence` with its own contract, and will find the naming already honest.

### ADR-P3-005 — Failure never becomes an empty list: `ObservationStage` and a typed outcome
**Status.** accepted
**Context.** Prompt §14: "Do not represent failure as an empty device list. An empty list means the observation completed successfully and no devices are currently reported." Phase 2 met the identical hazard at the adapter layer and answered it with a three-valued `ApiAvailability` plus `OperationOutcome`, and ADR-P2-012 recorded that Android returns falsy/empty values that are indistinguishable from a real negative. Phase 3 faces the sharper version: a denied `BLUETOOTH_CONNECT` may produce exactly the empty collection that means "nobody is connected".
**Decision.** Two separated answers. `ObservationStage` {`NOT_STARTED`, `OBSERVING`, `STOPPED`} describes where the observer's lifecycle is. Whether an observation round *produced a trustworthy answer* is carried by the outcome, which reuses `OperationOutcome` and its existing categories: `Success(snapshot)` — and only then may the device list be empty — `Failure(error)` for permission, adapter, platform or unsupported causes, and `Cancelled` for a called-off read, kept as cancellation rather than relabelled (ADR-P2-018). "Permission required", "Bluetooth disabled" and "Unsupported" from §14's list are therefore *failure facts with categories*, not lifecycle stages: putting them in the stage enum is how an app ends up rendering "disabled" as a state of the world rather than a statement about what we were allowed to see.
**Alternatives considered.** Fold the failure causes into `ObservationStage` to match §14's list literally — rejected: it satisfies a bullet by building the exact confusion that bullet exists to prevent, and it would give two representations for "we could not look" (the stage and the outcome), which Phase 1 prompt §24 forbids. Add a `Partial` outcome meaning "some profiles answered, some did not" — rejected for Phase 3: whether Android actually makes a *partial* enumeration observable is a research question, and an enum member invented before the platform answers is the DEDUPED mistake repeated (ADR-P2-018).
**Consequences.** §11's adapter-disablement rule ("do not claim physical power was turned off unless known") becomes expressible: the projection can be emptied by an *observation* of the adapter going down while the stage stays `OBSERVING`, and a consumer reading only the list cannot tell the two apart — which is the point of making the outcome typed rather than inferring from content. A test asserts the invariant directly: a failure outcome and an empty successful snapshot are distinguishable values, not the same value reached two ways.

### ADR-P3-006 — No new error category; observation failures reuse three existing ones
**Status.** accepted
**Context.** Prompt §15 lists nine error shapes. Phase 2 widened the set to 23 categories under ADR-P1-006's union rule, and `theCategorySetIsExactlyTheDocumentedOne` plus the two exhaustive retry/invalidation tables (ADR-P2-005) mean any new member has to be decided in three places and pinned in a table. The temptation in a new layer is to add `DEVICE_OBSERVATION_FAILED` and `PERMISSION_REVOKED` because they *sound* specific.
**Decision.** Add nothing. Map §15's list onto what exists: permission denied → `PERMISSION_DENIED`; adapter disabled → `BLUETOOTH_DISABLED`; Bluetooth unavailable → `ADAPTER_UNAVAILABLE`; unsupported operation → `UNSUPPORTED_OPERATION`; receiver registration failure → `RESOURCE_UNAVAILABLE` (the Phase 2 precedent for "a registration could not be made", already carrying `RETRY_AFTER_REREAD` and `invalidatesSession = false`); observation failure → the underlying cause's category, or `PLATFORM_EXCEPTION` when the platform threw; device information unavailable → `UNKNOWN`-shaped *state*, not an error at all, because "this device's name is not readable" is a fact about a field, not a failed operation; operation cancelled → `OperationOutcome.Cancelled`, never a category (ADR-P1-004); unknown platform exception → `PLATFORM_EXCEPTION` / `UNKNOWN_FAILURE` per ADR-P2-004's existing split.
**Alternatives considered.** Add `DEVICE_NOT_FOUND` — rejected: `UNKNOWN_DEVICE` already exists from Phase 1 and means exactly this; two names for one failure is how a retry table ends up disagreeing with itself. Add `PERMISSION_REVOKED` distinct from `PERMISSION_DENIED` — rejected on evidence *and* on structure: Phase 2's research Q5 found revocation kills the process rather than delivering an in-process signal, so the distinction would be a category with no producer, which is ADR-P2-004's refused `ADAPTER_STATE_UNKNOWN` in a new costume.
**Consequences.** §15's list being longer than the category set is now a recorded fact rather than an unimplemented requirement. Five of its shapes are pinned by named assertions on the categories this phase actually produces - `PERMISSION_DENIED` and `RESOURCE_UNAVAILABLE`, `PLATFORM_EXCEPTION` and `ADAPTER_UNAVAILABLE` in `AndroidConnectedDeviceSourceTest`, `BLUETOOTH_DISABLED` and `RESOURCE_UNAVAILABLE` in `ConnectedDeviceObserverTest` - and `theCategorySetIsExactlyTheDocumentedOne` holds the set at 23, so a new member cannot be added by accident. Two shapes have no Phase 3 producer: "unsupported platform operation" resolves to `UNSUPPORTED_OPERATION` only if a later phase asks for a profile the running Android cannot name, and "device information unavailable" is a state, not an error, by this decision's own reasoning. *Amended 2026-10-02: an earlier draft of this paragraph claimed a test walked all of §15's shapes to a category. It does not exist, the finding came from the requirements workstream, and the claim above is what the tree supports.*

### ADR-P3-007 — Instrumented verification lives in the boundary module, with five test-only coordinates
**Status.** accepted — user-selected route
**Context.** Phase 2 closed with every Android claim capped at `IMPLEMENTED` and four `System*` classes that no test had ever executed (`validation.md` known issues 1 and 2). Asked how Phase 3 should handle that, the user chose **instrumented tests on the phone** over a JVM-only phase or a new debug host app. The audit then measured what that actually costs on this workstation: `platform/android/src` contained `main` and `test` only, `platform/android/build.gradle.kts` declared no `testInstrumentationRunner`, and `androidx.test` was absent from the Gradle cache — while `google()` answered HTTP 200, so the offline habit had been a choice rather than a constraint. `:tools:companion-shell` cannot host these tests: ADR-P2-010 exists precisely because it must never import product code, so a green run there could never be evidence about OmniBuds.
**Decision.** Verification runs against `:platform:android`'s own `androidTest` source set. Five coordinates enter the build, all `androidTestImplementation` and none visible to `src/main`, `src/test` or `:core`: `androidx.test:runner:1.6.1`, `androidx.test:core:1.6.1`, `androidx.test.ext:junit:1.2.1`, `junit:junit:4.13.2` and `kotlin-test`. JUnit 4 is present because Android's runner and `ext:junit` are JUnit4-based; the project's JVM suites stay on Jupiter and the two never share a source set, so no test in this repository has to guess which framework it is in. Versions were chosen as a coherent set from `google()` rather than latest-available, and each POM was confirmed reachable before it was named in the catalog. `testInstrumentationRunner` is `androidx.test.runner.AndroidJUnitRunner`. The first suite asserts four things and nothing else: the instrumentation targets `com.omnibuds.android` and no other package; `BluetoothManager` is obtainable; an adapter-state read answers — and is checked to be coherent against the handle's own presence report; and standing reads return no unreachable state for any of the six permissions. Two prohibitions are enforced by the file's shape rather than by review: there is no permission-request call anywhere in the module, and every diagnostic string passes a MAC-shaped-pattern check, because SEC-LOG-002's redaction duty needs a form a test can fail.
**Alternatives considered.** A new debug-only host application — rejected: it duplicates what the user already has in the harness shell, adds a sixth module, and the tests would still have to live next to the code they exercise. Robolectric — rejected: it emulates the framework without emulating the Bluetooth stack, which would convert "never executed on hardware" into "executed against a simulation of hardware", a worse claim than the honest one. `adb shell` inspection of the phone's Bluetooth service from the host — rejected outright: `dumpsys bluetooth_manager` reports the system's and other apps' data, and the device-access policy permits this workstream only our own package.
**Consequences.** Three things this project had been able to say stop being true, and are recorded as such rather than quietly kept. `REQ-P2-020`'s statement that the test foundation is "plain JVM in both modules" becomes a Phase 2 snapshot, not a standing property. `docs/phases/phase-1`'s reproducibility claim now requires one online resolve of these five coordinates before `--offline` works on a fresh machine. And the architecture guards scan `src/main` only, so `src/androidTest` is not covered by the capability token list — an instrumented test could in principle reach a Phase 3-forbidden API and pass every check; the guard gap is real, and closing it is a Phase 3 decision rather than a Phase 4 surprise. Whether the phone is attached is now a build-adjacent fact: `compileDebugAndroidTestKotlin` runs anywhere, `connectedDebugAndroidTest` runs only with the user's handset connected and authorised, and no Phase 3 result may be reported from the former.


### ADR-P3-008 — Event-driven observation reconciled with a proxy snapshot, because the platform has no list-connected-devices call
**Status.** accepted
**Context.** Re-verified against the SDK rather than taken from the research summary: `BluetoothManager.getConnectedDevices(int)` documents `@param profile GATT or GATT_SERVER` and `@return List of devices. The list will be empty on error`; `BluetoothAdapter.getConnectedDevices` and `getSupportedProfiles` are absent from `android.jar` entirely; and `BluetoothProfile` carries `getConnectedDevices` and `getDevicesMatchingConnectionStates`, reachable only through a proxy from `getProfileProxy`. Meanwhile the broadcasts a normal app may receive — `ACTION_ACL_CONNECTED`, `ACTION_ACL_DISCONNECTED`, `ACTION_BOND_STATE_CHANGED` and the per-profile `ACTION_CONNECTION_STATE_CHANGED` — are public and not `@SystemApi`, with `BLUETOOTH_CONNECT` as the receiver permission.
**Decision.** Observation is event-driven first and reconciled second: the engine listens for ACL and profile connection-state changes, and takes an initial snapshot by unioning `getDevicesMatchingConnectionStates` across a **hard-coded profile list** held as a named value with the API level each entry was introduced at. No polling, no timer, no background service (prompt section 8). The profile list is a maintained decision, not an accident of the API: every profile not in it is a class of connection Phase 3 will not see, so the list carries its own reason per entry and the device session asks a human to check it against a handset. A proxy that never binds yields `DeviceAvailability.UNAVAILABLE` for that profile — never an empty device list, and never a silent skip.
**Alternatives considered.** Snapshot-only with periodic refresh — rejected twice over: prompt section 8 forbids aggressive polling, and a refresh interval is a guess at how fast a user can connect earbuds. Manifest-declared receivers — rejected: only a subset of these actions arrive that way, and a manifest entry is a component, which the boundary manifest check refuses and ADR-P2-011 forbids. `BluetoothAdapter.getRemoteDevice` from a remembered address — rejected: that invents a device the platform never reported.
**Consequences.** `getProfileProxy` is asynchronous and owns a binding that must be released, so the engine inherits a cleanup obligation Phase 2 never had and its teardown must be idempotent for the same reason the receiver registration's is. The research records U-6 (whether binding a proxy has side effects on the audio path) as UNVERIFIED and prompt section 17 forbids altering audio, so the proxy list is the first thing a device session must watch; a proxy that cannot be cleared is a reason to fall back to ACL-only observation with the profile axis reported as unobservable rather than absent.

### ADR-P3-009 — Permission standing is consulted before enumeration, because Android makes a refusal indistinguishable from an empty room
**Status.** accepted
**Context.** The sharpest finding in the research, and the platform's own Javadoc states it: `getBondedDevices()` and the GATT enumeration return an empty list on a permission failure, `getProfileConnectionState` returns `STATE_DISCONNECTED`, and broadcasts are silently undelivered — the only `SecurityException` in the whole surface is the legacy `targetSdk < 31` branch of `getProfileProxy`. Prompt section 14 requires that failure never be represented as an empty device list. The platform cannot satisfy that requirement, because it answers both questions with the same empty collection.
**Decision.** Ordering is the mechanism. Before any enumeration or registration, the source resolves permission standing for the operation it is about to perform through Phase 2's resolver and provider, and anything other than a grant (or `NOT_REQUIRED`, which no Phase 3 operation can produce) returns `ObservationRound.Failure` with `PERMISSION_DENIED`. The engine never asks the platform how many devices there are while it is not permitted to look, so an empty list can only ever arrive from a round that was allowed to see. A broadcast stream that produces nothing while standing is granted is a different finding and is reported as one rather than as zero devices, which is exactly what U-4 exists to distinguish on a real handset.
**Alternatives considered.** Trust the empty list and treat permission as a UI concern — rejected: it is the failure prompt section 14 names, in its most user-hostile form, because the app would say "no devices connected" to a user whose permission was refused. Try the call and catch `SecurityException` — rejected on evidence: the platform does not throw in the modern band, it returns empty, so the catch would never fire and the design would look defensive while being blind. Ask the user for the permission from the observer — rejected: section 13 forbids a background component prompting, and ADR-P3-007 keeps the instrumented suite free of any request call.
**Consequences.** Permission inspection becomes load-bearing rather than courteous, and a standing read returning `UNKNOWN` must refuse the round too — refusing to look is honest where reporting zero is not. The rule is testable without a radio, which is the point: a fake source that never answers a permission question fails the build, so no later phase can reintroduce the confusion by reordering the calls.

### ADR-P3-010 — `DeviceObservationKey` carries the address, redacts itself, and is the only join criterion
**Status.** accepted
**Context.** Prompt section 9 wants stable device keys and duplicate prevention; section 12 forbids merging two devices because they share a display name; section 13 forbids exposing Bluetooth addresses in ordinary logs. An app holding `BLUETOOTH_CONNECT` receives the real device address, so the key is genuinely identifying data — and it cannot be wished away by not storing it, because without it there is no way to join a broadcast to a snapshot entry or to tell two earbuds with identical names apart.
**Decision.** A sealed key type with an explicit `kind` — address-backed or absent — where absence is a value and not null. Equality and hashing are the sole join criterion, and `toString()` emits the kind and a length, never the identifier, so redaction is a property of the type rather than a convention every call site must remember. Name-matching as identity is prohibited by the shape: the observation carries a display name as a separate nullable field that participates in no equality.
**Alternatives considered.** A bare `String` key — rejected: it would leak into logs through interpolation with nothing to stop it, which is the lesson ADR-P2-015 and SEC-LOG-002 already paid for. A hash of the address — rejected for Phase 3: it remains a stable per-device identifier so it buys no privacy inside the local process, and it would break the join if a later phase legitimately re-derives the key from another source. A per-app masked identifier — rejected on scope: that is the BLE-scanner-side construct, and Phase 3 does not scan.
**Consequences.** Any future persistence of this key is a data-retention decision for a later phase with its own justification, and `DeviceIdentity` deliberately gains no field for it: a platform address is not identity (audit section 6), and letting the two meet in one type is how an address ends up shown to a user.

**Amended by ADR-P3-015, on the word "equality".** This decision's sentence saying a display name "participates in no equality" was read literally by the implementation and is narrower than what was meant. Prohibiting the name from `equals` would make two records of one device compare unequal whenever the platform refreshed its alias, which breaks any consumer that diffs a projection; the join rule, not the data-class comparison, is the thing that must exclude the name. ADR-P3-015 states the distinction, and `mergedWith` refusing on a key that cannot join is what enforces it.

### ADR-P3-011 — Bluetooth receivers must not declare themselves un-exported, and Phase 2's choice stays open until a handset answers
**Status.** accepted for Phase 3 — **settled and extended by ADR-P3-013**; the "stays open" half of this title no longer stands, because the platform's own receiver-export guidance resolved it against Phase 2 before any device was involved. Kept as authored because it records the reasoning that got here, including the part that was right (a filter that cannot receive is the worse failure) and the part that was parked (whether the flag actually governs these actions).
**Context.** The export-flag analysis (research section 4.3) found an asymmetry Phase 2 recorded and then resolved in the wrong direction for Bluetooth: the flag rule keys on whether a receiver listens for *non-system* broadcasts, and these announcements come from the Bluetooth stack's own UID rather than from system server. A receiver declaring `RECEIVER_NOT_EXPORTED` may therefore never be delivered the events Phase 3 depends on. Phase 2 chose `RECEIVER_NOT_EXPORTED` for `ACTION_STATE_CHANGED` on the reasoning that it is a protected system broadcast, and shipped that with a lint suppression for the flag-less pre-33 branch.
**Decision.** Phase 3 registers its receivers with no export flag below API 33 and with `RECEIVER_EXPORTED` from 33 up, and records the reason at the call site: a filter that cannot receive is worse than a filter that could receive from one known system component, because the silent failure is indistinguishable from "nothing happened" — the same hazard ADR-P3-009 exists to close. Phase 2's choice is **not** rewritten here. It is carried as a named device-session step: observe whether an adapter-state announcement reaches a not-exported receiver on a real handset, and if it does not, that delivery becomes a documented platform correction with its own ADR and the flag becomes exported with the reasoning stated. Deciding it now in either direction would be guessing with a security posture attached.
**Alternatives considered.** Flip Phase 2's receiver to exported for consistency — rejected: it loosens a guard on a hunch, and ADR-P2-016 exists precisely so broadcast posture is reasoned about rather than aligned. Keep not-exported everywhere and accept the risk — rejected: it would produce an observation engine that reports an empty room forever on some devices and looks correct doing it. `ContextCompat.registerReceiver` — rejected as in ADR-P2-016: the module's first AndroidX dependency for no behavioural gain, and the flag value is the decision, not the helper.
**Consequences.** The boundary module now has two receivers with deliberately different flags, each with a stated reason, and `RECEIVER_EXPORTED` on a Bluetooth action is a documented exposure with a named sender rather than an oversight. The open finding is recorded in the Phase 3 risk register as an entry whose only arbiter is the phone.

### ADR-P3-012 — `BLUETOOTH_CONNECT` is the only manifest entry this phase earns, and the guard learns exactly one allowed name
**Status.** accepted — amends ADR-P2-011
**Context.** ADR-P2-011 kept both module manifests empty because Phase 2 needed no permission. Phase 3 calls APIs whose own Javadoc names `BLUETOOTH_CONNECT` as required — the bonded list, the profile enumerations, the connection-state broadcasts — and ADR-P3-009 makes reading its standing load-bearing rather than courteous. Prompt section 13 forbids bypassing runtime permissions, and an undeclared permission is not a bypass but a refusal the app has chosen for itself.
**Decision.** Exactly one `<uses-permission>` is added, in `:platform:android`, with its reason beside it. `BLUETOOTH_SCAN` is not declared, because Phase 3 does not scan and declaring it would move the app into the Nearby devices prompt group for a feature that does not exist — over-declaration being expensive for exactly the reason ADR-P2-011 gave: a library manifest merges silently into every consumer. The location permissions stay undeclared, since nothing here is location-derived. `platformManifestDeclaresNothingUnjustified` gains an allowed set of one rather than being relaxed, and keeps refusing any component and every other permission name.
**Alternatives considered.** Declare it in a future application module and leave the library clean — rejected: a library that calls permission-gated APIs without declaring the permission hands its consumer a mystery, and the library is where the call lives. Declare `BLUETOOTH` and `BLUETOOTH_ADMIN` as well for the legacy band — rejected on the resolver's own analysis: those are install-time permissions the modern band ignores, Phase 3 targets the modern model, and if the legacy band is ever supported its rows already exist and that phase declares them with its own justification.
**Consequences.** The boundary manifest is no longer empty, so the audit's "declares nothing" property becomes "declares exactly what is cited" — the stronger claim, and machine-checked. Every consumer of the library now inherits one Nearby devices permission on install, stated plainly because that is the cost ADR-P2-011 accepted in the other direction and no reader should have to rediscover it.

### ADR-P3-013 — Bluetooth receivers are exported, including Phase 2's, and ADR-P2-016's flag choice is corrected
**Status.** accepted — supersedes the flag reasoning in ADR-P2-016 and settles ADR-P3-011's open finding
**Context.** ADR-P3-011 accepted exported receivers for Phase 3's connection events while leaving Phase 2's `RECEIVER_NOT_EXPORTED` on `ACTION_STATE_CHANGED` to be decided by a handset. Checking that open question against the platform's own words resolved it before any device was involved, and resolved it against code already committed and pushed. `developer.android.com/develop/background-work/background-tasks/broadcasts`, in its context-registered receiver guidance, states the rule in two sentences that decide the matter:

> "If this receiver is listening for broadcasts sent from the system or from other apps—even other apps that you own—use the `RECEIVER_EXPORTED` flag."

> "To receive all system broadcasts, including broadcasts from highly privileged apps, flag your receiver with `RECEIVER_EXPORTED`." — and, conversely, "If you flag your receiver with `RECEIVER_NOT_EXPORTED`, the receiver is able to receive some system broadcasts and broadcasts from your app, but not broadcasts from the highly privileged apps," the page naming Bluetooth as an example of a highly privileged framework app.

Phase 2 chose `RECEIVER_NOT_EXPORTED` on the reasoning that `ACTION_STATE_CHANGED` is a protected system broadcast, and lint's own message was quoted back as permission ("register with `RECEIVER_NOT_EXPORTED` to protect your receiver on all platform releases"). Both readings were half right. Protected — in AOSP's `core/res/AndroidManifest.xml`, verified this session against tag `android-15.0.0_r11` — are `android.bluetooth.adapter.action.STATE_CHANGED`, `...CONNECTION_STATE_CHANGED`, `android.bluetooth.device.action.ACL_CONNECTED`, `...ACL_DISCONNECTED`, `...BOND_STATE_CHANGED` and the LE Audio, CSIS, A2DP, HEADSET, HEARINGAID and HIDDEVICE connection-state actions. So no third-party app can forge them, which is the property that made "not exported" feel safe. But being protected governs *who may send*, and the export flag governs *who may receive* — and a broadcast relayed by the Bluetooth stack is exactly the privileged-app traffic that a not-exported filter is documented not to receive. The two facts were being read as one.
**Decision.** Both receivers in `:platform:android` register with `RECEIVER_EXPORTED` from API 33, and with no flag below 33, where the overload does not exist. Phase 2's adapter-state receiver is corrected in this phase rather than left to fail silently on a user's phone, because the documentation is explicit and the failure mode is the one this phase has spent three ADRs refusing to accept: an observation that reports nothing and looks correct doing it. The security cost is close to zero and is stated rather than waved away: the actions are protected, so export admits no spoofing; a sender would have to hold the Bluetooth stack's own privileges. `RECEIVER_NOT_EXPORTED` is retained for nothing in this module, and the lint suppression on the pre-33 branch stays for its original reason.
**Alternatives considered.** Keep Phase 2's flag and let the device decide — rejected once the documentation was read: leaving a known-likely-broken receiver in place while waiting for confirmation is choosing the comfortable answer twice over, once in code and once in the record. Register both flag-free (the pre-33 form) on every release — rejected: that is the state lint warns about and it leaves the export decision to a default. Use `ContextCompat.registerReceiver` — rejected as before (ADR-P2-016): the flag value is the decision, not the helper. Restrict with a sender permission instead of an export flag — rejected on evidence: no documented signature-level permission identifies these broadcasts to a receiver, and inventing one would be a second fabrication of the same class.
**Consequences.** ADR-P2-016's flag reasoning is now wrong in its own text and stays there as authored history, with this ADR as the correction indexed in `docs/decisions/README.md` — the same treatment ADR-P2-009 gave Phase 0's `SEC-PERM-002`. Device-session step for U-4 changes character: it is no longer "decide which flag is right" but "confirm that adapter-state and ACL announcements actually arrive under the documented rule on this handset", and a failure to arrive becomes a platform correction with its own record rather than a code shuffle. The Phase 2 known issue that described `ACTION_STATE_CHANGED` delivery as unverified now has a documented expectation to be tested against, which is progress of a kind: the claim became falsifiable.

### ADR-P3-014 — Device verification is deferred out of every phase's completion criteria; application building comes first
**Status.** accepted — user directive, 2026-10-01, standing from the next prompt onward
**Context.** The user had selected instrumented tests on the phone as Phase 3's verification route (ADR-P3-007), and the scaffolding was built and committed: an `androidTest` source set, an instrumentation runner, five test-only coordinates, and a first suite that compiles cleanly. They then changed the sequencing for the project as a whole — build the entire application first, and take up physical-device testing, marketing and design at the end. Asked specifically whether to delete the device-test scaffolding that now sits in the tree, they chose to keep it and simply stop gating on it. Leaving that decision implicit would have been the worse failure: it changes what "phase complete" means, and an ADR index is where a change to a completion criterion belongs, not in a commit message.
**Decision.** A phase is complete on the evidence it can produce without a handset: JVM unit tests, architecture and scope guards, lint, and a build that runs to completion. Where a claim can only be settled on real hardware, it is recorded as **deferred and UNVERIFIED**, with the deferred items collected in one place so the end-of-project device session is a list to execute rather than an archaeology exercise. Physical verification is removed from Phase 3's acceptance criteria for the two items that needed a phone — prompt section 19's ten-step manual validation, and the U-4 export-flag confirmation ADR-P3-013 raised — and both move to the deferred list. **Alternatives considered.** Delete the scaffolding to keep the build surface minimal — rejected by the user when asked directly; it removes nothing that ships and re-adds work at the end. Treat Phase 3 as incomplete until the phone returns — rejected: that is the failure mode the directive exists to prevent, and it would also stall Phases 4 onward behind an idle dependency. Keep claiming device parity in prose while never testing — rejected outright, and this is the sharp edge: deferral is only honest if the unverified stays visibly unverified. **Consequences.** Every phase prompt after this one is executed under the same rule without needing to restate it. The ADR-P3-013 correction keeps its value: it was made from documentation, so it needed no device, and the deferred session's job narrowed to confirming a documented rule rather than choosing one.

### ADR-P3-015 — Twelve rules the observation engine had to settle, and the one the orchestrator overrode
**Status.** accepted
**Context.** ADR-P3-001 through -014 fix the axes, the seams and the prohibitions, but they do not say what the engine does in the cases where the platform's answers arrive from different mechanisms at different times and disagree. The implementation reached twelve such decisions that no ADR covered; each is recorded here rather than left discoverable only in code, because each one is a claim about a device that a later phase will rely on. One of the twelve was changed on review, and that one is recorded with its reason.
**Decision.** The rules, as now implemented and tested:

1. **The profile union is seven entries, not the platform's whole list** — the audio and assistive profiles whose proxy types are public, plus GATT and HID, each carrying its own reason and the API level at which its constant arrived. LE Audio carries the level of the *constant* rather than of the class, because the enum holds one number and the constant is what is passed. Excluded with reasons: the deprecated health profile, profiles with a public constant but no public proxy type, the server role, and anything absent from the compile SDK. The list is a maintained decision (ADR-P3-008) and its exclusions are the part a reader would otherwise assume were oversights.
2. **The link state is derived from the profiles that currently report a live link**, because one field cannot say which service is in which state. Consequence accepted and documented rather than papered over: while one profile still holds a link, a second profile's `CONNECTING` is not observable, and there is no per-profile link map.
3. **A link-layer disconnect clears the whole profile set** — the one inference the layer makes, about the transport hierarchy rather than about a device, and the reason `LinkChanged` may carry no profile at all.
4. **An absent device in a snapshot means `DISCONNECTED` only when every profile in the union answered.** A profile that declined cannot withdraw a link it never reported, which is the fold-side counterpart of ADR-P3-008's per-profile rule.
5. **A completed round restores `availability = AVAILABLE` on carried records**, because otherwise a single adapter cycle would leave a device permanently unobservable after a good re-read — a stale `UNAVAILABLE` is a claim, not a caution.
6. **Unkeyed records are replaced by each snapshot and never carried forward.** There is nothing to recognise them by, so carrying them would accumulate a shadow population of devices nobody can attribute (ADR-P3-010); they are visible within a round, and that is the honest extent.
7. **A `Success` carrying no devices from a union where nothing answered is refused** — an empty list there is a statement about the observation, not about any device. Reclassified on review from `UNSUPPORTED_OPERATION` to `RESOURCE_UNAVAILABLE`, and this is the orchestrator's override: the operation *is* supported, a later enumeration of the same union will succeed, and a category whose retry class says `NEVER_RETRY` would instruct a caller to abandon a stack that was merely not ready. The agent had named `RESOURCE_UNAVAILABLE` as the alternative it actually wanted.
8. **Refused transitions are published inside the snapshot**, in a bounded window of eight, rather than as a second flow or a thrown error: they are facts about the observation and belong with it, and an unbounded window is a log buffer wearing a domain name.
9. **Two snapshot booleans** — whether the profile-capability question was consulted, and whether the records came from a round that completed. Without the second, a projection that has only ever been refused can report a complete union with zero devices, which is ADR-P3-009's confusion re-entering through a boolean.
10. **The engine owns the stage**; a source's claimed stage is ignored and restated, since a source that reported whether an observation was running would be asserting a fact outside its own view.
11. **Joining and comparing are different rules** (the amendment above): the key alone attributes an announcement to a record, `mergedWith` refuses on unjoinable keys, and a display name may differ between two observations of one device without making them two devices.
12. **Blank names are demoted at the factory, not by the constructor**, following the `DeviceIdentity` precedent that a domain type may not silently rewrite evidence — which leaves `DeviceObservation` constructible with a blank name and `hasReportedName` the guard that says so.

**Alternatives considered.** Leaving these as code comments — rejected: eight of the twelve are claims about a device that a later phase will treat as settled, and a phase record is where a claim is testable rather than merely readable. Promoting each to its own ADR — rejected: they are one decision (what the engine does when platform answers are partial and asynchronous) seen twelve times, and splitting them would make the index unreadable without making any entry more checkable.
**Consequences.** The engine is now the place where "connected" has a definition, and every one of the twelve is exercised by a named test in `ConnectedDeviceObserverTest` or `DeviceObservationKeyTest` — 39 new methods, `:core` at 408 with zero failures. Two of them are explicitly *not* claims about hardware: rules 2 and 4 describe what a union of declining sources can and cannot prove, and both stay `IMPLEMENTED` until a handset says otherwise (ADR-P3-014's deferred list). `architecture-audit.md` section 7 is now stale in two named places — it proposes `ConnectedDeviceProjection`, which ADR-P3-004 settled as `ConnectedDeviceSnapshot`, and an `ObservationPhase` type that was realised as `ObservationStage` — and the audit defers to the decisions in the authority order. *Amended 2026-10-02: the "39 new methods / `:core` at 408" figures measured the tree while this entry was being written and are superseded — `:core` now runs 433 across 47 classes with the paired census (ADR-P3-017) and the scope test added, and `validation.md` carries the re-summed totals. Rule 7's reclassification and the twelve rules themselves are untouched; the fold that rule 4 describes is now also the fold that credits a bond axis, which is the one place where this entry's "an absent device in a snapshot" sentence needs ADR-P3-017 read beside it: a paired device the bond list named and no profile reported is absent from `records` by construction rather than by rule 4's inference, and rule 4 governs only devices the union was in a position to list.*


### ADR-P3-016 — The instrumented source set is policed by the same guards, and receiver confinement widens in location only
**Status.** accepted — amends ADR-P2-016's confinement scope, closes ADR-P3-007's named guard gap
**Context.** ADR-P3-007 added `src/androidTest` to the boundary module and its own consequence recorded the hole that created: every architecture guard reads `src/main`, so an instrumented test could call `connectGatt`, start a discovery, or shut down the voice-recognition path, compile cleanly, never be executed, and pass the entire suite. A test that can reach a refused capability is still a module that can reach it, and the next editor copies the line out of a file that appeared to be sanctioned by a green build. Widening the scan then collided with rule 10, which confines receiver tokens to `bluetooth/adapter/` — but Phase 3's ACL, bond and per-profile connection-state listeners belong in `bluetooth/connection/` by ADR-P3-008, and a listener outside the adapter package is the same capability aimed at a different subject, not an extra one.
**Decision.** Rules 7 and 8 scan production **and** instrumented sources through one list, so widening the scan cannot be forgotten at one of two call sites; each scans a source root that fails the build if it is missing or contains no Kotlin, and a violation is labelled with the source set it came from so a failure says what has to change. `src/test` stays out of it, honestly stated rather than implied: those files script seams that declare no framework type, so there is nothing there to catch and pretending otherwise would be a check performing theatre. Rule 10's authorised-listener set becomes two packages — `bluetooth/adapter/` and `bluetooth/connection/` — and nothing else about it moves: the sender tokens stay banned everywhere, the token list is unchanged, and a receiver in a third package still fails. The last of those does not exist in the compileSdk 35 public surface at all, so it cannot fire today and is kept as the forward guard it becomes the first time the compile SDK widens, with that reason written into the list rather than dropped as dead weight. The method keeps its Phase 2 name, which now reads narrower than its body, because five Phase 2 records cite it by name and a rename would sever exactly the traceability those citations exist to give.
**Alternatives considered.** Leave `androidTest` unscanned on the theory that test code is not shipped — rejected: the guard's subject is what the module is able to do, and non-shipping is precisely why an unpoliced test set drifts into the production one. Add a second, narrower check for instrumented sources — rejected: two lists, one to forget. Rename the rule to match its new scope — rejected for the reason above, and the divergence is recorded here and in Phase 3's validation rather than hidden in a diff.
**Consequences.** The instrumentation surface is now a checked surface, so a forbidden call added there fails `:core:test` with a message naming the file. The guard was falsified in both directions before being trusted: a scratch `androidTest` file calling `fetchUuidsWithSdp` failed rule 7 and named `androidTest/ScratchProbeTest.kt`, and an injected second `<uses-permission>` failed the manifest check; both probes were then removed. Rule 10's confinement is now a set rather than a constant, which is the right shape for a second boundary and the shape a third one will have to argue for. ADR-P2-016's confinement text stands as authored history with this ADR as its amendment, the way ADR-P2-009 treats Phase 0's `SEC-PERM-002`. *Amended 2026-10-02: the exclusion this entry gave a reason for was wrong. The entry's other decisions — rules 7 and 8 sharing one list so a widening cannot be half-applied, the per-source-set violation label, the two-package listener confinement, the four forward-looking prohibited names — are unchanged.*


### ADR-P3-017 — The paired census is a second question with its own standing, and the bond type has no field that could claim a link
**Status.** accepted — implements prompt section 10's collection B, supersedes this phase's own drafts that recorded it as deliberately unenumerated
**Context.** Prompt section 3 lists "distinguish paired devices from connected devices" among the objectives, and section 10 names three collections and requires A and B to be told apart, adding of B that these devices "may be disconnected" and "do not present them as active connections". Every Phase 3 record written before this entry settled B the other way — *distinguishable in the vocabulary, not enumerated by any code path* — and the reasoning was coherent rather than lazy: section 16 forbids a persistent saved-device database, a bond list is the collection most easily mistaken for one, and `UNKNOWN` is an honest answer to a question the phase had decided not to ask. What that reasoning could not do is satisfy section 10.B, which is a requirement rather than a permission: a projection that never reads the pairing records cannot say "paired but disconnected", it can only fail to say anything, and section 3's distinction then exists only in an enum. The platform facts that decide the shape are the ones that made the question hard: `BluetoothAdapter.getBondedDevices()` ships, in its own Javadoc, "If Bluetooth state is not STATE_ON, this API will return an empty set" and "@return unmodifiable set of BluetoothDevice, or null on error", and the reference implementation also answers an empty collection to a caller whose standing was refused. Four different worlds — no pairings, adapter off, no adapter, refused — arrive as one value, so the confusion ADR-P3-009 was written to close is reachable from this call by every door at once.
**Decision.** Five rules, all of them the same refusal seen from different sides: the pairing question is asked separately, answered separately, and folded without ever being allowed to speak about links.

1. **A separate member with its own standing.** `ConnectedDeviceSource.bondedDevices()` returns its own `ObservationRound`, and the source settles `BluetoothOperation.BONDED_DEVICE_LIST_INSPECTION` through Phase 2's resolver and provider before the read, exactly as `snapshot()` settles `CONNECTED_DEVICE_INSPECTION` before enumerating. A grant for one is not a grant for the other. It is not a wider `snapshot()` carrying both collections with a flag, because then `isUnionComplete` and `restsOnCompletedRound` would each mean two things and an empty list would answer two questions with one value.
2. **A record type with no link field.** `BondedDeviceObservation` carries a key, a reported name, the device's own bond reading, and a reading time — and no `DeviceConnectionState`, no profile set, no availability axis, no device class, no manufacturer, no last-seen. Section 6's prohibition is enforced by that absence rather than by a convention: a consumer that wants "is this paired device connected?" asks the projection, and the two answers join on `DeviceObservationKey` and on nothing else.
3. **A refusal is never a census.** The Android half reports `BondedListing`'s four cases, and only `Reported` — reachable with an adapter present and reading itself as on — may carry an empty list. `AdapterAbsent`, `AdapterNotOn` and `ReadFailed` become an `ObservationRound.Failure`; the projection keeps the entries it last heard, withdraws the census claim through `isPairedCensus`, and records the reason in `pairedRoundRefusal`. A round that did not answer has no authority to restate zero pairings.
4. **Each answered round replaces the collection.** The bond list is the phone's live record, so a device unbonded since the last round leaves when the next read says so, and nothing accumulates. This is where section 10.C and section 16's no-history rule lives for collection B: an engine that unioned every bond list it had ever read would be a saved-device store wearing a projection's name.
5. **The fold credits one axis and introduces no record.** A paired round reaches `records` only through `DeviceObservation.creditingBond`, which takes a record and a bond state and returns the more positive bond reading with every other field untouched — there is no parameter through which a link, a profile or an availability could arrive. A device the bond list named that no profile reported is therefore absent from `connectedDevices` with its link unread, which holds both halves of section 6 without a predicate a consumer has to remember.

**Alternatives considered.** One round carrying both collections with a per-record marker — rejected on the second half of rule 1: it merges the two completeness questions and re-opens ADR-P3-009. Synthesising paired records into the projection with `link = UNKNOWN` — rejected: it is section 6's prohibited inference arriving as a default value, ADR-P0-016's "absence is not a negative" written backwards, and it would make `connectedDevices` a superset of what the platform reported. Leaving B unenumerated as this phase's drafts did — rejected for the reason in Context: it satisfies a caution at the cost of a stated requirement, and the caution has its own enforcement in rule 4. Caching the census so a cold round could answer — rejected: section 16, and a cache would be the history this collection must not have.
**Consequences.** Prompt section 10's collection B is implemented at T1: `BondedDeviceObservationTest` runs 17 methods over the fold, `AndroidConnectedDeviceSourceTest` grows to 39 including the four-case transcription, and `theBondListIsReadOncePerRoundAndNeverAsASideEffectOfAnotherRead` pins the call sequence so the census cannot smuggle itself into another read. `ConnectedDeviceHandle` gains a fifth member and it is still a read — the class KDoc's claim that no method can pair, connect, enable, discover or send anything now covers `getBondedDevices` as well, which asks nothing of any device. Five records written before this entry said collection B had no producer and are corrected with it: `design.md`'s out-of-scope row, `requirements.md`'s REQ-P3-019 AC-5 and its limitation list, `specs.md`'s "no `getBondedDevices()` call exists" and item 4 of its open list, `test-plan.md`'s `TEST-P3-026`, and `risk-register.md`'s RISK-052, whose live risk is now retention rather than absence. Two costs are accepted and named: paired records carry a `displayName`, so the census has the same label exposure the projection has and the design's logging paragraph had written for one collection now applies to two; and everything the census asserts about a handset — whether an OEM's bond read behaves as the reference implementation does — is unverified on hardware like the rest of the phase (ADR-P3-014, RISK-044).

Because the set is pinned by enumeration rather than by a list of prohibitions, the next phase that wants a new operation has to edit this file's data and a test's expectation, which is the pair of changes this project treats as a decision.


### ADR-P3-019 — The answerability ladder ranks a pending bind above a refusal, and the rank is a function rather than the enum's order
**Status.** accepted — corrects code that contradicted its own documentation and ADR-P3-008
**Context.** `SystemConnectedDeviceHandle.answerability()` may hold more than one channel's report about the same profile and takes the strongest, using `ProfileAnswerability.evidenceRank()`. The enum's declaration order puts `REFUSED` last, and both KDocs said the opposite ordering was the point: a refusal is a *weaker* claim than a bind that has not called back, because the refusal is about a mechanism this process actually tried while the silence is about nothing at all. The rank function existed precisely to break the ordinal and shipped with `REFUSED` above `AWAITING_CALLBACK` — reproducing, in a comparator, the exact failure its own comment named. What makes that more than cosmetic is where the value goes one level up: `REFUSED` maps to `ProfileObservationSupport.NOT_ANSWERABLE` and a pending bind maps to `UNKNOWN`, and `NOT_ANSWERABLE` is what makes a union count as declined. So one channel's `getProfileProxy` returning `false` could outvote another channel that had not called back, and "this round happened early" would be reported as "the platform declined the profile" — the distinction ADR-P3-008's never-an-empty-list rule and ADR-P3-009's refusal-is-not-empties rule both turn on. Nothing detected it: the rank had no test, and the multi-channel case that uses it is framework-facing.
**Decision.** The ladder is `NOT_REQUESTED < REFUSED < AWAITING_CALLBACK < ANSWERABLE`. It stays an explicit function and not the enum's order, because the ordinal is the ordering that caused this. `ProfileAnswerabilityTest` pins it in both directions: a pending bind outvotes a refusal whichever order the channels reported in, a refusal still outvotes a silence nobody asked about, a bound service outvotes all three, and the set of ranks is distinct — the last of those is the guard against the ladder silently collapsing back onto declaration order.
**Alternatives considered.** Stop ranking and return `UNKNOWN` whenever any channel is pending — rejected: `ANSWERABLE` must still beat a pending bind or a bound proxy would be hidden by an unbound one, which loses real evidence rather than protecting against it. Treat a refusal as terminal for the profile for the life of the observation — rejected: a bind can succeed on a later round, and burning a profile at first refusal would make the union less able to answer as the phone got warmer.
**Consequences.** The engine's "every profile declined" decision now keys on declines that actually happened, so a first round in which every profile is still binding reads `UNKNOWN` across the union; such a round carrying no devices is still refused by ADR-P3-015 rule 7's empty-union path, which keeps the two rules independently testable. The corrected ordering is a claim about how the platform's asynchronous binding behaves over time, and the half of it that needs a handset — what `getProfileProxy` actually does after returning `true`, and whether a refused bind ever recovers — stays UNVERIFIED (U-3) with the rest of the deferred device session.
