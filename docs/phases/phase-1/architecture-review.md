**Deliverable of:** Agent 2 — Architecture Agent (Phase 1 execution prompt section 4), answering the eight questions of prompt section 54.
**Method:** every verdict is derived from the code that exists, cited by path, not from the design prose that describes it. Where the code does not support a claim, the answer says so.
**Reviewed tree:** `:core` (71 main files, 5,196 lines, **no production dependency**), `:platform:android` (zero Kotlin sources), `core/src/test` (41 files, 5,885 lines, 302 tests), HEAD `a5f3bf2`.

Verdict scale: **YES** — true today, nothing to fix. **YES-with-caveat** — true today, and the caveat is owned by a named later phase. **NO** — not true today; prompt §54 requires the architecture to be fixed before Phase 1 is declared complete.

## Question 1 — Can Android-specific Bluetooth code later be added without modifying the domain model?

**YES.**

What makes it true: `core/src/main/kotlin/com/omnibuds/core/transport/TransportContract.kt` is an interface of `kind`, `isOpen`, `suspend open()`, `suspend close()`, `suspend exchange(request, timeoutMillis)` — no handle, no socket, no UUID, no callback type (ARCH-DEP-004). `device/DeviceIdentity.kt` is four nullable strings, so the `data class Device(val bluetoothDevice: android.bluetooth.BluetoothDevice)` shape that prompt §7 forbids has no home. `common/OmniBudsErrorCategory.kt` already contains `BLUETOOTH_DISABLED`, `GATT_FAILURE`, `RFCOMM_FAILURE`, so Android results arrive as existing vocabulary (ARCH-AND-003). The boundary module exists and compiles (`platform/android/build.gradle.kts`, `api(project(":core"))`), so a Phase 2 `GattTransport` is a **new file** in a different module that implements a contract nobody in `:core` implements — the last point being asserted by `noProductionClassImplementsTheProtocolOrRepositoryContracts` and `platformAndroidModuleStillContainsNoSources` in `core/src/test/kotlin/com/omnibuds/core/architecture/DependencyDirectionTest.kt`.

What would break it: any `android.*`/`java.*` import in `:core` (caught by two tests), a `TransportRequest`/`TransportResponse` field of a platform type (not caught by the import scan if it is written fully-qualified inline — see `kmp-review.md` §7), or a Phase 2 convenience that puts a `Context` into a domain constructor, which ARCH-KMP-004 forbids. The one soft spot is that the layer map permits `transport` at layer 1 to be imported by all eight areas above it, so a platform-shaped member added to `TransportContract` itself would propagate quickly; the fix is to add platform behaviour as a *new optional interface*, which is the pattern `protocol/` already uses.

## Question 2 — Can an RFCOMM device and a GATT device use the same higher-level protocol abstraction?

**YES-with-caveat.**

What makes it true: `protocol/EarbudProtocol.kt` never mentions a transport at all — `identify(fingerprint)`, `discoverCapabilities()`, `readState(session)`. Transport choice is *data*: `protocol/ProtocolDefinition.kt` carries a `TransportKind` and its `init` refuses `TransportKind.UNKNOWN` ("a protocol must name the channel its operations use"), and `common/TransportKind.kt` enumerates `GATT`, `RFCOMM`, `CLASSIC_BLUETOOTH`, `LE_AUDIO`, `VENDOR_SPECIFIC`, `UNKNOWN`. `transport/TransportAvailability.kt` records availability per kind per purpose with `available` and `reason` locked together, so one session can legitimately hold "BLE for bookkeeping, RFCOMM for configuration" without any layer assuming a single channel (ARCH-XPORT-002). `protocol/ProtocolParser.kt` and `ProtocolEncoder.kt` are pure `(commandId, ByteArray)` functions — byte logic has no channel opinion — and `protocol/CommandDefinition.kt` carries the retry policy that the transport is forbidden from improvising. That is the ARCH-XPORT-001 requirement expressed in types rather than in prose.

The caveat, stated plainly: **`TransportContract` is shaped like RFCOMM, not like GATT.** `exchange()` is strictly request/response, `TransportRequest` has no correlation identifier beyond `commandId`, and there is no seam for a device-initiated GATT indication/notification — the pattern several real earbud protocols use for battery and state pushes. Phase 1 cannot know whether that seam is needed (no device has been read), so adding it now would be invention; but the honest prediction is that Phase 6 will have to widen `transport`, and `transport` sits at layer 1 where five areas above it can see the change. Owner: Phase 6 (Bluetooth transport), with `TransportAvailability` as the place the second channel kind is recorded. It is not a Phase 1 defect; it is a Phase 1 limit that must not be discovered for the first time in Phase 6.

## Question 3 — Can the audio engine represent AAC, LDAC, aptX and LC3 without rewriting its architecture?

**YES.**

`audio/Codec.kt` already holds all four families — SBC, AAC, aptX, aptX HD, aptX Adaptive, aptX Lossless, LDAC (each `CLASSIC_A2DP`), LC3 (`LE_AUDIO`) — plus `UNKNOWN`; `audio/CodecFamily.kt` separates classic from LE Audio, which is the only structural distinction the audio path itself cares about. `audio/CodecState.kt` is the ordinal ladder `UNKNOWN < UNSUPPORTED < SUPPORTED < AVAILABLE < ENABLED < NEGOTIATED < ACTIVE` (ADR-P1-005 amending ADR-P0-015), and `audio/CodecCapability.kt` keeps `configurable` as an orthogonal boolean, which is what lets "LDAC is ACTIVE and configurable" and "AAC is ENABLED but not configurable" both be stated without contradiction — the six-boolean design prompt §17 proposed could not say either safely. `audio/AudioTransportState.kt` carries observed sample rate, bit depth (8..32, `require`d), bitrate, `ChannelMode` and `QualityMode` as nullable measurements, so a codec's concrete parameters are evidence, never defaults. `audio/CodecRegistry.kt` resolves normalised labels and refuses to bind one label to two codecs, so adding a codec is one enum entry plus a catalogue line — no new type, no branch.

Pinned by tests, not by my reading: `core/src/test/kotlin/com/omnibuds/core/audio/CodecStateTest.kt` has `ladderOrderSupportsItselfAndEveryRungBelow`, `unsupportedNeverSatisfiesActiveTarget`, `nonPositiveTargetIsNeverSatisfied` and `configurableIsOrthogonalToTheLadder` — so the ordinal dependency that `supportsAtLeast()` relies on is guarded against a rung being inserted in the wrong place.

Separate, already-recorded gap: one `CodecCapability` per codec means Phase 1 cannot express per-endpoint support ("this phone offers LDAC, this headset does not"), which `audio-governance.md` AUD-STATE-003 requires. That is ADR-P1-018, **status open, owned by Phase 11** — not an architecture rewrite, but a missing discriminator. What would break the YES: deriving codec truth from `AudioTransportKind` or from battery/session state (ARCH-BOUND-004 forbids it), or smuggling the endpoint discriminator in as a nullable field that decodes as `UNKNOWN` — ADR-P1-018 explicitly prohibits that route.

## Question 4 — Can vendor-specific features exist without polluting common feature interfaces?

**YES-with-caveat.**

What makes it true: `common/FeatureId.kt` is a `@JvmInline value class` whose constructor is **private**, obtainable only via `of(vararg segments)` (≥2 segments, each matching lower-kebab), `ofVendor(vendor, feature)`, or `parseOrNull(raw)` — which now enforces the same two-segment floor — so a qualified name cannot exist without having passed the grammar. `ofVendor(vendor, feature)` produces the reserved `vendor.<vendor>.<feature>` form (ADR-P1-008 amending Phase 0 `specs.md` §1.5). `capability/VendorExtension.kt` refuses construction twice over — the id must be vendor-namespaced, and the vendor segment must equal `metadata.vendor` — so a vendor feature cannot masquerade as a core one, and cannot be filed under the wrong vendor. `capability/CoreFeature.kt` mirrors the rule from the other side: its `init` checks that the 15 identity and definition catalogues agree, that no core feature is vendor-namespaced, and that none sits under the reserved `vendor` root. `capability/FeatureCategory.kt` isolates `VENDOR` as its own category. Most importantly, `protocol/FeatureReadSupport.kt` and `FeatureWriteSupport.kt` are generic over `FeatureId` + `config/ConfigurationValue`, so a Sony-only or Nothing-only capability is reachable through the same narrow surface as ANC, and `EarbudProtocol` gains no method when a vendor gains a feature — which is precisely why there is nowhere for `if (sony)` to live (ARCH-QUAL-003/014, ARCH-PROTO-003). `VendorExtensionTest` and `CoreFeatureTest` cover the refusals.

The caveat **was** `FeatureId.parseOrNull(raw)`, which validated each segment against the same pattern but omitted the ≥2-segment rule `of()` enforces, so it would build an un-namespaced single-segment id such as `anc`. That is fixed: `parseOrNull` now refuses anything below the `MIN_SEGMENTS` floor, so both entry points enforce one grammar, and `FeatureIdTest` pins it from both directions (`aSingleSegmentNameIsRefusedRatherThanGuessedIntoShape`, `uppercaseUnderscoreAndBlankSegmentsAreNotIdentities`, `parsingRoundTripsAStoredIdentifierAndRefusesGarbage`). `parseOrNull` still has no caller in `src/main` — it exists for the Phase 22 read path — but it is no longer a hole in the contract ADR-P1-008 declares stable.

The caveat that remains is **duplication of the grammar, not its absence.** `capability/VendorFeatureMetadata.kt:58` keeps a private copy of `FeatureId`'s `segmentPattern` because the kernel's copy is private, and `capability/VendorExtension.kt:88-95` re-derives with `feature.qualifiedName.split('.')` what `common/FeatureId.kt:33-34`'s `vendorName` already answers. The vendor-mismatch guard — the thing that makes this YES true — is only as strong as those three spellings agreeing, and nothing machine-checks that they do (code-quality finding Q-3). Owner: Phase 2, by exposing one validator or segment accessor on `FeatureId`, which the layer map already permits since `capability` sits above `common`. A second, smaller residue: `VendorExtensionTest`'s KDoc still asserts that `FeatureId.isVendorExtension` reports `false` for a documented vendor id "today", which has not been true since the kernel was repaired — stale prose in a test file whose assertions are correct and passing.

## Question 5 — Can a device be temporarily connected without being permanently saved?

**YES-with-caveat.**

What makes it true: `state/SessionClassification.kt` has exactly two values, `TEMPORARY` and `SAVED`, and it is orthogonal to `state/ConnectionState.kt` by decision (ADR-P1-016 supersedes Phase 0 `specs.md` §2.3's `SessionState`, which mixed the two axes). `device/DeviceSession.kt` starts `TEMPORARY` — `DeviceSessionTest.afreshSessionIsTemporaryUntilTheUserSaysOtherwise` — and `save()` flips that one field and nothing else, which `savingChangesNothingExceptTheClassification` asserts field by field while its KDoc states that it persists nothing; `forget()` is written to say precisely that it does **not** unpair the device, does not clear the phone's pairing record and does not delete a saved record held elsewhere, and `forgettingDropsTheSavedChoiceAndClaimsNothingAboutTheHardware` pins that scope. Since ADR-P1-020 the separation is cleaner than it was: `DeviceSession` holds no connection state at all, so "temporary" and "connected" cannot even be confused inside one record. On the storage side `persistence/SavedDeviceRecord.kt` is only reachable through `persistence/DeviceRepository.save(...)`, and `DeviceRepositoryContractTest.nothingButAnExplicitSaveEverEntersTheUsersList` plus `markingAnUnsavedDeviceSeenRefusesInsteadOfQuietlySavingIt` refuse the back door. ARCH-STATE-007 satisfied without a single line of persistence code.

The caveat: enforcement is by convention, not by contract. `SavedDeviceRecord` has no classification field and `DeviceRepository.save()` accepts any record, so a future caller could persist a merely-detected device and nothing in `:core` would object. The only guard of that shape in the tree is inside a test double (`FakeDeviceRepository.markSeen` refuses a key it has never saved, on the grounds that inserting one would be "saving a merely detected device by the back door") — instructive, but test-only. Owner: Phase 2 (session holder) plus Phase 22 (storage), which should decide whether the repository refuses `TEMPORARY` keys or whether saving is expressed as a distinct typed operation rather than a flag flip.

## Question 6 — Can persistent configuration be verified across reconnect?

**YES-with-caveat**, and the caveat is large enough to read twice.

What is genuinely in place at the model level: the ladder has a rung reserved for exactly this claim (`CapabilityState.PERSISTENCE_VERIFIED`), and `capability/FeatureCapability.kt`'s `init` refuses to build one unless `verification == VerificationLevel.PERSISTENCE_VERIFIED` — the message names the reason ("claims survival of a real disconnect and reconnect … which is exactly what PERSISTENCE_VERIFIED verification means"), and `FeatureCapabilityTest.aPersistenceClaimCannotRestOnLabEvidence` plus `observedSurvivalIsTheOnlyEvidenceForPersistenceVerified` hold that line. `SUPPORTED_PERSISTENT` is separately gated at `HARDWARE_VERIFIED` or better, which is ARCH-PERSIST-001 encoded as a constructor rather than as a comment. `persistence/DiscoveredCapabilityRecord.kt` stores the capability snapshot **together with its `VerificationLevel` and `identityKey`**, so a cache read cannot silently upgrade itself. `session/DeviceState.kt.invalidatedForDisconnect(...)` keeps discovered capability history while discarding live battery and audio readings, which is the correct shape for "we are back, re-read the live parts", and `DeviceStateTest.disconnectingClearsLiveReadingsButKeepsEstablishedCapabilityKnowledge` now asserts exactly that. `state/ConnectionState.kt` plus `ConnectionStateTransitions` provide the legal re-entry path `DISCONNECTED → … → IDENTIFYING → CAPABILITY_DISCOVERY → READY`, so re-discovery after reconnect is a legal route rather than an accident, and since ADR-P1-020 there is one place to walk it from: `DeviceState.attemptConnection`, whose refusal `anIllegalConnectionMoveIsRefusedWithStructuredErrorAndChangesNothing` pins. The key a claim is cached under is `DeviceFingerprint.identityKey()`, deliberately derived from observed evidence rather than from a MAC address.

What is **not** in place: the eight-step master §24 procedure (READ → WRITE → READ BACK → VERIFY → DISCONNECT → RECONNECT → READ AGAIN → VERIFY) has no orchestrating code — by design, ARCH-PERSIST-005 assigns it to Phases 17–18 — and **no Phase 1 test performs a reconnect of any kind**. `DeviceStateTest` walks forward to `READY` and then invalidates for a disconnect; nothing walks back. Nothing verifies that a `PERSISTENCE_VERIFIED` record is *reused* correctly after reconnect, nor that a config which fails to survive is downgraded to `SUPPORTED_VOLATILE` with the downgrade recorded (ARCH-PERSIST-003); the type can express both outcomes, and no code produces either. One further hazard the model does not yet answer: `identityKey()` is deterministic for identical inputs, so if a post-reconnect discovery pass returns *different* evidence — a partial service read, a rotated manufacturer-data payload — the key changes and the stored verification history is silently orphaned. That is a Phase 22 identity-stability question, and it should be settled before the first persistent claim is cached for a real user.

Verdict therefore: the architecture **permits** the verification, it now **tests** the invalidation half of it, and it does not **perform** the verification itself — no T1 test could. Phase 1 may close with this YES only because prompt §50 asks for foundations and contracts, not for verified hardware behaviour; the honest label on it is `INFERRED`.

## Question 7 — Can the core eventually compile in a KMP environment?

**YES-with-caveat** — and `kmp-review.md` in this directory is the detailed assessment; this is the verdict and its two hard facts.

For it: the import census over all 71 main files shows **zero** external imports — the only imports in the module are `com.omnibuds.core.*`, and since ADR-P1-021 there is no dependency to import *from*: `kotlinx-coroutines-core` was dropped from `core/build.gradle.kts` after a census showed no main source referenced it, so `:core`'s production dependency set is empty. That removes an entire class of portability question — one fewer artifact to prove available on a non-JVM target — and it makes the "no `kotlinx.*` symbol is used" statement structural rather than incidental. `suspend` is a language feature, `ByteArray`/`Regex`/`buildString`/`ArrayDeque`/`contentEquals`/`String.lowercase()` are common-stdlib, and timestamps are `Long?` epoch millis precisely so that `java.time` never appears (ADR-P1-012). The only JVM-targeted annotation in the module is `@JvmInline` on `FeatureId` (`common/FeatureId.kt:15`), which is legal in common source. Two tests guard this continuously: `coreMainSourcesDoNotImportAndroidFrameworks` and `coreMainSourcesDoNotImportJvmOnlyLibraries`.

Against it, and this is where I decline to give a clean YES: **the enforcement mechanism is weaker than the property it protects.** Both tests scan `import` lines only, so a fully-qualified call — `java.util.Locale.getDefault()`, `System.lineSeparator()`, `Thread.sleep(...)` — written inline in a function body passes every Phase 1 test and ends KMP support in one commit. The `Bluetooth*`/media and magic-literal rules do scan code bodies, but the JVM/Android rules do not. Beyond that, two files in `core/src/test` are genuinely JVM-only: `architecture/DependencyDirectionTest.kt` uses `java.io.File`, and `testing/TestDoublesAreNotHardwareTest.kt` uses `::class.java` reflection across six assertions (lines 228–237: `isInterface`, `isAssignableFrom`) — both must move to a `jvmTest` source set or be rewritten during the Phase 46 conversion. Finally, the non-portable part nobody mentions is the **build script**, not the source: `core/build.gradle.kts` applies `org.jetbrains.kotlin.jvm`, sets `JvmTarget.JVM_17`, `javaParameters`, and a `java { sourceCompatibility … }` block — all of which are replaced by a multiplatform `kotlin { jvm(); … }` target declaration. None of that invalidates the YES; all of it belongs in Phase 46's estimate rather than being discovered there.

## Question 8 — Can every future UI surface consume the same authoritative device state?

**YES** — and it was not, which is why this answer changed. When this review was first written the verdict was **NO**, prompt §54 required the architecture to be fixed rather than documented, and **ADR-P1-020** is that fix. The evidence that carries the upgraded verdict, item by item:

- **One owner, by removal rather than by declaration.** `session/DeviceState.kt` holds `connection`; `device/DeviceSession.kt` no longer holds a connection field at all. Its properties are now `sessionId`, `identity`, `fingerprint`, `classification`, `createdAtEpochMillis`, and its own KDoc states that connection state is "deliberately not held here". A duplicated field cannot be re-introduced by oversight while the review record and the ADR sit next to it, which is the point of recording the rejected alternative (keep both, document one as derived) in ADR-P1-020: a derived copy is still a copy.
- **One mutator, and it refuses.** `DeviceState.attemptConnection(next, atEpochMillis)` returns `OperationOutcome<DeviceState>`: `Success` with `revision + 1` when `ConnectionStateTransitions.canTransition` permits the move, `Failure(OmniBudsError(INVALID_STATE, operationId = "device-state.attemptConnection"))` when it does not. It neither throws — which would move the caller off the ADR-P1-004 outcome model — nor silently returns the receiver, which would make an illegal move indistinguishable from a no-op. `DeviceSession` has no transition method to compete with it.
- **Ordering travels in the data.** `revision` is incremented by every mutator (`attemptConnection`, `withCapability`, `withCapabilities`, `withBattery`, `withAudio`, `invalidatedForDisconnect`) and `applyIfNewer(candidate)` adopts only when `candidate.sessionId == sessionId && candidate.revision > revision`, so prompt §30's stale response is harmless at the model level rather than merely unlikely.
- **It is tested, in the type that carries it.** `core/src/test/kotlin/com/omnibuds/core/session/DeviceStateTest.kt`, 12 tests: `aLegalConnectionMoveAdvancesTheRevision`, `anIllegalConnectionMoveIsRefusedWithStructuredErrorAndChangesNothing` (asserting the refused move left both `connection` and `revision` untouched), `everyStateCanFallIntoErrorAndASelfMoveIsIdempotent` over all eleven `ConnectionState.entries`, `operationalOnlyWhileReadyOrInAControlSession`, `aStaleResponseCannotOverwriteNewerState`, `anEqualRevisionIsNotNewerInformation`, `aNewerStateFromADifferentSessionIsNeverAdopted`, `aNewerStateFromTheSameSessionIsAdopted`, `eachUpdateMovesTheRevisionForwardAndLeavesTheOriginalAlone`, `disconnectingClearsLiveReadingsButKeepsEstablishedCapabilityKnowledge`, plus the two "initial state asserts nothing" cases. Catalogued as `TEST-P1-060`/`TEST-P1-061`; before `a5f3bf2` the `session` area had no test file at all.
- **Everything else the answer always rested on is unchanged:** `DeviceCapabilities` is the only capability holder, `AudioTransportState` the only audio record, `BatteryState` the only battery record, and `isOperational` derives from `ConnectionStateTransitions` rather than being re-decided per surface.

Three residuals, named so nobody reads the YES as stronger than it is. (1) `DeviceState` is a `data class`, so `copy(connection = …)` still rewrites the owner without consulting the transition table — `DeviceStateTest`'s own `forceConnection` helper does exactly that to set up its table sweep. Nothing machine-enforces "no `connection` change outside `attemptConnection`"; recorded as `TEST-P1-065`. (2) `DeviceSession` and `DeviceState` still both carry `sessionId` and `DeviceIdentity`, now as descriptive facts rather than as competing state, and are joined only by the `sessionId` string: `EarbudProtocol.readState(session: DeviceState)` never sees a `DeviceSession`. Building and holding that pair is the Phase 2 session holder's job, and ADR-P1-009's no-singleton rule is why Phase 1 did not pre-empt it. (3) None of this is evidence about a real device: the whole cluster is tier T1, and the ceiling stays `IMPLEMENTED` (T3/T4 remain unwritten, per question 6).

`validation.md` may now record REQ-P1-017 as exercised by tests, with (1) and (2) as its named not-covered-by column.

## Where I disagree with the phase as it stands

Items 1–3 of this list were the disagreements I raised when the tree looked different; all three were accepted as defects and **fixed in commit `a5f3bf2`**, which is why the verdicts above read as they do. They stay listed because "the review said NO and the code moved" is the record that the review process works.

1. **RESOLVED — `ConnectionState` had two owners** (`device/DeviceSession.kt`, `session/DeviceState.kt`) with no link between them — Question 8. ADR-P1-020 made `DeviceState` the sole owner and trimmed `DeviceSession` to identity, evidence and the save choice, as prompt §54 required before Phase 1 could close.
2. **RESOLVED — `session/DeviceState.kt` shipped untested** while being the type the phase's authoritative-state claim depends on; zero of the then-275 tests reached it. `DeviceStateTest` (12 tests) now covers the transitions, the refusals, the revision ordering and the disconnect invalidation, taking the suite to 301.
3. **RESOLVED — `FeatureId.parseOrNull` was inconsistent with `FeatureId.of`** (single-segment ids accepted). Both paths enforce the same floor now, and `FeatureIdTest` pins the grammar.
4. **The KMP guard still scans imports, not bodies**, so the property it advertises protecting can be lost by a single fully-qualified call. Either extend both rules to scan code bodies or rename them so nobody reads them as stronger than they are.
5. **`TransportContract` still has no notification seam and no correlation id beyond `commandId`** — fine for Phase 1, but Phase 6 must be told explicitly rather than finding out.
6. **Reconnect verification is still expressible but never performed**, and fingerprint-keyed history can silently orphan when a post-reconnect discovery pass differs. ADR-P1-010/018 do not cover this second hazard; Phase 22 should own it. What changed is the half that could be tested at all: `invalidatedForDisconnect` now has a test.
7. **`DeviceState` cannot defend its own invariant.** `attemptConnection` refuses an illegal move, but `copy(connection = …)` rewrites the field without consulting `ConnectionStateTransitions`, and `DeviceStateTest` uses that bypass as a fixture. The single-owner decision is enforced by convention plus tests, not by the type; closing it is a Phase 2 job alongside the session holder (`TEST-P1-065`).
8. **A `DeviceSession` and a `DeviceState` are joined only by a `sessionId` string.** That is now a deliberate split rather than a duplication, but no type in the module states which session a given state belongs to beyond that key, and `EarbudProtocol.readState(session: DeviceState)` never sees a `DeviceSession`. Phase 2's session holder should make the pair explicit.
9. Two accepted gaps are correctly recorded as accepted (ADR-P1-018 per-endpoint codec support, ADR-P1-019 no redactor). They are not defects; they are the two places where Phase 1 chose an honest gap over a convenient fake, and they should be re-read in Phase 11 and Phase 36 respectively.
10. **`:core` had declared a production dependency no main source used** (`kotlinx-coroutines-core`). ADR-P1-021 removed it. Recorded here because an unused dependency is an architectural claim — it asserted a `Flow`-shaped surface that does not exist yet — and because the removal is what makes question 7's "zero external imports" structural.

No question in this review was marked YES because it was inconvenient to mark otherwise.
