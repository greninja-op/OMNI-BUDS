# Phase 1 — Code Quality Review

**Document class:** Phase 1 deliverable of the Code Quality workstream (execution prompt §4, Agent 6): naming, package structure, API visibility, dependency hygiene, formatting, Kotlin conventions and the static-analysis position.
**Assessed against:** `docs/phases/phase-0/architecture-governance.md` §11 (`ARCH-QUAL-001` … `015`), `docs/phases/phase-0/specs.md` §1 (naming), and the phase's own `docs/phases/phase-1/decisions.md`.
**Evidence base.** All 71 files in `core/src/main/kotlin/com/omnibuds/core/` and all 41 in `core/src/test/kotlin/` (37 test classes plus 4 test-only doubles), read on disk, plus `.editorconfig`, `core/build.gradle.kts`, `platform/android/build.gradle.kts`, `settings.gradle.kts`, `gradle/libs.versions.toml`, `gradle.properties`. Counts are greps, not impressions. Reviewed tree is HEAD `a5f3bf2`, which resolved several findings raised by this review pass; each resolution below says which.

## 1. The quality baseline as actually enforced

`ADR-P1-011` chose the compiler plus dependency-free architecture tests over a linter stack. What that means in practice, precisely:

- **`allWarningsAsErrors = true` in both modules** (`core/build.gradle.kts` `kotlin.compilerOptions`, and the same setting in `platform/android/build.gradle.kts`). Any warning the K2 compiler emits is a build failure: a deprecated call, an unchecked cast, a nullable-discipline slip, an unused import. `BUILD SUCCESSFUL` therefore *means* "zero compiler warnings", which is an enforceable statement rather than a style preference. `javaParameters = true` and `jvmTarget 17` / `sourceCompatibility 17` are set explicitly.
- **`DependencyDirectionTest` covers what a linter would otherwise be hired for**: no placeholders, no doubles in main, no production implementation of hardware-facing contracts, no magic hex/UUID, upward imports forbidden, packages matching directories. Those are the Phase 1 rules that matter; they run on every build with zero added dependencies.
- **Not added, deliberately**: detekt, ktlint, Spotless, Android lint wired into `check`, MockK (`ADR-P1-011`). The stated reasons are the workstations'-toolchain non-interference requirement and the prompt §35 warning against stacking overlapping tools.

**What the trade costs, concretely** (this is the part an ADR usually omits): nothing in the build checks import ordering, blank lines between imports, redundant same-package imports, KDoc link validity, function length, complexity, or comment-to-code ratio. Findings Q-9 … Q-12 below are all in that residual class — real, minor, and *uncheap*: they will accumulate silently. The advisory half of ADR-P1-011's baseline is now accurate: `.editorconfig` exists at the repository root (27 lines, `root = true`) and records what the conventions actually are — `indent_style = space`, `indent_size = 4`, `max_line_length = 120`, `charset = utf-8`, `end_of_line = lf`, `insert_final_newline = true`, `trim_trailing_whitespace = true`, with `indent_size = 2` for YAML/JSON/TOML and trailing-whitespace/line-length relaxed for Markdown so tables survive. Its own header states the position honestly: it "records the conventions the build already enforces; it does not add a tool". Nothing in the Gradle build reads it, so it constrains editors, not commits — finding Q-10's drift class is still unenforced. Empirically the conventions are being followed (0 lines over 120 characters in main sources, uniform 4-space indentation, no wildcard imports), which is a statement about this phase's authorship discipline, not about enforcement.

## 2. Naming

Strong and internally consistent. Types are named for the domain concept, not the mechanism: `EarbudProtocol` over `ProtocolService`, `ProtocolRecordAccess` over `IProtocolDao`, and no `Impl`, `Base`, `Utils`, `Helper` or `Manager` type exists anywhere in the module. Interfaces are declared as plain nouns (`DeviceRepository`, `CapabilityRepository`, `TransportContract`, `OmniBudsLogger`) with no `I`-prefix, and the optional-behaviour interfaces read as capabilities (`FeatureReadSupport`, `BatteryReportingSupport`) which matches ADR-P1-007's intent. Enum members are SCREAMING_SNAKE in the capability/state/protocol vocabularies and kebab-in-content for `FeatureId` segments, matching `specs.md` §1.2/§1.5.

The most distinctive convention is the one that carries the most meaning: **test method names are behaviour-plus-condition sentences** (`anAbsentFeatureIsUnknownAndNotUnsupported`, `aScriptedFailureIsReturnedAsFailureAndNotSwallowedIntoADefaultSuccess`, `addressTextCannotSurviveIntoTheIdentityKey`). A failing test names its own rule, which is worth more than a coverage number. Command and protocol ids in fixtures follow the symbolic rule (`example-vendor.read-battery-status`, not `send0x0A`).

Nits worth recording: `FeatureCapability.unknown(feature)` and `CodecCapability.unknown(codec)` are factories returning a *record in* the unknown state, and `DeviceCapabilities.unknown` is a `Set<FeatureId>` property — one word doing both jobs at different layers is mildly confusing at a call site. `CodecRegistry.all` excludes `Codec.UNKNOWN` while `Codec.entries` includes it; the exclusion is tested and documented, but the name `all` overstates it.

## 3. Package structure

`com.omnibuds.core.<area>` (ADR-P1-002, amending Phase 0's bare `omnibuds` root) with eleven areas: `common`, `state`, `transport`, `device`, `capability`, `audio`, `config`, `diagnostics`, `session`, `persistence`, `protocol`. The structure does real work rather than decorating the code: the layer map in `DependencyDirectionTest.areaLayer` is derived from these directory names, so a package is a *layer claim* and `everyCoreAreaIsRegisteredInTheLayerMap` forces a new area to be placed deliberately. Package statements match directories and that is checked (`packageStatementsMatchSourceDirectories`).

Two consequences are worth naming. First, `common` holds shared vocabulary only — including `TransportKind`, which ADR-P1-003a moved out of `transport` precisely because it is vocabulary, not implementation; the area now has its own tests (`FeatureIdTest`, `OmniBudsErrorCategoryTest`, `OperationOutcomeTest`), which it lacked when this review was first written. Second, `session` exists *because* of a violation: `DeviceState` composed capability, device and audio from inside `state`, which was a cycle, so it moved to a new area above all three (ADR-P1-003c). ADR-P1-020 then finished the same argument at the type level, moving connection state into that area exclusively and leaving `device/DeviceSession.kt` as an identity-and-choice record; the `device` ↔ `session` boundary is now stated in code rather than in prose, and both sides have tests. A package created to resolve a measured dependency error is a healthy sign; a package created in anticipation would not be.

File sizes support the boundary work: 71 files, smallest 16 lines, median 62, mean 73, largest `CoreFeature.kt` at 250 lines — and that one is an immutable catalogue of fifteen identities plus their definitions, not a class with behaviour. There is no giant manager owning several §3 boundaries (ARCH-QUAL-001), and no type in `:core` mixes a domain concept with I/O, threading or logging.

## 4. API visibility

Deliberately narrow, and measurable: **exactly two `internal` declarations exist in 71 main files** — `DeviceIdentity.normalised` (`device/DeviceIdentity.kt:113`) and `VendorExtension.vendorSegmentOf` (`capability/VendorExtension.kt:88`) — both chosen so sibling domain packages and same-module tests can reuse one normalisation rule instead of inventing a second. Everything else is either public API of a domain type or `private`. Constants that are contract are public (`AudioTransportState.MIN_BITS_PER_SAMPLE`, `CommandDefinition.MAX_READ_ATTEMPTS`, `DeviceState.INITIAL_REVISION`, `ProtocolIdentification.NO_PROTOCOL_MATCHED`, `DeviceFingerprint.NOTHING_KNOWN_KEY`, the doubles' `DOUBLE_MARKER`); constants that are implementation detail are private (`DeviceIdentity.FIELD_COUNT`, `KEY_PREFIX`, `LEVEL_RANGE`, `VENDOR_ID_SEGMENTS`, `FeatureId.MIN_SEGMENTS`).

`FeatureId` is the strongest visibility decision in the module: `@JvmInline value class` with a **private constructor**, so a qualified name cannot be formed except through `of`/`ofVendor`/`parseOrNull`, and the runtime cost of the wrapper is zero. `OperationOutcome` is a sealed interface with `Success`/`Failure`/`Cancelled` and `valueOrNull`/`errorOrNull` accessors that keep the three cases from being conflated — `TestDoublesAreNotHardwareTest` reads outcomes through those accessors specifically so "Success carrying null" stays distinguishable from "Failure". Call recording on the fakes uses `var … private set` (`FakeDeviceRepository.savedDevicesCalls`), so a test can read but not corrupt the record.

The residual risk is the ordinary Kotlin one: data classes expose every property and `copy()`, so invariants held by an `init` block survive construction but not `copy`. No `init` in this module re-validates `copy` differently from construction (copy re-runs `init`, which is why that is safe) — but the types that depend on *defensive copying* rather than on `init` are exactly the ones finding Q-9 addresses.

## 5. Dependency hygiene

Runtime dependencies of `:core`: **none.** ADR-P1-021 removed `api(libs.kotlinx.coroutines.core)` after a census showed no main source imports `kotlinx.coroutines` — `suspend` is a language feature needing no library and no `Flow` surface exists yet — so the four entries in `core/build.gradle.kts`'s dependency block are all `testImplementation`/`testRuntimeOnly`: `kotlin-test`, `junit-jupiter`, `kotlinx-coroutines-test`, `junit-platform-launcher`. The build file carries the reason in a comment next to the empty production slot, including where the library comes back (the Phase 2 state engine, with a recorded reason). `:platform:android` has `api(project(":core"))` and nothing else. Repositories are `google()` + `mavenCentral()` with `RepositoriesMode.FAIL_ON_PROJECT_REPOS` so no subproject can add a source behind the orchestrator's back. Every version is in `gradle/libs.versions.toml` with a recorded reason; nothing was added because it is popular (prompt §34).

Machine-local state is quarantined: `local.properties` and `.gradle/`/`.kotlin/` are git-ignored, no `org.gradle.java.home` is written into any user-level Gradle file, and `gradle.properties` states that rule in a comment so the next person does not "helpfully" add it (ADR-P1-014).

Negative greps that matter, all in main sources: zero `java.`/`javax.` imports (enforced, not just grepped), zero `android`/`androidx` imports, zero `!!`, exactly three `var` — two local accumulators inside hand-written `hashCode()` implementations and one field of the documented single-owner `SnapshotBuilder` — and zero `runBlocking`, `GlobalScope`, `Thread(`, `println(`, `Date(`, `System.`. The only textual `java.util` hit is inside `DiagnosticEvent`'s KDoc explaining why `java.util.Date` is *not* used. That is ARCH-QUAL-006 (no hidden global mutable state) satisfied at the level of grep, not of belief: the three `object` singletons (`CodecRegistry`, `CoreFeature`, `ConnectionStateTransitions`) hold immutable vals only, and `ProtocolRegistry.empty()`/`DeviceCapabilities.empty()` return shared immutable values rather than application-wide containers (ADR-P1-009).

Vendor branching (ARCH-QUAL-003/014): brand strings appear in main sources **only** inside KDoc examples (`e.g. vendor.sony…`); no `if (manufacturer == …)` exists anywhere, because `FeatureId` namespaces make the question unaskable.

## 6. Formatting

Consistent in the dimensions that are visible without tooling: 4-space indent, no wildcard imports, no line over 120 characters (longest main line 115), trailing commas used throughout, expression bodies where the body is one call, `when` over enums written exhaustively (and `DeviceCapabilities.evidenceOf` deliberately re-states the ladder as a non-exhaustive-by-design `when` so reordering the enum is a compile error). Brace style and KDoc shape are uniform across all 71 files, which is what one author-at-a-time integration produces. `.editorconfig` at the root now records these numbers where an IDE will find them, though no build task enforces them.

Where it is not uniform, see findings Q-10 and Q-11: four files have unsorted imports, two have a blank line inside the import block, one has redundant same-package imports, and no machine checks any of them.

## 7. Documentation quality (the project's own rule)

2,807 of 5,196 lines in main sources begin with a comment marker — documentation is the majority of the module. That is a deliberate consequence of the project rule that **the reason for each invariant travels with the type**, and it is what makes this phase reviewable at all: `TransportContract` can say "nothing in `:core` may implement this interface" next to the interface; `DiscoveredCapabilityRecord` can explain that a cache hit is a hint and cannot distinguish firmware; `FeatureFlagKind` can quote prompt §40 verbatim as the reason the enum exists.

It also creates the specific failure mode this module demonstrated, and which is now largely repaired: prose that was true when written and became false once the code it described was fixed. Finding Q-1 was that defect — `VendorExtension`'s KDoc still described a kernel bug that had already been repaired — and it is fixed in `a5f3bf2` (§9). One instance survives in a test file's KDoc, recorded under the same finding. What stops the next one is the discipline most files already follow: citing the enforcement next to the claim (`DependencyDirectionTest.coreReferencesNoBluetoothOrAudioFrameworkTypes`, `AUD-STATE-001`) and naming which test protects the rule, so that changing the code makes the citation visibly stale.

## 9. Findings

Ordered by how much they matter. Each names the file and the line the reader should look at. **Q-1, Q-2, Q-5, Q-11 and Q-13 were raised by this review pass and fixed in commit `a5f3bf2`**; they stay in place with their ids rather than being deleted, because a finding that vanishes cannot be audited. Q-13 sits last rather than in rank order because it arrived with the dependency decision ADR-P1-021 rather than from reading the sources.

**Q-1 — `FIXED in a5f3bf2` (documentation plus a dead guard branch).** As raised: `capability/VendorExtension.kt` opened with a "Kernel deviation this class works around" section asserting that `FeatureId.isVendorExtension` "currently compares the *whole* namespace (`"vendor.sony"`) against `"vendor"`" and "reports `false` for exactly the ids `ofVendor` produces" — untrue since the kernel property was repaired during the phase (`common/FeatureId.kt:29-30` reads `segments.size >= MIN_VENDOR_SEGMENTS && segments.first() == VENDOR_ROOT`), and the OR of two equivalent checks in `isVendorFeature` left the right operand dead. Now: the workaround section is replaced by "Why the vendor segment is checked here as well as in [FeatureId]", which states the real and still-true reason (the id shape is necessary but not sufficient; the vendor segment must also agree with `metadata.vendor`), and `isVendorFeature` is a single expression, `feature.isVendorExtension` (`capability/VendorExtension.kt:82`). `VendorExtensionTest.aVendorNamespacedIdentityIsAcceptedAndRecognised` still passes unchanged, which is the proof that the behaviour never depended on the dead branch. **Residual, not fixed here because it is in test source:** the same false claim survives in `capability/VendorExtensionTest.kt:69-72` ("answers `false` for this id today"). The assertions in that file are correct and green, so this is prose only — but it is the identical failure mode Q-1 describes, in the file that documents it.

**Q-2 — `FIXED in a5f3bf2` (`FeatureId.parseOrNull` did not enforce the invariant `of()` does).** As raised: `parseOrNull` accepted any string whose every dot-segment matched the segment grammar, so `parseOrNull("anc")` returned a `FeatureId` with `namespace == localName == "anc"` — a one-segment identity `of()` refuses outright — in the entry point that will ingest protocol-database text in Phase 22. Now `common/FeatureId.kt:63-67` splits, returns null below `MIN_SEGMENTS` (2), and only then checks each segment, so both entry points enforce one grammar; the KDoc says so ("it enforces the same shape as [of], so a stored one-segment name cannot become an identity"). Closed with tests rather than prose: `FeatureIdTest` (`core/src/test/kotlin/com/omnibuds/core/common/FeatureIdTest.kt`, 7 tests, `test-plan.md` `TEST-P1-062`) pins `of("anc")` refusing, five malformed strings refusing to parse (`"NoiseControl.ANC"`, `"noise control.anc"`, `"noise-control."`, `".anc"`, `"noise-control..anc"`) plus `""`, a round-trip for a stored vendor id, and the `vendor.example` case that is a legal core identity but too shallow to name a vendor.

**Q-3 — One grammar, three encodings.** `capability/VendorFeatureMetadata.kt:58` declares `vendorSegmentPattern` as a private copy of `common/FeatureId.kt:40`'s `segmentPattern`, with a comment explaining that the kernel keeps its copy private; and `capability/VendorExtension.kt:88-95` re-derives with `feature.qualifiedName.split('.')` what `common/FeatureId.kt:33-34`'s `vendorName` already answers. The vendor-mismatch guard is only as strong as the three agreeing. **OPEN — and it is now the only grammar risk left in this area**, since Q-2 removed the divergent fourth path. **Action:** expose one validator/segment accessor on `FeatureId` and delete the duplicates — a small, safe widening of a `common` API that the layer map already permits (config/capability sit above `common`).

**Q-4 — `FeatureCapability.unsupported()` hard-codes the strongest evidence tier.** `capability/FeatureCapability.kt:146-156` returns a record with `verification = VerificationLevel.HARDWARE_VERIFIED` and no parameter to say otherwise. The type goes to real trouble to stop claims being inflated elsewhere — `SUPPORTED_PERSISTENT` requires `atLeast(HARDWARE_VERIFIED)`, `PERSISTENCE_VERIFIED` requires exactly `PERSISTENCE_VERIFIED` (`capability/FeatureCapability.kt:90-103`) — yet a positive-absence verdict can be constructed asserting hardware evidence nothing supplied. ARCH-QUAL-010/PROTO-CAP-001 govern this by prose ("only a conclusive negative earns this record"). **Action:** take `verification` as a parameter so the caller states its tier, or add a `labEstablished` variant; keep the affordance rules untouched.

**Q-5 — `FIXED in a5f3bf2, with ADR-P1-020` (two refusal styles for one state rule).** As raised: `DeviceSession` returned `Failure(INVALID_STATE)` when `ConnectionStateTransitions.canTransition` refused a move, while `DeviceState`'s connection mutator silently returned `this` for the same illegal move — two defensible-in-isolation styles meaning a caller could not distinguish "refused because illegal" from "nothing to do", and neither path pinned by a test. The resolution is stronger than picking a style: **there is no longer a second type with a connection field to disagree with.** `DeviceState.attemptConnection(next, atEpochMillis): OperationOutcome<DeviceState>` (`session/DeviceState.kt:88-108`) is the module's only connection mutator and it uses the structured form, failing with `OmniBudsErrorCategory.INVALID_STATE` and an `operationId` of `device-state.attemptConnection` while leaving the receiver and its `revision` untouched; `DeviceSession` keeps identity, evidence and the save choice and has no transition method at all. Both halves are now tested — `DeviceStateTest`'s `anIllegalConnectionMoveIsRefusedWithStructuredErrorAndChangesNothing` and `aLegalConnectionMoveAdvancesTheRevision` (`test-plan.md` `TEST-P1-060`) — so ADR-P1-004's three-case outcome model is what the next caller meets. The ADR-P1-020 record notes the rejected alternative (keep both, document one as derived) and why: a derived copy is still a copy.

**Q-6 — `DeviceSession` validates nothing.** `device/DeviceSession.kt:26-41` has no `init` block, so a blank `sessionId` is representable while `FeatureFlag` (`config/FeatureFlag.kt:26`), `CommandDefinition` (`protocol/CommandDefinition.kt:63`), `ProtocolDefinition`, `TransportRequest`, `TransportResponse`, `ParsedResponse`, `ResponseDefinition`, `CapabilityMapping`, `OmniBudsError`'s users and both repositories all refuse blank identifiers. The house style is "a blank identity identifies nothing" and this is the one type where it is not enforced; the finding *narrowed* rather than closed in `a5f3bf2`, because the trimmed type now has fewer fields to leave unchecked but is still the only place a session key enters the model unvalidated. Low impact while sessions exist only in memory; matters as soon as one is keyed into a store or a log line — and `sessionId` is precisely the key that now joins a `DeviceSession` to its `DeviceState`, so a blank one silently orphaned is a worse bug after ADR-P1-020 than before it. **OPEN.**

**Q-7 — Public map aliases beside private defensive copies.** `protocol/ProtocolDefinition.kt:81-83` copies `commands`, `responses` and `capabilityMappings` into private indexes used by every lookup and derived fact, while the public properties on lines 69-75 keep referring to the caller's maps — which a `MutableMap` handed in still owns, and which `data class copy()` propagates. `protocol/ParsedResponse.kt:33` does the same with `fields`. The asymmetry is documented (`protocol/ProtocolDefinition.kt:41-50` explains that lookups are tamper-proof and properties report original content), and `aCallerCannotSmuggleACommandIntoADefinitionItAlreadyBuiltTheMapFrom` pins the lookup half. But a reader who uses `definition.commands` gets a live view of the lookups' stale source, and equality compares the alias. By contrast `capability/DeviceCapabilities.kt:34` and `config/DeviceConfiguration.kt:50-51` copy correctly and say why. **Action:** make the public properties return the copies, or mark them `@Deprecated`-style as original-input-only in favour of the accessors.

**Q-8 — Two copies of the same numeric policy.** `protocol/CommandDefinition.kt:115-118` (`MIN_READ_ATTEMPTS = 1`, `MAX_READ_ATTEMPTS = 5`) and `config/ProtocolConfiguration.kt:57-66` (`MIN_READ_ATTEMPTS = 1`, `MAX_READ_ATTEMPTS_LIMIT = 5`) encode one rule — "read attempts are bounded 1..5" — in two areas, kept equal by prose ("These bounds match `ProtocolConfiguration`") and by mirrored tests (`CommandDefinitionTest.aReadMustDeclareAnAttemptBudgetAndCannotEscapeTheCeiling`, `ConfigurationSeparationTest.protocolConfigurationRejectsAReadBudgetOutsideTheOneToFiveWindow`). The layer map (config at 2, protocol at 4) forbids the natural shared home, so the fix is a `common` constant, which the direction rule does permit.

**Q-9 — Byte-array ownership is documented but not protected, in two hand-written `equals` that differ.** `transport/TransportRequest.kt:31` and `transport/TransportResponse.kt:32` carry `ByteArray` without copying, with an explicit reason ("copying it here would imply the transport may queue a request and send the bytes that exist whenever it wakes up"). That is a coherent decision, and it makes every `copy()`/`componentN()` a path to a shared mutable array. Separately, `TransportRequest.equals` (line 52-58) begins with the `this === other` fast path and `TransportResponse.equals` (line 56-61) does not — a small inconsistency between two implementations of one concern, which is what ARCH-QUAL-005 is about in miniature.

**Q-10 — Import hygiene, unchecked by anything.** Four files have imports that are not in lexicographic order — `capability/FeatureCapability.kt`, `protocol/ProtocolDefinition.kt`, `transport/TransportContract.kt`, `transport/TransportAvailability.kt` (each placing `common.TransportKind` after `state.*` or after another `common` import, a residue of the ADR-P1-003a move). Two files (`transport/TransportContract.kt:3-6`, `transport/TransportAvailability.kt:3-6`) have a blank line *inside* the import block. `diagnostics/OmniBudsLogger.kt:3-4` imports two types from its own package — redundant, though the names are used, so no compiler diagnostic applies and the warnings-as-errors gate correctly stays silent. All five are exactly what ktlint/Spotless would have removed for free. **Action:** one formatting pass plus either an ADR to add ktlint to `check`, or a stated decision to keep the baseline as-is and accept this drift.

**Q-11 — `FIXED in a5f3bf2` (no `.editorconfig` in the repository).** As raised: ADR-P1-011 claimed "an `.editorconfig`-style convention set documented in `specs.md`" and `gradle.properties` set `kotlin.code.style=official`, but no `.editorconfig` existed to make an editor honour it — a missing artifact that made the ADR's wording untrue. `.editorconfig` is now at the repository root (`root = true`, 4-space space indent, `max_line_length = 120`, UTF-8, LF, final newline, trailing-whitespace trimmed; 2-space for YAML/JSON/TOML; whitespace and length relaxed for Markdown), with a header that says it records conventions the build already enforces rather than adding a tool. The ADR's baseline is therefore accurate as written. What this does **not** buy: no Gradle task reads the file, so Q-10's drift class is still unchecked — that remains a lint-gate decision, not a formatting-file decision.

**Q-12 — A dangling KDoc link in the type whose job is precise error naming.** `protocol/ParsedResponse.kt:19` writes "is a [ProtocolMismatch] from the parser", but no `ProtocolMismatch` symbol exists — the real member is `OmniBudsErrorCategory.PROTOCOL_MISMATCH`, correctly linked from `protocol/ProtocolParser.kt:12-14` and `protocol/ResponseDefinition.kt:11-12`. With no Dokka/linkage check in the build (Q-10's cost), a broken reference like this reads as a type name that a future reader will search for and not find. **OPEN.**

**Q-13 — `FIXED in a5f3bf2, with ADR-P1-021` (`:core` declared a production dependency no main source used).** `api(libs.kotlinx.coroutines.core)` was justified as "hardware operations are suspending and state will be exposed as `Flow`". Neither half held: `suspend` is a language feature needing no library, and no `Flow` exists anywhere in the module — a census over all 71 main files finds zero `kotlinx.coroutines` references. Prompt §34 and ADR-P1-011 require a reason per dependency, and an unused one is not neutral: it is a false claim about what the code does, and it widened the KMP surface that Phase 46 must prove portable by one artifact for nothing. Removed from `core/build.gradle.kts` and from `gradle/libs.versions.toml`, with `kotlinx-coroutines-test` retained as `testImplementation` because the 13 `runTest` cases genuinely need it. `:core` now has **zero production dependencies**, and the build file comments state when the library returns (the first `Flow` surface, in the Phase 2 state engine, with a recorded reason).

**Non-findings, recorded so they are not re-litigated.** The absence of detekt/ktlint/Spotless/MockK/Android-lint is a decision with reasons and a stated cost (`ADR-P1-011`), not an oversight, and section 1 of this review states what that cost actually buys and loses. `ADR-P1-019`'s deliberate non-implementation of a redaction helper, `ADR-P1-010`'s deferred serialisation, `ADR-P1-018`'s open per-endpoint codec gap and `ADR-P1-015`'s provisional `minSdk 26` are recorded gaps with owners, and the code reflects each one honestly rather than half-implementing it.

## 10. Verdict

The code is clean in the ways that are hard and cheap in the ways that are easy. Its discipline — invariants in `init` rather than in reviewers, ordinal ladders rather than boolean clusters, nullable-plus-validated rather than defaulted, sealed outcomes rather than exceptions across a boundary, **no production dependency at all** rather than five — is exactly what Phase 0's rule set asked for, and the enforcement is mechanical where it matters most. Documentation density (2,807 of 5,196 main lines, 54%) is not decoration: it carries the reason for each invariant, which is what let this review find Q-1 to Q-8 at all. Q-1 is the cautionary tale that density buys: prose is a claim, and a claim that outlives the code it described is worse than no prose, because it reads like a reason.

Where this review stands after commit `a5f3bf2`: five findings — Q-1 (stale kernel-defect documentation and its dead OR branch), Q-2 (`parseOrNull` bypassing the identity invariant), Q-5 (two owners and two refusal styles for one state rule), Q-11 (the missing `.editorconfig`) and Q-13 (an unused production dependency) — are **fixed**, each with the change that carries it named above, and Q-1's residual survives only as stale KDoc inside `VendorExtensionTest`. Four are **open and worth closing before Phase 2**: Q-4 (a hard-coded evidence tier on the unsupported path), Q-6 (an unvalidated `sessionId`), Q-3 (one grammar in three places, now the only remaining grammar risk), and the test-KDoc residue of Q-1. Three are duplication that will drift (Q-7, Q-8, Q-9), and two are the visible price of choosing a compiler-only baseline (Q-10, Q-12) — honest evidence to weigh when a later phase decides whether to pay for a linter.
