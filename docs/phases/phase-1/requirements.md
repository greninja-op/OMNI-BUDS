## Build, modules and boundaries

### REQ-P1-001 — The project compiles
**Description.** The build SHALL compile `:core` and `:platform:android` and SHALL run the whole Phase 1 test suite with zero failures, zero errors and zero skipped tests, via the wrapper and nothing else.
**Rationale.** Prompt §33 and §50: an architecture that does not compile is a sketch, and a foundation that needs a system Gradle or a hand-assembled classpath cannot be rebuilt by the next session (ADR-P1-014).
**Dependencies.** REQ-P1-012; ADR-P1-001, ADR-P1-014.
**Acceptance criteria.** AC-1 `./gradlew build` reaches BUILD SUCCESSFUL from a clean checkout. AC-2 `:core` compiles for JVM target 17 and `:platform:android` assembles as an Android library. AC-3 the test task reports 302 tests, 0 failures, 0 errors, 0 skipped. AC-4 the compilation emits zero warnings — with `allWarningsAsErrors = true` a warning fails the build rather than decorating it. AC-5 no build step depends on a Gradle or JDK installation outside the pinned wrapper and the `JAVA_HOME` selected per invocation.
**Verification.** `./gradlew build` (executed by the orchestrator at HEAD `a5f3bf2`), then the `:core` test report. This is a build-run record, not a test: it is re-proved by re-running the task, and no test asserts it.
**Priority.** MUST · **Status.** tested (build task)

### REQ-P1-002 — Core remains platform-independent
**Description.** The `:core` main source set SHALL import no Android type, no JVM-only `java.*`/`javax.*` type, and SHALL contain no Bluetooth or media-audio framework reference of any kind.
**Rationale.** Prompt §7, §8 and §32; master §51. The rule is the one a later commit breaks most easily, and prose did not stop it — so it is machine-checked (ADR-P1-003, ADR-P1-011).
**Dependencies.** REQ-P0-001; ADR-P0-008, ADR-P1-003, ADR-P1-012, ADR-P1-021.
**Acceptance criteria.** AC-1 no import begins `android.`, `androidx.` or `com.omnibuds.android.`. AC-2 no import begins `java.` or `javax.`. AC-3 no code line names `Bluetooth<anything>`, `AudioTrack`, `AudioManager`, `AudioRecord` or `MediaPlayer`. AC-4 each scan fails loudly when the source root is missing or empty, so a moved directory cannot make the rule pass by finding nothing. AC-5 no main source imports any external coordinate at all — `kotlinx.*` included — which ADR-P1-021 secured by deleting the last production dependency from `:core`.
**Verification.** `architecture/DependencyDirectionTest.coreMainSourcesDoNotImportAndroidFrameworks`, `.coreMainSourcesDoNotImportJvmOnlyLibraries`, `.coreReferencesNoBluetoothOrAudioFrameworkTypes`, with the fail-loudly clause in `.mainSources()`. The only `java.*` reference in the module is inside `diagnostics/DiagnosticEvent.kt` KDoc text, which the scan strips as a comment. AC-5 is established by that same import census plus **inspection** of `core/build.gradle.kts`: the area-layer rule sees `com.omnibuds.core.*` edges only, so an external library would not fail it — no test asserts the empty `dependencies {}` production block.
**Priority.** MUST · **Status.** partly-tested (AC-5: inspected)

### REQ-P1-003 — Android-specific code is isolated
**Description.** Android-facing code SHALL live only behind `:platform:android` (namespace `com.omnibuds.android`), which SHALL depend on `:core` and SHALL NEVER be depended upon by `:core`; in Phase 1 that module SHALL hold zero Kotlin sources and a manifest with no permissions, components or intent filters.
**Rationale.** Prompt §7 and §52; ADR-P1-001 keeps the boundary real and compilable without pretending to have platform code. An empty boundary module is a claim of structure, so its emptiness is asserted rather than remembered.
**Dependencies.** REQ-P1-002, REQ-P1-015; ADR-P1-001, ADR-P1-015, ADR-P0-001.
**Acceptance criteria.** AC-1 `platform/android/src/main` contains no `.kt` file. AC-2 `settings.gradle.kts` includes exactly `:core` and `:platform:android`, and only `:platform:android` declares `api(project(":core"))`. AC-3 the manifest element carries no `uses-permission`, no `<application>` and no component. AC-4 no `:core` source may name `com.omnibuds.android`.
**Verification.** AC-1 by `architecture/DependencyDirectionTest.platformAndroidModuleStillContainsNoSources`; AC-4 by `.coreMainSourcesDoNotImportAndroidFrameworks`; AC-2 and AC-3 **by inspection** of `settings.gradle.kts`, `platform/android/build.gradle.kts` and `platform/android/src/main/AndroidManifest.xml` — no check parses the manifest, so the no-permissions claim is a reading, not a test result.
**Priority.** MUST · **Status.** partly-tested

### REQ-P1-004 — Future KMP portability is preserved
**Description.** The platform-independent contracts SHALL be written so that moving `:core` to a multiplatform `commonMain` in Phase 46 requires no domain rewrite: no JVM-only library, no wall clock inside core, no platform type in any public signature.
**Rationale.** Prompt §8. A `java.time` import or a `System.currentTimeMillis()` call inside a domain type is invisible at review time and fatal at port time (ADR-P1-012).
**Dependencies.** REQ-P1-002, REQ-P1-003; ADR-P1-012, ADR-P0-008.
**Acceptance criteria.** AC-1 no `java.*`/`javax.*` import in main source. AC-2 every timestamp is `Long` or `Long?` epoch milliseconds, never a date-time type. AC-3 no `:core` type reads a clock; `SnapshotBuilder.build(capturedAtEpochMillis)` and every `DeviceState` mutator (`atEpochMillis`) take the reading from the caller, and `DeviceSession.createdAtEpochMillis` is a constructor value the session never fills in itself. AC-4 no main source imports `kotlinx.coroutines.*` at all — only `suspend`, a language feature, is used — and `:core` declares no production dependency to carry across a target boundary (ADR-P1-021). AC-5 `:platform:android` is the only module with a platform plugin.
**Verification.** AC-1 by `architecture/DependencyDirectionTest.coreMainSourcesDoNotImportJvmOnlyLibraries`. AC-2, AC-3, AC-4 are established **by inspection** of `session/DeviceState.kt`, `device/DeviceSession.kt`, `diagnostics/SnapshotBuilder.kt`, `persistence/*`, `core/build.gradle.kts` and the import list of all 71 main files; no test forbids a clock call. One migration residue is recorded honestly: `common/FeatureId.kt` uses `@JvmInline value class` resolved through the JVM default import, so a `commonMain` move needs an explicit `import kotlin.jvm.JvmInline`. Phase 46 owns that conversion.
**Priority.** SHOULD (the obligation is to *not foreclose* portability; its payoff and full proof belong to Phase 46) · **Status.** partly-tested

## Domain foundations

### REQ-P1-005 — Device identity supports unknown values
**Description.** Every `DeviceIdentity` field SHALL be nullable and SHALL stay null when unreported; blank text SHALL normalise to unknown; a merge SHALL fill only unknown fields and SHALL never restate an established one; the type SHALL hold no Bluetooth address.
**Rationale.** Master §53, ADR-P0-016: a fabricated manufacturer is how a support claim starts. `SEC-ID-001/003/004` keep an address out of identity (prompt §9.1).
**Dependencies.** REQ-P0-002; ADR-P0-016, ADR-P1-010; prompt §9.1, §10.
**Acceptance criteria.** AC-1 all four fields (`manufacturer`, `model`, `displayName`, `modelId`) nullable, `unknown()` returns all-null and never empty strings. AC-2 `"  "` counts as unknown and cannot win a field. AC-3 `knownFieldCount`/`isFullyKnown` count blank text as nothing known. AC-4 `mergedWith` keeps the receiver's established value even when the incoming one differs, and never splices a hybrid. AC-5 `FirmwareInfo` holds version text with a mandatory `verification` level and no default; a missing version stays null rather than `0` or `"0.0.0"`. AC-6 `DeviceFingerprint.identityKey()` folds the address separator `':'` out of every token, so an address cannot survive into the key.
**Verification.** `device/DeviceIdentityTest` (11 tests), notably `.unknownManufacturerStaysNullAndCountsAsNothingKnown`, `.blankTextIsTreatedAsUnknownRatherThanAsAValue`, `.mergeNeverRestatesAKnownFieldWithADifferentValue`, `.mergeNeverLetsBlankTextWinAField`, `.reportedTextIsTrimmedButNeverInvented`; AC-5 by `.firmwareMissingStaysMissingRatherThanBecomingVersionZero` and `.blankVersionTextIsNotCountedAsAVersion`; AC-6 by `device/DeviceFingerprintTest.addressTextCannotSurviveIntoTheIdentityKey` with `.nothingObservedProducesTheExplicitlyRecognisableNothingKnownKey`. The absence of any address *field* is established by reading `DeviceIdentity.kt` and `DeviceFingerprint.kt`, not by a test.
**Priority.** MUST · **Status.** tested (field-absence clause: inspected)

### REQ-P1-006 — Capability model supports all six states
**Description.** Capability SHALL be modelled as the six-rung `CapabilityState` ladder with affordances and evidence constrained by construction, and an unexamined feature SHALL read `UNKNOWN` rather than `UNSUPPORTED` or an error.
**Rationale.** Master §10, §53; REQ-P0-006, REQ-P0-007; prompt §13, §14. `supported = true` cannot express write-only, volatile, unverified or unknown (PROTO-CAP-001/004).
**Dependencies.** REQ-P0-006, REQ-P0-007, REQ-P0-002; ADR-P1-003 (kernel/state layering), ADR-P1-008.
**Acceptance criteria.** AC-1 all six values constructible and distinct. AC-2 affordances follow the rung: `UNKNOWN` and `UNSUPPORTED` permit neither read nor write; `READ_ONLY` requires readable and forbids writable; the three `SUPPORTED_*` rungs require both. AC-3 `SUPPORTED_PERSISTENT` requires at least `HARDWARE_VERIFIED`, `PERSISTENCE_VERIFIED` requires exactly `PERSISTENCE_VERIFIED`. AC-4 a lookup miss returns `UNKNOWN` and never throws. AC-5 `isControllable` is derived from state, never from the writable flag. AC-6 a merge never downgrades a stronger established rung, and a tie keeps the receiver's record. AC-7 `DeviceCapabilities` copies the map it is handed.
**Verification.** `capability/FeatureCapabilityTest` (19) — `.allSixStatesAreConstructibleAndRemainDistinct`, `.unknownCarriesNoAffordanceBecauseNothingIsEstablished`, `.readOnlyIsReadableAndRefusesToWrite`, `.aPersistenceClaimCannotRestOnLabEvidence`, `.observedSurvivalIsTheOnlyEvidenceForPersistenceVerified`, `.controllabilityIsDerivedFromStateAndNeverFromTheFlags`, plus the five rung-refusal cases; `capability/DeviceCapabilitiesTest` (18) — `.anAbsentFeatureIsUnknownAndNotUnsupported`, `.theEmptyContainerAnswersEveryQuestionWithoutThrowing`, `.aMergeNeverDowngradesObservedPersistenceToSessionOnlySupport`, `.aTieKeepsTheReceiversRecordWholesaleAndIsDeterministic`, `.aHandedInMapIsCopiedSoLaterEditsCannotReachTheSnapshot`; `.theCoreCatalogueAnsweredAgainstAnEmptySnapshotIsUnknownEverywhere`.
**Priority.** MUST · **Status.** tested

### REQ-P1-007 — Audio model represents codec state
**Description.** Codec state SHALL be one ordinal ladder (`UNKNOWN < UNSUPPORTED < SUPPORTED < AVAILABLE < ENABLED < NEGOTIATED < ACTIVE`) with `configurable` as an orthogonal attribute, and each audio measurement SHALL stay unknown independently.
**Rationale.** Prompt §17 proposed six booleans that permit `active = true, supported = false`; ADR-P1-005 replaces them (amending ADR-P0-015). Master §15, §16, §19, §20; AUD-STATE-001..005, AUD-QUAL-004.
**Dependencies.** REQ-P0-009, REQ-P0-010, REQ-P0-011; ADR-P1-005, ADR-P1-018.
**Acceptance criteria.** AC-1 ladder order is load-bearing and `supportsAtLeast` refuses positive targets for `UNKNOWN`/`UNSUPPORTED`. AC-2 `isActive` is true only at `ACTIVE` and is never `negotiated || enabled`. AC-3 `Codec` carries SBC, AAC, four separate aptX entries, LDAC, LC3 and `UNKNOWN`; LC3 sits in `CodecFamily.LE_AUDIO`. AC-4 `AudioTransportState` reports transport, codec, state, sample rate, bit depth, bitrate, channel mode and quality mode, each independently unknown, with `bitsPerSample` constrained to 8..32 and positive-only rates and bitrates. AC-5 `unobserved()` carries no fabricated numbers. AC-6 registry membership yields no availability claim, and an unrecognised label resolves to null rather than to the nearest codec.
**Verification.** `audio/CodecStateTest` (7), `audio/CodecCapabilityTest` (5 — `.ldacEnabledWhileAacActiveKeepsBothFactsSeparate`, `.contradictoryActiveAndUnsupportedIsUnrepresentable`, `.configurableIsOrthogonalToTheLadder`), `audio/CodecTest` (6 — `.aptxVariantsAreFourDistinctCodecs`, `.lc3IsLeAudioWhileLdacAndAacAreClassicA2dp`, `.everyPromptNamedCodecHasAnEntry`, `.unknownLabelIsNotGuessedOntoARealCodec`), `audio/CodecRegistryTest` (6), `audio/AudioTransportStateTest` (7 — `.unobservedStateCarriesNoFabricatedNumbers`, `.outOfRangeMeasurementsAreRejected`, `.activeStateIsTheOnlyOneThatClaimsToCarryAudio`). **Open gap:** per-endpoint codec support (AUD-STATE-003) is not modelled — one `CodecCapability` per codec — deferred to Phase 11 by ADR-P1-018; nothing tests that limitation because nothing can express it yet.
**Priority.** MUST · **Status.** tested (per-endpoint dimension: deferred to Phase 11, ADR-P1-018)

### REQ-P1-008 — Device session distinguishes active from saved
**Description.** Connection progress and user-saving SHALL be two orthogonal types — an eleven-value `ConnectionState` and a two-value `SessionClassification` — held by **different** owners after ADR-P1-020 (`connection` on `DeviceState`, `classification` on `DeviceSession`), and an illegal state move SHALL be refused as a structured failure.
**Rationale.** Prompt §12 and §24; ADR-P1-016 supersedes Phase 0 `specs.md` §2.3's mixed `SessionState`, because a second source of truth for "is it merely stale?" is exactly the failure prompt §24 forbids. ADR-P1-020 applied the same rule inside Phase 1's own types: `DeviceSession` used to carry a `ConnectionState` beside `DeviceState`'s. Master §5.
**Dependencies.** REQ-P0-004, REQ-P1-017; ADR-P1-016, ADR-P1-003c, ADR-P1-012, ADR-P1-020.
**Acceptance criteria.** AC-1 `ConnectionState` has the eleven values, including `TEMPORARILY_UNAVAILABLE`, and `UNKNOWN` is not `DISCONNECTED`. AC-2 `CONNECTING`, `ACTIVE_SESSION`, `STALE` and `FORGETTABLE` are expressed by combinations, not by a third enum. AC-3 `DeviceState.attemptConnection` returns `Failure(INVALID_STATE)` for an illegal move rather than throwing or silently succeeding, and a refused move leaves the receiver's connection and `revision` untouched; every state may reach `ERROR`; a self-move is idempotent. AC-4 `save()` and `forget()` change `classification` only — no identity, no fingerprint, no creation time is touched, and no hardware claim is made. AC-5 a new session is `TEMPORARY` until an explicit `save()`; `withEvidence` fills only unknown identity fields; a supplied fingerprint replaces rather than merges the previous one. AC-6 a move or update with no observed time leaves `lastUpdatedEpochMillis` unknown instead of inheriting the previous stamp, and an unrecorded session creation time stays unrecorded. AC-7 only `READY` and `CONTROL_SESSION` are operational, as answered by `DeviceState.isOperational`. AC-8 `DeviceSession` declares no connection-state property at all (ADR-P1-020).
**Verification.** `session/DeviceStateTest` (12) — `.aLegalConnectionMoveAdvancesTheRevision`, `.anIllegalConnectionMoveIsRefusedWithStructuredErrorAndChangesNothing`, `.everyStateCanFallIntoErrorAndASelfMoveIsIdempotent`, `.anInitialStateAssertsNothingAboutAnything`, `.operationalOnlyWhileReadyOrInAControlSession` for AC-1, AC-3, AC-6, AC-7. `device/DeviceSessionTest` (7) — `.afreshSessionIsTemporaryUntilTheUserSaysOtherwise`, `.savingChangesNothingExceptTheClassification`, `.forgettingDropsTheSavedChoiceAndClaimsNothingAboutTheHardware`, `.evidenceFillsUnknownsWithoutOverwritingWhatIsAlreadyKnown`, `.aNewFingerprintReplacesTheOldOneRatherThanMergingTwoObservations`, `.evidenceWithNoIdentityChangeLeavesTheSessionUntouched`, `.anUnrecordedCreationTimeStaysUnrecorded` for AC-4, AC-5, AC-6. AC-2's *supersession* of Phase 0's `SessionState` is established by ADR-P1-016 and the absence of such a type in `state/`, and AC-8 by reading `device/DeviceSession.kt`'s five declared properties — no test asserts either absence mechanically.
**Priority.** MUST · **Status.** tested (supersession and single-owner clauses: inspected, ADR-P1-016 / ADR-P1-020)

## Abstractions and enforcement

### REQ-P1-009 — Protocol abstractions do not fake hardware behavior
**Description.** `EarbudProtocol` SHALL declare only `identify`, `discoverCapabilities` and `readState`; every narrower operation SHALL live in an optional capability interface; and no production type SHALL implement a protocol, transport or repository contract.
**Rationale.** Prompt §26 and §53; master §9; ADR-P1-007. A mandatory `writeEqualizer()` can only be satisfied by a fake that reports success, which is how fabricated support begins.
**Dependencies.** REQ-P1-015, REQ-P1-016, REQ-P0-002; ADR-P1-007, ADR-P1-013.
**Acceptance criteria.** AC-1 the core interface holds three suspend operations plus `protocolId`. AC-2 `FeatureReadSupport`, `FeatureWriteSupport`, `BatteryReportingSupport`, `FirmwareReportingSupport`, `AudioStateReportingSupport` are separate interfaces, addressed generically over `FeatureId` and `ConfigurationValue`. AC-3 `ProtocolRegistry` ships empty: no record, no lookup hit, no candidate. AC-4 ANC, EQ and gesture value semantics are not invented; unmodelled values travel as `ConfigurationValue`. AC-5 `identify` can answer `FALLBACK_UNKNOWN` with confidence capped at `INFERRED`. AC-6 `ProtocolParser`, `ProtocolEncoder`, `TransportContract` and every repository are contracts with zero implementations in either source set.
**Verification.** AC-3 by `protocol/ProtocolRegistryTest.noProtocolRecordShipsInPhase1`, `.anEmptyRegistryAssertsNothingAboutAnyProtocolId`, `.anEmptyRegistryOffersNoCandidatesForAnyFingerprint` and `testing/TestDoublesAreNotHardwareTest.anUnscriptedProtocolSeamMatchesNoProtocolForAnyFingerprint`; AC-6 by `architecture/DependencyDirectionTest.noProductionClassImplementsTheProtocolOrRepositoryContracts`; AC-5 by `protocol/ProtocolIdentificationTest.theFallbackAnswerIsExpressibleAndIsNotAMatch` and `.aFallbackCannotBorrowTheConfidenceOfARealMatch`; AC-1, AC-2 and AC-4 by **inspection** of `protocol/EarbudProtocol.kt`, the five reporting interfaces and `config/ConfigurationValue.kt` — the interface shape is read, not executed, because nothing implements it.
**Priority.** MUST · **Status.** partly-tested

**Dependencies.** REQ-P1-021, REQ-P1-001; ADR-P1-011, ADR-P1-013.
**Acceptance criteria.** AC-1 302 tests across 37 classes pass with 0 failures, 0 errors, 0 skipped. **Priority.** MUST · **Status.** partly-tested

### REQ-P1-011 — Dependency direction is enforceable
**Description.** Core areas SHALL be ordered into layers and an import SHALL be permitted only into a strictly lower layer or the importing file's own area, with every area registered in the map.
**Rationale.** Prompt §32; ADR-P1-003, whose three real violations the enforcement test found and forced fixed. Prose dependency rules did not survive contact with code.
**Dependencies.** REQ-P0-001, REQ-P1-002; ADR-P1-003, ADR-P1-003a, ADR-P1-003b, ADR-P1-003c, ADR-P1-020.
**Acceptance criteria.** AC-1 layer map: `common`=0; `state`, `transport`=1; `device`, `capability`, `audio`, `config`, `diagnostics`=2; `session`, `persistence`=3; `protocol`=4. AC-2 a same-layer cross-area import fails, as does an upward one. AC-3 an unregistered area fails rather than being absorbed silently. AC-4 package statements match directories, since every import rule depends on that. AC-5 the three ADR-P1-003 violations are absent: `TransportKind` sits in `common`, the logging seam sits in `diagnostics`, `DeviceState` sits in `session`, and `session` remains the only area that owns connection state after ADR-P1-020.
