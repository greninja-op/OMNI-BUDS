**Phase:** 1 — Project Foundation & Kotlin Architecture · **Scope id:** `P1` · **Owner agent:** Agent 4 (testing) / orchestrator as integration owner
**Instantiates:** `docs/phases/phase-0/testing-governance.md` (tiers T1–T8, mandatory record TST-REC-001, grammar TST-REC-002, matrix TST-REC-006) using `docs/templates/test-plan-template.md`.
**ID discipline.** Prompt section 49 seeds ids in the `P1-BUILD-001` form; `ADR-P0-013` fixes the canonical grammar as `TEST-<SCOPE>-<NNN>`, so every test below carries `TEST-P1-<NNN>` and section 3 maps each seed id onto it. Ids are allocated monotonically and are never renumbered (TST-REC-002).
**Record shape.** One record per executing test cluster. Each record names the **exact `@Test` method names on disk** in `core/src/test/kotlin/`, so the cluster counts sum to the executed total of 301. No method name in this file is paraphrased.

## 1. What was run, and what it can prove

- `./gradlew build` → **BUILD SUCCESSFUL**; test execution: **302 tests, 0 failures, 0 errors, 0 skipped** (JUnit 5 XML results under `core/build/test-results/test/`, run 2026-10-01 against HEAD `a5f3bf2`, the commit that gave connection state one owner and closed the review findings).
- Framework: JUnit 5 via `useJUnitPlatform()` in `core/build.gradle.kts`, with `kotlin.test` assertions and `kotlinx-coroutines-test` (`runTest`) for the 13 suspending cases in `DeviceRepositoryContractTest` and `TestDoublesAreNotHardwareTest`. `kotlinx-coroutines-test` is **test-only**: `:core` now has no production dependency at all (ADR-P1-021), so no record in this plan runs against a coroutine library in `src/main`.
- Size: 71 main Kotlin files / 5,196 lines; 41 test files / 5,885 lines (37 test classes plus 4 test-only doubles in `com.omnibuds.core.testing`).
- **Every one of the 302 is tier `T1` (unit).** All are JVM unit tests. No hardware, no phone, no emulator, no Bluetooth stack, no instrumentation test and no coverage tool was used, and no CI exists.
- **Evidence ceiling.** Per `testing-governance.md` §2.1, a T1 pass justifies at most `IMPLEMENTED`. Nothing in this plan justifies `LAB_TESTED`, `HARDWARE_VERIFIED` or `PERSISTENCE_VERIFIED`, and nothing in it is evidence that any device supports anything (`TST-MOCK-001`, `TST-GOV-004`, `TST-ACC-006` by analogy). Codec `ACTIVE`/`NEGOTIATED`, capability persistence and every hardware claim remain **unavailable**, not merely untested.
- **Ceiling conflict, surfaced not resolved silently.** `docs/templates/test-plan-template.md` §3 lists the unit tier as able to earn `LAB_TESTED`; `testing-governance.md` §2.1 caps T1 at `IMPLEMENTED`. Governance is the stricter rule and TST-GOV-001 forbids a phase relaxing it, so **`IMPLEMENTED` is used throughout this plan**. The orchestrator should normalise the template row.
- `UNKNOWN` never becomes `false`, `0` or `UNSUPPORTED` anywhere in this plan or in the code it describes (`TST-FAIL-001` row 6).

## 14. Defects found and fixed during integration — evidence the suite bites

D-1 to D-3 were found by the tests, and **all three were defects in tests or architecture claims, not in shipped production behaviour**. D-4 to D-7 were found by the Phase 1 review pass rather than by a failing test, which is the other half of the honest record: the suite did not catch them, the reviews did. All seven are recorded because a suite that has never failed is not yet trusted.

**D-1 — self-contradicting battery asymmetry assertion.** A Phase 1 asymmetry case asserted both that a one-sided reading is asymmetric and that asymmetry requires both sides, which cannot both hold; the assertion contradicted itself and the correct expectation is `isAsymmetric == false` when either side is unknown. Fixed in `BatteryStateTest.asymmetryIsOnlyClaimedWhenBothSidesAreKnown` and pinned further by `asymmetryHoldsInEitherDirectionAndAcrossZero` (`TEST-P1-022`). Production `BatteryState.isAsymmetric` was already correct.

**D-2 — codec registry ordering assertion hard-coded the wrong alphabetical order.** A registry listing case asserted an expected order that was not the declaration order the model actually guarantees, so it encoded a wrong literal list rather than the invariant. Fixed by expressing the assertion as the property under test — `CodecRegistryTest.allIsDeclarationOrderWithoutDuplicates` now compares `CodecRegistry.all` against `Codec.entries` filtered of `Codec.UNKNOWN` (`TEST-P1-030`) instead of a hard-coded sequence.

**D-3 — the layer map caught three real architecture mistakes.** `DependencyDirectionTest.coreAreasDependOnlyOnMoreFoundationalAreas` produced a violation set that was not a test bug: three genuine dependency-direction errors in the code, fixed under **ADR-P1-003** as recorded there — `common -> transport` (resolved by moving `TransportKind` into `common`), `logging -> diagnostics` (the logging seam folded into `diagnostics`), and a `state <-> capability/device/audio` cycle (`DeviceState` moved to a new `session` area above all three). This is the clearest evidence in the phase that the architecture tests do work: they failed, and the code changed.

**D-4 — two owners of one connection state (architecture, fixed before the phase closed).** `DeviceSession.connectionState` and `DeviceState.connection` held the same fact for the same device, unlinked by anything, which is the disagreement prompt §24 forbids and the reason architecture-review question 8 was first answered NO. Fixed under **ADR-P1-020**: `DeviceState.attemptConnection` is now the only mutator of connection state and returns `Failure(INVALID_STATE)` on an illegal move, and `DeviceSession` keeps only `sessionId`, `identity`, `fingerprint`, `classification` and `createdAtEpochMillis`. The mechanism is pinned by `TEST-P1-060`/`TEST-P1-061` (12 tests), which did not exist when the defect was live — an unexercised safety mechanism is how D-4 survived as long as it did.

**D-5 — `FeatureId.parseOrNull` admitted a name the grammar refuses (code-quality Q-2).** `of()` required at least two segments while `parseOrNull` checked only each segment's shape, so stored text such as `anc` could decode into an identity nothing else uses — in the read path Phase 22 will key protocol records on. Fixed in the same commit by enforcing the `MIN_SEGMENTS` floor on both paths, and pinned by `FeatureIdTest` (`TEST-P1-062`).

**D-6 — documentation asserted a kernel defect that had already been repaired (code-quality Q-1).** `VendorExtension`'s KDoc still described `FeatureId.isVendorExtension` as broken "today" and `isVendorFeature` ORed two equivalent checks, so the right operand was dead code and a reader trusting the prose would "fix" correct code. Fixed by deleting the stale workaround section and reducing the guard to `feature.isVendorExtension`; `VendorExtensionTest.aVendorNamespacedIdentityIsAcceptedAndRecognised` still passes (`TEST-P1-026`), which is the evidence the behaviour never depended on the dead branch.

**D-7 — `:core` declared a production dependency no main source used (ADR-P1-021).** `kotlinx-coroutines-core` was an `api` dependency, but no file in `core/src/main` imports `kotlinx.coroutines`: `suspend` needs no library and no `Flow` exists yet. An unused dependency is a false claim about what the code does, and it weakened the KMP position by adding an artifact to prove portable. Removed from `core/build.gradle.kts`, and `kotlinx-coroutines-core` no longer appears in `gradle/libs.versions.toml` at all: the catalog keeps only `kotlinx-coroutines-test`, resolved from the same pinned `kotlinCoroutines = "1.9.0"` version and declared `testImplementation`, which is why the 13 suspending cases in `TEST-P1-050` and `TEST-P1-051` are unaffected.
