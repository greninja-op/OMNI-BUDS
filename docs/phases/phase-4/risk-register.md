# Phase 4 — Risk Register

**Numbering continues the single project-wide register and does not restart it.** Phase 0 wrote `RISK-001` … `RISK-015`, Phase 1 `RISK-016` … `RISK-025`, Phase 2 `RISK-026` … `RISK-043`, Phase 3 `RISK-044` … `RISK-064`, so **Phase 4 begins at `RISK-065`** and runs to `RISK-085` — twenty-one entries, the same count as Phase 3's. Scale as in all four earlier registers: probability and impact are `low | medium | high`, exposure = probability × impact, and the word `severe` marks the high × high band Phase 0 introduced. **Two entries here sit in it — RISK-065 and RISK-066 — and neither is new: both are Phase 3's RISK-044 and RISK-045 carried forward into a layer that has never been nearer a handset either.** That is the honest shape of the count. Phase 3 said three of its twenty-one were severe; Phase 4 has not reduced that number by any amount, it has simply not added to it, and it will not be reduced by further design work either. Field shape is Phase 2's, unchanged: id + title, then probability/impact/exposure, status where the entry's own text qualifies it, description, mitigation, detection, fallback, owner.

**Pre-cited ids were checked before allocation, and this time the check had a second job.** A `grep` for every `RISK-0…` number above `064` across the whole `docs/` tree returned two hits and no more: `docs/phases/phase-3/risk-register.md:5`, which is Phase 3's own record of *refusing* to mint a stray `RISK-065` it had found in a draft of its `validation.md`, and `docs/phases/phase-4/architecture-audit.md:170`, which allocates `RISK-065` as Phase 4's starting number and states at `:171-172` that it verified the number was free by running the same grep. The two are consistent — Phase 3 declined to mint it, so it was genuinely unallocated — and this register honours the audit's allocation rather than re-deriving it. The audit also cites `RISK-044`, `RISK-058` and `RISK-038` as earlier-phase entries Phase 4 inherits (`:177`, `:183`), and each of those is **re-scored here under its own number**, not re-minted. Two further audit sentences are honoured as instructions to this file: `:177` requires the register to treat the handset deferral as an inherited evidence limit rather than a missing mechanism, which is RISK-065 and RISK-066 below; and `:183` says `RISK-038` — the `docs/phases/phase-0/bluetooth-governance.md` that still does not exist — is "recorded again in this phase's risk register rather than repaired here", which is the final section's job and is done there. **The grep was re-run after this register was written, because Phase 4 has five sibling records landing concurrently and a numbering claim is a claim about a moving tree** (Phase 3's `:5` is the precedent for saying so rather than for pretending the check was once-and-for-all): `requirements.md`, `design.md`, `specs.md` and `task-list.md` cite exactly two `RISK-0…` numbers between them, `RISK-044` and `RISK-058`, both earlier-phase entries that are **re-scored in the final section under their own numbers**, and nothing anywhere in `docs/` cites a number above `RISK-085`. So the reconciliation is clean in both directions, and no citation had to be corrected the way Phase 3 corrected a stray `RISK-065` — the number that stray citation claimed is the first entry minted here. **This register mints no `TEST-P4-0NN` id, deliberately.** The audit at `:169-170` records that Phase 4's `TEST-P4-*` sequence *starts* at `001`, and `test-plan.md` is being written concurrently by a sibling record; a register that invented gap ids to point at would be manufacturing the very coordination failure Phase 3 documented as RISK-039. Every unchecked property below is therefore named by its **test method** (all 53 Phase 4 test methods exist on disk and are cited by name and line) or by the property itself, and the gap-id cells are left blank for the test plan to fill.

**The phase's central exposure is that Phase 4 adds an owner without adding any evidence.** It sits one layer above every claim Phase 3 made and inherits all of them unchanged: an engine that maps `availability`/`link`/`bond` to `ConnectionState` is only as true as the projection it reads, and the projection is a transcription of an API surface no code of this project's has ever called from a handset. Phase 4's own mitigation for that — a `Flow<ConnectedDeviceSnapshot>` input, a fake, 53 JVM tests — *increases* the exposure in one specific way worth naming before any entry does: it makes the mapping look settled. ADR-P4-012's closing sentence is the phase's most useful and most dangerous line, "Phase 3 proved the projection cannot lie about a device, Phase 4 proves the session layer cannot read it as one"; the first clause is conditional on RISK-048 and the second is a tautology about a table this phase wrote. **Every mitigation in this register is a design mitigation — a type, a derived constant, a bounded window, a KDoc prohibition, an assertion about our own code. None is evidence that a handset behaves as the transcription claims, and Phase 4 is the fourth consecutive phase for which that sentence is true.**

### RISK-065 — The engine inherits Phase 3's transcription risk wholesale, and a session is now the layer a user would read it through
**Probability.** high · **Impact.** high · **Exposure.** severe
**Status.** open, open-ended, and now one layer deeper. This entry is **the same exposure as `RISK-044`**, re-scored for Phase 4 rather than reduced, and RISK-044 stays the authoritative statement of the underlying facts.
**Description.** Every session claim Phase 4 publishes is derived, mechanically and without a check of its own, from a `ConnectedDeviceSnapshot` whose Android half is 1,372 lines of framework-facing transcription that has never executed (`phase-3/risk-register.md:14`, measured at Phase 3's close-out). `CONNECTED` in a session means "the projection's `link` was `CONNECTED`", which means "`getProfileConnectionState` answered `STATE_CONNECTED` on this handset", which is a `[SDK]`/`[AOSP-35]` document claim that research caps at existence and at "one implementation of one release; OEMs fork it". Phase 4 adds **1,293 lines of session code** (`core/src/main/kotlin/com/omnibuds/core/session/`, eight files, `wc -l` at `e5ff7bb`) with **zero framework reach** — `PhaseFourScopeTest.theSessionLayerReachesNoControlSeam` proves it and `phaseFourAddedNoNewSourceArea` pins it — which is exactly the property that makes this entry severe rather than merely inherited: the new code is *pure*, so it is thoroughly tested, so nothing about it fails, and a green suite is precisely what hides the fact that its input is unverified. Worse, the layer that is now unverified-by-inheritance is the layer a user would see: `DeviceSessionSnapshot.activeSessions` is the shape a Phase 49 screen renders, and `TrackedDeviceSession` carries a state name — `CONNECTED`, `PAIRED` — that reads as a sentence about the earbuds rather than about a projection. ADR-P4-012 states the limit in as many words: "That a real earbud produces a session" and "that a real disconnect arrives as `DISCONNECTED` rather than as silence" are both in its list of what Phase 4 cannot say.
**Mitigation.** The seam is one-directional and machine-checked rather than polite: the engine's entire input is `ConnectedDeviceSnapshot` (ADR-P4-011's consequence, enforced by `PhaseFourScopeTest:31-51`), so no session claim can be re-derived from a framework call — a wrong session can only be a wrong table or a wrong projection, and those two are separately attributable. ADR-P4-012 caps every Phase 4 claim at `IMPLEMENTED` (T1, TST-MOCK-001, TST-REC-005) and `SessionStatePurityTest.noSessionTypeCanClaimVerificationBeyondWhatThePhaseHas` (`:205-214`) asserts by reflection that no session type carries a `VerificationLevel` at all, so an inflated claim has nowhere to live. ADR-P4-004's table is one place with one row per mapping and "every cell of the table is a named test", so a later handset contradiction edits a decision rather than scattering fixes. And "a session is not a claim about a device" is written into `DeviceSessionEngine`'s KDoc (`:30-76`) and into `SessionTermination`'s (`SessionVocabulary.kt:46-60`), which is where an implementer of the next layer will read it.
**Detection.** The deferred handset session, and `adb devices -l`. Restated plainly because the honest form of this line is uncomfortable and Phase 3 already wrote it once: **no check in this repository can currently detect a wrong transcription of Android's behaviour**, Phase 4 has now put a user-facing layer on top of that fact, and Phase 4's 53 executed tests cannot make it smaller — they test a table, not a phone. The nearest machine-side signal inside Phase 4 is an *absence*: a session whose `timeline.lastObservedAtEpochMillis` never moves while `stage` is `RUNNING` would show a projection that stopped speaking, which is RISK-063's silence wearing a session name.
**Fallback.** `UNKNOWN`, and the design absorbs a contradicting handset answer better than Phase 3's did, because the mapping table is the only place a contradiction can be corrected (ADR-P4-004) and the session vocabulary has no field for a device claim (`SessionEngineStage` describes the engine, not the device — `SessionVocabulary.kt:3-22`, pinned by `theSessionEngineStageIsNotADeviceState`). Where a handset contradicts a row, the row changes under an ADR; where a handset contradicts the *whole* projection, the session layer reports `SessionObservationStatus.Refused`/`Unconfirmed` and the affected claim becomes unavailable rather than wrong.
**Owner.** Bluetooth Agent / Core Agent, with the device authorisation owned by the user; the presentation half owned by Phase 49.

### RISK-066 — The deferral now has a second store on top of it, and still no owner, no expiry and no trigger
**Probability.** high · **Impact.** high · **Exposure.** severe
**Status.** open. A process risk, deliberately separate from RISK-065 as Phase 3 kept RISK-045 separate from RISK-044: that entry is a state of the evidence, this one is that nothing any longer forces the state to change — and Phase 4 has made the silence cheaper to ignore, because it now looks like a passing suite.
**Description.** ADR-P3-014 removed device verification from every phase's completion criteria "for the whole of that stretch", and Phase 4's own ADRs consume that freedom cleanly: ADR-P4-012's alternatives reject Robolectric and reject claiming `LAB_TESTED`, which is the right ethic, and the result is a phase with **no instrumented test of any kind**. `docs/phases/phase-4/architecture-audit.md:176-178` records that nothing blocks Phase 4 and that RISK-044/045 are inherited rather than missing — accurate, and it is also the mechanism by which an unverified claim becomes a load-bearing one without anyone deciding: Phase 5 reads Phase 4's sessions to fingerprint devices, Phase 8 reads them to classify capabilities, Phase 49 renders them, and each of those phases inherits a `CONNECTED` nobody observed. Three concrete decay paths, all inherited from Phase 3 and one new: the eleven instrumented methods still have never compiled outside this working tree (RISK-045's first); `DeviceSessionEngine`'s rules are proven only against a hand-built fixture — `SessionStatePurityTest:266-284` and `DeviceSessionEngineTest:527-545` each construct `ConnectedDeviceSnapshot` by naming every field, and the engine test's own header states the consequence, "the input is a `ConnectedDeviceSnapshot` a test built" (`:37`) — so **no Phase 4 test has ever applied a snapshot the Phase 3 observer actually published** (this is new, it is the integration the audit's §5 was built for, and it is untested); and nothing re-checks that the deferred list is still valid.
**Mitigation.** The deferral is still an ADR with a status line and an index entry (`docs/decisions/README.md`), not a mood, and Phase 4 records its own share of it in prose rather than in a footnote: ADR-P4-012 has a section literally titled "What this phase therefore cannot say", naming five claims. ADR-P4-011 refuses the coupling that would have let Phase 4 *appear* to close the loop (`refresh()` stays uncalled, `PhaseFourScopeTest` makes the observer unimportable from `session`), which is the difference between an honest gap and a manufactured green. The new integration gap is stated as a gap rather than as a passing property, and this register names the cheapest test that would close it (RISK-073's detection line covers the same ground). Nothing here blocks the project, and this entry does not propose making it one — the user's rule is that device testing never becomes a blocker.
**Detection.** A Phase 5/8/49 record that cites a Phase 4 session state as hardware evidence; the first `HARDWARE_VERIFIED` claim attached to a session (TST-HW-003, TST-FAIL-001 row 4); a Phase 4 record asserting something about a handset with no deferred id behind it; and the specific new one — the first time anyone wires `ConnectedDeviceObserver.snapshot` into `DeviceSessionEngine.apply` outside a KDoc, which is RISK-075's subject.
**Fallback.** Keep the claims where they are — `UNKNOWN`, deferred, named — and let the session that runs them be scheduled by the user. If the device session is ultimately abandoned, RISK-045's rule binds Phase 4 too: the claims are retracted in an ADR, not left green by construction, and "green" here now means 53 unit tests over a table.
**Owner.** Orchestrator.

### RISK-067 — The engine trusts its projection completely, and a source that publishes a complete empty union would end every session it holds
**Probability.** medium · **Impact.** high · **Exposure.** high
**Status.** open, and this is `RISK-049` one layer up — RISK-049 stays the authoritative statement of the source-versus-engine problem, and the number is kept visible rather than absorbed.
**Description.** ADR-P4-004's eighth row says absence from a round the projection called a complete union *is* the platform's answer, and the engine implements that literally: `applyAbsence` at `DeviceSessionEngine.kt:342-374` moves a carried session to `DISCONNECTED` on the first such round and ends it on the second, and `targetStateOf` (`:480-501`) never second-guesses a record. The whole of that behaviour rests on two booleans the engine reads and cannot evaluate — `SessionObservationStatus.of` (`SessionObservationStatus.kt:82-90`) takes `restsOnCompletedRound` and `isUnionComplete` from the projection, and `Confirmed.unionComplete` is documented as "carried rather than recomputed, because the projection's own completeness rule … is Phase 3's decision and not this layer's to duplicate" (`:49-54`). A source that published `Success(emptyList())` with completeness set and nobody in it — a lie, a refactor that re-ordered the census test, or a second implementation that inherited no obligation from the compiler — would end every session in the store and publish `activeSessions == []` as an authoritative census, and **no test in Phase 4 can distinguish that from a genuinely empty room**: the fixture and the behaviour are the same two booleans (`anEmptyListIsOnlyEverAFindingUnderACompletedUnion`, `SessionStatePurityTest:147-163`, asserts the *rule*, not the source's honesty). Phase 3's version of this was "one implementation and one self-inspection"; Phase 4 makes it two implementations and one self-inspection each, with the second one unable to see the first. A second, smaller instance of the same trust lives three lines away: `apply` folds records into `LinkedHashMap<DeviceObservationKey, DeviceObservation>` with `keyedReports[record.key] = record` (`:146-152`), so **a round carrying two records under one key silently keeps the last one** — Phase 3 merges such a pair before publishing (`mergedWith`), but nothing obliges a future source to, and the stronger bond or the newer name could be in the record that was overwritten. `oneDeviceReportedTwiceInOneRoundStillOpensOneSession` (`DeviceSessionEngineTest:76-85`) proves the session count survives that; it does not prove the surviving record was the better one.
**Mitigation.** The vocabulary makes the dishonest shape awkward rather than impossible, which is Phase 3's technique and is stated honestly: `isEmptyMeaningful` is derived only from `Confirmed && unionComplete` (`SessionObservationStatus.kt:72-73`) and `DeviceSessionSnapshot.isEmptyMeaningful` (`DeviceSessionSnapshot.kt:56-57`) forwards it, so an empty list with no licence reads as *not meaningful* rather than as nobody-home; the precedence in `of` is exclusive and machine-checked (`observationStatusPrecedenceKeepsTheFourCasesExclusive`, `SessionStatePurityTest:120-145`); a refused round withdraws nothing at all (`aRefusedRoundKeepsEverySessionAndCarriesItsReason`), so the *accidental* empty-census case is confined to a source that affirmatively claims completeness. The `DeviceObservationKey` is unhashable-by-text and equality-only, so a mis-keyed fold cannot merge two devices quietly — the worst case is one session updated by one report.
**Detection.** A second `ConnectedDeviceSource`/snapshot producer appearing without Phase 3's `TEST-P3-015` call-log assertions copied onto it *and* without a Phase 4 test that feeds it; a projection that says `Confirmed(unionComplete = true)` with zero records while `unansweredProfiles` is non-empty (the two fields contradict, and nothing checks the pair — `aUnionWhereNothingAnsweredCannotReportAnEmptyRoom` guards the observer, not the consumer); and, at the session layer, the absence of a guard the cheapest detection test would supply: a snapshot whose `unansweredProfiles` is non-empty should never be able to end a session, and today nothing reads `unansweredProfiles` in `session` at all.
**Fallback.** Make completeness a value the engine can check rather than a flag it accepts: either carry the unanswered set into `SessionObservationStatus.Confirmed` so `unionComplete` is derived from evidence the projection already publishes, or require a census token that a refusal cannot forge — both are ADR-gated (this is RISK-049's own stated fallback, promoted one layer). Meanwhile say the boundary out loud: every session claim is conditional on a projection Phase 4 cannot audit.
**Owner.** Core Agent / Bluetooth Agent.

### RISK-068 — The one-round grace is a policy with no handset evidence: too short if announcements are slow, too long if a device flaps, and the id changes at the boundary
**Probability.** medium · **Impact.** high · **Exposure.** high
**Status.** open. The policy is real, deterministic and fully tested — and the unit it is measured in (a published round) has no handset-observable duration.
**Description.** Prompt §9 asked for a documented, testable answer to whether a reconnect resumes or restarts a session, and ADR-P4-006 answered with a *count*: a `DISCONNECTED` session is kept "for exactly one further published round", resumes the same id inside it, and is ended and re-minted after it. That is the right shape for testability (no clock, no scheduler, all three rules provable — `aDisconnectedDeviceIsHeldForOneRoundAndThenEnded`, `aDeviceThatComesBackInsideTheGraceKeepsItsSessionId`, `aDeviceThatComesBackAfterTheGraceIsANewSessionWithANewId`, `DeviceSessionEngineTest:145-197`), and the ADR states the cost itself: "anything that had keyed itself to the old one must re-key". What no test measures is the *duration*, because a round is whatever the observer decides to publish — the census path runs on `snapshot()`/`refresh()` and the delta path on announcements (RISK-051, RISK-058, RISK-063), and Phase 3's own research has announcements arriving under an export flag that has never been observed working. So the grace is one round, which on a handset that announces each profile transition separately may be **seconds**, and on a phone whose radio is quiet may be **the rest of the session**. ADR-P4-012 names the resulting unknown directly: "that the grace of one round is the right window on a phone whose announcements are slow (U-4)". The opposite failure is equally unmeasured: a device that flaps across a real transition boundary gets an id churn — `SESSION_ENDED(PROVEN_DISCONNECT_PAST_GRACE)` then `SESSION_CREATED` with a fresh `session-N` — for each blip that straddles a round, and `SessionTermination` records that the engine gave up, not that the device left. Third: because re-keying is required, any consumer that holds per-session state (a UI's selection, a future audio route, a Phase 8 capability cache) silently orphans it at the boundary, and the only thing that tells it so is an event on a `replay = 0` flow (RISK-072).
**Mitigation.** The window is a count and it is one place: `isAwaitingGraceExpiry` (`TrackedDeviceSession.kt:69-70`) is the grace's entire representation, both expiry paths use it (`applyReport:262-269` for a repeated disconnect report, `applyAbsence:343-349` for absence), and the code comment names the reason — "same window as the absence path, so the two cannot disagree about lifetime" — which is what makes the policy re-decidable in one edit rather than six. Termination reasons are an enum with a distinct value for each way a session ends (`SessionVocabulary.kt:61-83`, pinned by `terminationReasonsDescribeEngineDecisionsAndNeverADeviceAct`), so a churn is *attributable* to the engine's decision rather than being inferred from an absence. And blips do not churn at all: `TEMPORARILY_UNAVAILABLE` never sets `disconnectedAt` and never starts a grace (ADR-P4-006 rule 1), so a radio glitch is not an ending, and `sessionsArePublishedInCreationOrderWhateverTheRoundSays` keeps list identity stable while a device flaps inside that class.
**Detection.** U-4 and U-9, in the deferred session's timing run — measure the *elapsed* time of one grace on a real phone and whether `CONNECTING`/`DISCONNECTING` are delivered at all (RISK-080). Machine-side, the signature is `session-N` ids climbing faster than the user says they connected, or a consumer that keys anything at all to a `sessionId` beyond one session's lifetime; `aSessionIdCarriesNoPartOfTheDeviceThatProducedIt` (`:475-484`) proves ids carry no device content, which is what makes an id churn harmless to privacy and *not* harmless to state keyed on it.
**Fallback.** Two, both ADR-gated and neither a drive-by edit: restate the grace in a *bounded number of announcements* rather than published rounds (which needs the observer's delta cadence to be evidence, and so needs the deferred session), or keep one-round grace but publish a lineage token — explicitly refused by ADR-P4-005/006 as "a permanent device record wearing a session name", so it would need to clear prompt §10 and SEC-ID-006, not just an ADR. What must not happen is a wall-clock window added to the engine, which ADR-P4-006 rejects for non-determinism and prompt §14 rejects as polling-adjacent.
**Owner.** Core Agent, with the measurement owed by the deferred session and the re-keying consequence owed by Phase 49.

### RISK-069 — A handset that reports devices without addresses produces a stream of create/end events and an unstable list, because ambiguity cannot survive a round
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** ADR-P4-005 applies Phase 3's rule 6 one layer up: a record the platform could not attribute becomes a session with `identityBasis = AMBIGUOUS`, and `expireAmbiguousSessions` (`DeviceSessionEngine.kt:227-244`) ends **every** ambiguous session at the **start of every round**, with `AMBIGUOUS_SESSION_EXPIRED`, before this round's reports re-create them. The behaviour is exactly as designed and is the correct privacy and integrity trade — carrying an unkeyed session forward would weld two devices the platform never named, and `anUnkeyedDeviceBecomesOneAmbiguousSessionAndIsNeverCarriedForward` plus `twoUnkeyedDevicesInOneRoundStayTwoSessionsBecauseNothingCanTellThemApart` (`DeviceSessionEngineTest:199-214`, `:216-227`) prove the merge never happens. The user-visible consequence is the risk: on a handset where `getAddress()` returns nothing usable for some device class — plausible enough that Phase 3 built `NotReported` and an `isAttributable` predicate for it (RISK-054) — each round emits `SESSION_ENDED` + `SESSION_CREATED` with a fresh id for the *same* earbuds, `snapshot.sessions` keeps the same length while every element in it changes identity, and `ambiguousSessions` (a whole derived view, `DeviceSessionSnapshot.kt:52-53`) churns in lockstep. A UI bound to that list would animate a device leaving and arriving on every announcement, and no consumer could select it, because selection is by id and the id is one round old. ADR-P4-005's own consequence names the half of this it accepted — "two rounds of the *same* unkeyed device look like two ambiguous sessions" — but not the aggregate: the *rate* is set by Phase 3's announcement cadence, which has never been measured.
**Mitigation.** Ambiguity is a published state rather than a silent guess, which is prompt §8's requirement and the whole point of the design: `basis` is on the session, `SessionCreated` carries it (`DeviceSessionEvent.kt:36-40`), and `ambiguousSessions` lets a consumer *exclude* churning entries instead of rendering them — so a UI can honestly grey or omit them rather than animate them. Nothing is merged across the boundary, so the risk never becomes a data defect: the worst outcome is a list that looks restless, never two products welded into one (RISK-053's asymmetry, deliberately inherited). Two unkeyed devices in one round stay two sessions, so the churn does not smuggle in a merge.
**Detection.** The deferred session's per-device listing (does this handset report a key for the earbuds at all?), and inside the repository a missing check worth naming: **no test drives two consecutive rounds carrying the same unkeyed device**, so the churn is a code reading rather than an observed sequence. `anUnkeyedDeviceBecomesOneAmbiguousSessionAndIsNeverCarriedForward` (`:199-214`) comes closest — it proves the non-carry-forward, which is the *good* half.
**Fallback.** Report unkeyed devices through a separate "unattributed observations" field rather than as sessions, so a UI can show them without a lifecycle they do not have — this needs an ADR, and it weakens prompt §5's single authoritative list, so it must be argued, not added. Otherwise: keep the design, and instruct the render layer to key its animation on `(displayName, key-kind)` for ambiguous entries — never on a guessed identity (prompt §12, RISK-055's identical fallback).
**Owner.** Core Agent / UI owner (Phase 49).

### RISK-070 — The session store is unbounded, and the refusal window is the only number in the snapshot that has a limit
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** Phase 3's RISK-056 found a projection that never forgets; Phase 4 adds a second store with the same property and a second owner, and the copy-bypass entry (RISK-074) is the only reason this is not worse. `tracked: List<TrackedDeviceSession>` (`DeviceSessionEngine.kt:84`) grows with every key the phone reports and shrinks only through three paths, all of which require an *answered* round: absence from a complete union (`applyAbsence:342-374`), a repeated disconnect report past the grace (`applyReport:262-269`), and the ambiguity expiry (`:227-244`). Nothing evicts a session on elapsed time, on observation silence, or on refusal — `targetStateOf` maps an unobservable phone to `TEMPORARILY_UNAVAILABLE` and `applyAbsence`'s `else -> session` (`:377`) means a partial census, an unconfirmed round or a refusal carries every session forward forever, and `refusedMoves` is the sole bounded collection in the published value at `REFUSAL_WINDOW = 8` (`:518`, `takeLast` at `:445-447`) with `DeviceSessionSnapshot.kt:32-41` calling Phase 3's reasoning its own: "an unbounded list of them is a log buffer". The same phrase Phase 3 used to convict itself — "the same reasoning was not applied to the list beside it" — applies exactly here, one layer up, and to a list whose contents are more user-legible: each entry carries an identity label and a `ConnectionState`. Phase 3's RISK-054 rotation compounds it: a rotating address is a *new key*, hence a *new session*, so one earbud travelling through a day can add several entries that no round ever removes, since the union that would have to find them absent may keep being incomplete.
**Mitigation.** Nothing persists, and for Phase 4 that is enforced rather than asserted: `PhaseFourScopeTest.theSessionLayerStillImportsNoPersistenceContract` (`:54-65`) scans the area's sources, the layer map already made `session → persistence` arithmetically illegal (ADR-P4-010), `DependencyDirectionTest.kt:237-251` refuses production `DeviceRepository` implementations, and `everySessionThisEngineMakesIsTemporary` plus `beingObservedNeverPromotesASessionIntoASavedRecord` (`DeviceSessionEngineTest:63-74`, `SessionStatePurityTest:246-255`) prove no path reaches `DeviceSession.save()`. So the retention is bounded by process life by construction. Terminated sessions *do* leave the list — `next` is rebuilt each round (`:154-181`), so an ended session is never carried, which is what makes `activeSessions` an authoritative list rather than a filter over history (ADR-P4-006's third alternative). `sessionId` values are minted counters with no device content (`aSessionIdCarriesNoPartOfTheDeviceThatProducedIt`), and `DeviceObservationKey.toString()` cannot emit an address, so a long-lived list is not a long-lived log of identifiers.
**Detection.** A memory profile of a long-lived `consume`; the first consumer that wants sessions to survive a rotation, which is the moment incidental retention becomes a decision; any proposal to persist `sessionId` or `key`; and inside the repository a plain gap — **no test applies more than a handful of rounds, so nothing measures store growth**, and none tests the pathological case (a key present in round 1, absent from every *refused* round thereafter).
**Fallback.** Give carried-forward sessions an eviction rule with a stated window in the same shape the eight-item refusal window already uses, owned by the phase that owns observation lifetime — the honest version of this line is Phase 3's, unchanged: if a device must outlive a round it belongs under `persistence` with prompt §10's justification attached, not as a list that quietly never shrinks. A bounded store with typed overflow ("this engine holds at most N sessions, further devices are reported untracked") is expressible today and would need an ADR because it changes prompt §5's guarantee.
**Owner.** Core Agent / Security Agent.

### RISK-071 — A refused round withdraws nothing, so a revoked permission leaves sessions claiming `CONNECTED` indefinitely in the authoritative list
**Probability.** medium · **Impact.** high · **Exposure.** high
**Status.** open. This is `RISK-047` one layer up, and RISK-047 stays the entry that owns the underlying unknown (whether revocation is observable as anything other than process death).
**Description.** ADR-P4-007 makes the engine's treatment of a refusal absolute — "the session engine treats a refused round as **no new information**" — and `apply` implements it exactly: `SessionObservationStatus.Refused` reaches `applyAbsence`'s `else -> session` branch (`DeviceSessionEngine.kt:377`), so every carried session keeps its state, `activeSessions` is not recomputed, and the only new facts are a `SessionObservationFailed` edge and a status field. Compose that with Phase 3's standing facts and the sequence is concrete: permission revoked mid-observation → announcements stop and rounds fail (RISK-047) → nothing in the engine is told → `snapshot.activeSessions` keeps reporting the user's earbuds as `CONNECTED` for the lifetime of a process no longer entitled to know. The engine is *worse* placed than Phase 3's projection to notice, because it has no clock, no stage of its own that says "stale", and no `refresh()` it is allowed to call — ADR-P4-011 declines the observer coupling and `PhaseFourScopeTest.theSessionLayerReachesNoControlSeam` makes that decline structural, which is the right decision creating a genuine blind spot. `SessionEngineStage.RUNNING` compounds the readability problem rather than the logic: a refused round still publishes `RUNNING` (`:186-190` sets `STOPPED` only from `ObservationStage.STOPPED`), so a consumer that reads `stage` as freshness sees a healthy engine. The KDoc is honest ("`RUNNING` says the engine has applied at least one projection", `SessionVocabulary.kt:8-11`) and no machine check stops a UI from misreading it.
**Mitigation.** The reason travels with the value, which is the whole of ADR-P4-007 and the difference between a stale list and a lying one: `observation` is a four-case sealed interface (`SessionObservationStatus.kt:36-66`) with `Refused(error)` carrying Phase 3's own category, `isEmptyMeaningful` is false for it, and the `DeviceSessionSnapshot` KDoc says the confusion explicitly — "Reading the list length without reading that field is the confusion prompt section 12 forbids, and the type is shaped so that doing it takes an extra deliberate step" (`:20-24`). Two tests pin it: `aRefusedRoundKeepsEverySessionAndCarriesItsReason` and `aRefusalIsNotTheSameSentenceAsAnEmptyCensus` (`DeviceSessionEngineTest:117-143`). `SessionObservationFailed` carries no session id, because it is not about a device (`DeviceSessionEvent.kt:92-103`), so a consumer cannot mistake it for a per-device disconnect.
**Detection.** Any consumer of `activeSessions` that does not also read `observation` — which is the first UI, Phase 49, and this register should name it rather than let it be discovered. A stronger machine-side signal exists and is unwritten: **no test asserts the passage of time or the absence of rounds as a fact**, so "refused for an hour" and "refused for a second" are the same published value; the cheapest check is a test that applies N refused rounds and asserts the snapshot says so, which today it can only say as a category. Phase 2's manual revocation step, restated as Phase 3's `TEST-P3-024`, remains the only thing that would show revocation as silence rather than as death.
**Fallback.** Two, and the first is inside the engine's existing vocabulary: give a refusal-derived staleness an owner — a bounded count of consecutive refused or unconfirmed rounds published as part of `SessionObservationStatus` — so a UI can honestly grey a list it can no longer confirm. That is a Phase 5+ decision with a prompt §14 argument to make, because the alternative (a delayed re-read) is the polling prompt §14 and `TEST-P2-034` forbid. The second is ADR-P4-011's: accept that a grant is picked up when something announces, and let the phase owning a screen drive the re-read from a user action.
**Owner.** Core Agent / Security Agent, with the presentation half owed by Phase 49 and the measurement owed by the deferred session.

### RISK-072 — Event loss is designed in, and the risk is a future consumer that treats the event flow as a queue
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** `DeviceSessionEngine` publishes edges on a `MutableSharedFlow` declared `replay = 0`, `extraBufferCapacity = 64`, `BufferOverflow.DROP_OLDEST` (`DeviceSessionEngine.kt:93-101`, constants at `:520-521`), emitted with `_events.tryEmit(event)` (`:463-468`) *after* the snapshot value is assigned. Every one of those choices is deliberate and defended — ADR-P4-008 refuses `replay = 1` because it "duplicates the StateFlow and creates two histories that can disagree", refuses `Channel.UNLIMITED` as "the bounded window wearing a domain name", and refuses suspending on a consumer because that is "a consumer holding the state owner hostage" — and the aggregate is a stream that may silently drop. A collector that is slower than the engine loses the *oldest* edges in a burst; a collector that was not running when a round published loses everything about that round; and a collector whose `launch` is cancelled and restarted loses everything in between. `SESSION_ENDED` is the edge nobody should miss: a consumer that kept its own map keyed by `sessionId` and missed the end keeps an entry for a session the authoritative list no longer has, which is prompt §5's competing active-device list arriving through the back of an event. Note also that `tryEmit` on a zero-replay flow with a slow subscriber and no buffer room returns `false` and the engine discards the value without recording it anywhere — there is no drop counter, no "you missed edges" signal, and `publish` cannot see the failure because `tryEmit`'s boolean is not read (`:467`).
**Mitigation.** The StateFlow is the truth and the type says so in three places: `DeviceSessionSnapshot` is the "one published value the session engine owns" with derived views (`DeviceSessionSnapshot.kt:5-24`), `activeSessionsIsAViewOverTheOneValueNotASecondOwner` (`DeviceSessionEngineTest:286-299`) pins that there is nothing to fall out of sync, and rule 5.6 is quoted where an implementer will read it — `DeviceSessionEvent.kt:25-28`, "a collector that was not running misses the edge and reads `DeviceSessionSnapshot` instead… this is notification only", plus the `events` KDoc's "Never a record of anything" (`:103-104`) and ADR-P4-008's consequence that the DROP_OLDEST choice "is observable… which is stated in the type's KDoc so nobody reads a missing event as a device that did not change". Duplicate suppression at the edge limits the burst size in the first place — `everyRoundAdvancesTheRevisionAndAnIdenticalRoundEmitsNoEvents` (`:388-402`) proves a restatement publishes nothing, so "a flapping profile cannot generate an event storm". `oneRoundPublishesItsEventsInTheOrderTheStateWasBuilt` (`:417-429`) pins that event order matches construction order, so a collector that *does* keep up is never misled.
**Detection.** The first consumer that reacts to an event without ever reading `snapshot` — that is the risk arriving, and it is a review judgement, not a check. Two machine-side detections are cheap and unwritten: a test that registers no collector, applies ten rounds, then collects, and asserts the StateFlow alone is sufficient to reconstruct the current sessions (it is, and nothing proves it); and a test that emits more than 64 edges in one round with a suspended collector and asserts what the engine does about the overflow it currently ignores.
**Fallback.** Keep `replay = 0` — the alternative is two sources of truth, which Phase 1's §24 and ADR-P4-008 both refuse — and instead make loss *visible*: publish a monotonic `revision` alongside each event so a consumer can detect a gap and re-read the snapshot. `revision` already exists and already moves per published round (`DeviceSessionSnapshot.kt:16-19`, `revision += 1` at `:182`), so the fallback is a payload field, not a redesign, and it needs an ADR because it changes `DeviceSessionEvent`'s deliberately minimal shape (SEC-LOG-002's reason for the small payloads).
**Owner.** Core Agent / Reactive-state owner, with the queue-misreading half owned by whichever consumer writes one (Phase 49 first).

### RISK-073 — Concurrency is proven single-threaded: the mutex's actual contention has no test, and `apply` is public
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** Phase 3's RISK-057 said "no executed test creates a second thread" and Phase 4 repeats the finding about its own engine, which is a choice made knowingly rather than an oversight — but the specific properties left unproven are the interesting ones and they are narrower than Phase 3's, which makes the cheapest test that settles them smaller too. `DeviceSessionEngine` holds one `Mutex` (`:82`), one mutable counter (`sequence`, `:83`), three plain `var` fields (`tracked`, `revision`, `refusals`, `:84-86`) and a `MutableStateFlow`; `apply` wraps "the whole reconcile-and-publish step" in `lock.withLock` (`:134`), `terminateAll` wraps its teardown in `withContext(NonCancellable) { lock.withLock { … } }` (`:206-216`), and `consume` runs in the caller's scope (`:116-124`). All 34 engine tests are `runTest` on the single-threaded virtual scheduler and **no Phase 4 test file mentions `Dispatchers` at all** (grep over `core/src/test/.../session/`); the one `launch` is `launch { engine.consume(endless) }` (`:435`) on the same test thread. So unproven: (a) a `consume` racing a direct `apply` — both are public, both take the lock, but the *interleaving* of "cancel → `terminateAll` publishes empty/STOPPED" against "an in-flight `apply` publishes non-empty/RUNNING" has never been exercised, and the lock guarantees only mutual exclusion, not which one wins; (b) two collectors of `events` plus a producer, where `tryEmit` ordering relative to `_snapshot.value` assignment is observable per-consumer; (c) whether the `finally`-less cancellation path (`:119-122`, which calls `terminateAll` and rethrows) can leave a session created *after* the terminal publish, which is RISK-082's subject seen from the thread side. ADR-P4-009's consequence concedes exactly this and ADR-P4-012 names it as an honest limit: "Multi-threaded contention between `consume` and a future command path remains unproven and is recorded as a risk rather than claimed solved."
**Mitigation.** The design shrinks the surface instead of relying on luck: one lock around the whole step so no half-applied round is ever published (`:134`, ADR-P4-009), publication of the derived value inside the lock (`publish` at `:449-469`), `tryEmit` rather than `emit` so a stalled consumer cannot block the state owner (`:463-467`), the engine owning no scope and launching nothing (`:116-124`, rule 5.1) so there is no mailbox to leak, and `NonCancellable` teardown because a cancellation arriving mid-teardown would otherwise publish a torn value (Phase 3 used the same mechanism for the same reason). Ordering is carried by a per-engine `revision` rather than by wall-clock comparisons, so a misordered read is at least detectable by a consumer (`DeviceSessionSnapshot.kt:16-19`).
**Detection.** Name the cheapest test that would settle it, because this is a repository-side gap with no device in it: **a `Dispatchers.Default` test that launches two `apply(projectionA)`/`apply(projectionB)` calls concurrently over 100 iterations and asserts (i) `revision` equals the number of applied rounds, (ii) every published snapshot's `sessions` is internally consistent — no session whose `state.sessionId` is absent from the id set the engine minted, no half-folded round — and (iii) the `events` stream seen by one attached collector is a prefix-consistent sequence with no interleaved pair from different rounds.** A second, one-line version for the cancellation path: launch `consume(endless)`, emit concurrently, cancel, and assert the final published value is the empty/STOPPED one — which is the property RISK-082 states as unproven today. Neither needs a phone, and neither exists; `TEST-P3-034`'s first half was the same finding in Phase 3's vocabulary.
**Fallback.** Keep single-writer-by-construction as the contract and widen it deliberately if the test finds a race: confine mutation to a single actor, or move `tracked` into the `StateFlow`'s value and use `update { }` with pure decision functions. Both are ADR-gated — ADR-P4-009 already rejected the actor and the lock-free loop with reasons that a failing test would have to beat, not merely contradict.
**Owner.** Core Agent / Testing Agent.

The behavioural detection is a session whose `state.revision` moved without a corresponding `SessionUpdated`/`SessionDisconnected` event, which no test asserts against either.
**Fallback.** Give the confinement to Phase 24 as promised, and if a phase before 24 needs it enforced, the cheap move is a source-text guard (prohibit `connection =` outside the declaring file) minted as that phase's decision — not a visibility change, which Phase 1 already proved does not work on a data class. **Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** Phase 4's integration is two lines of caller code, and they are written as a `text` block inside a KDoc comment in `platform/android/src/main/kotlin/com/omnibuds/android/di/OmniBudsBluetooth.kt:139-145`: `launch { observer.observe().collect { } }` to drive the observation and `observer.snapshot.collect { engine.apply(it) }` to fold each projection into sessions. `omniBudsDeviceSessionEngine` (`:152-154`) constructs the engine and nothing else — no connection, no lifecycle, no start — which is correct by ADR-P4-009 and rule 5.1, and leaves the wiring as the reader's job. **A grep for `omniBudsDeviceSessionEngine` across the repository returns only the definition and the KDoc snippet that names it; no test, no DI graph, and no other call site constructs it**, and the engine in every test is hand-built (`DeviceSessionEngineTest:47`, `:275`). The DI file's `time` parameter defaults to `SystemTimeProvider`, "the same clock the platform reads" (`:133`, `:153`), which is the part of the wiring most likely to be got wrong being the part least left to the caller. **Fallback.** Let the phase that owns a composition root own it — Phase 49 for a screen, or the application-assembly phase — under an ADR, and refuse to invent a lifecycle holder here, which ADR-P4-009 rejected (an owned scope is what leaks). **Owner.** Core Agent / Integration owner, with the composition root owed by Phase 49.

### RISK-076 — Bond disagreement now surfaces as a published `PAIRED`, so a contradiction between two mechanisms becomes a user-visible state
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Status.** open. This is `RISK-064` reaching the surface, and RISK-064 stays the entry that owns the merge rule itself.
**Description.** `targetStateOf` maps a record whose `availability` is observable, whose `link` is `UNKNOWN`, and whose `bond == BONDED` to `ConnectionState.PAIRED` (`DeviceSessionEngine.kt:495-499`), and ADR-P4-004's sixth row justifies it as "the bond axis is a positive report". But the `bond` value it reads is already a *resolution*: Phase 3's `DeviceObservation.mergedWith` combines two mechanisms' bond answers by rank (`strongerBond` prefers `BONDED > BONDING > NONE > UNKNOWN`, `phase-3/risk-register.md:177`), and RISK-064's finding was that `BONDED` beating `NONE` is "picking a winner between two positive reports… done by a comparator", with no record that the disagreement happened and no test driving it (`TEST-P3-042`). The census-refusal distinction Phase 3 built (`isPairedCensus`) is not read here at all, so a refused bond round cannot be rendered as "unpaired" through this layer.
**Detection.** A "this device is paired, so offer to reconnect" affordance is the first consumer that would turn a wrong `PAIRED` into a wrong suggestion, and that is Phase 49. Machine-side, the missing check is the one Phase 3 named and still has not written, now with a second reason to want it: a test that merges `BONDED` against `NONE` and asserts what a consumer may conclude — `TEST-P3-042` — plus a Phase 4 test that a *bond-only* record does not open a session when its link is unknown and its bond is `UNKNOWN`.
**Fallback.** Either carry the disagreement into a published field (Phase 3's own two options: a third refusal kind, or keep both reports side by side and let a human decide — `phase-3/risk-register.md:180`), or stop mapping bond to `PAIRED` and leave such devices `UNKNOWN`, which loses a real user-visible fact to avoid a possible wrong one. Both need an ADR; what must not be chosen is "leave it ranked and quiet", which is the state that reads as agreement.
**Owner.** Core Agent, with the merge rule owed by Phase 3's `TEST-P3-042` and the presentation owed by Phase 49.

**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** `identityOf` builds identity from one field, `DeviceIdentity.of(displayName = report.displayName)` (`DeviceSessionEngine.kt:511-512`), and every later update goes through `mergedWith`, which is fill-only: `fillIfUnknown` on each of four fields (`DeviceIdentity.kt:63-70`), so a known value is never replaced. `applyReport` calls it and republishes only on growth (`:307-316`), and `DeviceState.withIdentity`'s KDoc states the rule as a limit — "this method cannot rewrite an established identity any more than the type above can" (`:81-92`). **Owner.** Core Agent / UI owner (Phase 49), with the merge rule owed by Phase 3.

**Owner.** Security Agent / Core Agent, with the log-sink half owed by Phase 36.

### RISK-079 — `displayName` crosses into the session layer, so a UI built on `TrackedDeviceSession` can print a user-chosen label — while the address guarantee holds, and each half is proved by a different test
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** Phase 3 kept the two halves of the label problem apart on purpose: the address became an opaque key, and the display name stayed a plain `String?` field, which is why Phase 3's own register says "the design made the identifier safe and left the label alone" and rated the naive `Log.i(tag, snapshot.records.toString())` both "more tempting and more informative" (`RISK-043` at `phase-3/risk-register.md:225`; `RISK-052`'s secondary exposure notes the paired census doubles it). Phase 4 takes that field across the seam and puts it on the object a screen is designed to read: `identityOf` copies `report.displayName` into a `DeviceIdentity` (`DeviceSessionEngine.kt:511-512`), `DeviceSession` holds it, and `TrackedDeviceSession.displayName` is a public read-through of it (`:57-58`). `TrackedDeviceSession` is a data class, so its generated `toString()` renders `session` and `state`, each of which renders its `identity`, each of which renders the label — one implicit `.toString()` in a log or a test failure message now carries user-chosen text about the user's belongings, from a list of all of them. The exposure is text a user chose about objects they own; it is not an identifier, and the distinction is the reason this entry is medium rather than high.
**Mitigation.** Each half of the claim is proved by its own test, and they are different tests, which is worth stating precisely because the two properties are often collapsed. **The address half:** `nothingTheEnginePublishesPrintsADeviceIdentifier` (`SessionStatePurityTest:166-189`) renders one session and all seven `DeviceSessionEvent` cases through `assertNoAddressText`, a MAC-shaped regex check (`:289-292`), and also asserts on `tracked(...).key.toString()` — the fixture key is a real address-shaped value, `00:11:22:AA:BB:CC` (`:295-296`), so the check would bite; and `aSessionIdCarriesNoPartOfTheDeviceThatProducedIt` (`DeviceSessionEngineTest:475-484`) asserts the minted id contains neither address fragments nor the name. **The label half:** deliberately narrow, because a name cannot be redacted without losing the feature — `DeviceSessionEvent.kt:18-21` states the rule that events carry `sessionId` and field *counts* "never a display name… and never an address", so the user-chosen text is confined to the state flow and out of the notification stream, and `SessionIdentityChanged`'s two ints (`:85-90`) are that confinement made structural. `DeviceIdentity.of` demotes blank text rather than storing it, and no Phase 4 code invents a label (ADR-P0-016, `identityOf`'s KDoc at `:503-510`).
**Detection.** Any `toString()`/`Log`/crash-report path over `DeviceSessionSnapshot` or `TrackedDeviceSession` outside a test — which is SEC-LOG-002's unresolved ownership (Phase 36) restated for a second, more UI-facing type. Machine-side the address half is defended and the label half is not, and that asymmetry is the entry: no check asserts anything about what `displayName` may become when printed, because a redaction rule for it is a policy decision this phase is not authorised to make.
**Fallback.** Keep the address guarantee exactly where it is (opaque key, minted ids, both tested) and give the label to the phase that owns a log sink: a `DeviceSessionSnapshot`-shaped diagnostic type with the label omitted, or SEC-LOG-002's redaction rules applied before any session reaches a printer. Prompt §12's ban on name-based attribution is the reason the label is not simply removed here — a UI needs it — so the honest fallback is a rendering-boundary decision, not a domain one.
**Owner.** Security Agent / Core Agent, with the redaction half owed by Phase 36 and the rendering half by Phase 49.

### RISK-080 — Two rows of the mapping table depend on transitions a handset may never deliver
**Probability.** high · **Impact.** medium · **Exposure.** high
**Status.** open. Its second half — an `arrival` rule the ADR claimed and the code did not implement — was **corrected at close-out in the record rather than the code**: ADR-P4-004 now states that the table reads the projection's completeness flags and never a record's `arrival`, and gives the reason (`DeviceObservation.kt:114-116` has already resolved same-round disagreement by the time a record reaches this layer). What remains below is the live risk.
**Description.** ADR-P4-004's second and third rows map `link == CONNECTING` to `DISCOVERED` and `link == DISCONNECTING` to `TEMPORARILY_UNAVAILABLE`, and the ADR itself flags them: "The two weakest rows (`CONNECTING`, `DISCONNECTING`) are the ones a handset may never deliver at all — research U-4/U-9". `targetStateOf` implements both (`DeviceSessionEngine.kt:490-491`), both are tested (`aLinkOnTheWayOutIsNeverReadAsADisconnect`, `aLinkStillComingUpIsDiscoveredRatherThanConnected`, `DeviceSessionEngineTest:310-322`) — and both tests are driven by a fixture that *asserts* the platform reports those values, so the coverage is real for the mapping and nil for the premise. If a phone's stack collapses both into a single `CONNECTED`/`DISCONNECTED` pair, then `DISCOVERED` is emitted only by the CONNECTING path (`:490`), that row never fires again, and the transition table's `DISCOVERED → CONNECTED` legal move becomes unreachable in practice — a state name in the vocabulary with no producer, which is precisely the shape Phase 3 convicted itself of at RISK-061 ("an unreachable guard reads as coverage"). `TEMPORARILY_UNAVAILABLE` would survive, because the unobservable-phone path also produces it (`:481-482`), so only one of the two rows goes dark — worth naming so nobody later reads the other's coverage as evidence. The claim that used to sit here — that the table is “the first place where a `DeviceObservation`'s `arrival` changes what is believed” — was **wrong, and was corrected in the record at close-out rather than papered over**: no session file reads `arrival`, and ADR-P4-004 now states that the only ordering belief available at this layer is the projection's completeness flags, because Phase 3's `mergedWith` (`DeviceObservation.kt:114-116`) has already resolved same-round disagreement by keeping the later arrival before a record ever reaches the engine.
**Mitigation.** The engine is written to be right if those states never occur, which is the ADR's own sentence and is true: every row of the table has a tested path, no row is required for the census-driven disconnect logic, and absence-based disconnect (ADR-P4-004's eighth row) does not consult `link` at all — so `DISCONNECTED` and `ENDED` remain reachable on a handset that never says `DISCONNECTING`. The identity-basis immutability is enforced structurally: `applyReport`'s contract is "cannot mint an id, cannot change the identity basis" (`:246-251`) and it holds regardless of arrival, which is the property prompt §8 actually asks for. The unminted-state problem is already machine-pinned at the vocabulary level: `theEngineCanOnlyReachSixStatesAndNoneOfThemImpliesCapabilityWork` prevents the *opposite* error (emitting an unearned state), and `aSessionCarriesNoEvidenceThisPhaseDoesNotHave` prevents a session asserting support.
**Detection.** U-4/U-9's timing run, which is the only thing that can settle it: 20 connect/disconnect cycles on a real phone, recording which link values actually arrive (`phase-3/risk-register.md:122`). Inside the repository, the honest detection is review of this file against the code, and the record's fix is the next phase's: a Phase 5+ reader must not treat `DISCOVERED` as a step a user experienced. `anEmptyListIsOnlyEverAFindingUnderACompletedUnion` gives no help here, since both rows concern a *present* record.
**Fallback.** If a handset proves never to deliver `CONNECTING`/`DISCONNECTING`, the correct move is a recorded platform correction plus an ADR amending ADR-P4-004's two rows; deleting an unused row is honest and inventing a state to keep the table looking exercised is not (ADR-P4-003's own refusal). The arrival half of that fallback has already been taken, so what is left here is purely the platform question. The alternative this phase already refused stays refused: inventing an intermediate state to make the table look exercised (ADR-P4-003).
**Owner.** Bluetooth Agent (U-4/U-9 measurement) / Core Agent, with the ADR amendment owed by whoever next edits the table.

### RISK-081 — The stale-input rule is prose: `applyIfNewer` exists, is monotonic, is documented as the answer, and is never called by the engine
**Probability.** medium · **Impact.** high · **Exposure.** high
**Description.** Prompt §14 requires a documented rule for an old event overwriting newer state, and this phase's first answer overclaimed one: ADR-P4-009 said ordering was “already guarded by `applyIfNewer`” (`DeviceState.kt:138-139`), which is a method the engine never calls. **The ADR has been corrected at close-out** to say what the code does: ordering across rounds is one `Mutex` around reconcile-and-publish plus the fact that the engine is the only writer, and `applyIfNewer` is named as the method Phase 6 must route through when a second writer exists. What remains as risk is the honest residue of that design rather than a record/code contradiction. `applyReport` mutates through `TrackedDeviceSession.moving` unconditionally (`DeviceSessionEngine.kt:272-305`), so whatever the newest published projection says is what the session believes — and the session layer *cannot* do better than that on its own, because it sits downstream of the only thing that knows which report is newer: Phase 3's own fold, which already merged announcements against the census inside one projection. A revision gate here would compare a candidate against a state that came from the same projection, which is a tautology, not a guard. The real exposure is therefore inherited rather than invented: if Phase 3's two pumps (RISK-057) interleave so that a superseded announcement lands in a later projection, the engine will faithfully apply the older fact — and nothing in `:core` could tell, because the projection carries no round identity. Prompt §14's requirement is met in the one form available at this layer: the published `revision` lets a consumer detect that it holds an older value, and the census-driven rules mean a wrong value has a lifetime of one round. The claim that there is no *input filter* is what RISK-082 and RISK-049 keep honest.
**Mitigation.** The direction of error is the safe one and it is worth saying so plainly: a late announcement can only move a session toward what the platform *just said about that device*, never invent a device, because sessions are created only from records and refused rounds withdraw nothing (ADR-P4-004, ADR-P4-007). A regression is self-healing — the next completed census restates the whole union and `applyReport`/`applyAbsence` fold it, so the wrong value has a lifetime of one round, which is the mirror image of RISK-068's grace rather than a new hole. Round-level atomicity is genuinely guaranteed: `lock.withLock` wraps reconcile-and-publish (`:134`) so no consumer sees a half-applied round, `everyRoundAdvancesTheRevisionAndAnIdenticalRoundEmitsNoEvents` (`DeviceSessionEngineTest:388-402`) proves `revision` moves per applied round, and `revision` is *published* on the snapshot (`DeviceSessionSnapshot.kt:16-19`) so a consumer can detect that it is holding an older value — which is the only part of prompt §14's requirement that Phase 4 truly implements, and it does so by giving consumers a counter rather than by filtering input.
**Detection.** A UI animating a device as connecting immediately after being shown connected, once, after a burst of announcements; and, machine-side, the test that would settle whether the pumps can actually interleave in the harmful order — which needs no device: **feed a completed census containing a device `CONNECTED`, then a snapshot whose `link` is `CONNECTING` for the same key, and assert what a consumer is entitled to conclude.** Today that test would pass by asserting `DISCOVERED`, i.e. it would document the regression rather than prevent it, which is the honest reason to write it. `aPhoneWhoseRadioWentQuietMakesTrackedDevicesUnavailableNotGone` (`:324-338`) is the closest existing check and it concerns a different axis.
**Fallback.** Taken, option (a): ADR-P4-009 was rewritten rather than left asserting a gate the code does not run, and this entry now describes the design's real limit. Option (b) stays available and is *not* free — it would need the projection to carry a round identity the engine could compare, which is a change to Phase 3's published type and an ADR of its own. The failure mode this entry was written to catch — a guard described in a record with no producer in the code (Phase 3's RISK-061 lesson) — is the reason the sentence was corrected instead of reinterpreted. **Owner.** Core Agent; the projection-round-identity question belongs to whoever next adds a second writer, which prompt section 17 puts in Phase 6.

### RISK-082 — `STOPPED` is not a terminal seal: a later `apply` restarts the engine, so two writers can resurrect sessions after cancellation
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** `terminateAll` clears `tracked`, bumps `revision` and publishes `SessionEngineStage.STOPPED` with `SessionObservationStatus.Stopped` (`DeviceSessionEngine.kt:205-217`), and `consume` runs it on both exit paths — caller cancellation (`:119-122`) and normal flow completion (`:123`). Nothing marks the engine as finished: `apply` is public (`:133`) and unconditional, and it sets `stage` from the *projection*, not from the engine's own history (`:186-190`), so the next applied snapshot silently returns the engine to `RUNNING` and re-creates sessions. The reuse is deliberate and tested — `anEngineReusedAfterAStopStartsFreshSessionsRatherThanResumingGhostOnes` (`DeviceSessionEngineTest:463-473`) and `SessionEngineStage.STOPPED`'s "a restart is legal" (`SessionVocabulary.kt:20-21`) — and the design is coherent, because the sequence counter is never reset (`sequence` at `:83`, used at `:397`), so restarted sessions get new ids and no ghost state survives. The risk is the *concurrent* reading of the same shape: a caller that runs `consume(flow)` and also pushes snapshots by hand — the exact two-line wiring the DI KDoc describes (`OmniBudsBluetooth.kt:139-145`), where nothing prevents a third `apply` — can publish a non-empty `RUNNING` snapshot *after* the cancellation path's empty `STOPPED` one, because the mutex gives mutual exclusion but no ordering and no terminal state. A consumer treating `STOPPED` as "this engine is finished" — which the name invites — would then be wrong in the direction prompt §11 forbids: devices looking active after nobody is looking.
**Mitigation.** Both terminal publishes carry a *reason* rather than an emptiness, which is what keeps a resurrection from being read as a census: `SessionTermination.OBSERVATION_STOPPED` and `ENGINE_CANCELLED` are distinct values (`SessionVocabulary.kt:78-82`), `SessionObservationStatus.Stopped` is neither a failure nor an empty room (`SessionObservationStatus.kt:65-66`), and `anExplicitStopClearsTheStoreAndSaysItStoppedRatherThanFoundNothing` (`DeviceSessionEngineTest:509-519`) asserts `isEmptyMeaningful == false` after a stop. A restarted engine mints fresh ids and starts from `DeviceState.initial` (`:407`), so it can never inherit a stale `CONNECTED`, and `absenceFromAnUnansweredRoundWithdrawsNothing` plus `aStoppedObservationEndsSessionsWithoutClaimingADisconnect` (`:259-272`) pin that a stopped projection ends sessions without asserting a device act.
**Detection.** A second `apply`/`consume` call site appearing on the same engine instance — grep-verifiable in review and unchecked by any test; and the behavioural signature is `stage` transitioning `STOPPED → RUNNING` while a consumer holds a `sessionId` from before the stop. The cheap missing test is named by RISK-073's detection line: cancel `consume` while applying concurrently and assert the last published value is the terminal one.
**Fallback.** Either make `stop` terminal for the instance (a sealed `ended` flag that refuses further `apply` calls, recorded as a refusal rather than applied) or keep restart legal and *document the ordering contract* on the type, stating that exactly one writer per instance is required — which is Phase 2's RISK-031 convention restated for this engine, and is prose today. An ADR should pick one; neither option may be "let the mutex imply ordering", which is the mistake this entry is about.
**Owner.** Core Agent / Reactive-state owner.

### RISK-083 — A binaural pair is two sessions, and `activeSessions.size` is a count of entries and not of devices the user owns
**Probability.** high · **Impact.** medium · **Exposure.** high
**Description.** Phase 3's RISK-053 established that there is no set, group or product concept anywhere in the model, that an LE Audio pair reports two independently transitioning entries, and that the group id which would close the gap (`BluetoothLeAudio.getGroupId()`) is UNVERIFIED (U-8) and LE-Audio-dependent — "the honest statement is that Phase 3's projection will show one earbud set as two entries… with nothing saying which is the case". Phase 4 takes that projection one layer up and turns entries into *sessions*, which is where the count becomes a user-facing sentence: the join is key-equality and nothing else (`DeviceSessionEngine.kt:146-152`, `keyedReports[record.key] = record`, and `applyReport` folds by key), one session per joinable key, and `twoDevicesCarryingTheSameNameStayTwoSessions` (`:87-95`) is a correct test that will be read as a sufficient one. A `StateFlow` of sessions is precisely the surface prompt §5's "one authoritative source of active session state" will be implemented as, so `snapshot.activeSessions.size == 2` for one set of earbuds is now an authoritative number in an authoritative flow — a stronger claim than Phase 3's projection made, at a layer whose whole purpose is to be authoritative. Nothing in Phase 4 can distinguish "two earbuds of one set" from "two unrelated devices": `SessionIdentityBasis` distinguishes attributable from unattributable, not one product from two (`SessionVocabulary.kt:38-44`), and `observedProfiles` — which is the only field that hints at a set relationship, via `CSIP_SET_COORDINATOR` — is recorded as evidence and never mapped (ADR-P4-004's last row, `targetStateOf` never consulting it).
**Mitigation.** The asymmetry Phase 3 chose deliberately is inherited intact rather than quietly improved: two entries for one product is a cosmetic defect while one entry for two products is a data defect, and the engine cannot do the second, because it never merges on a name, never merges across keys, and never merges across ambiguity (RISK-069). Session counts are honest about what they count — `DeviceSessionSnapshot.sessions` is a list of *sessions*, the type is named `TrackedDeviceSession`, and `TrackedDeviceSession` holds no device-level claim field (`noSessionTypeCanClaimVerificationBeyondWhatThePhaseHas`, `SessionStatePurityTest:205-214`), so nothing in this layer says "you own two devices". The per-profile machinery a future grouping decision builds on already survives a session: a device reported by two services updates one session (`oneDeviceReportedTwiceInOneRoundStillOpensOneSession`, `:76-85`).
**Detection.** Any UI that labels `activeSessions.size` as "devices", "your earbuds" or a badge count — the first one anyone writes, Phase 49 — and Phase 10's LE Audio work, where U-8 must be measured before any grouping is claimed (`phase-3/risk-register.md:90`). A second signal is behavioural: a session list in which two entries appear and disappear together on every announcement, which is a pair, and which nothing here is allowed to conclude.
**Fallback.** Render the count as *sessions observed* and never as devices — which is what the type supports — and introduce grouping in the phase that can justify it (Phase 10 for the set relationship, Phase 49 for the wording), under an ADR, once `getGroupId()` is measured. If the group id is unavailable, say the list is ungrouped; a name-based or count-based heuristic is what prompt §12 forbids and what RISK-055's fallback already refuses. Phase 4 explicitly does **not** get to add a `groupKey` field to `TrackedDeviceSession` retroactively — that would be a device claim with no evidence (ADR-P4-012).
**Owner.** Core Agent / UI owner (Phase 49), with LE Audio grouping owned by Phase 10.

### RISK-084 — An engine constructed without a clock publishes null times forever, and every ordering or freshness display a UI builds on them collapses
**Probability.** low · **Impact.** medium · **Exposure.** low
**Description.** `DeviceSessionEngine`'s first constructor parameter defaults to `NoTimeProvider` (`:78`), and the default is reachable: `DeviceSessionEngine()` with no arguments is how `anEngineWithoutAClockPublishesNullTimesAndNeverZero` builds it (`DeviceSessionEngineTest:274-284`). With that default, `time.nowEpochMillis()` returns null and every time in the published value is null forever — `SessionTimeline.startedAtEpochMillis`/`lastObservedAt`/`disconnectedAt`/`endedAt` (`SessionTimeline.kt:38-71`, whose `restatedAt` returns `this` on null at `:49-53`, so freshness never moves even across many rounds), `RefusedSessionMove.atEpochMillis`, every `DeviceSessionEvent.atEpochMillis`, and `DeviceSessionSnapshot.publishedAtEpochMillis`. This is ADR-P1-012/ADR-P0-008's rule honoured exactly — null means "no reading was taken", never zero, because "a zero would claim the session began at the epoch and a UI cannot tell the two apart" (`SessionTimeline.kt:9-11`) — and the consequence is a *legible but unusable* record: a UI that sorts by start time gets an order determined by list position, and one that shows "connected 3 minutes ago" gets nothing. The DI factory does pass `SystemTimeProvider` (`OmniBudsBluetooth.kt:152-154`), so the risk only bites a hand-built engine — which is also how the tests are all built (RISK-075), so nothing in the tree proves the clock arrives.
**Mitigation.** Null is honest rather than fake, and it is pinned as such by two tests: `anEngineWithoutAClockPublishesNullTimesAndNeverZero` and `aTimelineCarriesNoInventedTimeAndResumingClearsTheDisconnectMark` (`SessionStatePurityTest:192-202`, which also proves "first mark wins" on `markedDisconnected`, `SessionTimeline.kt:56-57`). No engine decision depends on a clock at all — the grace is round-counted, ordering is publication order, and `SessionTimeline.kt:33-36` states that the engine never compares these numbers — so a missing clock degrades *display* and cannot corrupt state. The factory's `time` parameter is named and defaulted to the platform's own provider, "the same clock the platform reads", so the wiring that a phase-49 root will write has one fewer choice to get wrong.
**Detection.** A UI column of identical or blank timestamps; a sort over `sessions` that silently falls back to list order; and the machine-side check that does not exist: no test asserts that `omniBudsDeviceSessionEngine()` produces a clock-bearing engine, which is the same missing-constructor-test gap as RISK-075 and would be closed by the same test.
**Fallback.** Delete the default and require a `TimeProvider` at every construction site, which turns a silent degradation into a compile error and costs one call site in the DI file — a small, honest tightening that needs no ADR because it changes no domain rule. If a caller genuinely has no clock, the answer is the current one and it should be stated in the UI: null, not zero, and not a timestamp borrowed from a handset.
**Owner.** Core Agent, with the display consequence owned by Phase 49.

### RISK-085 — Phase 4's honesty checks are a name list, a derived constant and a comment-stripping scan, and each is weaker than the claim it is cited for
**Probability.** medium · **Impact.** medium · **Exposure.** medium
**Description.** This is Phase 2's RISK-027 and Phase 3's RISK-059 shape, arrived at again, with three specific instances that should be named rather than generalised. **(1)** `PhaseFourScopeTest.theSessionLayerReachesNoControlSeam` forbids eight control type *names* by substring-matching `com.omnibuds.core.platform.$name` on trimmed code lines (`:31-51`, the list at `:34-43`). It is one list edit away from permitting a seam, it does not catch a wildcard import of the platform package followed by a bare `ConnectedDeviceObserver`, and it is confined to `session` main sources — a future `session` sub-package would still be caught (the scan walks the directory, `:113-121`), but a session-shaped engine written in `device` would not be. `codeLinesOf` strips lines beginning `//`, `*`, `/*` or `@/` (`:104-111`), so a single-line `/* … */` containing a forbidden name is invisible to the guard, and the guard's own reason for stripping comments — "documenting a forbidden thing is not a violation" — is right and is also the mechanism. **(2)** `theEngineCanOnlyReachSixStates…` asserts against `TrackedDeviceSession.reachableStates`, a constant derived from **one row** of the transition table — `allowedNext(ConnectionState.UNKNOWN)` minus `ERROR`, plus `UNKNOWN` (`TrackedDeviceSession.kt:131-134`) — while ADR-P4-003 claims the four excluded states are "pinned as never emitted by any engine path". They are not: sessions move from later states too, the excluded four *are* legal targets from some of those (the table permits `CONNECTED` onward, and `aMoveTheTransitionTableRefusesIsRecordedAndTheHeldStateKept` proves a refused move stays a refusal), and the real protection is `attemptConnection`'s runtime check plus the fact that `targetStateOf` has no branch returning them. A derived constant that reads as a path coverage is RISK-061's "an unreachable guard reads as coverage" in a new costume. **(3)** the scan roots on the relative path `File("src/main/kotlin/com/omnibuds/core/session")` (`:114`) and fails loudly if it is empty (`:116`, `:119`) — which is Phase 3's `scannedSourceRoot` discipline correctly inherited, and is also why a working-directory change silently retargets it rather than widening it.
**Mitigation.** The guards are real and were built deliberately: `phaseFourAddedNoNewSourceArea` proves Phase 4 wrote session code nowhere but `session` (`:85-91`), `nothingNewIsAuthorisedAtPhaseFour` proves the authorisation set is identical to Phase 3's (`:23-28`), `thePhaseThatFollowsIsStillNotAuthorisedToReachAnythingThisOneInvented` proves Phase 5 inherits no new reach (`:94-101`), `theSessionLayerStillImportsNoPersistenceContract` pins the storage boundary, and `nothingTheEnginePublishesPrintsADeviceIdentifier` covers the privacy half with a real MAC-shaped regex over a real address-shaped fixture key. Unlike Phase 3's instrumented suite, every one of these six executes (`PhaseFourScopeTest` is a `:core` test file), and the vacuity failure mode is refused by construction with a comment that names it: "A scan that finds nothing passes by accident, which is the failure mode every guard in this project refuses" (`:117-119`). The runtime transition table is the *actual* guarantee for the four excluded states, and it is separately tested by Phase 1's `DeviceStateTest` (`anIllegalConnectionMoveIsRefusedWithStructuredErrorAndChangesNothing`, `everyStateCanFallIntoErrorAndASelfMoveIsIdempotent`), so the claim is supported — just not by the check it is cited to.
**Detection.** A diff to `PhaseFourScopeTest.kt` changing the eight-name list or the forbidden-token list with no matching ADR in `decisions.md`; a second `session`-shaped engine outside the scanned directory; and the first record that cites `reachableStates` as proof of a per-path claim — which includes ADR-P4-003's consequence as written, and is corrected by this entry rather than by an edit.
**Fallback.** Three cheap tightenings, none of which needs a new type: derive the forbidden control names from the `platform` area's own registered surface the way `everyCoreAreaIsRegisteredInTheLayerMap` makes placement a registration act (Phase 3's RISK-059 fallback, restated); replace the constant-based state check with a path check that drives `targetStateOf`'s full input space and asserts no branch can return an excluded state; and treat any guard-list edit as an ADR-gated act, which ADR-P2-006 already requires for the capability lists. Phase 4 does none of these, and the reason is not laziness — each is a change to a guard another phase owns.
**Owner.** Architecture Agent / Core Agent.

RISK-073 and RISK-075 are the two that matter most, because both are one JVM test deep and both are cited by this phase's own ADRs as accepted limits; RISK-081 is the one where the repository's answer is a code change or an ADR retraction rather than a test. Phase 4's residue is smaller and bluer than Phase 3's in exactly one respect worth naming: none of it needs permission from anybody but us.

## What Phase 4 changed in the Phase 0, Phase 1, Phase 2 and Phase 3 registers

Phase 4 **raises, and re-scores under their own numbers**:

- **RISK-044** — the framework half has never executed, and every device claim is a transcription (`phase-3/risk-register.md:11-18`). **Raised, not reduced, and this is the entry `architecture-audit.md:170` allocates `RISK-065` against.** 1,293 lines of pure session code now sit above the transcription with 53 executed tests and no instrumented test of its own, so the phase that inherited the exposure is the first one whose suite is *entirely* green while its premise is entirely unobserved. RISK-044 stays open and stays severe; RISK-065 is the same exposure with a user-facing layer added.
- **RISK-045** — deferral has no owner, expiry or trigger (`:20-27`). **Raised.** Phase 4 makes the silence cheaper to tolerate — a passing unit suite reads like completion — and adds a decay path of its own: no Phase 4 test has ever applied a snapshot that Phase 3's observer published, so the deferred session is now the first time the two layers meet (RISK-066, RISK-075).
- **RISK-046** — a fresh install refuses every round and nothing here can change it (`:29-35`). Now has a second owner and a second surface: the refusal reaches the user through `SessionObservationStatus.Refused` and `SessionObservationFailed` (`DeviceSessionEngine.kt:139-141`), which is ADR-P4-007's machinery working as designed, and Phase 4 makes prompt §12's six-way distinction renderable at last — the reason category is Phase 3's and the carrier is Phase 4's. The prompt flow stays **Phase 49's**, and RISK-046's fallback ("never re-derive a UI-facing state from an empty list") is now structurally supported, since `isEmptyMeaningful` is false for a refusal.
- **RISK-047** — a permission revoked mid-observation is invisible, and the projection keeps claiming connections (`:37-43`). **Raised one layer, and the new layer is worse.** A refusal now keeps *sessions* alive forever, in a flow whose whole purpose is to be authoritative, and unlike the projection the session engine has no re-read path even in principle (ADR-P4-011 makes the observer unimportable, `PhaseFourScopeTest:31-51`). Continues as RISK-071; RISK-047's own unknown — whether revocation is observably silence or only process death — is untouched, and `TEST-P3-024` remains the measurement.
- **RISK-049** — the engine trusts its source and no test can catch a source that lies (`:53-59`). **Raised, and the number is kept visible rather than absorbed:** Phase 4 is that second consumer, the "second `ConnectedDeviceSource`" scenario RISK-049's Detection line predicted, except that it consumes a value rather than an implementation and so inherits no obligation from the compiler at all. A `Confirmed(unionComplete = true)` snapshot with nobody in it ends every session, and nothing distinguishes it from a real empty room (RISK-067).
- **RISK-052** — the paired census is read live, and the projection-versus-store boundary has no check (`:77-84`). Partly sharpened in a new direction: **Phase 4 reads the census nowhere** (no `pairedDevices` access in `core/src/main/.../session/`), which implements ADR-P4-004's "a device that appears only in the paired census gets no session" and removes one retention path while leaving RISK-052's real exposure (a later consumer persisting the list) exactly where Phase 3 put it. Bond values, however, now reach a published `ConnectionState` — that half continues as RISK-076.
- **RISK-053** — a binaural pair is two devices to the model (`:86-92`). **Raised.** Two entries became two *sessions* in an authoritative list with a count a UI is invited to render (RISK-083). U-8 remains unmeasured, and Phase 4 declined, in ADR-P4-012's terms, any field that would let it claim a product.
- **RISK-054** — a masked or rotating address changes the key and fragments a device (`:94-100`). Raised in one specific way Phase 3 could not: a rotated key is now not just a new projection record but a **new session with a new minted id**, plus an `SESSION_ENDED`/`SESSION_CREATED` pair for a device the user never touched, and Phase 4's grace makes the fragmentation show up as churn rather than as drift. The key's opacity carried forward intact (`RISK-079`'s address half, both tested), and U-2 is still owed by the deferred session.
- **RISK-055** — two devices with one display name can never be merged, and the ambiguity is inherited by whoever renders it (`:102-108`). Inherited whole, and its "the ambiguity is inherited by whoever renders it" sentence is now literally true one layer closer to the user: `TrackedDeviceSession.displayName` is a public read-through. Continues as RISK-077 and RISK-079.
- **RISK-056** — the projection never forgets, so a long-lived observation is an in-process device history (`:110-116`). **Raised: there are now two stores and both are unbounded.** Phase 4's is bounded by the same construction (nothing persists, `PhaseFourScopeTest:54-65`) and is *more* legible, because it is designed for screens; and the only bounded collection in Phase 4's published value is the eight-item refusal window, which is the identical omission Phase 3 convicted itself of ("the same reasoning was not applied to the list beside it"). Continues as RISK-070 and RISK-078.
- **RISK-057** — concurrency is proven only on one thread (`:118-124`). **Raised, and narrowed usefully.** Phase 4's surface is smaller — one mutex, three plain fields, no channels, no pumps, no `@Volatile` — and its exposure is larger, because the value being raced is the authoritative one; still no Phase 4 test mentions `Dispatchers`, so the finding is the same sentence with a new subject, and the cheapest settlement is a smaller test than Phase 3 needed (RISK-073). `TEST-P3-034`'s first half was the same finding; this phase leaves it open with its own id to be minted by `test-plan.md`.
- **RISK-058** — `refresh()` has no owner and is the recovery path for three failure modes (`:126-132`). **Re-scored, not duplicated, and not closed.** ADR-P4-011 declined the ownership Phase 3 assigned to "Phase 4 / Phase 49", with reasons: the engine's input is one flow, the observer stays unimportable, and a refused-then-retry loop without a delay is a hot loop while with one it is the polling prompt §14 forbids. The consequence in RISK-058's terms is unchanged and now sharper — a permission granted while idle is picked up only when something announces — and the entry it fed (RISK-051's cold-start refusal) still has no re-read trigger. Continues as RISK-071's detection line and RISK-075; **the ownership is now formally unassigned**, which is a worse answer than Phase 3's "Phase 4 will take it" and is recorded as such rather than smoothed.
- **RISK-062** — the instrumented suite can pass without having looked (`:159-165`). Untouched in substance — Phase 4 wrote no instrumented suite — but its *lesson* was adopted and should be credited: `replay = 0`, the conditional Phase 4 tests and `anEngineWithoutAClock…` all accept "nothing observed" as a legitimate outcome rather than manufacturing a green. The Phase 4 analogue worth naming is that a suite of 53 green unit tests over a faked input is exactly the object RISK-062 warns about, one layer down (RISK-066).
- **RISK-063** — the receiver-export correction ships unconfirmed and can make the engine silent (`:167-173`). **Raised, silently.** If announcements never arrive, Phase 4's engine sees one cold round and then nothing: sessions are created, `stage` stays `RUNNING`, `revision` stops moving, and `snapshot` looks like a stable room forever — with no refusal to read, because the observation never failed, it just stopped being restated. That is RISK-063's "a projection that never changes and looks like a quiet room" promoted to an authoritative session list, and it is why RISK-070's no-eviction finding is a correctness risk and not only a memory one.
- **RISK-064** — two mechanisms disagreeing about a bond are resolved by rank, in silence, by a data class (`:175-181`). **Raised to the surface.** The hybrid answer is now published as `ConnectionState.PAIRED` (`DeviceSessionEngine.kt:495-499`), so a contradiction between a census and an announcement becomes a state name a user reads, and `TEST-P3-042` — the one test Phase 3 named as the cheap missing check — is still unwritten and is now load-bearing for a second layer. Continues as RISK-076.
- **RISK-038** — the Bluetooth rulebook does not exist (`phase-2/risk-register.md:107-113`; `phase-3/risk-register.md:217`). **Recorded again, exactly as `architecture-audit.md:183-186` asked, and not repaired.** `docs/phases/phase-0/bluetooth-governance.md` still does not exist; Phase 4 wrote twelve ADRs about session state, identity minting, grace windows, event buffering, census authority and the storage boundary — including two security-adjacent ones (ADR-P4-005's opaque ids, ADR-P4-010's no-store rule) — none of which is a rulebook and none of which can be cited as one, making Phase 4 the **third** consecutive phase of Bluetooth-adjacent work to proceed without it. No file was invented here, for the same reason Phases 2 and 3 gave: a rulebook with no author is a fabricated governance source.
- **RISK-043** — the diagnostics sink redaction is defined against does not exist (`phase-2/risk-register.md:149-155`, re-scored at `phase-3/risk-register.md:225`). **Worse again, in the precise way Phase 3 predicted.** The label is now on a data class designed to be read by screens (`TrackedDeviceSession`), whose generated `toString()` renders the identity, and SEC-LOG-002 still has no owner before Phase 36. Continues as RISK-078 and RISK-079.
- **RISK-031** — single-slot uniqueness is per object and rests on one composition root (`phase-2/risk-register.md:51-57`). **Realised as predicted, in Phase 3's exact words** — "Phase 3 adds a second observer; the same convention must hold or the risk compounds" (`architecture-audit.md:98`, quoted at `phase-3/risk-register.md:216`). Phase 4 adds a *third* long-lived object and, unlike Phase 2 and 3, no slot at all: `DeviceSessionEngine` has no mutex-guarded single-occupancy, nothing refuses a second engine over the same observer, and the composition root that would establish one is prose in a KDoc constructed by no test. The convention now has three owners and no enforcement anywhere. Continues as RISK-075 and RISK-082.

Phase 4 **partly discharges**:

- **RISK-051** — the first union round is routinely unavailable, which is correct and user-visible (`:69-76`). The *unavailable* answer is now legible one layer up for the first time: `SessionObservationStatus.Refused(error)` carries `RESOURCE_UNAVAILABLE` with Phase 3's `RETRY_AFTER_REREAD` class intact, and `aRefusalIsNotTheSameSentenceAsAnEmptyCensus` proves the engine will not render it as nobody-home. What is **not** discharged is the entry's actual residue — the awaiting-then-answerable cold-start transition across two rounds, which needed no device, was Phase 3's "sharpest remaining T1 gap", and is still unscheduled. Phase 4's input is a flow of published snapshots, so it inherits the gap rather than closing it, and the `refresh()`-less recovery (RISK-058) is still the missing half.
- **RISK-019** / **RISK-035** — the Android boundary configured-but-unproven, and nothing in the project having executed on Android (`phase-1/risk-register.md:33-39`, `phase-2/risk-register.md:83-89`). Both stay superseded by RISK-044, and Phase 4 confirms the supersession a third time: the boundary is now configured, instrumented, **and consumed by a tested domain layer**, and still unproven. RISK-065 carries the whole of it.
- **RISK-014** — future desktop Bluetooth API differences (`phase-0/risk-register.md:113-119`). Marginally improved in the same way Phase 3's was: Phase 4's 1,293 session lines import no framework type and no `java.*`, `TimeProvider` stays injected, epoch millis stay the time representation (ADR-P1-012 honoured at `SessionTimeline.kt:6-11`), and the coroutines used are `kotlinx`, which the desktop target already carries. Phase 46 inherits no new obligation from Phase 4 beyond a state machine it will have to reproduce honestly.
- **RISK-012** — cross-phone differences (`phase-0` register). **Not reduced, and it should be said explicitly rather than folded into the untouched list:** Phase 4's policy choices (one-round grace, ambiguity expiry, `PAIRED` mapping, DROP_OLDEST at 64) are all *parameters that should vary by handset*, and Phase 4 has no measurement of any of them. A second phone would produce a different session churn rate from identical code, which is RISK-068's and RISK-069's shared blind spot.
