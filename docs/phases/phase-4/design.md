## 2. Prompt §5's diagram, and the three boxes that do not exist

Prompt §5 sketches five boxes below the observation: `Observation Normalizer` → `Session Reconciliation Engine` → `Device Session Repository` → `Authoritative Session State`, fanning out to `Active Sessions` and `Session Events`. **Two of those five exist as named things; three do not.** The realised shape is smaller, and the shrinking is the design.

```text
 Connected Device Observation                      exists: Phase 3's ConnectedDeviceObserver
   ConnectedDeviceSnapshot — records + census + two refusals + completeness flags
        │  DeviceSessionEngine.apply(projection)  (:133) · consume(flow)  (:116)
        ▼
 [Observation Normalizer]                          DOES NOT EXIST as a type
   the transcription Phase 3 already did is not done twice; what §5 means by it is
   targetStateOf() — ADR-P4-004's table — a private function inside the engine (:480-501)
        │
        ▼
 Session Reconciliation Engine                     exists: DeviceSessionEngine (the only class)
   folds one projection at a time under one lock: expiry, partition, apply, create, publish
        │
        ▼
 [Device Session Repository]                       DOES NOT EXIST — ADR-P4-011 refuses the name
   `Repository` already means the saved-device contract (persistence/DeviceRepository.kt:8-28),
   and this phase reaches neither storage nor that interface
        │
        ▼
 Authoritative Session State                       exists as a PAIR of values, not a store:
   DeviceSessionEngine.snapshot : StateFlow<DeviceSessionSnapshot>  (:91)
   DeviceSessionSnapshot        : the whole truth, one value        (:25-42)
        │
        ├── activeSessions / disconnectPendingSessions / ambiguousSessions  (:44-53, derived)
        └── events : SharedFlow<DeviceSessionEvent>                         (:104, edges only)
        │
        ▼
 Consumer                                          NONE EXISTS
```

| §5's box | Realised as | Why not the box |
|---|---|---|
| Observation Normalizer | `targetStateOf` (`:480-501`), a private function, plus `identityOf` (`:511-512`) | "normalising" here means *choosing one `ConnectionState` from three axes* — one 22-line `when`. A type for it would be a second owner of ADR-P4-004's table, and the table is the whole of its behaviour. Phase 3 already established that normalising means transcribing totals, not deciding meanings |
| Session Reconciliation Engine | `DeviceSessionEngine` | exists, and is the only new class in the phase |
| Device Session Repository | `DeviceSessionEngine` + `DeviceSessionSnapshot` | the engine **is** the authoritative-state owner, so a repository would be a second handle on the same map. `Repository` is already taken by the saved-device seam, and prompt §17 forbids this phase touching it (ADR-P4-011, ADR-P4-010) |
| Authoritative Session State | one `StateFlow<DeviceSessionSnapshot>` (`:91`, published at `:455-462`) | exists; it is a value, not a container, and the three "lists" §5 fans out to are computed properties over it (`DeviceSessionSnapshot.kt:44-53`) |
| Active Sessions / Session Events | `activeSessions` (derived) and `events` (a `SharedFlow`, `:93-104`) | exist, but asymmetrically on purpose: one is the truth, the other is a notification, and rule 5.6 (`docs/phases/phase-0/specs.md:146`) is what makes that the correct shape rather than a shortfall |

**Why inventing the missing boxes would be vocabulary without capability.** Each would be a class that holds no state, makes no decision, and can be tested only by being inlined: a `SessionNormalizer` would take a `DeviceObservation` and return a `ConnectionState`, and the entire content of that object is the table in §5 below — extracted, it would have exactly one caller (`:258`, `:352`, `:395`), no independent invariants, and a new place for the mapping to disagree with the ADR that decides it. A `SessionRepository` would wrap a `MutableStateFlow` the engine already owns, and the wrapper's only method would be `update`; two owners of one list is Phase 1 §24's failure with an extra indirection level, and rule 5.7 (`specs.md:147`) names one owner per area. A separate `AuthoritativeSessionState` type would be a third name for `DeviceSessionSnapshot`. The honest statement of this phase's shape is therefore *one class, one value, one derived view set, one edge flow* — and the boxes that Phase 5 or Phase 49 may need are named in §13 as API they cannot yet reach, not as classes stubbed now.

`PhaseFourScopeTest.theSessionLayerReachesNoControlSeam` (`:31-51`) is the guard that keeps the top of the diagram one-directional: the eight main sources are scanned for the nine control type names in the `platform` area (`ConnectedDeviceSource`, `ConnectedDeviceObserver`, `AdapterStateSource`, `BluetoothPlatform`, `BluetoothOperation`, `PlatformRegistration`, `ConnectedDeviceEventChannel`, `PermissionContext`) and must contain none. The engine reads a *value*. Prompt §8's "must not independently create another Bluetooth scanner or observer" is delivered by that scan plus the layer map — `session` (3) may import `platform` (1), and `platform` may import nothing from `session`, so the import that would let the session layer reach the phone does not exist in either direction (ADR-P4-001).

## 3. The dataflow: what comes in, what is derived, what is published, what is emitted

One projection in, one snapshot out, per round. `apply` (`:133-193`) is public and is the deterministic seam every rule is tested through; `consume` (`:116-124`) is the flow form of the same step.

| Stage | What it is | Where |
|---|---|---|
| **Input** | `ConnectedDeviceSnapshot`: `stage` (`ConnectedDeviceObserver.kt:77`), `records` (`:80`), `pairedDevices` (`:92`), `unansweredProfiles` (`:100`), `profileSupportConsulted`, `restsOnCompletedRound` (`:112`), **`deviceRoundRefusal`** (`:126`, new this phase), `restsOnCompletedPairedRound` (`:138`), `pairedRoundRefusal` (`:148`), `refusedTransitions` (`:151`), `observedAtEpochMillis` (`:154`), plus `isUnionComplete` (`:168`) and `isPairedCensus` (`:175`). Each record carries key, name, link, bond, availability, profile set, `arrival`, time and `isAttributable` (`DeviceObservation.kt:46-78`) | `apply(projection)` `:133` |
| **Belief** | `SessionObservationStatus.of(projection)` — one of five, in a fixed precedence (§4) | `:136`, `SessionObservationStatus.kt:82-90` |
| **Derivation** | four rules, in this order: (1) *expiry* — every `AMBIGUOUS` session present from the last round ends, `AMBIGUOUS_SESSION_EXPIRED`, because nothing can match it forward (§9); (2) *partition* — reports split into a `LinkedHashMap` keyed by `DeviceObservationKey` and a list of unattributable ones, on `record.isAttributable` alone (`:144-152`); (3) *mapping* — `targetStateOf(report, tracked)` answers one `ConnectionState` per device or refuses to open a session (§5); (4) *absence* — `applyAbsence` decides whether "not mentioned this round" is evidence at all (`:326-378`) | `:143-179` |
| **Transition** | every move goes through `TrackedDeviceSession.moving` → `DeviceState.attemptConnection` → `ConnectionStateTransitions.canTransition`; an illegal move returns `Failure(INVALID_STATE)`, is appended to `refusedMoves`, and the session keeps the state it held | `:272-305`, `:352-372`, `:411-424`, `TrackedDeviceSession.kt:117-122`, `DeviceState.kt:109-129` |
| **Publication** | one new immutable `DeviceSessionSnapshot(stage, sessions, observation, revision+1, publishedAt, refusedMoves)` into the `StateFlow` | `:181-191`, `:449-462` |
| **Emission** | the events collected during the round, `tryEmit` in the order the state was built, after the state value is set | `:463-468` |

Four properties of that pipeline are worth stating because they are what a reader will otherwise assume: **the projection is never mutated** (Phase 4 reads Phase 3's value and produces its own); **the engine never asks the platform anything** (the only suspending work in the fold is the lock acquisition at `:134`, and the clock is a plain synchronous call at `:135`); **the round is the unit of atomicity** (a consumer can observe revision `N` or revision `N+1`, never a half-applied round, because fold and publish are inside `lock.withLock`, `:134`); and **an unchanged round still publishes** — revision advances on every `apply` (`:182`), while emitting nothing (`everyRoundAdvancesTheRevisionAndAnIdenticalRoundEmitsNoEvents`, `DeviceSessionEngineTest.kt:388-401`). That asymmetry is deliberate: freshness of the *engine's* answer is a fact a consumer may want, and it is carried separately from the edges.

What the engine does **not** derive is equally load-bearing: `observedProfiles` decides nothing *and is retained as nothing* (`:144-152` reads no profile field, and no member of `TrackedDeviceSession` holds one), `pairedDevices` is read by no path in the engine (§5's last row), `arrival` — Phase 3's SNAPSHOT-versus-EVENT marker on each record (`DeviceObservation.kt:71`) — is read by no path either, so an announced record and a census record are folded identically (§17, RISK-080), and no `Long?` time is ever compared to another (`SessionTimeline.kt:34-37`; the only comparison in the fold is `session.key == key`).

## 4. What the engine is entitled to believe

`SessionObservationStatus` (`SessionObservationStatus.kt:36-66`) has five members — `Unread` (`:38`), `Unconfirmed` (`:44`), `Confirmed(unionComplete)` (`:54`), `Refused(error)` (`:63`), `Stopped` (`:66`) — four of which are derivable from a projection, `Unread` being the engine's own value before it has applied anything (`DeviceSessionSnapshot.notStarted()`, `:61-69`; the distinction is asserted at `SessionStatePurityTest.kt:126-130`). The precedence is fixed in `of` and is what keeps the cases exclusive:

```text
snapshot.stage == ObservationStage.STOPPED   -> Stopped          (:85)
deviceRoundRefusal != null                   -> Refused(error)   (:86)
restsOnCompletedRound                        -> Confirmed(isUnionComplete)  (:87)
otherwise                                    -> Unconfirmed      (:88)
```

An ended observation outranks a refusal, a refusal outranks a completed round, and a completed round outranks announcements that settled nothing. `isEmptyMeaningful` (`:72-73`) is true of exactly one of the five — `Confirmed` with `unionComplete` — and `SessionStatePurityTest.anEmptyListIsOnlyEverAFindingUnderACompletedUnion` (`:147-163`) pins that as a six-row truth table over the statuses. `observationStatusOf`'s last branch is the one a later reader under-reads: `Unconfirmed` means *devices may be listed and the list is still not a census of anything*, which is prompt §12's "successfully observed zero devices" kept apart from "observed nothing".

A cancellation is absent from the type deliberately (`:30-34`), for ADR-P1-004's reason: a called-off read is not a finding, and Phase 3 does not record one either, so deriving a fifth reading of the same silence is not available to this layer. Cancellation *is* recorded — as a termination reason on the engine's own teardown (`:119-121`), which is a different kind of fact from an observation status.

One consequence of §4's `Refused` arm deserves to be visible here rather than buried in ADR-P4-007: because a refusal restates nothing, a permission revoked mid-session leaves those sessions published as `CONNECTED` for as long as the engine keeps receiving refused rounds, with the reason beside them. That is prompt §12's rule honoured and RISK-071's exposure accepted in the same sentence — the alternative, clearing the list, is the forbidden representation, and the only real fix is the re-read this phase declined to own (ADR-P4-011, §11).

## 6. Identity and attribution: one join, minted ids, and a name that does nothing

**The Phase 3 key is the only join, and it is the only join.** Sessions are matched to reports by `DeviceObservationKey` and by nothing else: reports enter a `LinkedHashMap` keyed by the typed key (`:144-152`), a carried session looks itself up in it (`:156`), and a miss in the other direction mints a session for a key nobody held (`:165-170`). The engine never calls `joinableWith` (`platform/DeviceObservationKey.kt:114-115`) — and that is the same rule, not a weaker one, because `joinableWith` is the conjunction of *equality* and *attributability* and the engine holds the two halves apart structurally: `record.isAttributable` (`DeviceObservation.kt:77-78`, i.e. `key.canIdentifyAcrossObservations`, `DeviceObservationKey.kt:38,51,84-86`) gates entry to the map, so two `NotReported` records can never meet inside it, and equality alone is then safe. `mergedWith` on the identity is the only other place a device is compared, and it compares fields, not devices (`DeviceIdentity.kt:63-71`).

**Ids are minted, opaque, and carry no device content.** `sessionId` is `"session-$n"` from a per-engine counter (`:397`, `:83`, prefix default at `:515`), stable for the session's lifetime (prompt §6's requirement) and meaningless once the session is dropped (ADR-P4-005). `aSessionIdCarriesNoPartOfTheDeviceThatProducedIt` (`DeviceSessionEngineTest.kt:475-483`) drives a session built from an address-bearing key *and* a reported name and asserts the id is `session-1` and contains neither `00:11` nor `AA:BB` nor `Air` — the three ways a "clever" id would leak. The stronger claim, that nothing the engine publishes prints an identifier, is `SessionStatePurityTest.nothingTheEnginePublishesPrintsADeviceIdentifier` (`core/src/test/…/session/SessionStatePurityTest.kt:166-189`), which renders a `TrackedDeviceSession`, all seven event cases and the key itself against a MAC-shaped regex rather than against a fixture. A `deviceKey: String`, as prompt §6 sketches, would defeat both checks at once, which is why the field is typed (`TrackedDeviceSession.kt:36`) and why §17 records the divergence.

**`AMBIGUOUS` is a state with a one-round lifetime, not a ranking.** A report the platform could not key still becomes a session (`:171-179`, basis `AMBIGUOUS`, `SessionVocabulary.kt:38-44`): it is published, it is counted, it appears in `ambiguousSessions` (`DeviceSessionSnapshot.kt:52-53`), and it is never matched to a later round. Because it cannot be matched, it cannot be carried: the first step of every `apply` ends every ambiguous session with `AMBIGUOUS_SESSION_EXPIRED` (`:143`, `:227-244`) and the device is re-created from this round's report if it is still present. Two named cases hold the rule from both sides — `anUnkeyedDeviceBecomesOneAmbiguousSessionAndIsNeverCarriedForward` (`DeviceSessionEngineTest.kt:199-213`), where the *same* unkeyed fixture in two rounds yields a *different* session id plus an expiry event, and `twoUnkeyedDevicesInOneRoundStayTwoSessionsBecauseNothingCanTellThemApart` (`:216-226`). This is ADR-P3-015 rule 6 applied one layer up, where ADR-P4-005 says the temptation is stronger: an ambiguous session is as real as a keyed one while it lasts, and what it cannot do is last.

**A display name participates in nothing.** `identityOf` (`:511-512`) is the only line in the phase that reads `report.displayName`, and what it does is put the text into `DeviceIdentity.displayName` for description. Attribution uses the key (§above); termination uses the round (`SessionVocabulary.kt:61-80`); the transition table sees neither. `displayName` on the tracked record is a read-through to the identity (`TrackedDeviceSession.kt:56-57`), so there is no second copy to diverge. `twoDevicesCarryingTheSameNameStayTwoSessions` (`DeviceSessionEngineTest.kt:87-94`) is prompt §12's requirement as a build failure, and `aNameArrivingLateFillsIdentityAndADifferentNameLaterNeverRestatesIt` (`:229-241`) pins the other half: a name arriving after attribution fills the gap and fires `SessionIdentityChanged`, and a *renamed* device changes nothing at all, because `mergedWith` is fill-only and a restated alias stays a finding for a human rather than a silent overwrite. The cost of choosing the honest half is recorded as RISK-077: once a name is in, nothing in Phase 4 can correct it, because the only correction available — a restatement — is the same operation that would let a name participate in identity.

**The association Phase 1 asked for is enforced at construction.** `TrackedDeviceSession` holds the `DeviceSession`, the `DeviceState`, the key, the basis and the timeline (`:35-40`), and its `init` block (`:42-49`) refuses a record whose three ids disagree or whose two identity copies disagree — the exact pairing defect Phase 1's `validation.md` known issue 5 named and left for this phase. The two refusals are tested by name: `SessionStatePurityTest.aSessionCannotBeBuiltWhereTheStateAndTheRecordDisagreeAboutIdentity` (`:61-76`) and `.aSessionCannotBeBuiltWhereTheTwoIdsDoNotMatch` (`:79-92`), and the one legal way to change an identity is `withMergedIdentity` (`:89-92`), pinned by `mergingIdentityUpdatesBothRecordsOrNeither` (`:95-104`). `DeviceState.withIdentity` (`DeviceState.kt:92`) exists solely so that path can update both records without moving a revision — a fill-in of an unknown field is not a state transition, and letting it bump the revision would let an identity update beat a real connection change.

## 7. Lifecycle: one axis, six reachable states, and a refused move that is recorded

**There is no second lifecycle enum** (ADR-P4-002). Prompt §6 sketches `connectionState` *and* `lifecycleState` on one record, and prompt §7 sketches `CREATED → OBSERVING → ACTIVE → TEMPORARILY_UNAVAILABLE → RECONNECTED → DISCONNECTED → ENDED`. Adopting those names would put `ACTIVE` beside `CONNECTED` and `ENDED` beside `DISCONNECTED` in one type and require a mapping table proving they never contradict each other — a second source of truth wearing a reconciliation sheet, and the exact duplicate Phase 1 deleted from `DeviceSession` (`device/DeviceSession.kt:9-15`). The realised answer splits the sketch along the seam that makes contradiction impossible:

| What prompt §7 asks a lifecycle to say | Where it actually lives | Why it cannot disagree |
|---|---|---|
| where the device has got to | `DeviceState.connection` only; `TrackedDeviceSession.connectionState` is a read-through (`:52-53`), not a field | there is one place to say it (ADR-P4-002) |
| whether the engine is running | `SessionEngineStage` {`NOT_STARTED`, `RUNNING`, `STOPPED`} (`SessionVocabulary.kt:13-22`) — a fact about *this object*, derived from the projection's own `ObservationStage` (`:186-190`) | it describes no device, so it cannot contradict one |
| ACTIVE / RECONNECTED | `CONNECTED` plus `SessionCreated` / `SessionReconnected` / `SessionUpdated` edges (§8) | an edge is not a state; nothing to keep in step |
| TEMPORARILY_UNAVAILABLE | `ConnectionState.TEMPORARILY_UNAVAILABLE`, one of the six reachable states | it *is* the state |
| ENDED, and why | `SessionTermination` on the `SessionEnded` event (`SessionVocabulary.kt:61-80`, `DeviceSessionEvent.kt:71-75`), then removal from the list | a reason travels with the edge; the list holds only live sessions |
| the times | `SessionTimeline`'s three nullable numbers, each with one documented producer (`SessionTimeline.kt:16-32`) | timestamps answer "when did we decide", never "what is true" |

`theSessionEngineStageIsNotADeviceState` (`SessionStatePurityTest.kt:234-244`) pins the three-member stage set *and* asserts that no `ConnectionState` member is named `ACTIVE` or `ENDED` — the crept-in second axis is a test failure, not a review catch. `noSessionTypeCanClaimVerificationBeyondWhatThePhaseHas` (`:204-212`) reads `TrackedDeviceSession`'s declared field list and refuses a `verification` field, on the same logic: a session asserts that the platform reported a device and nothing about what the device can do (ADR-P4-012).

**The reachable set is six, and it is derived rather than listed.** `TrackedDeviceSession.reachableStates` (`:125-128`) is `allowedNext(ConnectionState.UNKNOWN)` minus `ERROR` (`:125-127`) plus `UNKNOWN` — `UNKNOWN, DISCOVERED, PAIRED, CONNECTED, TEMPORARILY_UNAVAILABLE, DISCONNECTED` — computed from Phase 1's table so it cannot silently drift when the table changes. `theEngineCanOnlyReachSixStatesAndNoneOfThemImpliesCapabilityWork` (`:36-58`) asserts the set equals those six, that `IDENTIFYING`, `CAPABILITY_DISCOVERY`, `READY` and `CONTROL_SESSION` are absent from it, and that `ERROR` is absent from it too. That last assertion is where this record and ADR-P4-003 disagreed, and the ADR was corrected at close-out rather than the code being re-read. Its title read "five states plus ERROR", which both counted the reachable set wrongly and named ERROR as a state the engine produces, while the code and its test pinned six with ERROR excluded (`SessionStatePurityTest.kt:57`). It now reads "Phase 4's reachable `ConnectionState` subset is six states, and the other five — including `ERROR` — are pinned unreachable" (`decisions.md:98`), its decision text (`:106-113`) derives the set the way `reachableStates` does, and it adds why ERROR is refused with the other four instead of kept as the safety valve it looks like: an evidence gap is this app's condition, not the device's fault, and ADR-P4-007 already represents that condition where it actually lives — as an observation status carrying the platform's own category. What the correction leaves intact is the subtlety this file first had to name: `allowedNext` adds `ERROR` to *every* state's permitted moves (`ConnectionState.kt:100-101`), so ERROR is **permitted by the table**, while no Phase 4 path ever **requests** it — `targetStateOf` (`:480-501`) returns it in no branch, and `grep` finds `ConnectionState.ERROR` exactly once in the session area, in the filter at `:127`. ERROR is therefore reachable-by-permission and unreachable-by-construction, which is what the corrected ADR now says in its own words, and what the test's second half pins. The four forbidden states stay constructible by *any other layer* — that is the point of §14's UI rule and of ADR-P4-003's consequence that Phases 5, 6 and 8 each inherit a check saying "this state was already reachable and you did not produce it."

**An illegal move is recorded, not performed** — §5's last table row and `recordRefusal` (`:438-447`) carry it, `SessionStatePurityTest.aConnectionMoveThatTheTableRefusesReturnsAFailureAndLeavesTheRecordAlone` (`:107-117`) carries the model-level half, and ADR-P4-003's `DeviceState.attemptConnection` refusal (`DeviceState.kt:113-121`, `Failure(INVALID_STATE)` with the table's own sentence in the detail) is the mechanism. What the phase does *not* claim: that this is confinement. `copy(connection = …)` still compiles for anyone holding the record (`DeviceState.kt:30-36`), and ADR-P4-001 keeps the single-mutation-owner obligation at Phase 24 rather than absorbing it here.

Three sentences this diagram is not allowed to generate. A session that ended by absence is **not** "the device powered off, was put away or was unpaired" (`SessionVocabulary.kt:56-59`). And an empty list after a `Refused` or `Unconfirmed` round is **not** "nobody is connected" (§12's emptiness rule).

## 9. Multiple devices, duplicates, and what order things publish in

Prompt §11's list maps to one data structure and four small rules.

- **Multiple simultaneous sessions, no single-device assumption.** `tracked` is a `List<TrackedDeviceSession>` (`:84`) and `sequence` a counter; there is no "the" session anywhere in the area, and no member of the published type takes a singular device. Independence is what the two-device cases show: `activeSessionsIsAViewOverTheOneValueNotASecondOwner` (`:286-298`) leaves one session `CONNECTED` and the other in the grace from a single round, and `aRefusalIsNotTheSameSentenceAsAnEmptyCensus` (`:131-142`) carries two sessions through a refusal and then into two grace slots at once, with `activeSessions` empty and both records still present.
- **No duplicate sessions from multiple profile observations.** The partition map is keyed by device, so N reports of one key collapse to one (`:144-152`) — `oneDeviceReportedTwiceInOneRoundStillOpensOneSession` (`:76-84`) feeds A2DP and HEADSET reports of the same address and asserts one session and `session-1`. Profile set is never mapped to a state (§5), which is what keeps "which service" from becoming "what capability" (ADR-P3-002).
- **Identical names, missing names, ambiguous identity.** §6: two names never merge, and a nameless connected device is a session (`aSessionCarriesNoEvidenceThisPhaseDoesNotHave`, `:244-256`, builds one from a blank name and asserts `isEntirelyUnknown` alongside a live `CONNECTED`).
- **Partial observations.** A round in which profiles did not answer is `Unconfirmed` or `Confirmed(false)`, and absence in it withdraws nothing (`:377`; `absenceFromAnUnansweredRoundWithdrawsNothing`, `:108-114`) — prompt §19's "partial observations are supported" is delivered as *partial information changes nothing rather than ending things*.
- **Deterministic ordering.** Two orders, both pinned. Session order is creation order, not round order: carried sessions are emitted first, then new keys in the round's own order, through a `LinkedHashMap` (`:144`, `:154-179`) — `sessionsArePublishedInCreationOrderWhateverTheRoundSays` (`:404-414`) has `session-1` remain first when a later round lists `KEY_LEFT` before `KEY_RIGHT`. Event order within a round is the order the state was built, and events are emitted *after* the state value is set (`:455-468`) — `oneRoundPublishesItsEventsInTheOrderTheStateWasBuilt` (`:417-428`). Phase 0's rule 5.6 reading of "documented ordering" (prompt §13) is satisfied by that pair: a consumer that reads the flow and then the edges sees a state no earlier than the edges it is holding.

**Duplicate suppression** lives at the edge, not in a buffer: `applyReport` emits only when `target != current.connectionState` (`:272`) or when the identity actually grew (`:307-308`), so a flapping profile that keeps reporting the same link produces no events at all, and an unchanged round produces none. The engine therefore has no `saysSameAs` analogue of Phase 3's — it does not need one, because Phase 3 already deduplicates per device and this layer's deduplication is "same state, no event". What remains genuinely new here is the suppression across *round classes*: a refused round emits exactly one edge (`SessionObservationFailed`) and no device edges, which is prompt §13's "avoid duplicate emission" applied to a failure that a platform can repeat on every poll.

## 10. Events: seven of prompt §13's eight, and what a payload may not contain

`DeviceSessionEvent` (`:34-104`) declares `SessionCreated`, `SessionUpdated`, `SessionDisconnected`, `SessionReconnected`, `SessionEnded`, `SessionIdentityChanged` and `SessionObservationFailed`. **`SESSION_ACTIVATED` was refused** (ADR-P4-008), and the reason is stated in the type's own KDoc (`:8-14`): "activated" reads as a device becoming *usable*, which is the claim ADR-P4-003 makes unreachable — a move to `CONNECTED` is the phone reporting a link, first arrival is already `SessionCreated`, and a return is already `SessionReconnected`. An event whose meaning is the union of two others is how a UI ends up rendering a readiness nobody verified.

Three payload rules, each with a file:line and all three held by the constructor shapes rather than by convention. **No device text:** every case carries `sessionId` and, where a device is involved, counts or states — `SessionIdentityChanged` carries `knownFieldCountBefore`/`knownFieldCountAfter` (`:85-90`) precisely so an identity improvement can be announced without announcing a name, and `SessionObservationFailed` carries no session id at all (`:100-103`) because it is the engine reporting that it was told nothing. **No restatement:** §9's suppression rule. **Not a history:** published on a `MutableSharedFlow(replay = 0, extraBufferCapacity = 64, onBufferOverflow = DROP_OLDEST)`, all three declared with the reason beside them (`DeviceSessionEngine.kt:93-101`, constants `:520-521`), because rule 5.5 (`docs/phases/phase-0/specs.md:145`) requires every flow to state its buffering and overflow rather than inherit a default. `tryEmit` (`:466`) is the other half of that choice: an engine that suspended on a consumer that stopped caring would let a consumer hold the state owner hostage. A lagging collector loses the *oldest* edge and reconciles from the `StateFlow` — which is why `replay = 1` was rejected (ADR-P4-008) and why `nothingTheEnginePublishesPrintsADeviceIdentifier` enumerates all seven cases rather than three. Two residuals are named rather than smoothed: the `DROP_OLDEST` behaviour itself is never exercised, because no case emits 65 edges, and `RISK-072` owns the design's one soft spot — the shape is safe exactly as long as a consumer reads `events` as a notification, and nothing in the build stops the first UI from reading it as a queue it must not miss.

Two consequences worth naming before someone reads them as gaps. `DisconnectEvidence` (`:107-113`) exists because the two ways a disconnect is established — a positive report, and absence from a union in which every profile answered — mean different things to a consumer and must not collapse into one event (ADR-P3-015 rule 4); absence from a refused or unanswered round produces no event *at all*, because it is not evidence. And `atEpochMillis` on every case is the engine's clock reading at publication, nullable when no clock was injected (`:30-32`; `anEngineWithoutAClockPublishesNullTimesAndNeverZero`, `DeviceSessionEngineTest.kt:274-283`), never a claim about when the device did anything.

The `Mutex` makes a concurrent second `apply` *defined* — it waits, then sees the first one's `tracked` — and *unproven*, and because `apply` is public (§3) a caller can race `consume` with it today. ADR-P4-009's own consequences concede the point and `RISK-073` owns it with the three specific interleavings left unexercised; it is the same shape as RISK-031's "enforced by nothing" pattern that Phase 2, Phase 3 and now Phase 4 each recorded rather than closed |

One more resource note, because it is the phase's cheapest safety property: there is no resource to leak. The engine registers no receiver, binds no profile proxy, opens no stream and holds no framework handle — everything it owns is Kotlin objects on the heap (`:82-88`). The leak classes Phase 3 had to design around are therefore absent here by scope rather than by cleanup, which is what makes the `NonCancellable` block three lines instead of a disposal protocol with counts.

## 12. Privacy and retention: what SEC-ID-005/006/007 require of a session store

Phase 0's identifier governance (`docs/phases/phase-0/security-governance.md:69-78`) is the spec this section implements, and its active-session row is the sentence the whole phase is built to satisfy: *enters by being currently connected, leaves by disconnect unless explicitly saved, identifier retention "cleared with the session; no durable record."* Three consequences, each with a mechanism rather than an intention.

- **An active session list must die with the session.** Every end path removes the record rather than flagging it: the grace is one published round (`:262-269`, `:343-348`), ambiguity is one round (`:227-244`), and stopping empties the list wholesale inside `NonCancellable` (`:205-217`). ADR-P4-006's rejection of "keep ended sessions with an `ENDED` flag" is the same rule read forward: a filtered history would make `activeSessions` a query over a device list the user never approved.
- **Scanning is not saving (SEC-ID-006).** The engine creates no session from the paired census — the input loop reads `projection.records` and nothing else (`:146`) — and mints no session from absence, an unconnected first sighting, or an unobservable device (`:388-395`, §5's `null` rows). `sequence` starts at zero per engine instance (`:83`), so even the id space carries no memory across a restart: two engines that saw the same phone number their sessions independently.
- **Deletion completeness (SEC-ID-007) is discharged here by absence, and only here.** There is nothing for a delete to miss inside Phase 4, which is a property of this store and not of the product: the obligation lands intact on whichever phase first persists, and `persistence/DeviceRepository.kt:8-28` remains the seam that owns it. `forget()` (`device/DeviceSession.kt:85`) is untouched — no Phase 4 path has a saved record to forget.

**What a session cannot hold,** and where each prohibition lives: an address (the join is the typed `DeviceObservationKey`, `TrackedDeviceSession.kt:36`, whose `AddressBacked` prints kind and length and exposes no getter — `platform/DeviceObservationKey.kt:50-59`); a fingerprint (`DeviceSession.fingerprint` stays null, asserted at `DeviceSessionEngineTest.kt:253`, because fingerprinting is Phase 5 and prompt §17 forbids starting it); capabilities, battery, audio, firmware or codec (`DeviceState.initial` leaves them empty/unobserved, `DeviceState.kt:168-177`; the withers that would fill them — `withCapability`, `withBattery`, `withAudio` — have **no session-engine caller**, and the only calls this engine makes are `initial`, `attemptConnection` and `withIdentity`); identity fields no report supports (`identityOf` `:511-512` fills a name or nothing, and `aSessionCarriesNoEvidenceThisPhaseDoesNotHave` `:244-256` asserts manufacturer, model and model id all null); a verification level (`SessionStatePurityTest.kt:204-212` reads the declared field set and refuses one); and pairing material or link keys (SEC-ID-008 — reachable by no seam this layer may import).

**`displayName`, carried up from Phase 3.** Phase 3's design recorded that redaction is a property of the *key* type and not of the name: a reported name is a platform string in a data class, so a record's own `toString()` prints it. That exposure now travels one layer further, and the honest accounting has two sides. **Wider:** the name is held in a store a future UI will render and diff, and it *survives rounds* — an identity that grew keeps the text across the grace and across subsequent rounds (`:307-316`), whereas Phase 3's records are replaced at every round boundary; a session list is therefore a longer-lived copy of the phone's labels than a snapshot was. **Narrower:** the emission surface got smaller rather than larger, because no event carries text — `SessionIdentityChanged` carries two integers (`DeviceSessionEvent.kt:85-90`) and every payload is id/state/count (§10). The check that exists catches addresses, not names: `nothingTheEnginePublishesPrintsADeviceIdentifier` (`SessionStatePurityTest.kt:166-189`) matches a MAC-shaped regex over sessions, all seven event cases and the key, and would pass a printed alias — exactly Phase 3's residual, and `assertNoAddressText` is the same style of guard its instrumented suite used. Nothing can emit it either: `diagnostics/OmniBudsLogger` is untouched by this phase and ADR-P1-019's redaction duty still has no owner, so the discipline that matters remains the type-level one — which is the split `RISK-079` records: the address guarantee is carried by a type, the label by nothing but the absence of a sink.

**Nothing is persisted, and the reason is a layer rule rather than a mood.** `session` and `persistence` are both layer 3, and the direction check flags any import of an area at the same or higher layer (`DependencyDirectionTest.kt:37-52` for the map, `:258-266` for the rule), so a convenience call into the saved-device seam would fail the build before a reviewer saw it. Two scans say the rule was not quietly widened: `PhaseFourScopeTest.theSessionLayerStillImportsNoPersistenceContract` (`:54-65`) greps the eight main sources for `import com.omnibuds.core.persistence.`, and `noProductionClassImplementsTheProtocolOrRepositoryContracts` (`:237-251`) refuses any production implementation of `DeviceRepository` — which is how ADR-P4-010's "nothing in Phase 4 reaches storage" is machine-checked rather than promised. The consequence is stated as a design fact, not a gap: no session survives process death (ADR-P4-012).

## 13. What a screen may read, and the four sentences it must not be allowed to imply

Prompt §16 asks for API shape without UI. The surface a Phase 49 screen may read is exactly this, and none of it is a command (rule 5.6, `specs.md:146`):

| A screen may read | Where |
|---|---|
| the whole authoritative value, and only that | `snapshot: StateFlow<DeviceSessionSnapshot>` (`DeviceSessionEngine.kt:91`) |
| the devices, in creation order | `sessions` (`DeviceSessionSnapshot.kt:27`) |
| the three views it would otherwise be tempted to filter itself | `activeSessions` (`:44-45`), `disconnectPendingSessions` (`:48-49`), `ambiguousSessions` (`:52-53`) — each `get()`, none stored |
| whether an empty list means anything | `isEmptyMeaningful` (`:56-57`) over `SessionObservationStatus.isEmptyMeaningful` (`SessionObservationStatus.kt:72-73`) |
| why the list is the way it is | `observation` (`DeviceSessionSnapshot.kt:28`), including `Refused(error)` whose category is Phase 3's |
| where the engine itself is | `stage` (`:26`) — `NOT_STARTED` / `RUNNING` / `STOPPED`, about the object, not the phone |
| per device | `sessionId` (`TrackedDeviceSession.kt:35`), `connectionState` (`:52-53`), `displayName` (`:56-57`, nullable), `basis` (`:37`), `isSaved` (`:73-74`), the three nullable `timeline` times (`SessionTimeline.kt:40-42`) |
| what the engine was refused | `refusedMoves` (`DeviceSessionSnapshot.kt:41`), newest last, 8 wide |
| staleness, without a clock | `revision` (`:29`) and `publishedAtEpochMillis` (`:30`, nullable) |
| edges, if it wants to animate rather than diff | `events` (`DeviceSessionEngine.kt:104`), with `replay = 0` and no history (§10) |

Prompt §16's seven display needs all land on that table. What the table must not be allowed to *generate* is the phase's real UI requirement, and four sentences are refused by structure:

1. **"This device is supported" / "this is an earbud."** There is no field for it, and `DeviceObservation`'s arrival evidence cannot fill one — a session asserts that the platform reported a device and nothing about what the device is (prompt §6, ADR-P4-012). The temptation Phase 3 refused at the platform (`BluetoothClass` proves nothing) is refused here at the store, which is why no `isSupported` or `deviceKind` exists to be populated later by accident.
2. **"This device is ready to be controlled."** `READY` and `CONTROL_SESSION` are unreachable by every path (§7), and `DeviceState.isOperational` (`DeviceState.kt:57-58` → `ConnectionStateTransitions.isOperational`, `state/ConnectionState.kt:107-108`) is true only of those two, so it is `false` for every session this engine can ever build. A screen that renders "ready" must therefore import the claim from a phase that has not run.
3. **"Its capabilities / battery / codec are known."** Capabilities are empty, battery entirely unknown, audio unobserved, and the methods that would change any of them have no caller here (§12). A null battery stays null; `SessionTimeline`'s times are nullable and never zero-filled (`SessionTimeline.kt:6-11`), so "never observed" cannot render as `0%` or as a 1970 date.
4. **"This device is saved, so it will be here tomorrow" — or "this session id identifies a device."** `isSaved` is false always, `classification` is `TEMPORARY` always (`everySessionThisEngineMakesIsTemporary`, `DeviceSessionEngineTest.kt:63-73`), nothing persists, and the id is not stable across a grace boundary (§8's `session-2`). ADOPTING the id as a UI key is therefore legitimate only for the lifetime of a connection, which is ADR-P4-006's stated cost and the one sentence Phase 49 must inherit rather than discover.

The fifth trap is the one the type was shaped to make awkward rather than impossible: `sessions.isEmpty()` is true in five worlds (nothing read, announcements unsettled, refused, stopped, and a genuine empty census), and only `isEmptyMeaningful` distinguishes them — reading the length without the status "takes an extra deliberate step" (`DeviceSessionSnapshot.kt:21-23`). And prompt §16's own prohibitions hold: no screen, layout, navigation or component exists (rule 9 in the architecture guard), no device is hardcoded into the state model (`tracked` is a list, §9), and the first UI remains Phase 49.

## 14. Platform limits: every one inherited, every one UNVERIFIED

Phase 4 asserts nothing about a handset that Phase 3 did not already assert. The engine's inputs are `DeviceConnectionState`, `DeviceBondState`, `DeviceAvailability`, `isUnionComplete`, `restsOnCompletedRound`, `deviceRoundRefusal` and the key — all of them Phase 3's transcriptions of Android documentation (`platform/DeviceObservation.kt:46-78`, `platform/ConnectedDeviceObserver.kt:75-175`), all of them sitting behind research U-1 … U-12 and under RISK-044 (`phase-3/risk-register.md:11`, "the framework half of this phase has never executed, and every device claim in it is a transcription"), and all of them capped at `IMPLEMENTED` here by ADR-P4-012. The two that name this phase's weakest rows are U-4 (`connection-observation-research.md:1053` — do the connection broadcasts actually arrive, under which registration shape) and U-9 (`:1058` — the real latency and ordering of ACL versus profile versus aggregate events, and whether they are coalesced or dropped under load).

The useful form of the limit is conditional: **if a handset contradicts the transcription, here is what changes.**

| If the platform turns out to… | Then this engine… | And the design that would have to move |
|---|---|---|
| never deliver `CONNECTING` / `DISCONNECTING` (U-4, U-9 — the aggregate action fires only on 0↔1) | be unaffected in correctness and impoverished in detail: two of §5's rows never fire, `DISCOVERED` and the blip `TEMPORARILY_UNAVAILABLE` are never emitted, and every transition is `CONNECTED ↔ DISCONNECTED` | nothing; ADR-P4-004 wrote those rows to be right if they never occur. The loss is a UI affordance, and ADR-P3-001's refusal to synthesize intermediates stays correct |
| deliver announcements slowly, coalesced or dropped (U-9) | use the grace up before the reconnecting round arrives, so a physical reconnect mints a **new** `sessionId` and emits `SessionCreated` instead of `SessionReconnected` | the *window*, not the rule: ADR-P4-006's one-round grace is the tunable, and a second parameter (rounds of grace) would be a decision with its own ADR. This is the phase's most likely real-world divergence, and it is unproven either way |
| rotate or mask addresses (U-2, unresolved by design) | see one product as two keys: two sessions, each `KEYED`, each independently graced and ended, with no merge available — the failure direction Phase 3 chose deliberately ("the same product appears twice", never "two products became one") | nothing in Phase 4; a real fix is Phase 5's fingerprint, and the honesty rule is that a duplicate here is visible rather than welded |
| report a device with no key as the normal case rather than the exception | run mostly on ambiguity: most sessions would be `AMBIGUOUS` and therefore one-round-lived, so the store would empty itself between rounds | the one-round rule (`:227-244`) would need re-deciding under a new ADR; nothing in this phase may match unkeyed reports by name, and §6 is why |
| answer a denial with an *empty* list rather than a refusal (U-1, U-11) | publish `Confirmed(unionComplete = true)` with no records, end every session by absence, and mark `isEmptyMeaningful` true — a revoked permission would read as everybody going home | Phase 3's ordering guard (`standing before looking`, its design §5) is the only defence, and it is upstream: this layer cannot tell a lying empty union from a true one. Nothing here adds a second guard, and that is a stated limit rather than an oversight |
| report `bond == BONDED` for a device with no live link as the common case | open `PAIRED` sessions from link records (§5's row) — which is fine, but a bond axis that lags would produce `PAIRED` states that outlive the pairing | `targetStateOf`'s `UNKNOWN + BONDED` branch (`:495-496`) is the only bond-driven row, and it never touches `pairedDevices`, so the census cannot become a session by any path |
| hand us null or incoherent timestamps | behave identically: no `Long?` time is ever compared (§11's authority rule), and a missing clock is a supported configuration (`anEngineWithoutAClockPublishesNullTimesAndNeverZero`, `:274-283`) | nothing — this is the one row where the design is *already* independent of the platform's clock |
| not announce at all under the current registration shape (U-4's sharper half) | see one projection per round boundary, so sessions stay correct at round granularity and the grace becomes the only debounce | `refresh()` would finally need an owner; ADR-P4-011 refused to give it one here and RISK-058 (`phase-3/risk-register.md:126`) keeps the shape open, which is exactly the case that ADR records as "visibly refused, not silently absent" |

**The register carries each row by name**, so a later reader can find the exposure without this table: RISK-067 is row 5 (the engine trusts its projection completely, and a source that published a complete empty union would end every session it holds), RISK-068 is row 2 (the one-round grace is a policy with no handset evidence — too short if announcements are slow, too long if a device flaps), RISK-069 is row 4 (an address-less handset produces a stream of create/end events and an unstable list), RISK-076 is row 6 (a bond disagreement now surfaces as a published `PAIRED` rather than a silent note), RISK-080 is row 1 plus the `arrival` divergence (§3, §17), RISK-083 is row 3's counting half (a binaural pair is two sessions, so `activeSessions.size` counts entries and not devices the user owns), and RISK-084 is row 7's display consequence. RISK-065 is the umbrella: Phase 4 inherits Phase 3's transcription risk wholesale and adds the layer a user would actually read it through.

What Phase 4 adds to the evidence base is one sentence and it is not about a handset: Phase 3 proved the projection cannot lie about a device, Phase 4 proves the session layer cannot *read* it as one (§15's machine checks on both sides of the mapping). Everything else remains `NOT RUN`, and prompt §19's "do not report unexecuted device tests as passed" is honoured by there being no device tests to report.
