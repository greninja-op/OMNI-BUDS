### REQ-P4-001 — One type owns session state, it lives at `core/session` layer 3, it reads the Phase 3 projection and no control seam, and the composition root only constructs it
**Description.** Exactly one production type, `DeviceSessionEngine` in `com.omnibuds.core.session`, SHALL own the map of live device sessions; no 13th area, Gradle module, second engine, repository-shaped class or competing active-device list SHALL appear; the engine SHALL consume `ConnectedDeviceSnapshot` **values** — as a `Flow` handed to `consume()` (`DeviceSessionEngine.kt:116-124`) or one at a time through `apply()` (`:133-193`) — and SHALL NOT reference `ConnectedDeviceSource`, `ConnectedDeviceObserver`, `AdapterStateSource`, `BluetoothPlatform`, `BluetoothOperation`, `PlatformRegistration`, `ConnectedDeviceEventChannel` or `PermissionContext`; the session area SHALL import no `android.`/`androidx.`/`com.omnibuds.android.` type and no framework token; `session` (layer 3) SHALL import nothing from `persistence` (layer 3) or `protocol` (layer 4); the only `:platform:android` change SHALL be `omniBudsDeviceSessionEngine(time)` (`di/OmniBudsBluetooth.kt:152-154`), which constructs the engine, starts nothing and owns no scope; and the views a consumer reads — `activeSessions`, `disconnectPendingSessions`, `ambiguousSessions` — SHALL be derived at read time from the one published `StateFlow<DeviceSessionSnapshot>` (`DeviceSessionSnapshot.kt:44-53`), never stored beside it.
**Rationale.** Prompt §5 ("there must be one authoritative source of active session state … do not create separate competing active-device lists"), §8 ("it must not independently create another Bluetooth scanner or observer"), §3 (the session engine must be platform-independent wherever practical); ADR-P4-001 places the engine, refuses a 13th area under ADR-P3-003's rule and refuses the alternative of the engine owning an observer, because that would make session state depend on observation *control*; `docs/phases/phase-0/specs.md` rule 5.7 (one owner writes, others read); the layer map at `DependencyDirectionTest.kt:37-52`.
**Dependencies.** REQ-P3-001, REQ-P3-012, REQ-P2-001; ADR-P4-001, ADR-P3-003, ADR-P3-004.
**Acceptance criteria.** AC-1 the engine publishes one `StateFlow<DeviceSessionSnapshot>` (`snapshot`, `DeviceSessionEngine.kt:91`) and no second authoritative state flow exists. AC-2 the three projections are `get()`-derived filters over `sessions`. AC-3 the session area's only `platform` import is the value type `ConnectedDeviceSnapshot` plus `DeviceObservation`, `DeviceObservationKey`, `DeviceBondState`, `DeviceConnectionState`, `ObservationStage`, `isObservable`, `TimeProvider`/`NoTimeProvider` — no control type. AC-4 no session source imports `persistence`. AC-5 all Phase 4 session sources sit under `core/session`, in one area. AC-6 no Bluetooth operation is newly authorised at phase 4. AC-7 `:core` main sources import no Android framework and name no framework token. AC-8 the DI function returns a constructed engine and launches nothing. AC-9 the module set and the area count are unchanged.

### REQ-P4-003 — The engine moves sessions only among the states its evidence supports, and the four later-phase states are pinned unreachable by a machine check
**Description.** The engine SHALL target only `UNKNOWN`, `DISCOVERED`, `PAIRED`, `CONNECTED`, `TEMPORARILY_UNAVAILABLE` and `DISCONNECTED`; it SHALL NOT reach `IDENTIFYING` (Phase 5), `CAPABILITY_DISCOVERY` (Phase 8), `READY` or `CONTROL_SESSION` (Phase 6), and it SHALL NOT target `ERROR`, which the transition table permits from every state but no Phase 4 path has evidence for; every move SHALL pass through `DeviceState.attemptConnection` (`DeviceState.kt:109-129`), which refuses an illegal move as `Failure(INVALID_STATE)` rather than performing it; the reachable set SHALL be stated in code where a guard can read it (`TrackedDeviceSession.reachableStates`, `:131-134`) and pinned by a test that fails if it widens; and no session value SHALL imply vendor support, control readiness or discovered capability.
**Rationale.** Prompt §6 ("a session must not imply vendor support … control readiness … that hardware capabilities have been discovered") and §7 ("do not claim that Android exposes every intermediate connection transition"); ADR-P4-003, which reasons that a `StateFlow` of sessions is exactly the surface a future UI reads, so an unreachable-but-constructible state is a claim waiting to be made; master §2 (never simulate) and §53; `state/VerificationLevel.kt`'s ladder.
**Dependencies.** REQ-P4-002, REQ-P4-004; ADR-P4-003, ADR-P4-012.
**Acceptance criteria.** AC-1 `reachableStates` equals exactly the six named states and contains neither `ERROR` nor the four later-phase states. AC-2 the four excluded states appear nowhere in the engine's mapping function. AC-3 a refused move leaves the held state and records the refusal. AC-4 a session built from any projection carries empty capabilities, an unknown battery and an unobserved audio state. AC-5 the transition the table permits but this phase declines (`CONNECTED → IDENTIFYING` and onward) is named, not left to inference. AC-6 `isOperational` can never be true for an engine-built session.
**Verification.** AC-1 `session/SessionStatePurityTest.theEngineCanOnlyReachSixStatesAndNoneOfThemImpliesCapabilityWork` (`SessionStatePurityTest.kt:36`), which asserts the six-member set equality with the message "the reachable set changed, and ADR-P4-003 has to be re-decided rather than widened" (`:54`) and separately asserts `ERROR` absent (`:57`); AC-3 `.aConnectionMoveThatTheTableRefusesReturnsAFailureAndLeavesTheRecordAlone` (`:107`) and `DeviceSessionEngineTest.aMoveTheTransitionTableRefusesIsRecordedAndTheHeldStateKept` (`DeviceSessionEngineTest.kt:356`); AC-4 `.aSessionCarriesNoEvidenceThisPhaseDoesNotHave` (`:243`), which asserts `capabilities.features.size == 0`, `battery.isEntirelyUnknown` and a null `fingerprint`; AC-6 is a consequence of `ConnectionStateTransitions.isOperational` (`core/state/ConnectionState.kt:107-108`, true only for `READY`/`CONTROL_SESSION`) plus AC-1, asserted at `DeviceStateTest.kt:195`. **Inspection residue (AC-2, AC5):** no check walks `targetStateOf` (`DeviceSessionEngine.kt:480-501`) for the four names — `PhaseFourScopeTest.theSessionLayerNamesNothingThatImpliesAControlSession` (`:68`) bans transport tokens (`:72`: `TRANSPORT_RFCOMM_OPEN`, `TRANSPORT_GATT_OPEN`, `connectGatt`, `createRfcommSocket`) and not `ConnectionState` names, so AC-2 is a reading of the mapping function; and AC-5 is documented at `TrackedDeviceSession.kt:118-121` rather than asserted. ## Observation-to-session mapping

### REQ-P4-004 — Every positive report maps to exactly one `ConnectionState`, cell by cell, and no cell maps to something stronger than its evidence
**Description.** For a record the projection carries, `targetStateOf` (`DeviceSessionEngine.kt:480-501`) SHALL answer one way and no other: `availability` observable with `link == CONNECTED` → `CONNECTED`; `link == CONNECTING` → `DISCOVERED`, never `CONNECTED`; `link == DISCONNECTING` → `TEMPORARILY_UNAVAILABLE`, never `DISCONNECTED`; `link == DISCONNECTED` → `DISCONNECTED` for a tracked session and no session at all for a first sighting; `availability` not observable → `TEMPORARILY_UNAVAILABLE` for a tracked session and nothing for an untracked one; `link == UNKNOWN` with `bond == BONDED` → `PAIRED`; `link == UNKNOWN` with the availability observable and no positive bond → `UNKNOWN` for a tracked session and nothing for an untracked one; and no mapping SHALL be derived from a profile set, a display name, or the paired census.
**Rationale.** Prompt §8's reconciliation steps 2–5 and §7's "use only evidence-supported transitions"; ADR-P4-004's table, whose whole subject is these rows, and the trap it names — `DeviceConnectionState.UNKNOWN` means "no report was obtained", so mapping it to `DISCONNECTED` would invent a negative that ADR-P0-016 forbids and prompt §9's "prevent stale active status" does not license; the `CONNECTING`/`DISCONNECTING` rows are deliberately the weakest readings because the platform's promise that those states are ever *delivered* is research U-4/U-9, so the engine must be right if they never arrive and wrong in no way if they do.
**Dependencies.** REQ-P4-003, REQ-P3-002, REQ-P3-003; ADR-P4-004, ADR-P3-001, ADR-P0-016.
**Acceptance criteria.** AC-1 a reported-connected device yields `CONNECTED` and nothing stronger. AC-2 `CONNECTING` yields `DISCOVERED`. AC-3 `DISCONNECTING` yields `TEMPORARILY_UNAVAILABLE`. AC-4 a tracked device reported disconnected yields `DISCONNECTED`. AC-5 a tracked device whose availability stops being observable yields `TEMPORARILY_UNAVAILABLE` and not a disconnect. AC-6 a bonded device with no live-link report yields `PAIRED` and not `CONNECTED`. AC-7 an untracked device reported disconnected, or with an unobservable availability, opens no session. AC-8 a tracked device whose link reads `UNKNOWN` with the availability observable and no positive bond stays `UNKNOWN`. AC-9 a move the table declines leaves the held state and records the refusal.
**Verification.** AC-1 `session/DeviceSessionEngineTest.aConnectedDeviceOpensExactlyOneSession` (`DeviceSessionEngineTest.kt:49`); AC-2 `.aLinkStillComingUpIsDiscoveredRatherThanConnected` (`:316`); AC-3 `.aLinkOnTheWayOutIsNeverReadAsADisconnect` (`:309`); AC-4 `.aRepeatedDisconnectReportUsesTheSameGraceWindow` (`:158`); AC-5 `.aPhoneWhoseRadioWentQuietMakesTrackedDevicesUnavailableNotGone` (`:323`); AC-6 `.aBondedDeviceWithNoLinkReadingIsPairedAndNotConnected` (`:300`); AC-7 `.aFirstSightingOfAnUnconnectedDeviceOpensNoSession` (`:339`); AC-9 `.aMoveTheTransitionTableRefusesIsRecordedAndTheHeldStateKept` (`:356`). **AC-8 is produced by no test:** the arm at `DeviceSessionEngine.kt:497` (`tracked -> ConnectionState.UNKNOWN`) is reached only when `bond != BONDED` and the link reads `UNKNOWN` while the availability is observable, and no test scripts that combination — `:356` scripts `bond = BONDED` (which answers AC-6's row, and moves the session into a refusal instead), and `:323` scripts `UNAVAILABLE` availability (which answers AC-5). It is therefore a reading of `:495-499`, and it is also a no-op in behaviour: a move to the state already held emits no event (`:272`), so a check would assert only that nothing happens. The wider ceiling on this whole group: **every row here is a mapping over faked reports**; which rows a real handset ever fills is U-4/U-9 and untouched by this phase (ADR-P4-012's "what this phase therefore cannot say").

### REQ-P4-005 — Absence becomes evidence only when the union answered, and a round that refused or went unanswered withdraws nothing

## Identity, keys, ambiguity and the session id

### REQ-P4-007 — Duplicates are impossible by key: one joinable key owns one session, the update path cannot mint an id, and a repeat never re-creates

## Disconnect, reconnect and termination

### REQ-P4-011 — A disconnect leaves the active projection, is recorded as a transition, is never a save, is never a deletion, and never leaves a device looking active
**Description.** When a session's evidence supports `DISCONNECTED` — a positive report, or absence from a complete union — the engine SHALL move it through the transition table, SHALL record `disconnectedAtEpochMillis` once and keep the first mark (`SessionTimeline.markedDisconnected`, `:56-57`), SHALL drop it from `activeSessions` while leaving it in `sessions` for the grace (`DeviceSessionSnapshot.kt:44-49`), SHALL NOT write anything anywhere, SHALL NOT delete or demote any user-saved device profile (Phase 4 creates none to delete, and no path to `persistence` exists), and SHALL prevent stale active status: no session whose connection is not `CONNECTED` may appear in the active projection. **Dependencies.** REQ-P4-005, REQ-P4-006, REQ-P4-012; ADR-P4-006, ADR-P4-010, ADR-P3-015.
**Acceptance criteria.** AC-1 a disconnected session leaves `activeSessions` and stays in `sessions`. AC-2 `disconnectPendingSessions` names it while it is in grace. AC-5 no disconnect path reaches `persistence`, and no disconnect changes a session's classification. AC-6 two reports of one key in one round produce one transition. ### REQ-P4-012 — The reconnection policy is one documented, clock-free answer: a blip resumes, the grace is exactly one further published round, and reappearance after removal is a new session
**Description.** The engine SHALL implement ADR-P4-006's three rules and no timer: (1) a session that reaches `TEMPORARILY_UNAVAILABLE` and is reported connected again SHALL resume **the same session id**, and `disconnectedAtEpochMillis` SHALL never have been set for it, because a blip is not an ending; (2) a session that reaches `DISCONNECTED` — by report or by absence from a complete union — SHALL be kept with its disconnect mark for **exactly one further published round**, so that downstream consumers can see the transition, and SHALL be ended with `PROVEN_DISCONNECT_PAST_GRACE` if the next confirmed round still omits or still reports it down; if it reappears inside that window it SHALL keep its id and publish `SESSION_RECONNECTED` and clear the mark; (3) after removal, reappearance SHALL mint a **new** id and publish `SESSION_CREATED` with no lineage pointer retained. No reconnection path SHALL initiate a Bluetooth connection or a pairing.
**Rationale.** Prompt §9's named policy question ("define a clear policy for whether reconnection creates a new session ID or resumes an existing session … must be consistent and testable") and its two prohibitions on pairing/connecting automatically; ADR-P4-006, which refuses a time-window grace because "a timer makes the engine's behaviour depend on wall-clock scheduling rather than on observations", and refuses one-id-forever because that is prompt §10's forbidden history wearing a session name; Phase 1's `DeviceSession.sessionId` KDoc (`device/DeviceSession.kt:27-28`), which already said the id is not stable across reconnects.
**Dependencies.** REQ-P4-011, REQ-P4-013, REQ-P4-016; ADR-P4-006.
**Acceptance criteria.** AC-1 a disconnect-then-reconnect inside the grace keeps the id, clears the mark, and ends with `CONNECTED`. AC-2 the last event of that sequence is `SESSION_RECONNECTED`. AC-3 a second confirmed down-round past the grace ends the session with `PROVEN_DISCONNECT_PAST_GRACE` and empties the store. AC-4 reappearance after that ends creates `session-2`, connected, with no field linking it to `session-1`. AC-5 the whole policy is driven by published rounds and uses no clock comparison and no delay. AC-6 a `TEMPORARILY_UNAVAILABLE` session is not in `activeSessions` and is not in `disconnectPendingSessions`. AC-7 no engine path calls a connect, pair or discovery API.
**Verification.** AC-1/AC-2 `DeviceSessionEngineTest.aDeviceThatComesBackInsideTheGraceKeepsItsSessionId` (`:169`); AC-3 `.aDisconnectedDeviceIsHeldForOneRoundAndThenEnded` (`:144`) and `.aRepeatedDisconnectReportUsesTheSameGraceWindow` (`:158`), which runs the reported half; AC-4 `.aDeviceThatComesBackAfterTheGraceIsANewSessionWithANewId` (`:185`); AC-5 by the same three tests, none of which advances a scheduler, plus the injected `TickingClock` (`:553-556`) which proves no behaviour depends on the *value*; AC-7 `PhaseFourScopeTest.theSessionLayerReachesNoControlSeam` (`:31`) and `.nothingNewIsAuthorisedAtPhaseFour` (`:23`). **AC-6 is partly read:** `disconnectPendingSessions` (`DeviceSessionSnapshot.kt:48-49`) filters on `DISCONNECTED && termination == null`, so a `TEMPORARILY_UNAVAILABLE` session is excluded by construction, and no test asserts that exclusion; **and rule (1) has no test** — no check drives `CONNECTED → TEMPORARILY_UNAVAILABLE → CONNECTED` and asserts the id held and the mark never set (`:323` stops at the unavailable half), so the blip rule rests on `DeviceSessionEngine.kt:278-282`'s `from == DISCONNECTED` condition plus the fact that `markedDisconnected`'s only two callers (`:286`, `:363`) both sit inside the `DISCONNECTED` branch and never on the unavailable path. ### REQ-P4-013 — Every ending names an engine decision, and no termination reason can claim that a device did anything
**Description.** A session leaves the store only with one of the recorded reasons in `SessionTermination` (`SessionVocabulary.kt:61-83`) — `ABSENT_FROM_COMPLETE_UNION` is not emitted by any path (see Verification), `PROVEN_DISCONNECT_PAST_GRACE`, `AMBIGUOUS_SESSION_EXPIRED`, `OBSERVATION_STOPPED`, `ENGINE_CANCELLED` — published as a `SESSION_ENDED` carrying that reason; no reason SHALL read as "powered off", "unpaired", "went away" or any other claim about a device, because the most a census can support is that this phone enumerated every profile it could and named this device in none of them; a stopped or cancelled engine SHALL publish an empty authoritative list **with a reason attached** rather than a silent empty; and "why did this session end" SHALL be answerable from the event rather than inferred from an absence.

## Observation failure, status and the six distinctions

### REQ-P4-014 — A refused round never empties the session list, and the projection now carries the reason for its own refusal
**Description.** The engine SHALL treat a refused round as **no new information**: sessions keep their state, `activeSessions` is not recomputed as empty, and the published snapshot carries `SessionObservationStatus.Refused(error)` whose `OmniBudsError` is Phase 3's own, with its category intact (`PERMISSION_DENIED`, `BLUETOOTH_DISABLED`, `ADAPTER_UNAVAILABLE`, `RESOURCE_UNAVAILABLE`, `PLATFORM_EXCEPTION`); Phase 4 SHALL mint no new error category and add none to the documented set. `ConnectedDeviceSnapshot` SHALL gain and carry `deviceRoundRefusal: OmniBudsError?` (`core/platform/ConnectedDeviceObserver.kt:114-126`), set on a refused link round (`:459`, and the empty-union refusal at `:467`) and cleared on a completed one (`:768`), mirroring `pairedRoundRefusal` (`:148`) exactly, so that the reason an empty list is empty is available without subscribing to the round flow; a cancelled round SHALL set nothing there, because a called-off read is not a finding.
**Rationale.** Prompt §12's "do not represent observation failure as an empty session list" and §15's list; ADR-P4-007, which names the asymmetry it closes — an error type existed at one of two symmetric places, so a consumer could explain its empty pairings and not its empty devices — and refuses both clearing sessions on refusal ("a revoked permission would look like everybody going home") and wrapping Phase 3's error in a second type; ADR-P3-006's category set; ADR-P2-018 for cancellation staying a case.
**Dependencies.** REQ-P4-005, REQ-P3-013, REQ-P3-016; ADR-P4-007, ADR-P3-009, ADR-P3-006.
**Acceptance criteria.** AC-1 a refused round leaves the sessions and their states untouched. AC-2 it publishes `Refused` with the category the platform's refusal carried. AC-6 `deviceRoundRefusal` is set by the observer's failure and empty-union-refusal folds and cleared by a completed snapshot fold. AC-7 `ObservationRound.Cancelled` leaves `deviceRoundRefusal` as it found it. AC-8 a refused round emits `SESSION_OBSERVATION_FAILED` and no session-shaped event.

### REQ-P4-015 — Prompt §12's six things are six distinguishable values, derived in one documented precedence, and never re-derivable differently downstream
**Description.** The state SHALL keep distinct: successfully observed zero devices (`Confirmed(unionComplete = true)` with an empty list), observation unavailable, permission denied and bluetooth disabled (each a `Refused` whose category is the distinction), observation failed (`Refused` with a fault category), the observation not yet settled (`Unconfirmed`, and `Unread` before the first projection), and the session engine stopped (`Stopped`); derivation SHALL happen once, in `SessionObservationStatus.of` (`:82-90`), in the precedence order stopped outranks refusal, refusal outranks a completed round, a completed round outranks unsettled announcements; `isEmptyMeaningful` SHALL be true only for `Confirmed(unionComplete = true)`; a cancellation SHALL be absent from the type by design; and no consumer SHALL be left re-deriving any of it from the list length.
**Rationale.** Prompt §12's six-item list, quoted as the requirement it is; ADR-P4-007's two-boolean discipline inherited from ADR-P3-015 rule 9; ADR-P3-005's refusal to let lifecycle and failure answer for each other; ADR-P1-004 for cancellation-as-a-case; `SessionObservationStatus.kt:7-35`, whose stated reason for four cases instead of "a boolean and a nullable error" is that a consumer reading `sessions.isEmpty()` as "no earbuds connected" has made a hardware claim out of an observation status.

## Events

### REQ-P4-016 — Seven session events exist, `SESSION_ACTIVATED` is one of prompt §13's candidates and is refused, and an event appears only where something actually moved
**Description.** `DeviceSessionEvent` SHALL carry `SessionCreated`, `SessionUpdated`, `SessionDisconnected` (with its `DisconnectEvidence`), `SessionReconnected`, `SessionEnded` (with its `SessionTermination`), `SessionIdentityChanged` (with known-field **counts**) and `SessionObservationFailed` (with Phase 3's error and no session id), and SHALL NOT carry `SESSION_ACTIVATED`, because activation reads as a device becoming usable and that is the claim REQ-P4-003 makes unreachable: first arrival is already `SessionCreated` and a return is already `SessionReconnected`. **Rationale.** Prompt §13's eight candidates and its five "events must" rules, including "use only events supported by the actual state model"; ADR-P4-008, whose refusal of `SESSION_ACTIVATED` is reasoned ("an event whose meaning is a subset of two other events is how a UI ends up displaying a readiness nobody verified") and whose duplicate suppression is defined at the edge, not in the buffer; `DeviceSessionEvent.kt:8-14`.

## Concurrency, ordering and lifecycle

### REQ-P4-018 — One lock owns the whole reconcile-and-publish step, the engine owns no scope, and there is nothing of its own to leak
**Description.** Reconciliation and publication SHALL happen inside one `Mutex` (`DeviceSessionEngine.kt:82`, `apply` wrapped at `:134`, `terminateAll` at `:207` under `withContext(NonCancellable)` at `:206`), so no consumer ever observes a half-applied round and event order matches state order because both are produced inside the lock; the engine SHALL own no `CoroutineScope`, launch nothing, and pick no dispatcher — `consume()` runs in the **caller's** job (`:116-124`) — which is rule 5.1's requirement and the reason there is no mailbox to leak and no dispatcher to close; the only shutdown SHALL be the cancellation of that caller; no `GlobalScope`, `delay`, `Timer`, `while (true)` polling loop or `Dispatchers` reference SHALL appear in the session area; and the engine SHALL register no platform resource, because it opens none (ADR-P4-001's input contract).
**Rationale.** Prompt §14's list ("one authoritative session-state owner, structured concurrency, explicit cancellation, atomic reconciliation, no unmanaged global coroutine scopes, no resource leaks") and §12's "no leaked collectors"; ADR-P4-009, which reuses Phase 2's and Phase 3's single-owner shape and refuses both an actor (same serialisation at the cost of a mailbox and a scope) and lock-free `update` loops ("a state machine that runs twice is not deterministic"); `docs/phases/phase-0/specs.md` rule 5.1.
**Dependencies.** REQ-P4-001, REQ-P4-019, REQ-P4-020; ADR-P4-009.
**Acceptance criteria.** AC-1 every mutation of `tracked`, `sequence`, `revision` and `refusals`, and every publication, sits inside `lock.withLock`. AC-2 the engine declares no scope, no job, no dispatcher and no `GlobalScope`. AC-3 `consume()` completes or is cancelled by the caller and terminates accordingly. AC-4 a snapshot is never published mid-round. AC-5 events for a round are emitted after the state they describe is set. AC-6 no timer or polling construct exists in the area. AC-7 cancellation still publishes (the teardown is `NonCancellable`).
**Verification.** AC-2/AC-6 are **a census, not a check**: a scan of `core/src/main/kotlin/com/omnibuds/core/session/` for `GlobalScope`, `CoroutineScope`, `launch`, `delay(`, `Timer`, `while (true)` and `Dispatchers` returns one hit only, the word "launches" inside the KDoc at `:109`, and **no architecture rule forbids a future loop** — the same limit Phase 3 recorded for its own module (REQ-P3-011 AC-4). ### REQ-P4-019 — Ordering is carried by a monotonic revision and by a documented hierarchy of authority, never by comparing a handset's timestamps
