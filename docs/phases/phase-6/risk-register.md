# Phase 6 — Risk Register

**Phase:** 6 · **Owner:** orchestrator
**Document status:** continues the single project-wide sequence; Phase 5 closed at `RISK-097`, so Phase 6
opens at `RISK-098`. Each entry is risk, the mitigation actually in the tree at `83740c5`, and the residue
the mitigation does not remove.

| id | risk | likelihood / impact | mitigation in the tree | residue |
|---|---|---|---|---|
| RISK-098 | A later phase reads a successful `open()` as "this device speaks protocol X", driving a wrong-channel write (prompt §13's last line, PROTO-RESEARCH-006) | High / High | `TransportState.CONNECTED` means only the platform confirmed a link; `TransportResponse.acknowledged` is delivery-level (rung 2); no transport method reports protocol compatibility; resolution selects nothing (ADR-P6-005) | Enforcing the *next* step (protocol handshake before any write) is the capability/protocol phases' job; the ceiling here is advisory and structural, not a runtime gate on a future caller |
| RISK-099 | The Android mechanism is mistaken for verified behaviour because it compiles | Med / High | Ceiling `IMPLEMENTED` stated in every KDoc and in `validation.md`; `System*Handle` exercised only by the instrumented suite, compiled and never run (ADR-P3-016); `TransportResolution` caps at `INFERRED` | Inherent to a JVM-only phase; closes only in the deferred device session (RISK-097 continues) |
| RISK-100 | A transport auto-connects, reconnects, or opens a channel nobody chose (prompt §16) | Med / High | The factory constructs and never opens; `open()` is explicit; there is no reconnect loop (a drop becomes `DISCONNECTED`/`FAILED`); `UndeterminedTransportResolver` connects nothing | A careless later caller could still call `open()` in a loop; nothing in this phase issues that call, and `PhaseSixScope`-equivalent guards are the existing boundary/architecture tests |
| RISK-101 | A leaked GATT client, socket, or notification subscription survives a dropped consumer | Med / Med | One `Mutex`, no queue; `awaitClose { cancelSubscription }`; `close()` idempotent and `NonCancellable`; teardown releases once (ADR-P6-007/011) | The real platform's double-close/throw behaviour is unexercised until hardware; `AndroidTransportTest` proves the seam contract, not the framework's exact release semantics |
| RISK-102 | Concurrency corrupts operation ordering that a future protocol's framing will depend on | Med / High | Operations serialised under the mutex inside the state check, so a write can't interleave with a teardown or another write (prompt §10 "prevent concurrent writes") | Ordering across *two* channels of one device is the session's concern (PROTO-XPORT-005), not a single transport's |
| RISK-103 | A raw framework exception or status crosses into `:core` and gets stringified into a log or an error | Med / Med | `OperationOutcome<OmniBudsError>` is the only crossing; `TransportErrorMapping` names each category; `System*Handle` catches `IOException`/`SecurityException` (ADR-P6-006, prompt §13) | Payload bytes never appear in a `TransportRequest/Response.toString` (SEC-LOG-004, Phase 1), but a future caller printing the raw `status` int could leak operational detail; categories not ints are the contract |
| RISK-104 | Device-specific GATT/RFCOMM UUIDs get baked into the transport as "sensible defaults" (PROTO-NOMAGIC-002) | Med / High | `RfcommEndpoint` requires a caller-supplied UUID/channel with **no default**; GATT members take caller-supplied `GattUuid`; no vendor value exists in any main source | A later phase could still hard-code a UUID; the absence today is enforced by review + the empty-registry discipline carried from Phase 5, not by a compile-time ban on the string type |
| RISK-105 | Phase 6 quietly becomes a scanner or a discovery engine (it is now the first phase that *could*) | Med / High | `DEVICE_DISCOVERY_SCAN` stays authorised at 6 but nothing exercises it (ADR-P6-012); `DependencyDirectionTest` keeps `startScan`/`startDiscovery`/`BluetoothLeScanner` on the forbidden list | The tag records capability, not a runtime gate (Phase 0 forbids an ambient current-phase value); the real barrier is the absence of any scanner call site |
| RISK-106 | The audio path is entangled with control (a codec/A2DP claim smuggled into transport) | Low / High | The layer map makes `transport`(L1)→`audio`(L2) uncompilable; no A2DP/AVRCP/HFP `TransportKind`; `DependencyDirectionTest` keeps `startVoiceRecognition`/`stopVoiceRecognition`/`setPriorityPolicy` forbidden (ADR-P6-009) | None for this phase's code; the boundary is structural |
| RISK-107 | Amending the two inherited guards (Phase 2/3 forbidden-token lists) is read as weakening them wholesale | Med / Med | The amendments are narrow and dated — client GATT/RFCOMM opens moved to allowed (ADR-P6-008), scanning/discovery/server-listen/audio/UI/pairing kept forbidden — and the change is called out in `validation.md` and the commit body | A future reader must understand the amendment; the message text in `DependencyDirectionTest` was rewritten to state what Phase 6 permits vs forbids |
| RISK-108 | The pre-API-33 deprecation suppression (`@Suppress("DEPRECATION")`) hides a real bug | Low / Med | The suppression is confined to `SystemGattTransportHandle.kt` with a written platform-constraint reason; nothing in `:core` carries it; the API is version-continuous across minSdk 26 | It also suppresses any *other* deprecation in that one file; acceptable at this size, but a future API change there should re-read the file rather than trust the blanket |
| RISK-109 | A channel-number-only RFCOMM endpoint is silently assumed to work on Android | Low / Med | The platform has no public client API for it, so `SystemRfcommTransportHandle` refuses a channel-only endpoint and `probe()` reports it; the limitation is stated in `specs.md` §8 | Callers must handle the refusal as "unavailable on this platform," not "device lacks RFCOMM" — the type makes the distinction available, not mandatory |
